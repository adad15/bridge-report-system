# 模块 05 病害与照片联合校对及确认链路加固设计

日期：2026-07-10

状态：设计已确认，等待实施计划

## 1. 背景

模块 05 已具备导入记录读取、草稿保存、入库前检查、年度事实确认入库和取消导入等基础能力。真实 Word 联调和代码审查暴露出以下问题：

1. 病害和照片位于两个独立页面，用户不容易判断照片是否与病害对应。
2. 照片候选只能看到题注，不能稳定读取和展示真实归档图片。
3. 照片人工确认后的状态组合不能稳定通过最终预检。
4. 病害引用的照片缺失时，没有明确的人工确认缺图流程。
5. 最终确认可能使用预检阶段构造的旧数据，而不是事务加锁后重新读取的最新草稿。
6. 数据库提交回调完成前存在提前返回成功的风险。
7. 已确认或已取消的导入记录仍可能进入可编辑页面。
8. 保存请求进行期间发生的新修改可能被错误地标记为已保存。

本设计在保留模块 05 既有业务范围的前提下，完成病害与照片联合校对、图片归档预览、契约升级和确认链路加固。

## 2. 目标

本轮目标：

1. 将照片合并到普通病害中，以病害组为单位完成联合校对。
2. 保留原普通病害的全部核心字段和编辑方式。
3. 支持逐张确认、重新关联、标记无关和忽略照片。
4. 支持人工确认病害引用的照片确实缺失。
5. 在进入校对页前，由 C++ 主服务完成图片正式归档。
6. 通过受控接口展示真实病害图片，不暴露本机文件路径。
7. 将 `BridgeAnnualInspectionData` 契约升级到 1.1，表达病害组确认结果。
8. 最终确认必须在事务内重新读取、校验并使用最新草稿。
9. 只有数据库 `COMMIT` 真正成功后，接口才能返回确认成功。
10. 修复保存期间的脏状态竞争，并让已确认、已取消记录保持只读。

## 3. 非目标

本轮不实现：

1. 图片裁剪、旋转、重新上传和拖动排序。
2. 图片内容识别或 AI 病害判断。
3. 跨年度病害对比和病害线索归并。
4. 正式报告生成。
5. 多人协同编辑和完整审签流。
6. 模块 04 的 Word 表格及题注识别规则优化。

## 4. 核心概念

### 4.1 病害组

一个病害组由以下内容组成：

```text
一条 DefectCandidate
+ 所有 linked_defect_candidate_id 指向该病害的 PhotoCandidate
+ defect.photo_numbers 中引用但没有对应图片的照片编号
```

病害组是模块 05 的最终确认单位。病害字段正确、实际照片逐张处理完成、缺失照片逐项人工确认后，用户才能执行“确认该病害及照片”。

### 4.2 照片已解决

照片候选满足以下任一状态时，视为已经处理：

1. 确认与当前病害匹配。
2. 人工重新关联到另一条病害。
3. 标记为与报告病害无关。
4. 标记为忽略。

照片仍处于高置信候选、待校对或未明确处理时，不视为已解决。

### 4.3 确认缺图

“确认缺图”只适用于以下情况：

```text
病害 photo_numbers 引用了某个照片编号
且 photos[] 中没有该照片编号对应的图片候选
```

如果已经存在照片候选，但其归档文件损坏或丢失，不能通过“确认缺图”绕过。该情况属于归档错误，必须重新解析或恢复归档文件。

## 5. 契约 1.1

### 5.1 版本

`contract.version` 从 `1.0` 升级为 `1.1`。模块 04 更新后直接输出 1.1；模块 05 的草稿保存、预检和确认接口只接受经过兼容升级后的 1.1 数据。

### 5.2 DefectCandidate 新字段

每条 `DefectCandidate` 增加：

```json
{
  "group_review_status": "待确认",
  "confirmed_missing_photo_numbers": []
}
```

字段含义：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `group_review_status` | `"待确认" | "已确认"` | 病害字段和所属照片是否已经完成联合校对 |
| `confirmed_missing_photo_numbers` | `string[]` | 用户已经明确确认缺失的照片编号 |

约束：

1. `confirmed_missing_photo_numbers` 不允许重复。
2. 其中每个编号必须存在于当前病害的 `photo_numbers`。
3. 如果后来找到并关联了该编号对应的图片，必须从该数组移除。
4. 修改病害核心字段、照片编号、照片关系或照片处理状态时，相关病害组必须退回 `待确认`。

### 5.3 兼容旧版 1.0

对于 `import_status = 待校对` 的 1.0 草稿，GET 校对接口在内存中执行确定性升级：

```text
contract.version = 1.1
每条病害 group_review_status = 待确认
每条病害 confirmed_missing_photo_numbers = []
```

接口返回 `contract_compatibility = upgraded_1_0`。用户保存草稿后，数据库中的 JSON 正式变为 1.1。系统不会把旧草稿自动视为已经完成病害组确认。

对于已经确认或取消的 1.0 记录，接口使用只读兼容适配器展示，返回 `contract_compatibility = legacy_read_only`，不修改历史 JSON。

## 6. 页面设计

### 6.1 左侧导航

页面导航调整为：

```text
需要处理
病害与照片
技术状况评定
来源证据
原始 JSON
```

删除独立的“病害照片”导航。照片必须在所属病害组中审查。

### 6.2 病害字段必须完整保留

“病害与照片”不能简化为只有病害摘要和图片。每条普通病害继续保留原页面的表格字段、编辑方式和校对能力：

```text
结构部位
构件
位置
病害类型
数量
尺寸原文
照片编号
校对状态
备注
```

对应契约字段包括：

```text
structure_part
component_name
component_alias
defect_location
defect_type
defect_description
quantity_text
measurement_text
photo_numbers
review_status
review_note
```

病害字段行保持紧凑表格形态。照片审查区放在该病害行的展开区域或紧邻下方，不能用照片卡片替代病害字段表格。

### 6.3 A3 照片布局

每个展开的病害组一次显示一张大图，下方显示该组全部照片的缩略图条：

```text
病害字段行
  -> 当前照片大图
  -> 照片编号、原始题注、匹配状态、校对状态
  -> 单张照片操作
  -> 底部缩略图条
  -> 缺失照片编号清单
  -> 确认该病害及照片
```

点击缩略图只切换当前大图，不改变任何业务状态。照片区域应保持稳定尺寸，图片使用等比缩放，不因图片宽高变化引起页面明显跳动。

### 6.4 逐张照片操作

每张照片提供以下操作：

| 操作 | 数据结果 |
| --- | --- |
| 照片正确 | 保留当前关联；`match_status = 已确认`；`review_status = 已确认` |
| 重新关联 | 指向目标病害；`match_status = 已确认`；`review_status = 已修改` |
| 标记无关 | 清空病害关联；`match_status = 未关联`；`review_status = 已确认`；备注保留人工结论 |
| 忽略 | 清空病害关联；`review_status = 已忽略` |
| 取消处理 | 回到待校对状态，相关病害组退回待确认 |

重新关联时，原病害组和目标病害组都必须退回 `group_review_status = 待确认`。

### 6.5 缺图确认

病害引用但未找到图片的编号显示在病害组的“缺失照片”区域。用户逐项点击“确认缺图”后，将编号写入 `confirmed_missing_photo_numbers`。

如果用户修改 `photo_numbers` 删除该编号，系统同步从缺图确认数组删除；如果后来重新关联到同编号图片，也同步删除。

### 6.6 病害组最终确认

“确认该病害及照片”按钮只有在以下条件全部满足时可执行：

1. 病害必填字段完整。
2. 病害自身没有阻断 error。
3. 所有关联照片都已经逐张解决。
4. 所有引用但缺失的照片编号都已经人工确认缺图。
5. 所有关联照片都具有可读取的归档文件。

执行成功后：

```text
group_review_status = 已确认
病害 review_status = 待确认 时改为 已确认
病害 review_status = 已修改 时保持 已修改
```

按钮不会把已经修改的病害覆盖成普通的“已确认”。之后任何病害或照片变更都会使病害组重新变为待确认。

### 6.7 需要处理

“需要处理”只集中显示异常或未完成对象：

1. 未关联且尚未处理的照片。
2. 病害引用照片缺失且尚未确认缺图。
3. 照片归档文件缺失。
4. 病害字段错误或必填字段缺失。
5. 尺寸表达未能完整结构化的警告。
6. 尚未完成联合确认的病害组。

错误和警告分组展示。错误阻止最终入库，警告允许用户审查后继续。

### 6.8 只读状态

只有 `import_status = 待校对` 的记录允许编辑：

| 状态 | 入口文字 | 页面能力 |
| --- | --- | --- |
| 待校对 | 进入校对 | 可编辑 |
| 已确认 | 查看结果 | 只读 |
| 已取消 | 查看结果 | 只读 |

只读不能只依赖隐藏按钮。所有输入框、选择框、照片操作和草稿操作都必须禁用，后端写接口也必须再次校验导入状态。

## 7. 图片归档与读取

### 7.1 归档责任

Python 工具层仍只负责从 `.docx` 提取图片和返回临时文件信息，不直接访问数据库，也不决定正式归档路径。

C++ 主服务负责：

1. 为本次解析创建受控临时目录。
2. 调用 Python 解析服务。
3. 校验 Python 返回的临时文件名和实际文件。
4. 计算文件哈希、大小和扩展名。
5. 将图片复制或移动到模块 02 的归档根目录。
6. 写入 `archived_files`。
7. 写入对应的 `import_record_files` 关联记录。
8. 将安全的 `storage_relative_path` 回填到照片候选的 `extracted_file.archive_relative_path`。
9. 保存完整候选 JSON 后再清理临时目录。

临时绝对路径不得进入正式 JSON、数据库事实表或前端响应。

### 7.2 安全校验

C++ 只接受受控临时目录内的普通文件。以下情况必须拒绝归档：

1. 文件名包含 `..`。
2. 返回绝对路径或盘符路径。
3. 规范化后路径越过临时目录。
4. 文件不存在或不是普通文件。
5. 扩展名、检测到的媒体类型和允许的图片类型不一致。

归档数据库写入和最终 JSON 保存必须保持一致。如果中途失败，导入记录进入明确的失败状态，并清理已经创建但未关联成功的文件或记录。

### 7.3 照片内容接口

新增：

```http
GET /api/import-records/{import_record_id}/photos/{photo_candidate_id}/content
```

接口处理：

1. 根据 `import_record_id` 读取候选 JSON。
2. 根据 `photo_candidate_id` 找到照片候选。
3. 通过该导入记录的 `import_record_files` 和 `archived_files` 解析归档文件。
4. 校验归档相对路径仍位于归档根目录内。
5. 返回真实图片字节和正确的 `Content-Type`。

接口不接收任意文件路径，也不把 `archive_relative_path` 当作客户端可直接访问的 URL。

## 8. 草稿保存安全

前端维护本地单调递增的 `draft_revision`。每次病害、照片、评分或缺图确认发生变化时递增。

开始保存时记录 `save_revision`。保存成功后，只有当前 `draft_revision == save_revision` 才能清除脏状态。保存、预检、确认和取消操作进行期间，编辑控件暂时禁用。

任意草稿修改都会使前端缓存的预检结果失效。最终确认不能只相信旧预检结果，后端必须始终重新检查。

## 9. 最终确认事务

确认接口不得在事务外构造最终 `ConfirmPlan`。正确顺序：

```text
BEGIN
  -> SELECT import_records ... FOR UPDATE
  -> 校验 import_status = 待校对
  -> 读取锁定后的最新 parsed_result_json
  -> 严格校验 1.1 契约
  -> 在事务内重新执行 preflight
  -> 根据同一份最新 JSON 构造 ConfirmPlan
  -> 锁定并检查同桥同年当前版本
  -> 写年度、构件、病害、尺寸、照片和评分事实
  -> 更新 import_records.import_status = 已确认
COMMIT
  -> COMMIT 回调成功后返回 HTTP 成功
```

任何数据库语句或提交回调失败都返回失败。不能在异步 `COMMIT` 完成前设置 `success = true` 或发送成功响应。

正式 `defect_photos` 记录必须解析到本次导入关联的 `archived_files.id`，且 `archived_file_id` 非空。仅有题注或临时文件名的照片不能进入正式事实表。

## 10. 严格校验和预检

C++ 1.1 校验器至少检查：

1. 契约名称和版本。
2. 必填对象、数组和字段类型。
3. `candidate_id` 非空且在各自集合中唯一。
4. `structure_part`、`review_status`、`match_status` 和 `group_review_status` 等枚举值合法。
5. 照片关联的病害候选真实存在。
6. 缺图确认编号无重复且属于当前病害引用编号。
7. 已确认病害组满足病害字段、逐张照片和缺图确认条件。
8. 归档相对路径安全。
9. 待入库照片能解析到本次导入的归档文件记录。

预检错误示例：

```text
group_confirmation_required
missing_photo_confirmation_required
photo_archive_missing
contract_validation_failed
revision_confirmation_required
database_commit_failed
```

警告示例：

```text
measurement_not_fully_structured
photo_marked_unrelated
contract_upgraded_from_1_0
```

## 11. 状态与数据流示例

以病害 `defect_0008` 为例：

```text
病害引用：照片 2.1-4、照片 2.1-5
照片 2.1-4：已抽取并关联
照片 2.1-5：Word 中未找到
```

处理过程：

1. 用户核对结构部位、构件、位置、病害类型、数量和尺寸原文。
2. 用户查看照片 2.1-4 大图并点击“照片正确”。
3. 用户确认 Word 中确实缺少照片 2.1-5，点击“确认缺图”。
4. 系统将 `2.1-5` 写入 `confirmed_missing_photo_numbers`。
5. 用户点击“确认该病害及照片”。
6. 病害组变为已确认。
7. 如果用户随后把构件从“主梁”改成“横梁”，病害 `review_status` 变为已修改，病害组重新变成待确认。

## 12. 测试策略

### 12.1 契约测试

1. JSON Schema、Python Pydantic、C++ 校验器和 TypeScript 类型同时支持 1.1。
2. 缺少新增字段、非法枚举、重复缺图编号和悬空照片关联均被拒绝。
3. 1.0 待校对草稿按固定规则升级，已确认和已取消记录保持只读兼容。

### 12.2 前端状态测试

1. 病害原有字段全部显示并可编辑。
2. 照片正确、重新关联、无关、忽略和取消处理的状态结果正确。
3. 重新关联同时使原病害组和目标病害组失效。
4. 确认缺图和取消确认正确维护数组。
5. 修改已确认病害或照片后，病害组自动回到待确认。
6. 保存期间控件禁用，旧保存响应不能错误清除新脏状态。
7. 已确认和已取消记录全部只读。
8. A3 大图、缩略图切换和无图片占位状态稳定。

### 12.3 C++ 归档和接口测试

1. 正常图片归档后生成哈希、相对路径和数据库关联。
2. 路径穿越、绝对路径、文件缺失和非图片文件被拒绝。
3. 照片内容接口返回正确字节和媒体类型。
4. 候选存在但归档文件缺失时，预检阻止确认。
5. 正式 `defect_photos.archived_file_id` 始终非空。

### 12.4 事务测试

1. 草稿保存与确认并发时，确认只使用加锁后读取的最新 JSON。
2. 事务中任一步失败都不留下半截年度事实。
3. `COMMIT` 回调失败时接口不返回成功。
4. 同桥同年修订确认仍遵守显式 `confirm_revision` 规则。

### 12.5 真实 Word 回归

使用辽宁国省干线真实 `.docx` 样例核对：

1. 病害数量和病害字段与 Word 表格一致。
2. 照片候选数量、归档文件数量和可预览图片数量一致。
3. 每张照片能够在正确病害组下逐张校对。
4. 缺失照片编号能够人工确认。
5. 最终病害、尺寸、照片和评分正式表记录与确认草稿一致。

## 13. 验收标准

1. “病害与照片”页面保留结构部位、构件、位置、病害类型、数量、尺寸原文、照片编号、校对状态和备注。
2. 每条病害下可使用 A3 布局查看实际图片和缩略图。
3. 用户能够逐张确认或处理照片，并能够人工确认真正缺失的照片编号。
4. 只有病害字段、照片和缺图项全部处理完成后，病害组才能确认。
5. 修改已确认组内任何业务数据都会撤销组确认状态。
6. 图片在进入校对页前已经由 C++ 归档，前端不依赖 Python 临时目录。
7. 照片内容接口不接受任意路径，且能稳定返回真实图片。
8. 最终确认只使用事务加锁后读取的最新 1.1 JSON。
9. 数据库提交真正成功前，接口不会返回成功。
10. 已确认和已取消记录只读。
11. 1.0 待校对草稿可升级继续校对，历史记录不被自动改写。
12. 所有新增契约、页面状态、归档安全和事务路径都有自动化测试。

## 14. 与原模块 05 规格的关系

`docs/superpowers/specs/modules/05-review-workspace.md` 仍定义模块 05 的总体目标、业务入口、年度修订和正式事实映射。本设计覆盖其中以下旧规则：

1. “普通病害”和“病害照片”两个独立页面，改为“病害与照片”联合页面。
2. 普通候选批量确认照片的方式，改为照片逐张处理和病害组最终确认。
3. 照片只展示题注的方式，改为 C++ 归档后通过内容接口展示真实图片。
4. 事务外构造确认计划的实现方式，改为事务内读取最新 JSON 后构造。
5. 仅依赖候选 `review_status` 的预检方式，增加病害组和缺图确认约束。
