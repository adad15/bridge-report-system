2026-08-25 病害线索批量整理设计评审意见

评审对象：
docs/superpowers/specs/2026-08-25-defect-thread-batch-triage-design.md

评审结论：

整体方向正确。把现有“一条观测一张卡”的操作方式提升为“按相同模式组成批次，由人批量确认”，能够同时解决冷启动时逐条新建成本过高、候选请求 N+1，以及构件标识不清的问题。

不过，当前设计在人工确认边界、服务端校验、幂等、空位置、分页提交和事务语义等方面仍有未闭环之处。建议先修正本文列出的高优先级问题，再进入实施。


一、实施前必须解决的问题

1. “每组都经人工查看”与批次界面互相矛盾

设计在用途约束中要求：不允许任何一组在没有人看过的情况下落库。

但批次界面默认只展示三条样例，同时允许用户直接确认整个批次。例如，一个包含 166 组的批次，用户实际只看过三组，就可以让全部 166 组落库。

建议明确采用以下哪一种信任模型：

方案 A：允许抽样确认。
把约束改成“每个批次必须经过人工确认，系统必须提前排除已知异常，用户可展开并剔除个别组”。此时不再宣称每一个组都被人看过。

方案 B：要求逐组查看。
展开列表需要记录每组的已查看或已确认状态，只有所有组均被浏览或勾选后，才能提交整个批次。

当前设计同时表达了两种不同的安全边界，需要统一，否则测试和验收无法判断何为正确。


2. apply 接口不能信任客户端提交的组描述

当前请求体由客户端提交以下内容：

- bridge_component_id；
- thread_id；
- defect_type；
- defect_location；
- observations。

但是校验章节只列出了观测状态、年度状态、updated_at 和对比引用校验，没有要求服务端重新验证组的业务含义。

如果前端存在缺陷或请求被错误构造，可能出现：

- URL 中的 bridge_id 与观测实际所属桥梁不一致；
- 观测不属于声明的构件；
- 不同病害类型或不同位置的观测被放入同一组；
- 同一年多条观测绕过 multiple_in_year 检查；
- 同一观测在多个组中重复出现；
- bind 的目标线索并不是该组精确命中的线索。

建议规定：客户端请求只表达用户选择，不能作为业务事实来源。服务端必须在事务中锁定全部观测后，从数据库重新计算并验证：

- 所有观测均属于 URL 指定桥梁；
- 每组观测属于同一 bridge_component_id；
- 每组具有相同的规范化病害类型和规范化位置；
- 每个年度最多一条观测；
- 请求中不存在重复观测 ID；
- create 组当前确实没有精确匹配线索；
- bind 组当前恰好精确匹配请求指定的 thread_id；
- 目标线索与观测属于同桥、同构件。

应当先完成所有锁定与校验，再进行任何插入或绑定操作。


3. 当前幂等方案与 updated_at 校验顺序冲突

设计要求完整复用乐观并发校验，同时要求成功请求重复提交时返回“已完成”。

第一次提交成功后，观测绑定操作会更新 updated_at。客户端如果因为响应丢失而使用原请求重试，携带的一定是旧 updated_at。若继续沿用现有顺序，服务端会先返回 observation_revision_conflict，根本没有机会判断该组已经完成。

建议明确批量接口的处理顺序：

1）按固定顺序锁定请求涉及的全部观测；
2）检查组内所有观测是否已经绑定到预期的同一条线索；
3）如果全部符合预期，返回 already_completed，允许原请求中的旧令牌；
4）如果不是已完成状态，再检查 updated_at；
5）部分观测已绑定、绑定到其他线索或组内观测分散到多条线索时，返回明确冲突，不得误判为已完成。

还可以增加请求级 idempotency_key，使网络重试不必完全依赖业务状态推断。


4. 空位置与当前线索创建规则冲突

设计的最大批次依赖“空位置也算位置全等”，请求体也允许 defect_location 为 null。但当前单条线索创建接口要求 defect_location 是非空字符串，现有默认名称逻辑还会在空位置时产生类似“渗水泛碱｜”的名称。

建议在设计中明确：

- 批量创建接受 null 位置；
- 数据库存储 null，不转换为空字符串；
- 空位置的默认名称使用“病害类型｜未记录位置”，或直接使用病害类型；
- 明确单条创建接口是否同步支持空位置；
- 再次归组和精确匹配时，null 与空字符串是否统一视为同一规范化空值。

如果不补充这部分，166 个无位置铰缝组无法按当前接口规则创建线索。


5. 分页明细与显式提交全部观测之间没有闭环

设计规定批次明细分页返回，同时要求 apply 请求显式列出全部组、全部观测及其 updated_at。

用户在未展开批次时点击“确认这 166 组”，前端只有摘要和三条样例，并没有其余观测的 ID 与并发令牌，因此无法构造设计中的 apply 请求。

建议增加明确的数据准备流程，例如：

- 批次明细中的照片、尺寸等重数据继续分页或按需加载；
- 点击确认时，单独获取不含照片的完整 apply_manifest；
- apply_manifest 包含全部组、观测 ID、updated_at 和整体指纹；
- 提交前显示最终处理数量，例如“将处理 166 组、498 条观测”；
- 如果服务端发现 manifest 对应的数据组成已经变化，则拒绝提交并要求刷新。

也可以改为提交 batch_id、排除的 group_id 和批次指纹，由服务端重新计算最终清单。但不能既不提交 batch_id，又不让前端获得全部观测清单。


6. “前端拆分请求”会破坏整批原子性

设计一方面规定“整批一个事务，全成或全败”，另一方面又规定超过 500 组时由前端拆分请求。

一旦拆成多个请求，前一个分片可能提交成功，后一个分片失败，此时不再满足整批原子性。

建议二选一：

- 一个业务批次只允许一次提交，服务端上限按观测数、请求体大小和数据库能力设置；
- 明确事务单位是“提交分片”，并设计部分完成后的进度展示、失败恢复和重新提交方式。

目前实际最大批次只有 166 组，没有必要提前引入这个语义冲突。


二、匹配和归组规则需要补充的问题

7. 病害类型是否归一化没有写一致

组键写的是 bridge_component_id、原始 defect_type 和归一化位置，但现有候选算法实际上同时归一化病害类型与位置。

建议统一使用：

(bridge_component_id, normalized_defect_type, normalized_defect_location)

同时保留病害类型和位置原文用于界面展示及新建线索。否则空格、全角符号或 ASCII 大小写差异可能导致候选认为相同，而批量归组认为不同。

还应明确空位置是一项额外的业务规则：当前候选算法的“位置全等”要求双方位置非空，不能仅靠复用 normalize_suggestion_text 自动获得“空位置相等”的行为。


8. location_overlap 必须同时检查已有线索

当前异常定义主要描述未绑定组之间的位置包含关系。增量场景中还可能出现：

未绑定观测位置：大小里程侧
已有线索位置：大小里程侧及左悬臂底部

此时未绑定观测没有精确命中，也不一定存在另一条未绑定组。若 overlap 检测只看未绑定组，它会被判定为 create，从而生成疑似重复线索。

建议 overlap 检测覆盖：

- 未绑定组与未绑定组；
- 未绑定组与同构件已有线索。

manual 响应中应附上相关组和相关已有线索的 ID、名称及系统编号，便于人工判断。


9. 批次键建议加入 structure_part

当前批次键只使用部件类型。像“其他”“附属构件”等宽泛类型可能出现在不同结构部位，却被归入同一个判断批次。

建议批次键改为：

(structure_part, component_type, normalized_defect_type,
 normalized_defect_location, year_set, action)

如果通过真实数据验证能够证明 component_type 在全桥范围内已经足够唯一，再有依据地省略 structure_part。


10. batch_id 需要定义稳定性和碰撞处理

“批次键的哈希”还不足以形成接口约定。建议明确：

- 使用的哈希算法和截取长度；
- 批次键的规范化序列化规则；
- 年份集合的排序规则；
- null 与空字符串的编码区别；
- 哈希碰撞时的检测和返回方式；
- 数据变化导致 batch_id 消失时返回 404 还是 409。

如果 batch_id 只用于短期读取，也可以直接使用服务端生成的不可解释游标，并附带快照指纹。


三、界面与操作流程需要优化的问题

11. bind 批次不存在唯一的目标线索

一个批次会覆盖多个构件，而病害线索属于具体构件。因此，一个包含多个构件的 bind 批次实际上会分别绑定到多条不同的线索，不可能整个批次只绑定到一个 BHXS 编号。

界面文案不应写成：

“将绑到：渗水泛碱｜大小里程侧（BHXS-000123）”

建议改为：

“将分别绑定到各构件中精确命中的已有线索”

展开明细后，再逐组显示对应的线索名称和 BHXS 编号。


12. 异常项不宜简单退化为现有逐观测卡片

location_overlap 是多个组之间的关系。如果把相关观测打散成现有的一观测一卡，用户会失去异常上下文，难以判断两个位置究竟应该合并还是分开。

建议把“需单独处理区”设计成异常簇，而不是普通单条卡片：

- 同屏展示所有相关位置组和历年观测；
- 支持“合并为一条线索”“分别创建”“绑定已有线索”；
- multiple_in_year 将同一年多条观测并排显示；
- 明确显示异常原因和相关对象。

文档中“10 条逐条项”的说法也应统一。现有统计是 10 组、23 条观测；如果沿用逐观测卡片，实际是 23 个操作项，而不是 10 个。


13. “事后可在档案页修改名称”与现有实现不符

当前代码只有创建线索和绑定、解绑、换绑接口，没有发现修改 thread_name 的接口或界面。

建议：

- 补充单条线索编辑能力；或
- 删除“事后可在档案页修改”的说明，并确保批量创建的默认名称可以长期使用。

“线索命名的批量编辑”可以继续作为非目标，但单条编辑能力是否存在必须写准确。


14. “暂不处理”的状态需要说明

需要明确“暂不处理”是：

- 仅当前页面会话折叠；
- 浏览器本地持久化；
- 还是服务端记录为待处理状态。

如果只在本地折叠，提交其他批次或页面刷新后批次列表会重新计算，batch_id 也可能变化。设计应说明刷新、返回页面和跨设备时的表现。


四、事务和性能方面的建议

15. 事务应分成“批量锁定、完整校验、批量写入”三个阶段

如果处理一组就立即创建和绑定，最后一组失败时虽然可以回滚，但只能方便地返回第一个错误，难以兑现“返回失败明细”。

建议事务流程为：

1）收集、去重并按 UUID 固定顺序排列全部观测 ID；
2）一次或分块 SELECT ... FOR UPDATE 锁定；
3）对全部组执行只读校验，收集所有错误；
4）存在任何错误则直接回滚并返回完整错误列表；
5）全部通过后批量创建线索、批量绑定观测；
6）集中重算涉及线索的 first_seen 和 latest_seen。

固定锁顺序还能降低两个重叠批量请求发生数据库死锁的风险。


16. 不宜在设计中直接断言 498 次 FOR UPDATE 是毫秒级

性能不仅取决于锁数量，还取决于 SQL 往返次数、同步数据库调用、索引、连接池和每条线索的重算次数。

建议将表述改为可验证的性能目标，例如：

- 498 条观测的批次在本地基准数据库中 P95 小于某个目标值；
- 事务不超过 HTTP 和数据库配置的超时时间；
- 使用批量锁定和批量更新，避免 498 次独立 SQL 往返；
- 为最大真实批次增加集成性能测试。


五、建议补充的接口约定

建议补充 apply 成功和失败响应的完整 JSON 示例，并明确：

- HTTP 状态码；
- already_completed 是成功还是冲突；
- 整批失败时错误列表的结构；
- 错误如何关联 group、component 和 observation；
- 空 groups、超过上限、重复 observation ID 的错误码；
- create 携带 thread_id、bind 缺少 thread_id 时的错误码；
- 批次在读取与提交之间变化时的错误码；
- 成功响应是否返回新建 thread_id 和观测的新 updated_at。

推荐的失败结果至少包含：

- code；
- message；
- group_key 或 group_id；
- bridge_component_id；
- observation_id；
- reason_code。


六、建议补充的测试

在现有测试策略基础上，建议增加：

1. 客户端把跨桥观测放入请求时整批拒绝；
2. 客户端把跨构件观测放入同组时整批拒绝；
3. 同组观测的规范化病害类型或位置不同时时整批拒绝；
4. 同一观测在两个组中重复出现时整批拒绝；
5. bind 目标不是服务端重新计算出的精确匹配线索时拒绝；
6. 成功但响应丢失后，携带旧令牌重试仍返回 already_completed；
7. 部分观测已绑定、部分未绑定时不误判为已完成；
8. 观测已绑定到同键但不是预期目标的其他线索时返回冲突；
9. 未绑定组与已有线索位置互相包含时进入人工区；
10. 空位置批量创建后的数据库值、默认名称和再次精确匹配均正确；
11. 两个并发创建请求不会为同一批观测生成重复线索；
12. 两个观测集合交叉的批量请求不会死锁；
13. 分页浏览、跨页剔除和最终 apply_manifest 保持一致；
14. bind 批次的每个组显示各自对应的 BHXS 编号；
15. 超过接口限制时不会出现未说明的部分提交；
16. 真实数据夹具携带数据来源说明或指纹，避免数据变化后只看到数量断言失败却无法追踪原因。


七、建议的实施优先级

P0，进入编码前必须写清：

- 人工确认边界；
- 服务端重新计算并验证组；
- 幂等判断顺序；
- 空位置的创建和命名规则；
- 分页数据如何形成完整提交清单；
- 整批事务与前端拆分之间的取舍。

P1，建议在首版一并完成：

- 病害类型归一化口径；
- 与已有线索的 location_overlap 检测；
- structure_part 是否进入批次键；
- bind 批次的多目标线索展示；
- 异常簇界面；
- 完整的响应结构和错误码。

P2，可在实施计划中补充：

- batch_id 的稳定编码方式；
- “暂不处理”的持久化语义；
- 性能基准；
- 单条线索名称编辑能力。


最终建议：

该设计可以作为实施基础，但不建议按当前版本直接编码。先补齐 P0 项目后，接口、事务和前端状态才能形成完整闭环。尤其要确保服务端不信任客户端组装结果，并解决成功重试与 updated_at 校验的顺序冲突；这两点直接决定批量整理是否会写入错误关系或产生无法解释的失败。
