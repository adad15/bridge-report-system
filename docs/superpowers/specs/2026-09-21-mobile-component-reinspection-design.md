# 移动端构件复查、分工提交与服务器评分设计

日期：2026-09-21  
版本：1.3  
状态：设计稿，依据已讨论的业务流程整理；尚未实施正式移动端、同步接口与数据库变更。  
范围：两级构件分组、业务规则、数据模型、本地存储、同步协议、服务器评分与结果展示、现有系统衔接和验收。**不包含界面设计。**

## 1. 设计目标与约束

当前系统通过第三方软件导入年度检测资料，来源构件名称、编号和病害描述与本系统不完全一致，导致导入后仍需构件绑定和人工校对。移动端应直接使用本系统的完整构件台账及年度病害指标，在现场形成有明确归属的检测记录。

用户已明确的业务要求：

1. 以实际构件为基本作业单元，采用两级构件组：一级为上部结构、下部结构、桥面系；二级为对应规范构件类别，例如上部承重构件、上部一般构件。在二级组中选择实际构件。
2. 检测当前年度时，能够查阅该构件最近一次正式检查的病害、测量值及照片。
3. 对既有病害逐条复查，记录变化情况和维修情况；同一构件可以新增多条病害。
4. 日常记录及照片先保存到设备本地，不逐条上传，不因恢复网络而自动上传。
5. 一座桥可由多人按构件分工。成员离线保存自己负责构件的记录；联网后各自主动提交负责的已完成构件，取得构件级回执。成员主动同步后才能读取队友已提交的版本，无需任务负责人再统一提交。
6. 保留桌面端内容复核、正式确认、系统评定和报告生成流程，减少重复的构件名称匹配。
7. 增加 APP 桥梁评分结果展示功能页。任务范围内的构件均提交并通过服务器校验后，由服务器算分并将结果提供给 APP；APP 不在本地计算桥梁评分。

现场可能没有网络，业务采用本地优先。网络恢复不自动提交或同步；用户分别主动执行提交和同步。队友尚未提交的本地记录不能当作团队已完成数据，已提交但未同步的记录也不能假装为本机已获取的最新内容。

本文规定“桥梁评分结果展示页”的功能边界和所需信息，不规定其布局、导航形式、卡片、列表、网格、控件、颜色、字体或交互视觉，也不约束其他页面划分。原型中的具体呈现方式不构成实施约束，后续界面可独立重新设计。原型的示例构件、初始完成状态及照片占位均不是实际业务数据。

## 2. 现有能力与新增边界

| 领域 | 当前系统能力 | 本设计新增内容 |
| --- | --- | --- |
| 构件档案 | 已确认的版本化完整台账、编号、类别映射与分组查询 | 下载为可离线使用的作业快照、构件检查覆盖记录 |
| 年度上下文 | 年度关联台账、规范及评定树版本 | 作业包固定这些版本，构件提交时校验是否仍适用 |

| 导入与确认 | 候选校对、关系化构件及评分树解析、正式确认 | 成员构件提交的汇总接收与适配，不靠名称重新猜测归属 |
| 跨年语义 | 线索整理已有；完整病害变化确认流程尚未完成 | 显式关联前次观测，保存变化判断和维修观察事实 |
| 本地作业、提交与同步 | 原型仅演示 | 持久化记录、照片文件、按构件分工、成员独立提交、主动同步、版本冲突及构件级回执 |
| 服务器评定 | 已有试算和正式评定，含全桥、结构部位、类别及构件结果 | 按整桥已提交构件的冻结汇总版本编排计算任务，APP 查询与缓存对应评分结果 |

现有技术边界保持：C++ / Drogon 是唯一业务编排及数据库写入入口，PostgreSQL 保存结构化业务数据；Python 服务负责导入、地图、报告等工具工作，不直接写业务数据库。移动端不得直连 PostgreSQL 或绕过 C++ 写入归档文件。

本文以下接口、实体和状态均为目标设计，不表示仓库已有同名实现。客户端框架和发布载体不在本文中锁定；应满足本文的存储与同步契约后再独立选型。

## 3. 业务对象与身份规则

### 3.1 桥梁年度作业任务

一次作业任务对应一座桥、一个目标检测年度及固定的一组台账和规范版本。第一期允许多设备按构件并行分工，同一桥梁年度仅允许一个有效任务；每件构件在同一分工版本内只有一名录入负责人，不做同一构件的字段级自动合并。

任务范围默认包含所锁定台账中全部启用且纳入检测范围的实际构件，不能把“存在病害的构件集合”当作全桥台账。任务范围、生成时间、责任人、版本及构件总数需要可追溯。

服务器任务是授权和基线依据；各设备的本地作业副本是现场记录载体；构件提交版本是个人已上传的冻结快照；本机同步副本是已获取的队友提交版本；服务器整桥汇总版本是评分输入。五者不能混为一个状态。

### 3.2 两级构件组

作业层级固定为：**桥梁 → 一级构件组 → 二级构件组 → 实际构件 → 病害记录**。构件仍是采集及检查覆盖的基本单位，两个层级的组用于分类、定位和进度汇总。

| 一级构件组 | 稳定结构部位标识 | 二级构件组举例 |
| --- | --- | --- |
| 上部结构 | `superstructure` | 上部承重构件、上部一般构件；其余按当前桥型的规范类别提供 |
| 下部结构 | `substructure` | 桥墩、桥台、翼墙/耳墙等适用规范类别 |
| 桥面系 | `deck_system` | 按该桥型及锁定规范包提供相应桥面系构件类别 |

上述二级类别为说明性示例，不硬编码为所有桥型共用的一份完整目录。具体类别、归属、名称和顺序由服务器依据当前桥型、锁定规范包及已确认构件映射生成。

规则如下：

- 一级按结构部位组织；二级按 `standard_component_category_id` 对应的规范构件类别组织。二级组键至少绑定规范包身份和类别 ID，并保留父级键。
- “主梁、挂梁”等现场构件类型位于相应二级组内，例如“上部结构 → 上部承重构件 → 1-1# 主梁”。`site_component_type` 仍作为构件属性，可用于组内检索；不再直接作为二级组键。
- 同一二级组可以包含多个现场类型、跨号及位置。跨号、墩台号是组内定位和排序维度，不新增为第三层构件组。
- 类别目录由规范提供，实际成员由台账已确认映射决定。不能从来源软件树或名称文字推断成员，不能把来源树中“上部承重构件、上部一般构件”的合并标题直接当作一个规范二级组。
- 每个范围内实际构件必须唯一归入一个有效二级组，并通过父级归入一个一级组。发现映射缺失、多个有效类别或部位不一致时，列为分类异常，由服务器核实；APP 不自行选一项或丢弃构件。
- 无法落入三个一级组的台账项目不得悄悄隐藏。需要纳入实际构件检查范围的，先解决分类；全桥控制项等非实际构件事项独立保留，不凑成第四个一级构件组。
- 一级进度由所属二级组实际构件去重汇总；二级进度由组内构件检查状态汇总。未检异常单列，不把组数当作已检查构件数。
- 组内保留台账 `sort_order`、编号及位置，不能用简单字符串排序替代已有台账顺序。切组、返回或恢复应用时，保留一级组、二级组及当前构件定位。

该分类用于作业组织，也与服务器评分结果的结构部位和规范类别建立可追溯对应；但**组的进度统计不能代替规范评分权重或聚合算法**。

### 3.3 实际构件

记录引用 `bridge_component_id`，并同时保存台账修订版和对应条目身份。编号、名称、类型和位置作为快照用于现场核对；不能以名称或编号字符串作为写回身份。

发现实物缺失、台账缺项、名称不符或构件更换时，记录异常及证据，交由有权限的人员修正台账。移动端不自行创建正式构件、自动换绑或把疑似同名构件当成同一件。

### 3.4 病害身份

既有病害复查必须引用明确的前次正式观测 ID；已有可靠线索 ID 时一并携带。没有线索 ID 的历史观测仍可复查，不能因此强制先整理全部线索。

同一构件、同一病害类型、不同发生位置可能是多条病害，不得按类型合并。仅凭文字相似不能自动认定为原病害延续。新增病害具有独立本地记录 ID，由服务器在接收时生成正式候选身份。

## 4. 历史基线与资料准备

### 4.1 “上次记录”的定义

默认采用目标年度之前、该构件最近一次有效正式检查的结果，不固定为上一自然年度。例如录入 2026 年，某构件最近正式检查只有 2024 年，则基线为 2024 年。被新修订替代的年度版本不能作为当前有效基线。

基线必须保留来源年度、检查/修订身份和正式观测 ID，并在作业包生成时固定。作业期间不静默替换基线。

历史覆盖与病害存在是两个不同问题：

| 历史资料情况 | 可得出的结论 |
| --- | --- |
| 有正式构件检查结果，明确检查完成且无病害 | 上次检查未发现病害 |
| 只有正式病害观测，没有构件检查覆盖记录 | 有这些历史病害；不能证明记录完整 |
| 查询不到历史观测或构件检查结果 | 无可用历史记录；不能推断构件健康 |
| 历史构件身份无法与本次台账可靠对应 | 基线存在身份异常，需核实 |

首次接入旧数据时，可以使用最近年度的正式病害集合，但必须标记基线完整性。不得只取“最近一条非空病害”而忽略之后已记录的维修、未见或正常检查结果。

历史中已存在维修、未见等正式处置结论时，结论与原病害一并保留；不把已闭合历史重新当作未处理病害。缺少明确闭合证据的记录保持可复查，不能凭记录缺失自动闭合。

### 4.2 本地作业包

现场作业前，由服务器生成一致性快照，内容包括：

- 桥梁身份、年度任务、范围、任务负责人、成员身份、每件构件的指定负责人及作业包版本。
- 完整构件条目、一级组和二级组目录、父子关系、成员映射、编号、位置及有效分类。
- 所锁定的规范和评定树版本，各构件适用的病害指标及测量规则。
- 每件构件的历史基线、观测、尺寸、历史照片及基线完整性说明。
- 文件清单、大小、哈希、数据摘要和生成时间。

只有结构化资料和必需文件下载、校验成功后，作业包才可标记为就绪。下载不完整可以重试，不得把历史照片加载失败解释为没有照片。现场默认可离线查看纳入作业包的历史资料。

普通查询接口按需分页的现状不要求改变；新增作业包服务负责稳定快照及分段下载，避免移动端通过数千次逐构件调用自行拼接不一致数据。

## 5. 构件检查与病害复查规则

### 5.1 构件作业流程

选择一级构件组 → 选择二级构件组 → 选择实际构件 → 查阅历史基线 → 逐条复查既有病害 → 记录新增病害 → 点击构件页主按钮确认并完成检查。无新增病害时，主按钮明确写为“确认无新增病害并完成”；无历史及本次病害时写为“确认无病害并完成”，不另设重复勾选。

组内任意构件均可直接访问。可以按台账顺序继续下一件，也可以切换其他一级或二级构件组；切组、返回或中断作业不能改变已保存记录。查阅资料本身不计为完成检查。

### 5.2 两个独立的复查维度

病害变化与维修情况分别存储，不使用一个互斥枚举替代两者。

| 维度 | 值 | 规则 |
| --- | --- | --- |
| 病害变化 | 无明显变化、加重、减轻、本次未见、无法判定 | 逐条选择，不因打开记录自动赋值 |
| 维修情况 | 未见维修、已维修、不确定 | 表示现场观察或已核实情况，不等同于维修工程验收 |

“已维修且加重”是有效组合。“本次未见”不等于“已修复”；“无法判定”不等于“无明显变化”。维修事实不能自动把当前尺寸、病害标度或病害数量清零。

填写“已维修”时，必须说明维修部位、方式或观察依据。维修日期、施工单位等未知信息可以为空，不要求现场编造。第一期只记录与本次复查有关的维修观察，不建设完整维修工程、费用或验收管理模块。

### 5.3 测量与描述

- 本次测量与历史测量分开保存，不能覆盖历史字段。
- 支持单值、范围、单位、近似值和原始测量文字，兼容现有尺寸表达；不把范围强制压成一个数值。
- 仅在人员明确核实后允许沿用上次测量值，并标记数据来源为“现场核实沿用”。不能因为选择“无明显变化”就自动当作本次重新测量。
- “本次未见”不填写虚构尺寸；“无法判定”记录原因及已获得的部分信息，保留未测项。
- 病害指标来自当前构件适用的年度锁定评定树。描述基于指标、位置和测量字段生成，补充说明独立保留。
- 如提供描述模板，应按适用指标关联并版本化；不得通过描述模板或自由文本反推唯一评分指标。
- 本地只作字段完整性与量纲校验。正式技术状况等级、标度合法性及评分仍由既有服务器规则决定，不从“加重”等变化标签直接换算扣分。

### 5.4 新增病害

新增记录必须明确关联当前构件和适用病害指标，包含位置、所需测量信息及本次证据。可以新增多条同类型病害，但须能够按位置及记录身份区分。

“新增”首先表示本次未与任何既有记录关联。历史基线不完整时，不自动宣称病害一定在两次检测之间新发生；正式跨年语义结论交由复核确认。

没有新增病害也需明确记录“已检查，未发现新增病害”。该结论由人员点击明确标识的构件完成按钮时写入本地记录；仅查看、返回或切换构件不生成否定结论。页面不另设独立勾选。新增记录被修改、删除或重新分类后，应重新检查构件完成条件。

### 5.5 构件状态与异常

| 状态 | 含义 | 是否可直接计为检查完成 |
| --- | --- | --- |
| 未检查 | 尚无实际检查记录 | 否 |
| 检查中 | 部分既有病害已处理，或新增记录仍未补齐 | 否 |
| 已检查完成 | 应复查病害均处理，新增病害结果已明确，必要资料完整 | 是 |
| 已登记未检异常 | 因不可达、遮挡、实物不符等无法完成，已说明原因和证据 | 否，单独计数 |

进度分别统计已检查完成、已登记未检异常、未处理，不将“无病害”“未检”和“未见原病害”合并。

每名成员提交前，其负责范围内的构件都须有结论：已检查完成或显式登记未检异常。含未检异常的构件资料可作为待复核资料提交，但不能标记为已检查完成；服务器汇总和正式确认前必须补检，或由有权限的人员依据业务规定明确接受例外并留痕。不存在默认为正常的批量完成操作。

## 6. 本地数据与照片存储

### 6.1 保存边界

所有输入先写设备持久存储。保存成功提示必须以本地事务和必要文件落盘成功为准；网络请求成功与否不参与日常保存。

正式应用采用能够支持事务、索引、迁移和附件文件管理的本地存储层。原生或混合客户端可使用本地数据库与应用文件目录；浏览器载体必须提供等价的结构化数据及大文件持久存储能力。**原型中的 localStorage 文字保存及照片计数不能作为正式实现。**

客户端界面与持久存储通过本地仓储接口隔离，后续界面重做不改变保存协议。结构化记录与文件之间采用可恢复的写入流程：临时文件写入并校验 → 建立记录引用 → 标记完成；启动恢复时识别中断写入和孤立文件。

### 6.2 核心本地实体

以下为逻辑模型，物理表名可在实施时映射，但身份及关系不得省略。

| 实体 | 关键内容 |
| --- | --- |
| 作业包 | `task_id`、桥梁/年度 ID、台账和规则版本、包版本/摘要、范围、基线引用 |
| 构件组快照 | 一级组键/结构部位、二级组键/规范类别 ID、父级关系、规范包身份、名称、顺序 |
| 构件快照 | `bridge_component_id`、台账条目 ID、一级/二级组引用、现场类型、编号、位置、顺序 |
| 历史观测快照 | 原观测 ID、可选线索 ID、来源年度修订、指标、尺寸、照片、完整性 |
| 构件检查结果 | 构件 ID、状态、新增病害检查结论、未检原因、人员、检查时间、本地修订号 |
| 既有病害复查 | 本地 ID、前次观测 ID、当前指标身份、变化、维修、测量、说明、确认状态 |
| 新增病害 | 本地 ID、构件 ID、指标 ID、位置、测量、描述和补充说明 |
| 本次附件 | 本地 ID、关联记录、路径、MIME、字节数、哈希、拍摄/导入时间 |
| 成员提交 | 成员 ID、负责构件清单、各构件本地修订和摘要、传输进度、服务器会话与构件级回执 |
| 队友同步缓存 | 来源成员、构件 ID、服务器提交修订、内容摘要、获取时间和本机已读版本 |
| 本地变更日志 | 记录身份、变更顺序、人员/设备、旧新修订、保存结果 |
| 评分结果缓存 | 任务/桥梁/年度、整桥汇总版本及修订、输入摘要、计算任务 ID、可用时的 `assessment_run_id`、结果性质、规则版本、分层结果、问题清单、计算/获取时间、是否当前有效 |

本地 UUID 仅用于现场身份、照片关联和幂等同步；它不是现有系统的 `candidate_id`。正式候选 ID 继续由 C++ 后端生成。

### 6.3 附件与恢复

本次照片保存实际文件，不只保存相册临时地址或内存引用。历史照片始终保留历史来源，不复制为本次拍摄证据；缩略图与原图区分，压缩版本具有独立哈希。

记录和照片关联随本地业务记录保存。没有本次照片时要求说明原因，并作为待复核警告；不因其没有照片而编造上传成功状态。跨病害共享附件只允许显式建立关系，不能按文件名隐式匹配。

应用重启、进程终止或设备断网后，应恢复最后一次成功落盘的数据；正在写入但未完成的内容单独提示。存储空间不足、文件丢失或数据库写入失败时，不得计入完成状态。

注销、切换账号、升级应用或刷新作业包均不得静默删除未提交数据或已同步的队友副本。本地资料按用户、服务器环境、桥梁年度任务隔离。需要清理时由用户明确操作，优先限制清理尚无成功回执的资料；提供可校验的本地备份与恢复能力，不依赖上传作为唯一备份。

### 6.4 多人分工与离线作业

同一年度任务可分配给多名现场人员。每件构件在一个分工版本内只指定一名录入负责人；其他成员可以查阅已下载的历史基线，以及本人主动同步取得的队友已提交资料，但不能修改该构件的本次记录。调整分工时增加版本并记录交接；旧分工版本不得继续提交。

各设备独立保存本地记录和照片。离线保存不等于团队共享。构件完成只表示本机已完成检查，不表示服务器已收到；成员联网后主动提交自己负责且已完成的构件。服务器逐件校验任务、人员、构件、基线、分工版本、内容摘要及附件，并返回构件级回执。提交后再次编辑，保留已提交版本和本地新修订，明确提示“有未提交修改”，再次提交才更新服务器版本。

同步是独立的用户操作：联网时查询服务器上队友已提交的构件版本，下载差异并校验，再写入本机同步缓存。同步不上传本机记录，也不更改队友的提交。离线时可以查看已同步的旧版本，但必须保留其来源、修订和同步时间；未同步时不能显示队友未获取的本次病害细节。成员可据此了解全桥进度、避免重复检查，并在现场对已提交内容提出复核意见；跨人修改仍需通过分工交接。

同一构件出现不同设备或修订的提交候选时，服务器保留双方来源并报告冲突，不采用最后写入覆盖。任务负责人会同原负责人核对病害、测量和附件，选择经确认版本或退回重查；处理人、时间、原因及版本摘要留痕。第一阶段不支持同一构件多人同时编辑后的字段级自动合并。

## 7. 成员提交与团队同步协议

### 7.1 提交边界

每名成员仅能主动提交自己负责的构件，不等待其他成员完成，也不需要负责人再执行整桥统一提交。一次提交可以包含该成员多件构件及其照片，并允许分段传输、断点续传和幂等重试。单纯保存、切组、完成构件、恢复网络及执行同步都不触发提交。

提交成功表示服务器接收了指定构件的冻结版本，不表示整桥完成、资料正式确认或评分已经生成。服务器根据任务范围、分工及各构件最新有效提交版本自动汇总全桥状态。全部范围内构件提交、附件齐备且无阻断冲突时，服务器生成一致的整桥输入版本并启动试算；这一汇总是服务器业务编排，不要求某位成员再次点击提交。

### 7.2 成员提交阶段

1. 成员本地预检本人负责构件的检查覆盖、既有病害复查、新增病害结论、异常、字段和附件。
2. 冻结本次提交的构件清单、各构件本地修订和内容摘要；后续本地编辑形成新修订，不改变传输中的快照。
3. 服务器验证登录人员、任务、分工版本、构件身份和历史基线，创建或恢复成员提交会话，并返回缺失附件清单。
4. 客户端只传缺失的记录和附件；服务器按文件身份及哈希校验。中断后保留本地数据和已完成传输进度。
5. 服务器以构件为单位接收有效快照并返回稳定回执，列明成功、失败或冲突的构件。不得把部分成功说成全部成功；失败构件保留本地待提交状态。
6. 服务器在提交版本改变后重新核对整桥覆盖与冲突。全部满足条件时冻结新的整桥汇总版本，可靠调度试算，供 APP 查询。

本机在收到回执后保存服务器构件修订与本地身份映射，保留本地副本。照片校验成功但构件提交尚无回执时，不得标记该构件已提交。数据库与文件存储不共事务时，先校验文件、后建立事务关联，并按引用关系延迟清理失败上传。

### 7.3 主动同步、幂等与冲突

- 同步请求携带任务、分工版本及本机已知的服务器变更游标；服务器返回有权限查看的新增或修订构件清单。客户端按构件获取差异并在校验完成后原子更新本机同步缓存和游标。
- 同步失败或中断时，保留旧缓存及旧游标；重试不得产生重复记录。同步成功后标明获取时间。离线时只展示已缓存的版本，不推断队友本机尚未提交的数据。
- 提交的幂等身份由任务、成员、构件、本地修订和内容摘要共同确定。相同身份与摘要的重试返回相同回执；相同身份而摘要不同应拒绝并要求新修订。
- 提交超时先查询回执再重试；不能仅凭客户端没有收到响应就判定失败。服务器使用分工版本和构件级并发控制，拒绝旧设备或越权提交。
- 已提交构件重新编辑后，旧版本对团队仍可见，但本机明确标记新修改尚未提交。新修订通过校验后替换该构件最新有效提交版本；整桥汇总版本和试算随之更新，历史版本保持可追溯。
- 相同构件的跨设备争议须授权核对并留痕，不自动字段合并。队友同步时只取服务器确认的有效版本，不以本机缓存覆盖服务器版本。

本地状态建议区分：未完成、已完成未提交、提交中、提交失败可重试、已提交、有未提交修改、提交冲突。队友同步状态另行区分：未同步、已同步、服务器有更新、同步失败。评分计算状态和正式复核状态分别保存。

## 8. 与现有后端、合同和档案的衔接

### 8.1 新采集协议独立于导入合同

新增版本化移动采集包协议，例如 `MobileBridgeInspectionPackage/1`。协议保存构件检查覆盖、前次观测引用、维修观察、现场测量和本地身份等事实。

当前 `BridgeAnnualInspectionData 5.0` 继续作为现有导入候选边界。5.0 中已经移除的构件 ID、评分树解析状态不能重新塞入其候选 JSON；移动采集包也不能直接冒充 5.0 合同。

由服务器适配器在接收事务中完成：

1. 校验移动端引用的真实构件和锁定版本。
2. 为适合进入病害校对的当前病害观测生成候选 ID。
3. 通过关系化解析模型保存构件及评分树关联，避免二次名称匹配。
4. 独立保存构件检查结果、变化及维修事实、前次观测引用和同步来源。
5. 建立本地 ID、候选 ID、附件 ID 和后续正式观测 ID 的追溯关系。

服务端生成候选和关联的过程应复用现有命令/领域服务的约束，但不是让移动端逐条调用现有手工新增接口。若确需修改 5.0 合同，应另行提出版本变更并同步 Schema、Python、C++、TypeScript 和样例，不能静默扩展。

### 8.2 复查结果不全部等价为当前病害

“未发现新增病害”“本次未见原病害”“构件无法检查”不能伪造成一条零尺寸、零标度的当前病害候选。

当前仍存在的病害按真实观测进入现有病害校对链路；无病害的构件检查结果、未见结果及无法判定结果进入扩展的检查/复查事实模型。维修观察不直接覆盖历史观测，也不自动关闭病害线索。

现有合同中虽然有对比类型及基础结构，但完整跨年语义确认和维修管理尚未实现。新增模型必须允许独立保留变化与维修两个维度，不能把二者挤入单一“原病害修复”值。

### 8.3 正式确认与评定

成员构件回执仅表示服务器已接收该构件的冻结版本；全部范围内构件通过校验后，服务器形成待复核的整桥汇总资料。桌面端仍需检查内容、异常、照片和适用规则后正式确认。

当前系统已有试算能力，正式确认链路会产生正式系统评定。移动采集在整桥汇总版本就绪后可由服务器对冻结资料进行试算，供 APP 查看；正式评定仍接入现有受控确认链路，不新增绕过正式确认的正式评分入口。对未检、无法判定、历史不完整等情况，必须在正式确认前明确处理，不得自动按健康构件参与评定。

已正式确认的数据修正沿用修订版思路，不原地覆盖历史事实。新年度是否“新增、持续、减轻、维修后仍存在”作为可追溯复查事实保留；不自动改变现有报告的条数对比统计口径。

### 8.5 桥梁评分结果展示功能页

该功能页负责获取和展示服务器计算结果，不承担本地算分。本文只定义其业务内容、数据边界及状态，不规定界面布局。

#### 8.5.1 计算链路与结果性质

各成员分别提交负责构件 → 服务器校验并自动形成整桥汇总版本 → 服务器试算 → APP 获取和展示试算结果 → 桌面端复核及正式确认 → APP 获取正式评定结果。

- 整桥汇总就绪后可查看的是“试算结果”，必须标明尚未正式确认，不能用作正式报告结论。
- 桌面端完成正式确认后，APP 读取已保存的正式评定及其 `assessment_run_id`，不为展示重新计算。正式结果可能因复核修改而与原试算不同。
- 本地新增修改未提交时，已有分数只能代表上次已提交的整桥汇总版本。必须标明“本地存在未提交修改”，不能把旧分数称为当前本地数据的结果。
- 查询某个整桥汇总版本的评分不能回退为其他版本、其他年度或该桥的任意最近一次评分。同年度历史正式结果可以查阅，但必须明确其来源及是否仍为当前有效版本。

#### 8.5.2 结果应提供的信息

| 层级或信息 | 内容要求 |
| --- | --- |
| 全桥 | 全桥分数、计算等级、最终等级及必要说明；最终等级以服务器结果为准 |
| 一级构件组 | 上部结构、下部结构、桥面系的服务器分数、等级及评定所使用的权重 |
| 二级构件组 | 对应规范构件类别的分数、等级、实际参与评定构件及服务器返回的适用信息 |
| 实际构件 | 构件身份、编号、得分、病害标度、扣分项和可追溯规则依据 |
| 特殊控制 | 触发的单项控制、控制依据及其对最终等级的影响 |
| 问题与状态 | 未检、无法判定、标度缺失、无效映射等阻断问题或警告及所涉及的构件/病害 |
| 来源与时效 | 桥梁/年度、整桥汇总版本及修订、输入摘要、规范与算法版本、计算时间、试算/正式标记、正式修订与当前有效性 |

APP 按稳定结构部位和规范类别 ID 对应两级构件组，再按服务器映射定位实际构件；不按显示名称关联。现有返回中的 `component_instance_id` 需由服务端给出与台账 `bridge_component_id` 的明确对应，不能假定两者可直接互换。

客户端不对构件分数做简单平均来重建二级、一级或全桥分数，不自行四舍五入重判等级，不忽略特殊控制。没有适用评分项或结果缺失时，表达为“不适用”或“暂无结果”，不能显示成 0 分或 100 分。

#### 8.5.3 计算状态、幂等和失败恢复

计算任务状态包括：等待计算、计算中、计算完成、缺少必要数据、计算失败。状态附带任务 ID、输入身份、问题清单和完成时间；结果另附试算/正式性质以及当前有效/历史/已过期标记，避免用一个枚举混合这些维度。

- 整桥汇总版本就绪后，通过持久任务记录或等价的可靠调度机制启动试算。汇总事务成功而调度暂时失败时应可恢复，不依赖移动端保持在线。
- 同一冻结整桥汇总版本、输入摘要以及规则/算法/评定树版本组合只对应一个有效计算任务；重复请求或 APP 重连不能重复产生冲突结果。
- 服务器复用既有 evaluator。移动端不上传计算公式，也不执行简化评分算法。
- 现有试算接口涉及导入记录草稿与编辑锁；新增移动任务由服务器构造冻结输入并遵守既有服务约束，不能让 APP 绕过锁或假装持有桌面编辑锁。
- 试算缺少必要输入时返回可定位的问题，不默认补标度、补尺寸或把未检查构件视为健康。修正后由负责成员重新提交受影响构件，服务器形成新的整桥汇总版本并重新计算。
- 纯计算故障可以重试同一计算任务，不需要重新上传已校验的构件数据和照片。
- APP 离开功能页或退出应用后，服务器计算可继续；重新进入时按任务和整桥汇总版本查询。允许有界轮询或显式刷新读取状态，不触发业务资料自动上传。

#### 8.5.4 缓存与版本一致性

APP 可以缓存服务器已返回的结果用于离线查阅，明确标注缓存时间、结果来源和最后已知有效性。离线时不能保证服务器此后未发生修订，也不在本地重新算分。

缓存按桥梁、年度、任务、整桥汇总版本、输入修订及结果性质隔离。服务器返回的数据版本与请求不一致时不作为本次结果展示；刷新失败可以保留旧缓存，但必须说明未获取最新结果。

正式结果若已被新修订替代，作为历史结果保留；规范包升级不会导致读取旧正式结果时重算。单个构件、二级组、一级组和全桥分数必须来自同一计算运行或一致的结果快照。

## 9. 版本、权限与异常处置

| 情况 | 处理原则 |
| --- | --- |
| 现场网络中断 | 本地采集和已同步缓存查阅继续；成员提交或同步暂停，联网后由用户主动重试 |
| 登录会话过期 | 已授权作业副本可继续本地记录；上传前重新认证并校验权限 |
| 台账或规则出现新版本 | 已锁定版本仍有效时继续使用；不强制追随“最新”版本 |
| 任务实际依赖版本被替换、撤销或不再允许接收 | 返回版本冲突，保留原包及本地修改，显式迁移或人工处理 |
| 历史正式记录被修订 | 不静默修改现场基线；提交时提示受影响记录，重新确认引用 |
| 构件被停用、更换或身份不明 | 不自动改绑；保存异常，管理员处理身份及任务范围 |
| 附件损坏或丢失 | 阻止完整提交，列明受影响记录；不能将历史照片充作本次照片 |
| 构件资料已传输但提交超时 | 查询同一成员提交会话和构件回执，保留本地数据及服务器暂存文件 |
| 提交后发现错误 | 原构件提交版本保持可追溯，由负责成员提交新修订；正式事实修正走既有授权修订链路 |
| 评分计算失败或必要输入缺失 | 构件提交回执仍有效；可重试计算，或由负责成员补齐并提交新修订；不伪造评分 |
| APP 离线、未同步或本地有未提交修改 | 可查阅带来源说明的缓存结果，但不能声称反映当前最新数据 |

现有部署以本机服务为主，手机不能访问服务端的 `127.0.0.1`。正式部署需要明确可达的受控服务地址及认证保护；不能为了移动端直接开放数据库或把当前本地只读接口无鉴权暴露到公网。具体网络部署与客户端发布方式单独设计。

原型中“保存”“照片”“提交”“同步”的模拟操作不是正式权限控制、可靠文件存储或服务端幂等机制的证据。

## 10. 第一阶段范围与实施顺序

第一阶段交付完整业务闭环：准备作业包、两级构件分组、构件选择、历史复查、新增病害、本地持久保存、按构件分工、成员各自提交、主动同步队友资料、冲突处理、服务器整桥汇总与评分、APP 结果展示、桌面端复核及正式链路衔接。

按依赖顺序实施：

1. 定义作业包、历史基线、检查/复查事实及版本化采集协议；验证与 5.0 适配边界。
2. 实现本地仓储、附件保存、自动本地保存、恢复、备份及本地预检。
3. 实现一级结构部位、二级规范类别与实际构件的分组及作业服务，接入后续独立设计的界面。
4. 实现成员构件提交、队友增量同步、分工版本、冲突处理、整桥自动汇总、幂等、断点恢复和构件级回执。
5. 接入服务器试算任务、状态查询和结果缓存，提供 APP 桥梁评分结果展示功能。
6. 接入桌面复核、当前病害候选、非病害检查结果及授权异常处理，再验证正式确认、正式评分获取和报告不受破坏。

第一阶段不包含同一构件多人实时编辑及字段级自动合并、维修工程管理、自动病害识别、自动跨年匹配、电子签名、移动端报告生成，也不包含界面设计和客户端框架选型。业务规则不得依赖某种页面或控件才能成立。

## 11. 验收标准

| 编号 | 场景 | 应达到的结果 |
| --- | --- | --- |
| A01 | 按两级组组织完整台账 | 一级为三个结构部位，二级为适用规范类别，实际构件归属唯一；层级汇总无重复，无病害构件也在范围中 |
| A02 | 同编号出现在不同构件类别 | 通过构件身份正确区分，不按编号单独关联 |
| A03 | 2026 年对应上次 2024 年正式记录 | 正确固定 2024 基线，保留来源版本 |
| A04 | 历史为空或仅有病害观测 | 不自动标记历史健康或完整检查 |
| A05 | 同一构件有多条同类型病害 | 分别引用历史观测、分别复查，不自动合并 |
| A06 | 已维修但仍加重 | 两种事实同时保存，历史不被覆盖 |
| A07 | 本次未见、无法判定、未检查 | 三者独立处理，不生成虚假零尺寸病害，不自动按健康评分 |
| A08 | 单值、范围及不同单位测量 | 原值、范围边界、单位、近似标记与来源保持一致 |
| A09 | 同一构件既复查旧病害又新增病害 | 旧记录关联保持，新记录身份独立 |
| A10 | 无新增病害的构件 | 点击“确认无新增病害并完成”后，才写入否定结论并满足构件完成条件；仅查看或切组不生成结论 |
| A11 | 断网、应用重启、写入中断 | 已成功保存的记录及实际照片恢复；未完成写入可识别 |
| A12 | 空间不足或附件丢失 | 不提示保存成功，不计为可完整提交 |
| A13 | 保存、切组、完成构件、恢复网络 | 均不自动提交现场记录或附件，也不自动同步 |
| A14 | 某成员负责范围仍有未处理构件 | 阻止该成员提交；不阻止其他成员提交自己的完整范围，显式未检异常单列 |
| A15 | 文件中断、提交超时、重复重试 | 保留本地资料；同一构件修订无重复候选或照片，可查询稳定的构件级回执 |
| A16 | 并发提交、年度变更、任务交接 | 识别任务级、分工版本及构件修订冲突，不覆盖他人数据 |
| A17 | 构件映射与评分树归属 | 校验稳定身份后直接建立关联，无需再次按名称猜测；异常明确返回 |
| A18 | 无病害及未见记录适配 | 保存检查事实，不伪造病害候选；正式确认受控处理例外 |
| A19 | 正式确认与修订 | 当前观测、变化事实和附件可追溯，历史保留，评定仍来自既有系统 |
| A20 | 真机与实际大台账 | 使用实际规模台账及照片集验证存储容量、启动、分组检索、连续保存、成员提交及队友同步；记录设备和实测结果 |
| A21 | 现场类型与规范二级类别不同 | 主梁等现场类型归入上部承重构件等规范类别，不把来源树的合并标题当成单一二级组 |
| A22 | 范围内构件均已提交且校验通过 | 服务器自动形成整桥汇总版本并可靠启动试算，APP 获取对应结果；无需负责人再次提交 |
| A23 | 试算、正式及旧版本并存 | 明确标明性质、数据来源及有效性，正式结果按已有运行读取，不混为同一结果 |
| A24 | 两级组及全桥分数展示 | APP 展示服务器分层结果和控制依据，不自行平均、重判等级或补缺失分数 |
| A25 | 计算失败、重连及重复请求 | 不改写已成功的构件提交状态，不重复建冲突任务；可独立恢复计算与查询 |
| A26 | 离线缓存或本地新增修改 | 明确缓存时点及未提交修改，不把旧分数当成最新本地结果 |
| A27 | 必要评分输入缺失 | 返回问题及对应构件/病害，不能把未检当健康或默认补齐评分输入 |
| A28 | 多人按构件分工并离线采集 | 仅指定负责人可修改负责构件；队友不误认为尚未提交的本地记录已共享 |
| A29 | 网络恢复 | 不自动提交或同步；成员主动提交本人已完成构件并获得构件级回执 |
| A30 | 提交后又修改 | 本机标记有未提交修改；队友仍可看旧提交版本，新修订经再次提交后更新服务器汇总 |
| A31 | 全桥尚有未提交构件或待处理冲突 | 其他成员可继续提交本人范围；服务器暂不形成可评分的整桥汇总版本 |
| A32 | 两设备提交同一构件的竞争版本 | 保留双方来源与附件，阻止静默覆盖，授权核对留痕后确定有效提交版本 |
| A33 | 全部构件由各负责人分别提交且无冲突 | 服务器自动冻结整桥汇总版本并触发试算，无负责人统一提交步骤 |
| A34 | 队友提交后本机未同步或离线 | 本机不显示未获取的病害细节；已缓存旧版标明来源、修订和同步时间，不被服务器新版本静默覆盖 |
| A35 | 队友提交新修订后主动同步 | 本机只下载差异并更新缓存；旧版本和评分输入版本可追溯，切换账号不会混用缓存 |

A20 可使用现有 5,174 件台账规模作为验证基准，不能以原型四件构件的演示性能代替验收。具体时间与容量指标在确定目标设备后建立基线，本文不声称已经测得正式移动端性能。
