# 构件台账标准化编号与导入绑定 重设计

> 日期：2026-07-21
>
> 状态：已实施；2026-08-14 由河床构件生成设计补充
>
> 当前维护分支：`codex/06-6-interaction-redesign`
>
> 来源：用户提供的《构件编号规则》文档 + 多轮讨论收敛

## 1. 背景与问题

现有构件台账向导让用户配置抽象的"编号方式（连续/按跨/按墩位）+ 前缀 + 后缀"，与真实的构件编号规则脱节，用户填起来"太乱"：真实编号是"多维索引 + 位置词 + 类型词"（如 `1-1#梁`、`1-1-1#横隔梁`、`0#台左侧锥坡`），现有三种模式表达不了。

导入病害与台账的匹配此前拿**构件名**（如台账"空心板" vs 报告"上部承重构件"）去比，而报告用词各不相同，导致大面积误判（真实案例 279 条病害全部落入"未找到唯一构件"）。

本设计重构台账构建方式、导入数据保真、匹配键，并新增导入绑定界面。编号形状仍属于产品生成约定，不改变评定算法。2026-08-14 为开放河床生成准入，另行发布 H21 1.0.4 和评定树 2.0.3；详见 `2026-08-14-riverbed-inventory-generation-design.md`。

## 2. 目标与非目标

### 2.1 目标

- 台账按**规范/设计文件的正式名**命名，并按标准编号规则**自动生成**构件编号；用户只描述桥的物理构成（孔数 + 每部件数量）。
- 导入病害的构件编号**按报告表格原文保真**存储与显示。
- 匹配键改为**部件类别 + 构件编号（精确比对）**，构件名不参与匹配。
- 新增**导入绑定界面**，集中处理自动对号的结果与少数例外。

### 2.2 非目标

- 不做绑定映射的持久化 / 跨年自动套用（YAGNI，每次导入独立绑定）。
- 不改评定算法、权重、扣分、标度和等级边界。普通编号形状调整不触发规范包版本；河床生成准入元数据的版本化例外见 2026-08-14 河床设计。
- 覆盖 H21 **全部 6 种桥型**（梁式桥、板/肋/箱/双曲拱、刚架/桁架拱、钢混组合拱、悬索、斜拉）：下部结构/桥面系/支座部件在桥型间共享；各桥型上部结构中，梁式桥用《规则》确定形状，**非梁桥型（拱圈/拱片/拱肋/斜拉索/主缆/索塔等）先用临时编号形状**，标 `provisional`，与下部结构一样待真实报告校准（见 §3.2 [注]），不阻塞、由绑定界面兜底。
- 不改编辑锁、草稿保存、确认入库、修订规则。

## 3. 编号规则（真值来源）

来源：用户提供的《构件编号规则》。骨架与各部件编号形状如下。

### 3.1 骨架

- 输入 **孔数 N**（即跨数）。
- 派生：支承线 = `0#台、1#墩、…、(N-1)#墩、N#台`（N+1 条）；墩数 = N−1；台数 = 2（两端恒为台）。
- 派生量只用于生成"孔/墩/台"的编号标签，是拓扑，不需用户填。

### 3.2 部件编号形状（梁式桥）

各部件的编号格式、所需数量输入、以及映射到的规范评定类别：

| 分部 | 现场构件类型（默认名） | 编号形状（示例 N=5） | 数量输入 | 规范评定类别 |
| --- | --- | --- | --- | --- |
| 上部 | 梁板 | `1-1#梁 … 5-M#梁` | 每孔梁片数 | 上部承重构件 |
| 上部 | 湿接缝 | `1-1#湿接缝 …` | 每孔条数 | 上部一般构件 |
| 上部 | 横隔梁 | `1-1-1#横隔梁 …` | 每孔道数 | 上部一般构件 |
| 上部 | 支座 | `1-1-1#支座 …`（孔-墩-支座，按《规则》第10条）[注] | 每墩支座数 | 支座 |
| 下部 | 墩柱 | `1-1#墩柱 …`（墩 1..N−1，右→左） | 每墩根数 | 桥墩 |
| 下部 | 盖梁 | `1#墩盖梁 … (N−1)#墩盖梁` | 每墩个数（默认 1） | 桥墩 |
| 下部 | 系梁 | `1-1#系梁 …`（下→上） | 每墩个数（默认 0） | 桥墩 |
| 下部 | 台身 | `0#台、5#台` | 每台（=1） | 桥台 |
| 下部 | 台帽 | `0#台帽、5#台帽` | 每台（=1） | 桥台 |
| 下部 | 墩台基础 | `0#台基础 … 5#台基础`（支承线） | 每支承线（=1） | 墩台基础 |
| 下部 | 翼墙/耳墙 | `0#台左侧翼墙 …` | 每台左/右 | 翼墙、耳墙 |
| 下部 | 锥坡 | `0#台左侧锥坡 …` | 每台左/右 | 锥坡、护坡 |
| 下部 | 护坡 | `0#台护坡 …` | 每台（0/1） | 锥坡、护坡 |
| 下部 | 河床 | `河床` | 整桥（0/1，默认不选） | 河床 |
| 桥面系 | 桥面铺装 | `1#跨桥面铺装 … 5#跨桥面铺装` | 每跨（=1） | 桥面铺装 |
| 桥面系 | 伸缩缝 | `1#伸缩缝 …` | 数量 | 伸缩缝装置 |
| 桥面系 | 人行道 | `左侧人行道、右侧人行道` | 左/右 | 人行道 |
| 桥面系 | 栏杆护栏 | `左侧栏杆、右侧栏杆` | 左/右 | 栏杆、护栏 |
| 桥面系 | 排水系统 | `排水系统` | 整桥（0/1） | 排水系统 |
| 桥面系 | 照明、标志 | `照明、标志` | 整桥（0/1） | 照明、标志 |

数量输入**全部由用户直接填**，不做跨部件推导（例如湿接缝条数不从梁片数自动推算）。孔/墩/台/支承线的外层编号标签从 N 推导。

[注] 目前只见过梁式桥上部结构病害表（表 2.1-1）。**支座编号已按《规则》第10条定案**（`N-A-B#支座`
= 第N孔第A号墩第B个支座；A 为一孔两个支承、恒 2、自右至左，不问用户；只填每墩支座数），不再待校准。
**其余下部结构、桥面系部件的编号形状**（是否带类型词、台/墩标记怎么写），以及**非梁桥型的上部结构编号形状**（拱圈/拱片/拱肋/斜拉索/主缆/索塔/加劲梁等），均需在实施阶段结合真实报告（表 2.2-1 等）最终确认；上表与部件目录按《规则》9 种形状拟定，作为实施起点并在目录里标 `provisional`。编号与报告若有出入，由绑定界面兜底人工处理，不阻塞。

### 3.3 编号引擎的"形状"抽象

上表的编号可归纳为少数参数化形状，编号生成器按形状实现（替换现有的"3 种编号方式"）：

1. `孔×构件`：`{孔}-{n}#{名}`（梁板、湿接缝）。
2. `孔×子×构件`（三级）：`{孔}-{a}-{b}#{名}`（横隔梁；两级子维都由用户填）。
2b. `孔×支承×构件`（三级）：`{孔}-{支承}-{n}#{名}`（支座，《规则》第10条）。中间的"第A号墩"是
   **一孔的两个支承，恒为 2、由几何派生**，自右至左记 1、2；用户只填最内层的每墩支座数。
3. `支承线`：`{线}#{名}`，线标签 = `0#台/1#墩/…/N#台`（墩台基础）。
4. `墩×构件`：`{墩}-{n}#{名}`，墩 = 1..N−1（墩柱、系梁）。
5. `墩`：`{墩}#墩{名}`（盖梁）。
6. `台` / `台×侧` / `台+词`：`{台}#台`、`{台}#台{左/右}侧{名}`、`{台}#台{名}`（台身/台帽、翼墙、锥坡、护坡）。
7. `跨`：`{跨}#跨{名}`（桥面铺装）。
8. `纯序号`：`{n}#{名}`（伸缩缝）。
9. `侧` / `整桥`：`{左/右}侧{名}`、`{名}`（人行道、栏杆、排水、照明、河床）。

构件名（"梁""湿接缝"…）默认取正式名、可改，仅用于**生成编号里的类型词和显示**，不进匹配。

## 4. 系统分块

### A. 台账构建（与导入解耦）

- 台账按规范/设计文件建，是桥的构件真值，与任何报告用词无关。
- 向导流程：选规范包 + 桥型 → 填孔数 N → 逐部件卡片（勾选启用 + 名称 + 数量）→ 自动生成标准编号 → 生成草稿台账 → 确认。
- 复用现有"生成即确认映射""分组核对表""查看构件弹窗"（已实现）；向导内部改为按 §3 的部件目录 + 编号引擎。

### B. 导入数据保真

- 病害解析结果中：`部件名称` = 报告"部件名称"列原文（规范部件名，可靠）；`构件编号` = 报告"构件编号"列**原文**（`1-1#`、`33-25#板`、`0#台` 原样存、原样显示，不裁剪、不归一化存储）。
- 现有合同已有 `component_name`（承载部件名称）与 `component_number`（承载编号原文）字段，本设计不改合同版本，仅明确其语义与使用方式。

### C. 匹配

- 匹配键 = **部件类别 + 构件编号**。
- **部件类别**：报告"部件名称"列 → 规范类别，通过一张固定对照表（H21 的 16 个部件名 → 类别 id，含个别同义写法）解析。
- **构件编号**：**精确比对**，仅做无害归一化（首尾空白、全角数字/`#`/`-`/括号→半角、去内部空格、大小写），**保留构件类型词**（梁/板/湿接缝）。
- **构件名不参与匹配**。
- 多构件部件（如上部一般构件含湿接缝、横隔梁）靠编号里的类型词与层级天然区分（`1-1#湿接缝` vs `1-1-1#横隔梁`）。
- 结果分级：唯一命中→自动绑定；多候选→歧义（候选列表）；无命中→未匹配。匹配记录来源（精确/候选/人工）。

### D. 绑定界面（新增，导入解析后 / 校对前）

- **前置**：台账已建且已确认（沿用评定的前置要求）。导入/解析可先做，绑定这一步需要已确认台账。
- **布局**：按部件分组核对（与现有台账"分组核对表"同一套样式）。每组一行：部件类别 | 数量 | 绑定情况（全部已绑定 / 未匹配 n / 歧义 n）| 处理。点"处理"展开该组构件行。
- **行单位 = 报告里出现的每个不同编号**：一个编号可能被多条病害引用，行内显示"引用 N 条"，绑一次，所有引用它的病害一起挂上。
- **行内容**：报告编号（原文）| 引用病害数 | 台账构件 | 状态徽章（已绑定/未匹配/歧义）| 操作。
- **手动绑定**：未匹配/歧义点"选择构件"，就地展开搜索框（已按同部件预筛，容错标点/全半角），选中即绑；复用现有校对页搜索式选择器。
- **标记缺失**：台账确实没有的构件可"标记缺失"，不阻塞流程，留待补台账。
- **不做记忆持久化**，每次导入各绑各的。
- **进入校对**：底部"全部绑定完成，进入校对"；亦可"稍后再绑"。

> **实现形态已变更（2026-07-24，提交 `ef8d316`、`9f0594f`、`da566e3`）**：绑定不再是独立页面，而是
> **校对工作台左侧导航的一个分区**（"需要处理"与"病害与照片"之间），侧栏显示待处理数。因此本节的
> "进入校对/稍后再绑"页脚在分区形态下不渲染（已经在校对页内），仅独立入口存在时才有意义。
> 另：行内**默认只显示待处理行**，已绑定/已标记缺失收起，页头提供"显示已处理 N 项"开关——
> 真实数据下 257 行中有 211 行已处理，全列出来反而淹没需要处理的那些。

### E. 校对页

- 进入时构件已由绑定阶段确定；"病害与照片"页的"实际构件"改为只读展示 + 个别调整，不再逐条手选。减轻该页负担（并与前期已修的分页/搜索改造叠加）。

## 5. 数据流

```
建台账(规范/设计命名 + 标准编号) ─确认→ [台账真值]
                                              │
上传 Word ─解析→ 病害(部件名称+编号原文) ──→ 绑定界面
                                              │ 按(部件类别+编号)精确对号
                                              ├─ 自动绑定(唯一命中)
                                              ├─ 未匹配/歧义 → 人工搜索选 / 标记缺失
                                              ▼
                                          校对(构件已绑) ─确认入库→ 评定
```

## 6. 组件边界

### 6.1 后端（C++）

- **编号生成器**（`inventory/ComponentInventoryGenerator`）：从"3 种编号方式"重写为"按部件形状生成"（§3.3）。输入 = 孔数 + 各部件数量 + 部件目录；输出 = 构件条目（编号 + 名称 + 规范类别 + 结构分部）。
- **部件目录**（全桥型）：编号形状、默认名、规范类别映射、数量输入定义属于产品约定，作为代码配置；类别是否允许进入生成流程仍严格取所选规范包 taxonomy 的 `generatable`。河床产品部件为 `lower.riverbed`、模板 `{name}`、无数量输入。
- **匹配器**（`inventory/ComponentMatcher`）：由"构件名 + 编号"改为"部件类别 + 编号（精确）"；新增"部件名称 → 规范类别"对照。
- **绑定仓储 + 路由**：导入记录的绑定状态查询、按编号绑定/改绑/标记缺失、进入校对的前置校验（台账已确认）。
- 解析提交边界：`component_name`/`component_number` 保真存储不变。

### 6.2 前端

- **台账向导**（`bridges/BridgeInventoryWizard`）：重写为"孔数 + 逐部件勾选/填数量"，按部件目录自动生成编号；移除"编号方式/前后缀"抽象配置。
- **绑定界面**（新增）：按部件分组核对表 + 展开行级绑定 + 搜索选择器 + 标记缺失 + 进度/进入校对。
- **校对页**（`review/components/ComponentMatchField` 等）：实际构件改为只读展示 + 个别调整。

## 7. 错误处理与边界

1. 台账未建 / 未确认时进入绑定 → 明确阻止，引导先建/确认台账。
2. 未匹配不阻塞浏览与绑定，但**正式确认入库前**该导入的病害必须已绑定或被明确标记（缺失/无需绑定），否则评定缺构件。
3. 歧义（同部件同编号多候选）→ 候选列表人工选，不自动绑。
4. 编号精确比对失败的（报告与台账类型词不一致等）→ 落到绑定界面人工处理，不做静默模糊匹配。
5. 绑定、搜索、标记缺失不得改动病害事实字段，不触发保存或改变校对状态。
6. 编号生成的上限与去重沿用现有生成器保护（单次数量上限、同类型内编号唯一）。

## 8. 测试与验收

- **编号生成器**：各形状单测（孔×构件、三级、支承线、墩×构件、台/台侧、跨、纯序号、侧/整桥）；孔数派生的墩/台/支承线标签正确；数量为 0 不生成；河床勾选后只生成一个全桥级条目。
- **匹配器**：部件类别+编号精确命中；多构件部件靠类型词/层级区分；全半角/空格容错；构件名差异不影响；无命中/歧义分级正确。
- **部件名称→类别对照**：16 项及同义写法解析正确。
- **绑定**：自动绑定计数、未匹配手动绑、歧义选择、标记缺失、按编号绑定影响所有引用病害、前置（台账已确认）校验、进入校对。
- **前端**：向导按目录生成、绑定界面分组/展开/搜索/标记缺失、校对页只读化。
- **回归**：台账生成/确认、评定试算与确认、确认入库、既有分页/搜索/弹窗改造不受影响。
- 全量：Python、前端全量 + 生产构建、C++ 隔离 schema 全量 + Debug 构建；`git diff --check`；保护目录不提交。

## 9. 实施顺序建议

1. 编号引擎（形状化）+ 部件目录 + 台账向导重写（含测试）。
2. 导入保真语义确认 + "部件名称→类别"对照 + 匹配器改为"部件类别 + 编号"。
3. 绑定仓储/路由 + 绑定界面 + 进入校对前置。
4. 校对页实际构件只读化。

每步保持台账生成/确认、评定、确认入库可回归。
