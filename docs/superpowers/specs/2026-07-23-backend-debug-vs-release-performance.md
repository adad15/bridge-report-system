# 2026-07-23 性能记录：后端 Debug 与 Release 的差距及处理

> 日期：2026-07-23
>
> 分支：`codex/06-5-interaction-redesign`
>
> 涉及提交：`61fb00f`
>
> 触发背景：台账页与年度检测页在真实数据（4941 条构件）下都明显迟滞。年度检测页只查几行记录却也慢，说明瓶颈不在单条 SQL，于是转向排查全局因素，发现日常运行的后端一直是 Debug 构建。

## 现象

两个页面同时慢，但两者的数据量差着好几个数量级：

- **构件台账页**：4941 条构件，慢可以理解；
- **年度检测页**：`list_inspection_years` 只是一条按 `bridge_id` 的索引查询、返回个位数行，理论上零成本，却也停在"加载年份…"。

同一个后端上两个负载悬殊的页面都慢，指向的是**与具体查询无关的公共开销**，而不是某条 SQL 写得不好。

## 根因：日常运行的是 Debug 构建

`backend-cpp/CMakePresets.json` 此前只有 `vs2022-x64-debug` 一个预设，`scripts/dev/start-cpp-backend.ps1` 也写死跑 `build/vs-debug/Debug/bridge-report-backend.exe`。也就是说，**从开发第一天起，日常使用的后端就没有一次是优化过的构建**。

### 为什么 MSVC 的 Debug 会慢这么多

不是"少了点优化"这么简单，Debug 同时叠加了三层开销：

**1. `/Od` 关闭优化**

不内联、不做寄存器分配、不消除临时对象。标准库里大量本应内联掉的小函数（`begin()`、`operator[]`、`size()`、比较器）全部变成真实的函数调用。像 `std::find_if` 遍历一个 vector，在 Release 里是一个紧凑循环，在 Debug 里是每个元素一次间接调用。

**2. 迭代器调试（`_ITERATOR_DEBUG_LEVEL=2`，MSVC Debug 默认开启）**

这是最重的一层，也是最容易被低估的：

- 每个 `std::vector`/`string`/`map` 的迭代器都携带一个指回容器的指针；
- 容器内部维护一张**活跃迭代器链表**；
- 每次迭代器的构造与析构都要**修改这张链表**，且该操作带锁；
- 每次解引用、自增都要校验迭代器是否仍然有效。

结果是：容器操作不仅慢了常数倍，还**凭空多出内存分配与同步开销**。范围 for 循环、`emplace`、`find` 这些看起来无害的写法，代价被显著放大。

**3. 调试堆**

Debug CRT 的堆会在每次分配的前后写入哨兵字节、用固定模式填充内存（`0xCD`/`0xDD`）、并维护额外簿记。分配越频繁，这层开销占比越高。

### 为什么这个项目受影响特别大

上面三层惩罚打击的都是**容器、字符串、内存分配**，而后端的热点恰好全是这些：

- 构造 4941 个 `InventoryEntry`，每个含多个 `std::string`；
- 逐条写入 `Json::Value`——jsoncpp 的 `Value` 本身就是一棵由 map 和 string 构成的树，每次字段赋值都是一次被校验的 map 操作；
- 序列化成 JSON 文本，又是一轮大规模字符串拼接；
- 编号引擎按占位符做笛卡尔积展开，反复执行 `std::string` 替换。

这些代码里几乎没有"纯计算"，全部是标准库容器与字符串的往返——正是 Debug 惩罚最重的形态。所以年度检测页那种"只查几行"的请求也一样受累：它排在同一个进程里，公共开销一分不少。

## 实测

同一台机器、同一份代码，只改构建配置：

| 测试范围 | Debug | Release | 倍数 |
| --- | --- | --- | --- |
| 编号/目录/生成器/匹配器（局部） | 141 ms | 46 ms | 3.1× |
| **全量测试套件** | **3800 ms** | **999 ms** | **3.8×** |

### 测量口径的说明

这两组数字测的是**测试套件**，不是真实接口。原因是台账接口需要登录，而代填密码不在可做范围内。因此：

- 「3.8×」是可靠的**方向性结论**——同一批 C++ 代码在两种构建下的真实差距；
- 它**不是**台账接口的精确加速比。测试套件里大量用例轻量或被跳过，而真实负载（数千条构件的序列化）几乎全是 Debug 惩罚最重的操作，实际差距**很可能更大**，但这一点未经直接测量，不应作为承诺。

另外，此前记录的数据库耗时（映射查询 3004 ms → 155 ms）与本次无关：那部分工作发生在 PostgreSQL 内，不受 C++ 构建配置影响。

## 处理

1. **新增 Release 构建预设。** Visual Studio 是多配置生成器，同一个 `build/vs-debug` 目录可直接产出 Release，无需重新 configure，也不影响既有 Debug 产物。
2. **启动脚本保持默认 Debug，Release 作为显式选项**：

   ```powershell
   .\scripts\dev\start-cpp-backend.ps1                          # Debug（默认，开发期）
   .\scripts\dev\start-cpp-backend.ps1 -Configuration Release   # 用真实数据量点界面时
   ```

   这里曾一度把默认改为 Release，随后按开发期的实际需要改了回来。取舍见下节。

3. **推荐前先验证 Release 的正确性**：Release 构建针对全新 schema 跑完全量 **389 项测试全部通过**。优化构建可能暴露未定义行为或改变时序，未验证就切换是拿正确性换速度——这一步不能省。

## 开发期该用哪个

两者不是二选一，取决于当下在做什么。**Debug 的价值不只是断点**，更重要的是 `_ITERATOR_DEBUG_LEVEL=2` 与调试堆构成的 bug 探测器：迭代器失效、越界访问、缓冲区溢出会当场断言，而不是几个月后变成一次诡异崩溃。这层安全网在 Release 下完全静默，不应轻易放弃。

| 场景 | 用哪个 | 理由 |
| --- | --- | --- |
| 跑测试 | **Debug** | 安全网最该在此生效；3.8 s 与 1.0 s 的差别在这里无关紧要 |
| 调后端逻辑、需要断点 | **Debug** | 变量不被优化掉，单步准确 |
| 用真实数据量点界面、导入、看台账 | **Release** | 此时验证的是业务流程而非 C++ 内部，Debug 的等待纯属摩擦 |

`scripts/dev/check-backend-tests.ps1` 始终使用 Debug 产物，不受本次改动影响——即每次 C++ 改动跑的 389 项测试都带着完整的检查。

Release 下若后端崩溃，栈信息可读性差很多；**遇到后端异常应先换回 Debug 重现**。

## 这个改动解决什么、不解决什么

**解决**：一切发生在后端进程内的 CPU 工作——JSON 序列化、字符串处理、编号展开、导入解析。年度检测页那类"查询本身很轻"的请求，迟滞几乎全部来自这层公共开销，预期基本消失。

**不解决**：数据量本身。台账原始数据 2.4 MB，转成 JSON 后更大，仍需序列化传输、前端解析、并建立约 4941 条 React 状态。**这部分与后端构建配置无关**，因此台账页会明显变快，但不会瞬开。若切换后仍嫌慢，剩下的路只有端点分页/按需加载（见 [2026-07-23-bugfix-inventory-route-and-import-dialog.md](2026-07-23-bugfix-inventory-route-and-import-dialog.md) 中记录的方案 B）。

## 经验

1. **多个负载悬殊的页面同时变慢，应当怀疑公共开销，而不是逐个去优化各自的查询。** 年度检测页只查几行却也慢——正是这个矛盾把排查方向从 SQL 引到了构建配置。
2. **"开发时用 Debug"的默认做法，在数据规模变大后会给出误导性的性能信号。** 小数据量下 Debug 与 Release 的差距不可感知，于是没人怀疑它；等到数据变大，慢下来的表象又很容易被归因到刚写的业务代码上。
3. **C++ 的 Debug 惩罚不是线性的常数因子，它与代码风格强相关。** 纯数值计算受影响有限，而容器与字符串密集的代码会被迭代器调试和调试堆放大数倍。判断影响有多大，要看热点长什么样。
4. **切换构建配置前先跑全量测试。** 优化会改变时序、可能暴露原本被掩盖的未定义行为，把它当作一次有风险的变更来验证。
