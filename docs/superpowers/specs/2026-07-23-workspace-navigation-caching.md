# 2026-07-23 缺陷修复记录：页签切换重复加载

> 日期：2026-07-23
>
> 分支：`codex/06-5-interaction-redesign`
>
> 涉及提交：`92d236c`、`4714509`
>
> 触发背景：把台账移出总览页（见 [2026-07-23-bugfix-inventory-route-and-import-dialog.md](2026-07-23-bugfix-inventory-route-and-import-dialog.md)）之后，落地页不再受拖累，但"构件台账"与"年度检测"这两个页签本身仍是每次切回都要等几秒。用户指出这不符合正常网页的观感：首次加载可以等，之后切换不该再等。

## 现象

在桥梁工作区的四个页签之间来回切换：

- 切到**构件台账** → "加载中…"，等待数秒（该桥 4941 条构件）；
- 切到**年度检测** → "加载年份…"，页面空白后才出现内容；
- 再切回去 → **同样再等一遍**，每次如此。

## 根因

React Router 在离开路由时卸载组件，组件内 state 随之丢弃；切回来重新挂载，`useEffect` 再次触发完整拉取。系统没有任何缓存层，因此每一次挂载都是一次从零开始的加载。

年度检测页还额外做了一件事，把体感放大：

```ts
setWorkspace(null);   // 拉取前先清空
```

即便后端返回很快，这一行也保证了每次切回都必然先闪一次空白/加载态。

值得注意的是，`list_inspection_years` 只是一条按 `bridge_id` 的索引查询、返回个位数行——**它慢不是因为查询重，而是因为每次都要重新走一遍完整往返**。这也说明问题出在加载策略上，而不是某条 SQL。

## 方案选择

考虑过三种做法：

1. **把数据提升到 `BridgeWorkspaceShell`。** 外壳在页签切换时不卸载，数据自然存活，且没有"缓存失效"这一层语义要维护。但需要把 `revision` 等状态从组件里拆出来交给 context，两个页面都要改结构，改动面大。
2. **纯缓存（只读缓存，不重新校验）。** 改动最小，但一旦缓存与后端不一致就会长期显示过期数据，正确性风险高。
3. **stale-while-revalidate（采用）。** 再挂载时先用上次结果立即渲染，同时后台重新拉取并覆盖。

选 3 的理由：它同时满足"切换瞬时"和"不会停留在过期数据"两个要求，且对现有代码结构侵入最小——每个页面仍然自己拥有加载逻辑与各自的错误语义（例如台账对 `component_inventory_not_found` 的特殊处理），只是在原有的加载函数里多读写一次缓存。

## 修复

新增模块级缓存 `frontend/src/api/resourceCache.ts`，覆盖三个资源：构件台账、年度列表、年度工作台。

关键点：

- **再挂载先渲染缓存、不进加载态**，随后后台拉取并覆盖；
- **年度工作台不再拉取前清空**，改为用缓存打底，消除必然出现的闪烁；
- **台账的改动结果直接写回缓存**：保存、删除、确认后拿到的新版本同步入缓存，下次挂载不会闪出改动前的旧台账；
- **年度页的显式刷新先丢弃缓存再重拉**。新建年度、导入资料、删除记录之后如果仍先渲染旧内容，用户会看到自己刚删掉的东西又出现一下——**这类场景下先闪旧数据比多等一会儿更糟**。页签切换不经过这条路径，仍然享受缓存。

### 测试隔离

缓存位于模块作用域，会在同一测试文件的用例之间残留，使执行顺序影响结果。首次全量运行 247 项全部通过，但那是顺序碰巧成立，不是隔离性成立。因此提供 `clearCachedForTests()` 并接入两个测试文件的 `beforeEach`。

新增用例锁定行为：卸载后重新挂载时不出现加载态，但 `fetchLatestComponentInventory` 仍被调用第二次——即"立即可见"与"仍会校验"两件事同时成立。

## 后续：加速暴露出的原始 ID 回退

提交：`4714509`（fix(inventory): stop showing raw category ids while the standard catalog loads）

### 现象

上述缓存生效后，切到构件台账时出现新的观感问题：分组核对表的"规范映射"列先显示

```
技术评定规范 · h21.component.beam.upper_bearing
技术评定规范 · h21.component.lower.pier
```

数秒后才变成 `JTG/T H21—2011 · 上部承重构件（主梁、挂梁）`。

### 根因

映射的友好名称并不来自台账本身，而是**另一条独立请求**——规范目录（`fetchStandardPackages` + `fetchStandardCatalog`）。`inventoryGroupSummaries` 在目录缺失时有一段回退：

```ts
`${catalog?.package.standard_code ?? "技术评定规范"} · ${
  category?.name ?? mapping.standard_component_category_id   // 回退成原始 ID
}`
```

这段回退一直存在，只是此前被台账自身数秒的加载耗时掩盖——台账渲染出来时目录早已到达。**缓存把台账变成瞬时渲染后，这个窗口才第一次可见。** 因此它不是本次引入的缺陷，而是被本次加速暴露的既有问题。

### 修复

- **目录未加载时不再回退成原始 ID。** `h21.component.*` 对用户没有意义，属于噪声；标签留空，由渲染层显示为 `—`，目录到达后 memo 重算即得到正确名称。宁可先空着，也不显示看不懂的内容。
- **把规范目录纳入同一份缓存。** 它是与桥无关的全局参考数据，本就不必每次重拉；台账页与向导共用同一个键，切回页签时目录立即可用，上述空窗口基本不再出现。

### 测试

新增用例锁定：目录为空时 `mappingLabel` 必须为空；目录到位后必须解析为 `JTG/T H21—2011 · 上部承重构件`。

同时修正了测试本身的缺陷——原先 `fetchStandardPackages` 被 mock 成返回空数组、`fetchStandardCatalog` 根本没有 mock，等于映射名称的解析路径从未被真正覆盖，那段回退逻辑因此长期无人发现。

## 补充：校对工作区分区切换保活

> 补充日期：2026-07-27
>
> 涉及页面：`ReviewWorkspacePage`

### 现象与差异

校对工作区左侧包含“需要处理”“构件绑定”“病害与照片”“系统技术状况评定”“原始 JSON”五个分区。它们不是独立路由，而是在同一个 `ReviewWorkspacePage` 中通过条件渲染切换。离开某个分区时，该分区组件会被卸载；再次进入时组件重新挂载。

这和本文前半部分的路由页签问题有相同的用户现象，但等待来源更多：

- “构件绑定”重新请求绑定概览和构件台账；
- “病害与照片”“需要处理”重新生成大量列表节点；
- 分区内部的筛选、搜索、展开和拆分选择等局部状态随卸载丢失。

因此，仅把接口结果放入 stale-while-revalidate 缓存并不能完整解决问题：缓存可以减少空白等待，但组件和大列表仍会重新创建，局部操作状态仍会重置。

### 采用方案：首次访问挂载，之后只隐藏

五个分区采用统一的懒挂载保活规则：

1. 页面初次打开时只挂载当前活动分区，不提前创建其他大列表；
2. 用户首次进入某分区时挂载该分区；
3. 分区挂载后加入本页面会话的“已访问分区”集合；
4. 后续切换只改变可见性，不再卸载已访问分区；
5. 离开整个校对页面时仍由 React 正常释放全部分区，不建立跨页面永久保活容器。

隐藏分区统一使用原生 `hidden` 属性，不参与布局、键盘焦点和辅助技术导航。活动分区保持原有 DOM 结构和样式，不改变各业务组件的职责。

### 数据一致性

- `ReviewWorkspacePage` 持有的草稿、需要处理清单、系统评定结果和绑定概览继续作为页面级状态；这些值变化时，已挂载的隐藏分区仍会收到最新 props。
- “构件绑定”首次进入时允许按原逻辑加载。切走再切回时沿用已加载的 `overview`、`inventory`、筛选和拆分选择，不重新进入加载态。
- 绑定、标记缺失、取消处理和拆分等显式操作仍以接口返回结果更新组件状态和页面级绑定概览；不增加只读后长期不校验的业务缓存。
- 本次目标是同一个校对页面内的分区切换。离开校对路由后再次进入仍按现有加载策略执行；若以后需要跨路由瞬时恢复，再单独把绑定概览纳入 `resourceCache` 的 stale-while-revalidate 机制。

### 组件边界

`ReviewWorkspacePage` 在页面内新增只管理生命周期的 `ReviewWorkspacePanel`：

- 记录 `visitedGroups`；
- 侧栏选择分区时把目标加入集合并切换 `activeGroup`；
- 已访问分区始终保留在 React 树中；
- 仅活动分区可见。

`NeedsAttentionSection`、`ComponentBindingWorkspace`、`DefectsSection`、`AssessmentSection` 和 `RawJsonSection` 不承担页签生命周期管理，也不为此复制业务数据。

### 测试

测试必须锁定以下行为：

1. 未访问分区不会提前挂载或请求数据；
2. 首次进入“构件绑定”允许显示加载态并发起请求；
3. 切到其他分区再切回“构件绑定”，不会再次请求，也不会重新显示加载态；
4. 构件绑定筛选或其他可观察局部状态在切回后保持；
5. 隐藏分区不在布局和可访问性树中，但在再次激活后恢复原内容；
6. 草稿或绑定概览更新后，已挂载分区显示最新数据。

前端单元测试需继续在 `beforeEach` 中清理现有模块缓存，避免本节改动与既有 `resourceCache` 测试互相污染。

## 边界

- **仅限当前会话**：缓存不持久化、不设过期，刷新浏览器即清空。这是导航加速，不是离线能力。
- **只加速"切回来"**：首次进入某座桥仍要完整等待一次。要缩短这一次，剩下的手段是后端改用 Release 构建（见 [2026-07-23-backend-debug-vs-release-performance.md](2026-07-23-backend-debug-vs-release-performance.md)）与台账端点分页。
- **跨标签页/多用户场景下仍可能短暂显示过期数据**，直到后台校验返回。对当前的单人使用场景可接受；若将来变成多人并发编辑，需要改为由服务端推送或加版本号校验。

## 经验

1. **"首次可以等、之后不该等"是用户对网页的默认预期**，不是额外要求。任何会被反复进入的页面都该按这个标准检验一次。
2. **加缓存的风险不在读，而在写之后。** 真正会出问题的是"用户刚改完，却看见改动前的内容"。因此凡是显式的变更动作，要么把新结果写回缓存，要么直接丢弃缓存，不能沿用旧值。
3. **模块作用域的缓存会破坏测试隔离，且症状是间歇性的。** 用例顺序变化才暴露，全绿并不代表隔离成立——引入这类全局状态时，应同时提供测试用的重置入口。
4. **加载慢未必是查询慢。** 年度列表只有几行却也要等，症结在"每次都完整重来"这一策略上；如果一开始就扎进 SQL 优化，方向就错了。
5. **提速会暴露被耗时掩盖的缺陷。** 原始 ID 回退早就存在，只因页面本来就要等几秒而从未显形。优化之后应当重新审视页面的中间状态——那些"反正没人看得见"的过渡态会突然变成主要观感。
6. **回退值要按"用户能否理解"来选，而不是"能否填满"。** `h21.component.beam.upper_bearing` 填满了单元格，却不传达任何信息；`—` 反而诚实。数据未就绪时留白优于显示内部标识。
7. **mock 返回空集合会让整条分支不被覆盖。** 本例中目录被 mock 成空数组、另一个接口干脆没 mock，于是映射名称的解析路径从未被执行过，回退逻辑长期无人发现。给 mock 填真实形状的数据，比只求"测试能跑通"重要。
