## 1. 目标与边界

A 批次为后续性能优化和模块拆分建立工程基础，交付三个可验证的结果：

1. 启动结果可信：命令失败、进程退出、端口冲突和旧实例均能识别，只有实际就绪才报告成功。
2. 构建环境可复现：公共配置不依赖个人盘符，依赖安装遵循锁定结果，构建与测试明确使用同一组产物。
3. 优化结果可比较：性能和回归记录附带源码、工具链、数据规模、运行模式及测量方法。

沿用现有 C++20/Drogon、Python/FastAPI、React/TypeScript/Vite/Ant Design 和 PostgreSQL 架构。Office 字段更新仍采用 Windows 交互式会话及单进程 FIFO。

### 1.1 本批包含

- 环境清单、代表性样本和验证基线。
- 四个启动脚本及健康检查的可靠性修复。
- 公共 CMake 预设去除本机绝对路径，测试入口明确选择产物。
- npm、uv 的锁定安装流程，以及经核对的 vcpkg baseline。
- C++ 构建标识、服务启动标识及启动结果核验。
- 针对性自动测试、干净目录验证及运行文档同步。

### 1.2 本批不包含

- 报告模板快照、过期清理、WebP、XML 关系解析和地图问题等 B 批次工作。
- 前端分包、图表懒加载、复杂页面拆分、后端线程池及仓储重构。
- Vite、React、Ant Design、Python 或 Drogon 的主动大版本升级。
- 业务数据库迁移、报告合同变更、正式评分规则变更。
- Office 多实例执行、Windows Service 部署或新增微服务。
- 自动提交、推送或发布代码。

原第 11 条“构建失败仍可能启动旧程序”纳入本批。已经完成的 P1 和冗余代码清理作为回归基线保留。

## 3. 统一约定

### 3.1 路径和配置

- 所有脚本从自身的 PSScriptRoot 推导仓库根，使用解析后的绝对路径。
- 子脚本既能独立调用，也能被统一入口调用；不依赖调用者所在目录。
- 使用 Push-Location / try-finally / Pop-Location，避免改变调用者会话目录。
- C++ 构建在 backend-cpp 下执行，后端业务进程仍以仓库根为工作目录，保持相对归档路径语义。
- 配置优先级为显式 ConfigPath、config/local.json、config/local.example.json；显式路径无效时失败，不静默回退。
- 启动检查使用各服务最终生效的地址及端口。共享配置解析应与后端现有语义对齐，不只检查默认 18080/18081/5173。
- 核对 BRIDGE_REPORT_DATABASE_URL 在当前各入口的实际支持范围；预检查连接必须与后端实际连接一致。若要统一覆盖行为，必须在配置层实现并测试，不能只让脚本读取环境变量。
- 不向日志、命令失败摘要或基线记录写入完整数据库凭据、令牌或地图 key。

### 3.2 PowerShell 与外部工具

- 启动入口保持 Windows PowerShell 5.1 和 PowerShell 7 的兼容写法，并分别验证；子脚本使用当前会话对应的可执行文件，不固定依赖 pwsh。
- 以 Get-Command 和显式环境配置定位工具；psql 支持 PSQL_EXE，再查 PATH，既有本机路径只作为兼容回退。
- 对 cmake、psql、npm、uv 及服务进程分别检查退出结果；不依赖 ErrorActionPreference 把全部非零退出码变成异常。
- 外部命令使用参数数组传递，路径按字面值处理，避免拼接成第二层 shell 命令。
- 如抽取公共脚本，只包含根路径、配置、工具定位、命令检查、日志及就绪等待等小函数，不引入通用部署框架。
- 默认后台启动并写日志；需要独立可见控制台时使用显式选项。Office 服务即使隐藏窗口也必须保留在已登录用户的交互式会话，不能转为系统服务。

### 3.3 准备依赖与启动分离

依赖准备、构建和启动是三个可区分阶段。日常启动不默认清空依赖目录或重新解析版本；依赖缺失、锁定状态不匹配时明确失败并给出准备命令。允许显式选项串联准备流程，但日志和失败结果仍分阶段记录。

## 5. A2：启动链路可靠性

### 5.1 执行流程

统一入口按以下顺序执行：

1. 解析根目录、配置、构建类型和工具路径。
2. 检查依赖准备状态及目标端口，冲突时停止。
3. 检查与后端实际一致的 PostgreSQL 连接。
4. 完成 C++ 配置与构建，确认目标产物和构建标识。
5. 启动 Python，等待身份匹配的健康响应。
6. 启动 C++，核对进程标识、构建标识、数据库就绪及 C++ → Python 连通性。
7. 启动前端，检查子进程、实际监听端口及 HTTP 页面。
8. 全部成功后输出地址、构建类型和日志位置；浏览器打开作为可选动作。

构建及安装不计入 HTTP 就绪等待时间。每个 HTTP 探测设置单次超时；服务就绪默认最多等待 60 秒，允许显式参数调整，间隔 1 秒检查进程退出与健康状态。超时或进程提前退出立即给出所在阶段。

“已创建进程”“进程仍运行”“服务就绪”是不同状态，前两者不能显示为完整启动成功。

### 5.2 数据库检查

- 设置连接超时，执行只读连通检查并核对 psql 退出码。
- 连接失败只输出脱敏后的目标和错误摘要。
- 初始检查不执行迁移或 smoke tests；数据库结构是否满足启动要求由明确的后端就绪检查验证。
- 保持后端可独立启动用于故障诊断的现有能力；统一启动入口可因依赖未就绪而返回失败，不能擅自改写业务后端的容错语义。

### 5.3 端口冲突与已有服务

- 默认不复用占用目标端口的已有实例，无论是否返回健康响应，均报告占用并停止本次启动。
- 不自动结束端口上的陌生进程，也不按进程名批量结束 node、Python、后端或 Office。
- 前端启动使用严格端口约束，禁止 Vite 自动换到另一个端口后仍打印原地址。
- 即使预检查无冲突，也要防范检查到启动之间的竞争：最终仍核对本次进程及响应身份。

### 5.4 日志与失败清理

- 每次启动生成 launch_id，三个服务各自保存 stdout/stderr，统一入口输出摘要。
- 保留本次启动的进程句柄/创建时间等归属信息；PID 单独不足以证明归属。
- 发生失败时仅清理能够确认属于本次启动的进程及包装器子进程。
- 优先正常终止；归属不明时保留并明确报告，不扩大终止范围。
- 停机清理不调用 Office 按名称强杀；已有 Office 所有权与恢复阻断机制继续负责其生命周期。
- 启动记录包含构建产物和配置路径，但健康响应不新增凭据或完整环境转储。

## 6. A3：构建路径与产物选择

### 6.1 CMake 公共和本机配置

- 公共 CMakePresets.json 保留 VS2022、x64、C++20 及 Debug/Release 约定。
- 公共 toolchain 路径通过 VCPKG_ROOT 环境变量定位，并提前验证脚本是否存在。
- 默认依赖安装目录置于构建目录内；用户需要共享缓存/安装目录时在被忽略的 CMakeUserPresets.json 覆盖。
- 提供不含个人凭据的本机预设示例及初始化说明。
- 本批优先保留现有预设名称及 backend-cpp/build/vs-debug 的兼容路径，避免无必要地重命名全部入口；Debug/Release 子目录仍由多配置生成器区分。
- 改变 triplet、toolchain 或依赖安装目录时使用新构建目录，不复用带旧配置的 CMakeCache。

CMake 预设机制区分共享项目配置和用户本机配置，见 [官方说明](https://cmake.org/cmake/help/latest/manual/cmake-presets.7.html)。

### 6.2 单一产物定位规则

构建、启动和测试入口共享“构建目录 + Configuration + Target”的解析规则。check-backend-tests.ps1 增加明确的构建目录/类型选择，删除“从多个位置选首个存在 EXE”的行为。

构建完成后读取对应产物标识，检查目标文件存在；日志输出实际执行路径。跨目录或跨配置发现旧 EXE 不能作为回退。

运行中的 EXE 导致链接失败时，明确报告文件占用，不自动停止已有业务服务。可以在独立验证目录构建，但后续测试必须明确指向该目录。

### 6.3 路径验收

覆盖仓库根目录、服务子目录及任意外部目录调用；另建包含空格和中文的验证路径。仓库路径变化后重新配置构建，不搬运旧 CMakeCache 作为“可移植”证明。

没有第二台机器时，本批只能完成本机干净目录复建，跨机器验证单独标记为未完成。

## 7. A4：依赖固定与准备流程

### 7.1 前端

- 保留并校验 package-lock.json，干净环境使用 npm ci。
- 从当前已通过验证的环境选择并记录 Node/npm 支持版本；不凭空指定“最新版本”。
- 版本约束与检查脚本配合；仅声明 packageManager 或 engines 不视为已经强制生效。
- 镜像源通过本机 npm 配置或显式参数选择，移除启动脚本中的固定镜像地址；同时核对锁文件 resolved 地址，记录实际依赖来源。
- 日常启动不执行 npm ci；依赖缺失或准备记录与锁摘要不匹配时提示运行准备入口。
- 包清单与锁文件不一致直接失败，不自动执行 npm install 修复锁文件。

npm ci 的锁文件一致性要求及其会重建 node_modules 的行为见 [官方说明](https://docs.npmjs.com/cli/v11/commands/npm-ci/)。首次验证使用独立目录，避免直接覆盖现有开发依赖。

### 7.2 Python

- 保留 uv.lock，准备命令使用 uv sync --locked --extra dev。
- 服务运行使用 locked 约束，确保 pyproject.toml 与锁文件不一致时失败，而非在启动期间改锁。
- 记录实际 Python/uv 版本与解释器来源，在隔离虚拟环境复建。
- 如果已有虚拟环境混入未锁定依赖，以独立新环境验证为准，不将现有环境“能运行”等同于可复现。
- 锁文件更新通过独立依赖维护步骤进行，不隐藏在日常启动中。

--locked 会检查锁文件并在需要更新时失败；--frozen 跳过该一致性检查，因此本方案优先使用 locked，见 [uv 官方说明](https://docs.astral.sh/uv/concepts/projects/sync/)。

### 7.3 C++ / vcpkg

实施前先保存以下实际信息：

1. vcpkg 工具和 registry 的来源提交。
2. installed 状态中的 Drogon、OpenSSL、GTest 及传递依赖版本、port-version 和 triplet。
3. 现有 toolchain、编译器及依赖安装目录。
4. 本机是否存在自定义 ports、registry 或 overlays。

然后为 vcpkg.json 选择有证据支持的 builtin-baseline，并在独立目录解析、安装、构建和测试。baseline 固定 registry 的基线，但不应当作所有环境因素的完整锁文件；实际解析清单也必须保存。必要的 overrides 须逐项说明理由。

不得把本机 vcpkg 当前 HEAD 直接认定为旧安装的来源。如果不能重建原依赖组合，记录差异并将其作为需单独评审的依赖变更，不静默升级后宣称“仅锁定”。

版本机制参考 [vcpkg 官方说明](https://learn.microsoft.com/en-us/vcpkg/consume/lock-package-versions)。

## 8. A5：构建与运行身份

### 8.1 标识语义

| 字段 | 来源/生命周期 | 用途 |
| --- | --- | --- |
| version | 项目语义版本 | 保留既有兼容字段 |
| build_id | C++ 构建元数据嵌入二进制 | 区分实际产物 |
| git_revision | 构建时或 Python 启动时固定 | 关联代码提交 |
| worktree_dirty | 同一时点固定 | 提示存在未提交内容 |
| source_digest | 相关源码与构建输入的稳定摘要 | 区分同一提交下不同工作区内容 |
| configuration | 构建时固定 | 区分 Debug/Release |
| launch_id | 启动器传入，服务启动时固定 | 关联本次统一启动 |
| instance_id | 服务自身每次启动生成 | 区分进程实例 |

launch_id 是诊断关联标识，不是认证令牌。手工启动服务时允许 launch_id 为空，服务仍生成 instance_id；这种实例不能被统一启动入口认作本次创建的服务。

### 8.2 C++ 构建标识

- 在构建依赖链中生成元数据，源文件、构建配置或锁定输入变化时重新生成并重新链接。
- build_id 从源码摘要、工具链/依赖标识及配置推导，不能仅使用固定版本号、提交号或每次 configure 的时间。
- 无输入变化的增量构建可以保留同一 build_id；进程区别由 instance_id 表示。
- 产物旁保存同源构建清单，启动器读取预期 build_id，与二进制 /health 返回值比较。
- 清单不能由启动器在旧 EXE 旁临时生成后当成成功证据；必须与实际目标在构建中一起产生。
- 验收覆盖“只修改已有源文件、不手工重新 configure，增量构建后标识仍更新”。

### 8.3 Python 启动标识

- 服务启动时固定源码和锁文件摘要、提交信息及 instance_id。
- /health 每次返回启动时保存的信息，不按请求实时读取 Git，否则修改磁盘文件会让旧进程伪装成新代码。
- 开发流程修改源码后需重启；本批不引入热重载与多 worker，保持 Office 单队列约束。
- 启动器先计算预期输入标识，确认 /health 与本次 launch_id 匹配。

### 8.4 健康和就绪语义

保留现有 /health 字段并追加可选诊断字段，同步 Python HealthResponse 及相关测试。新的启动核验要求标识匹配；旧服务缺少字段时明确报告无法确认版本，不默认视为通过。

服务身份正确不等于依赖就绪。统一启动还需核验 /health/db 及 /health/tools 的预期状态；前端则校验本次进程、监听端口及 HTTP 结果。单纯访问根页面得到 200 不能证明所有业务功能已验收。

新字段不增加密码、令牌或完整路径输出。现有健康接口中的路径字段为兼容暂保留，收敛其暴露范围可另列变更。

## 12. 回退与兼容

- 所有验证先在独立构建/依赖目录执行，保留现有可运行环境。
- 不覆盖用户 CMakeUserPresets.json、config/local.json 或包管理器凭据。
- A 批次不增加业务数据库迁移，代码回退不需要逆向修改业务事实。
- 健康字段采用追加方式；回退服务后，新启动器应报告缺少身份信息，不假装验证成功。

- 启动失败清理不删除归档、数据库数据或未确认归属的临时目录。
- 已有运行服务被 EXE 占用或端口冲突保护时保持不动，由用户按正常开发流程停止后再启动新版本。
