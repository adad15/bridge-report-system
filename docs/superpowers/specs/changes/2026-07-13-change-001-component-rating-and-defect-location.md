# 变更提案 001：构件评分与病害详细位置进入年度事实链

> 日期：2026-07-13
>
> 状态：已实施（2026-07-14，实施计划见 `docs/superpowers/plans/2026-07-13-component-defect-archive-implementation-plan.md`；第 10 节验收标准全部通过，真实 Word 精确回归 65/65/55.81、86.62、85.61 命中）
>
> 影响模块：03、04、05、06

> 采用方案：方案 A——先修正年度事实链，再建设只读构件病害档案

## 1. 变更背景

模块 05 已完成真实 Word 导入、人工校对和年度事实入库，但模块 03 的 `BridgeAnnualInspectionData` 1.1 仍未表达表 2.1-1、表 2.2-1、表 2.3-1 中的三个关键事实：病害标度、病害扣分和构件评分。病害位置虽已存在，但需要明确为可编辑的详细位置，并作为跨年病害线索的重要组成部分。

现有 C++ 确认映射还把候选对象的 `severity` 写入数据库 `defect_observations.scale`。`severity` 实际表示 `info / warning / error` 的校对提示级别，不是规范中的病害标度，二者语义不同，必须停止混用。

用户确认模块 06 以“只读档案优先”为主线，并以病害为基本单位展示跨年记录。例如在 `2-1#板` 下，`蜂窝、麻面` 是病害卡片，2024、2025 是卡片中的年度观测；`0#台顶处`、`小桩号立面`、`左侧端部` 等详细位置用于帮助人工判断跨年记录是否属于同一病害。

## 2. 规范依据与样例证据

评分校验依据《公路桥梁技术状况评定标准》JTG/T H21-2011。交通运输部现行标准页面与官方 PDF：

- [交通运输部公告](https://xxgk.mot.gov.cn/2020/jigou/glj/202006/t20200623_3312369.html)
- [JTG/T H21-2011 官方 PDF](https://xxgk.mot.gov.cn/2020/jigou/glj/202006/P020240521541427295157.pdf)
- [交通运输部 2021 年标准解读](https://xxgk.mot.gov.cn/jigou/glj/202110/t20211026_3623037.html)

构件技术状况评分按第 4.1.1 条计算。将同一构件的病害扣分 `DP` 按从大到小排序：

```text
U1 = DP1
Ux = DPx / (100 × sqrt(x)) × (100 - ΣUj), x >= 2
P = 100 - ΣUx
```

计算全程使用未舍入值，只在最终展示或与 Word 比较时按规定精度舍入；任一病害扣分为 100 时，构件评分为 0。

真实辽宁国省干线样例中的关键证据为：

| 对象 | 病害扣分 | Word 构件评分 | 规范复算 |
|---|---:|---:|---:|
| `1-1#板` | 35 | 65 | 65 |
| `1-2#板` | 35 | 65 | 65 |
| `2-1#板` | 35、20 | 55.81 | 55.81 |

`2-1#板` 不是简单取最低单病害分数。第二项扣分经衰减后参与累计：`100 - 35 - 20 / (100 × sqrt(2)) × 65 ≈ 55.8076`，最终为 55.81。

## 3. 方案比较

### 3.1 方案 A：先修正 03–05，再建设模块 06（采用）

把病害标度、扣分、详细位置和构件评分的双值校验纳入正式合同，依次修正 Python 解析、模块 05 校对和 C++ 确认入库，再由模块 06 读取可信事实。

优点：事实语义完整；模块 06 不需要从旧 JSON 或展示文本猜测；模块 07 可直接复用病害线索。缺点：模块 06 前需要一次受控的跨模块升级。

### 3.2 方案 B：模块 06 直接从旧 JSON 推断

不改上游合同，由档案页面临时解析原始行和评分表。

拒绝原因：同一事实出现两套解析路径；历史数据不可审计；会固化 `severity` 与 `scale` 的错误映射。

### 3.3 方案 C：模块 06 只展示病害，不展示或校验构件评分

拒绝原因：构件评分是用户明确要求的年度事实，也是判断报告数据是否可信的重要依据；延后会导致档案模型再次迁移。

## 4. 合同升级：BridgeAnnualInspectionData 1.2

### 4.1 病害候选

`defects[]` 增加或明确：

```json
{
  "defect_location": "左侧端部",
  "defect_scale": 2,
  "defect_deduction": 35.0
}
```

- `defect_location`：该年度 Word 中的详细位置原文，进入人工校对；允许完整自由文本，不在第一版拆成方向、里程、端部等结构化列。
- `defect_scale`：规范意义的病害标度；与提示级别 `severity` 完全分离。
- `defect_deduction`：表 2.x-1 中的病害扣分 `DP`。
- `severity`：继续只表示校对提示严重程度，不得写入 `scale`。

### 4.2 构件评分候选

`ratings` 增加 `component_ratings[]`。每项至少包含：

```json
{
  "component_ref": {
    "structure_part": "上部结构",
    "component_name": "上部承重构件",
    "component_alias": "2-1#板"
  },
  "source_score": 55.81,
  "calculated_score": 55.8076118446,
  "confirmed_score": 55.81,
  "score_validation_status": "一致",
  "score_resolution_reason": null,
  "deduction_defect_candidate_ids": ["defect-...", "defect-..."],
  "calculation_details": {
    "standard": "JTG/T H21-2011 4.1.1",
    "ordered_deductions": [35.0, 20.0],
    "rounding_scale": 2
  }
}
```

字段语义：

- `source_score`：Word 表中读取到的构件评分。
- `calculated_score`：根据已解析病害扣分复算出的未过早舍入结果。
- `confirmed_score`：用户最终确认、正式入库的评分。
- `score_validation_status`：`一致`、`不一致`、`无法复算`、`人工接受Word值`、`人工采用复算值`。
- `score_resolution_reason`：人工处理“不一致”或“无法复算”时的必填原因；自动一致时为空。
- `deduction_defect_candidate_ids`：参与本次计算的病害候选，形成可追溯证据链。

`defect_scale` 为可空正整数；`defect_deduction`、三个评分字段均为可空的 0–100 数值。来源分和复算分都按两位小数比较：`round(calculated_score, 2) == round(source_score, 2)` 时为 `一致`。不一致或无法复算的初始候选中 `confirmed_score=null`，只有用户作出明确选择后才能赋值；自动一致时可预填来源值，但仍需随候选完成校对。

1.2 只根据 Word 已给出的 `DP` 复算构件评分，不尝试根据病害类型和标度独立推导 `DP`。完整病害扣分规则库及更高层级评分重算不属于本变更。

## 5. 模块 04 解析责任

Python 导入器应从第二章病害检查表读取详细位置、标度、病害扣分和构件评分，并生成 `component_ratings[]`。同一构件多条病害的扣分进入第 4.1.1 条计算；排序不得依赖 Word 行顺序，计算过程中不得提前舍入。

无法稳定提取扣分时，保留 Word 来源分并标记 `无法复算`，不得编造扣分。Python 的计算结果是候选证据，不直接成为 PostgreSQL 正式事实。

## 6. 模块 05 校对与确认责任

校对工作台增加：

- 病害详细位置、标度和病害扣分编辑；
- 构件评分的 Word 来源值、规范复算值、差值和校验状态展示；
- 不一致时，必须显式选择“接受 Word 值”或“采用复算值”，并填写原因；
- 无法复算时，必须确认来源值或修正缺失扣分后再确认。

C++ 在入库前独立执行同一纯函数校验，不能只信任前端或 Python 结果。`severity` 不再映射到 `defect_observations.scale`。

正式事务写入：

- `defect_observations.defect_location / scale / defect_deduction`；
- `condition_ratings` 中 `rating_level='构件'`、绑定 `bridge_component_id` 的年度构件评分；
- 构件评分的来源值、复算值、状态和计算明细。

`defect_observations.component_score` 作为历史兼容字段保留，但不再作为构件年度评分的唯一规范来源；新查询以构件级 `condition_ratings` 为准。

## 7. 数据库变更

复用已有 `defect_threads`、`defect_observations.defect_thread_id` 和 `condition_ratings.bridge_component_id`。对 `condition_ratings` 增加：

- `source_score`
- `calculated_score`
- `score_validation_status`
- `score_resolution_reason`
- `calculation_details_json`

对当前有效年度建立“同一 `inspection_id + bridge_component_id + rating_level='构件'` 唯一”的约束或等价事务校验。`score` 保存最终确认值。

历史 1.1 数据不反向猜测标度或扣分。它们继续可读，并显示“历史数据缺少评分校验明细”。尚未确认的 1.1 草稿应重新解析为 1.2；不得静默补造字段。已确认年度如需补齐，应通过同桥同年的显式修订流程重新导入。

## 8. 对模块 06 的边界影响

模块 06 只读取当前有效、已确认或已修改的年度事实，默认不混入旧修订版。它负责：

- 只读展示构件、病害卡片、年度观测、照片、构件评分和校验依据；
- 允许人工创建病害线索并把年度观测绑定到线索；
- 保留线索标准位置与年度实际位置两层位置文本。

模块 06 不判断病害发展、减轻、修复或新增；这些结论属于模块 07。

## 9. 风险与约束

- 真实 Word 表格可能有合并单元格，构件评分只在组首行出现；解析必须按构件组传播，不能把评分复制为多个正式评分事实。
- 相同构件、相同病害类型和相似位置只能形成建议，不能自动认定为同一病害。
- 自由文本位置第一版利于忠实建档，但会降低自动匹配精度；模块 07 可在不修改原文的前提下增加结构化辅助字段。
- 评分公式与舍入规则必须在 Python、C++ 和测试夹具中一致，防止跨语言漂移。

## 10. 验收标准

1. JSON Schema、Python、C++ 和 TypeScript 均接受合同 1.2 并拒绝语义错误的字段映射。
2. `severity` 永不写入数据库 `scale`。
3. 单病害扣分 35 复算为 65；扣分 35、20 复算并展示为 55.81；扣分顺序不影响结果；扣分 100 得 0。
4. 真实 Word 回归数量保持 25 条病害、31 个照片候选、36 个 Word 图片、31 张归档照片和 15 个原评分项。
5. 真实 Word 还应精确得到：`1-1#板=65`、`1-2#板=65`、`2-1#板=55.81`、上部承重构件 `86.62`、全桥 `85.61`。
6. 评分不一致时，未经显式选择和原因不得正式入库。
7. 旧 1.1 已确认事实仍可读取，且明确显示缺少评分校验明细，不做猜测性回填。
