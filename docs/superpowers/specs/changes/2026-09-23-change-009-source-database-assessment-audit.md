# 变更提案009：来源数据库年度系统评分独立核验

日期：2026-09-23。接续变更提案008和2026年度隔离正式入库结果，目标是确定系统自动生成的技术状况评分是否符合锁定的 H21 1.0.4 规则，而不把“写入成功”视为“计算正确”。

## 核验边界

仅从私有 PostgreSQL 25432 读取导入 DRJL-000010 对应的正式评定版本和430条正式观测、5,174件已确认台账。先校验数据库身份、正式版本与规范包校验和，再导出评分结果、逐级构件结果和规则轨迹。业务库和来源SQLite保持只读。

## 独立计算与判断

使用单独的 Python 审核脚本读取本仓库锁定的规范包 JSON，按正式观测的实际构件、评定树节点与规范指标生成输入，再独立复算：

1. 最高标度合并、指标扣分、同构件多病害按扣分从高到低累计。
2. 5,174件构件分数；按构件数 t 值、主要部件低分直取计算部件类别分数。
3. 现有类别权重的比例分配、上/下部和桥面系分数、全桥总分及等级。
4. 6条显式选择的不计分来源记录应保留观测但不产生规范扣分；两个25件范围和一条双侧构件应逐目标参与计算，不能只影响照片或只计算首件。
5. 核对单项控制触发条件和正式结果的来源身份、状态与轨迹条数。

脚本不得调用 C++ 求值器，也不能只对照它自身写下的输入摘要和轨迹；主要期望值应由正式观测、台账映射及版本化规则包推导。对照数值采用适合数据库 numeric(12,6) 的误差界限，并保存差异清单。发现实际代码错误时做最小修复和相关回归；若来源事实本身需要现场判断，记录限制，不推测实际桥梁状况。

## 收尾

结果写入 docs 下独立验收记录，更新项目入口。停止私有数据库服务，保留隔离数据与被Git忽略的证据。评分核验完成后再决定是否进入来源数据库路线的报告输出。
