# 模块 05 人工校对工作台设计记录

日期：2026-07-07

## 1. 设计结论

模块 05 采用“完整校对入库闭环”方案。

核心流程：

```text
桥梁 -> 年度检测任务 -> 导入记录 -> 校对工作台
  -> 保存校对草稿
  -> 入库前检查
  -> 确认年度事实入库
  -> 后续模块进入历史病害对比
```

模块 05 的正式模块规格见：

```text
docs/superpowers/specs/modules/05-review-workspace.md
```

## 2. 本次确认的范围

包含：

1. 读取 `import_records.parsed_result_json`。
2. 展示导入概览、顶层 warnings/errors 和对象级 warnings/errors。
3. 按“需要处理 / 普通病害 / 病害照片 / 技术状况评定 / 来源证据 / 原始 JSON”组织校对页面。
4. 编辑病害核心字段。
5. 修改尺寸原文，并由系统重新结构化。
6. 确认、忽略、修改病害候选。
7. 确认、取消、标记照片匹配。
8. 校对评分。
9. 批量确认普通候选。
10. 保存校对草稿。
11. 入库前检查。
12. 写入正式病害、尺寸、照片、评分表。
13. 同桥同年已有正式事实时走修订确认。

不包含：

1. 历史病害对比候选生成。
2. 历史对比确认页。
3. Word 继续解析规则优化。
4. 完整图片管理、裁剪、重传。
5. 全量 JSON 编辑器。
6. AI 判断病害事实。

## 3. 用户已确认的关键选择

### 3.1 完成标准

用户选择：校对后真正入库。

解释：前端能查看、修改候选 JSON，用户确认后由 C++ 写入 PostgreSQL 正式事实表。模块 06 和模块 07 可以继续依赖正式事实。

### 3.2 编辑粒度

用户认可：核心字段可编辑，结构化细节由系统处理。

第一版让用户编辑业务字段，不直接编辑所有 JSON 底层字段。尺寸只编辑原文，系统重新生成结构化尺寸。

### 3.3 页面入口

用户选择：按桥梁年度进入校对页。

```text
桥梁详情 -> 年度检测任务 -> 导入记录 -> 校对
```

第一版不做独立全系统待校对任务中心。

### 3.4 页面组织

用户认可：问题优先 + 业务分区。

`需要处理` 分组放在第一位，集中展示带 warning/error 的候选。普通候选单独分组，便于批量确认。

### 3.5 普通候选批量确认

用户选择：允许批量确认普通候选，但后端入库前必须兜底校验。

普通候选条件：

```text
无 warning/error
必填字段完整
照片关系明确
评分字段完整
```

### 3.6 同桥同年已有事实

用户选择：已有正式事实时禁止直接入库，必须显式作为修订版确认。

系统不静默覆盖旧事实。确认修订版后，新版本生效，旧版本标为已被修订。

### 3.7 历史病害对比

用户选择：模块 05 不生成历史对比候选。

模块 05 只负责年度事实校对入库。病害对比算法和对比确认页放到后续模块。

## 4. 典型建库流程

用户提出并确认的场景：

```text
上传一份往年的正式文件实现建库
再上传最新的带病害信息的非正式 Word 实现病害录入
```

系统流程：

```text
2025 年正式报告
  -> 模块 04 解析第二章病害、照片和第四章评分
  -> 模块 05 人工校对
  -> 确认为 2025 年正式事实

2026 年软件导出的非正式 Word
  -> 模块 04 解析第二章病害、照片和第四章评分
  -> 模块 05 人工校对
  -> 确认为 2026 年正式事实

后续模块
  -> 读取数据库中的 2025 和 2026 年事实
  -> 生成病害变化对比候选
  -> 人工确认对比
  -> 生成正式报告章节
```

桥梁基本信息仍以系统数据库为准。正式 Word 可以辅助建历史事实库，但不自动覆盖桥梁主数据。
