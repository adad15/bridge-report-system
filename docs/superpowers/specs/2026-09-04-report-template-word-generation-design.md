# 报告模板管理与 Word 即时生成设计

> 日期：2026-09-04
>
> 状态：讨论确认，待文档评审
>
> 适用范围：系统管理、年度检查工作区、报告模板套用、Word 生成、Word/WPS 字段更新

## 1. 背景

系统已经具备桥梁档案、构件档案、年度检查、正式病害、病害照片和正式技术状况评定等数据能力。报告模块不应重新建立一套构件或病害事实，而应把现有正式数据装配为可继续编辑的 `.docx` 文件。

本次设计参考以下两份正式定期检测报告：

- `Q202604001-JZ-113太和区S320大养线百股大桥定期检测报告-（2类）.docx`
- `Q202605001-JZ-024-S319辽小线绕阳河二号桥定期检测报告（2类）.docx`

两份报告具有相近的章节、表格和附录结构，但样式、编号及 Word 域数量已经发生明显漂移。直接把其中一份旧报告持续改造成新报告，会把历史遗留的 `SEQ`、`REF`、`PAGEREF`、`STYLEREF` 和手工格式差异带入系统。

因此第一阶段采用“新建干净模板 + 语义锚点装配”的方案。正式报告只作为版式和内容参考，不直接作为运行时模板反复修改。

## 2. 本次目标

1. 在系统管理中提供报告模板、报告人员和检测设备维护界面。
2. 允许管理员维护多套当前有效模板，并设置一个默认模板。
3. 允许年度检查用户选择模板、历史对比检查、签字人员和检测设备。
4. 从当前数据库正式数据即时生成完整 `.docx`。
5. 模板决定章节顺序、章节名称、分页和横竖版，生成器不写死章节编号。
6. Word 和 WPS 均可打开、编辑生成结果，并可作为字段更新程序。
7. 大型报告仍能稳定生成，包括约 120 页、470 余张图片的报告规模。
8. 对当前不完善的历史对比能力建立明确的替换边界，避免把条数差误写成病害语义变化。

## 3. 不在本次范围内

1. 不保存生成报告的历史版本。
2. 不把生成报告作为正式档案长期归档。
3. 不支持用户把下载后人工修改的最终报告上传回系统。
4. 不提供电子签名图片自动盖章；第一版只填写人员信息并保留手写签名位置。
5. 不开发第三章和第五章对应的业务数据。
6. 不开发附录二桥梁基本状况卡片的数据填报能力。
7. 不实现病害“新增、持续、消失、修复”的自动语义判断。
8. 不使用大模型自由编写结论与建议。
9. 不输出 PDF。
10. 不把正式旧报告作为可自动识别任意结构的模板；上传模板必须遵守本设计的模板契约。

## 4. 与早期总设计的关系

本设计是报告模板套用和 Word 生成第一阶段的实施依据。若与 `2026-07-01-bridge-report-system-design.md` 中下列旧设想冲突，以本设计为准：

- 生成报告归档；
- 草稿、审核版、最终版等报告版本管理；
- 基于上一年度正式报告直接生成桥级模板；
- 用户上传人工修改后的最终报告；
- 以历史 Word 文件作为下一年度报告生成依据。

结构化数据库事实仍是后续年度的依据。Word 只是随时可以重新生成的输出物。

## 5. 核心原则

### 5.1 业务事实只来自现有正式数据

- 构件存在性来自当前年度正式评定所锁定的构件档案修订版。
- 每条正式病害已经绑定实际构件；报告生成不得再猜测或创建构件。
- 病害表只输出有正式病害记录的构件。
- 无病害构件不进入病害表，也不生成“构件不存在”占位行。
- 技术状况等级和扣分结果来自当前有效的正式评定运行记录。
- 照片来自正式病害关系和文件归档记录。

### 5.2 模板控制结构，生成器提供语义内容

生成器不假定病害必须位于第二章，也不假定评定必须位于第四章。模板通过语义锚点决定内容块出现的位置和顺序。

### 5.3 系统即时生成，不管理报告版本

- 不建立 `generated_reports`。
- 不保存报告版本、永久输入快照或历史 Word 文件。
- 每次生成读取当时数据库中的当前正式数据和当前模板。
- 模板或桥梁档案变化后，重新生成的 Word 可以与过去不同。
- 系统不承诺重现过去某次下载文件的每一个字节。

### 5.4 一次生成内部必须一致

虽然不永久保存快照，但同一个生成任务不能混入生成过程中发生的后续修改。C++ 后端在一次一致性读取中构造临时 `ReportContext`；Python 仅使用该上下文完成本次任务。任务过期后上下文一并删除。

### 5.5 确定性生成

同样的模板文件和 `ReportContext` 必须生成相同的业务内容、顺序、编号和文字。第一版不让大模型参与正式内容编写。

## 6. 总体架构

```text
年度检查生成报告页面
        |
        v
C++ 报告编排服务
  - 权限与生成前检查
  - 一致性读取
  - ReportContext
        |
        v
Python Docx Builder
  - 模板字段替换
  - 语义锚点装配
  - 表格、图片和文字生成
        |
        v
OfficeFieldUpdater
  - Microsoft Word Updater
  - WPS Writer Updater
        |
        v
DOCX 最终校验 -> 临时下载 -> 到期清理
```

职责边界：

- React/TypeScript 负责配置、预检结果、任务进度和下载交互。
- C++ 后端是权限、正式数据选择、生成规则编排和任务状态的权威入口。
- Python 不直接连接数据库，只接收 C++ 生成的 `ReportContext` 和模板副本。
- Word/WPS 只负责需要真实排版引擎的目录、页码和总页数字段更新，不参与业务计算。

## 7. 模板管理

### 7.1 模板记录

`report_templates` 每行代表一套可选模板，只保存当前文件，不维护修订历史。建议字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 模板 ID |
| `template_code` | 稳定、唯一的模板代码 |
| `template_name` | 用户可见名称 |
| `description` | 模板说明 |
| `contract_type` | 第一版固定为 `periodic_inspection_v1` |
| `file_id` | 当前模板文件 |
| `file_checksum` | 当前文件校验值 |
| `contract_config_json` | 编号规则、所需角色及其他模板配置 |
| `validation_status` | `valid` 或 `invalid` |
| `validation_result_json` | 最近一次校验明细 |
| `is_enabled` | 是否可供普通用户选择 |
| `is_default` | 是否为默认模板 |
| `updated_by` / `updated_at` | 最近修改信息 |

系统同时只能有一个已启用的默认模板。

模板替换流程必须先把新文件放入暂存位置，完成结构校验和测试生成，再原子替换当前文件。校验失败时保留旧模板。替换完成后不保留旧模板版本。

运行中的生成任务在开始时已复制模板到自己的临时目录，因此模板随后被替换不会改变该任务。

### 7.2 标量占位符

标量占位符用于把短文本写入现有段落或表格单元格，例如：

```text
{{report_no}}
{{bridge_name}}
{{route_code}}
{{route_name}}
{{administrative_region}}
{{inspection_date}}
{{overall_grade}}
{{comparison_year}}
```

人员角色可使用语义字段，例如：

```text
{{personnel.approver.names}}
{{personnel.reviewer.names}}
{{personnel.lead_inspector.names}}
{{personnel.compiler.names}}
```

替换器必须支持占位符被 Word 拆分为多个 run 的情况，不能依赖单个 run 内完整命中。未知占位符使模板校验失败。

### 7.3 内容块锚点

内容块锚点必须独占一个普通段落。第一版语义锚点包括：

```text
[[REPORT:BRIDGE_PROFILE]]
[[REPORT:PERSONNEL_TABLE]]
[[REPORT:EQUIPMENT_LIST]]
[[REPORT:DEFECT_TABLES]]
[[REPORT:DEFECT_PHOTOS]]
[[REPORT:PREVIOUS_COMPARISON]]
[[REPORT:ASSESSMENT_RESULT]]
[[REPORT:CONCLUSION]]
[[REPORT:ASSESSMENT_APPENDIX]]
```

锚点名称描述业务内容，不携带章节号。Docx Builder 按锚点在文档中的真实位置替换整个锚点段落。

`periodic_inspection_v1` 定义必需核心锚点和允许的可选锚点。模板可以改变章节顺序、标题名称及锚点间距，但启用前必须包含该契约要求的全部核心内容。若将来出现内容体系完全不同的报告，应新增契约类型，而不是在生成器中根据模板名称写分支。

### 7.4 模板决定顺序

模板 A 可以是：

```text
第一章 桥梁概况
[[REPORT:BRIDGE_PROFILE]]

第二章 病害检查
[[REPORT:DEFECT_TABLES]]
[[REPORT:DEFECT_PHOTOS]]
```

模板 B 可以是：

```text
第一章 技术状况评定
[[REPORT:ASSESSMENT_RESULT]]

第二章 检查结果
[[REPORT:DEFECT_PHOTOS]]
[[REPORT:DEFECT_TABLES]]

第三章 桥梁概况
[[REPORT:BRIDGE_PROFILE]]
```

生成器不得按章节编号排序内容块。标题编号、分页符、横竖版分节和目录层级全部由模板控制。

### 7.5 表号和图号

因为章节顺序可以变化，生成器不得写死“表 2-1”或“图 2-1”。模板配置保存各内容块的编号格式，例如：

```text
病害表：表 2-{n}
病害照片：图 2-{n}
评定表：表 4-{n}
附录评定表：附表 1-{n}
```

顺序不同的模板可以配置为：

```text
评定表：表 1-{n}
病害照片：图 2-{n}
病害表：表 2-{n}
```

系统管理界面提供编号格式输入和示例预览，管理员不需要直接编辑 JSON。生成正文中的表图引用时使用同一编号服务，以普通文本写入。

对 `DEFECT_PHOTOS` 而言，`{n}` 必须取导入校对阶段已经确认的照片编号，不能按照图片在新模板中的位置重新从 1 编号。模板只改变“图 2-”这类前缀和显示格式。其他没有既有确认编号的动态表格，才按照对应内容块的数据顺序生成 `{n}`。

### 7.6 Word 域约束

允许使用：

- `TOC`；
- `PAGE`；
- `NUMPAGES`；
- TOC 结果内部由 Word/WPS 生成的内部超链接和页码引用。

禁止把以下字段用于业务题注、交叉引用或动态页眉：

- `SEQ`；
- 独立的 `REF`；
- TOC 之外的独立 `PAGEREF`；
- `STYLEREF`。

表号、图号、正文引用和动态页眉文字由生成器确定性写入。模板上传时校验字段；字段更新后再次校验。

## 8. 首个标准模板

首个标准模板从两份正式报告提炼版式，但重新建立样式和字段，避免继承旧文档内部漂移。

保留：

- 封面和固定声明页；
- 签字页布局；
- 正文标题样式；
- 页眉页脚；
- 纵向和横向分节；
- 表格及照片版式；
- 目录、页码和总页数。

不保留：

- 旧报告的病害数据和桥梁事实；
- 旧题注序号；
- 旧交叉引用；
- 动态 `STYLEREF` 页眉；
- 手工残留的隐藏占位内容。

首个标准模板的内容安排如下。这里描述的是该模板，不是生成引擎的固定章节顺序：

| 位置 | 第一版行为 |
| --- | --- |
| 封面 | 桥梁档案、年度检查和报告配置字段 |
| 声明页 | 模板固定内容 |
| 签字页 | 填写所选人员信息，保留手写签名位置 |
| 目录 | Word/WPS 更新 |
| 第一章 | 当前桥梁档案能够提供的字段；缺失的可选字段留空 |
| 第二章 | 正式病害表、正式病害照片和条数对比 |
| 第三章 | 保留标题和版式，正文为空 |
| 第四章 | 正式技术状况评定结果 |
| 第五章 | 保留标题和版式，正文为空 |
| 第六章 | 确定性规则生成结论与建议 |
| 附录一 | 正式桥梁技术状况评定表 |
| 附录二 | 保留标题和版式，内容为空 |

第一章缺少的字段后续在桥梁档案模块补充。当前生成器不编造值，也不因为尚未建设的可选字段阻止整份报告生成。

## 9. ReportContext

`ReportContext` 是一次生成的临时、只读输入模型。它至少包括：

```text
report_identity
bridge_profile
inspection
inventory_revision
defect_observations[]
defect_photos[]
assessment_run
assessment_results[]
comparison
personnel_assignments[]
equipment_assignments[]
template_config
```

关键约束：

1. `defect_observations[].bridge_component_id` 必须存在并属于评定锁定的构件档案修订版。
2. `defect_photos[]` 只引用正式病害关联的归档文件。
3. `assessment_run` 必须与本次正式病害和构件档案版本一致，不接受已失效评定。
4. `comparison` 明确包含所选检查 ID、年份、当前计数、历史计数和 `comparison_mode`。
5. 人员和设备读取本次年度配置及当前资料库字段。
6. `ReportContext` 不写入永久报告快照表；任务结束或过期后删除。

## 10. 病害表生成规则

### 10.1 数据范围

- 只读取当前年度正式病害观测。
- 只输出有病害的构件。
- 不输出“基本完好”的无病害构件行。
- 不输出“无此构件”或“构件不存在”行。
- 一个构件有多条正式病害时，输出多条病害记录。

### 10.2 排序

排序固定为：

1. 评分树的桥面系、上部结构、下部结构顺序；
2. 构件档案自然编号顺序；
3. 同一构件内正式病害记录顺序。

生成器不得根据构件名称字符串临时猜测结构部位，也不得根据 Word 模板顺序重新解释业务排序。

### 10.3 无病害情况

某个结构部位没有正式病害时，不生成虚假表格行。模板需要概述文字时，可以输出“本次检查未记录明显病害”之类的确定性结论，不能据此声称构件不存在。

## 11. 病害照片生成规则

1. 使用导入校对阶段已经确认的照片编号和标题，不在报告阶段重新编号来源照片。
2. 照片按照确认编号排序。
3. 固定两栏布局，左右图片框等宽、等高。
4. 图片按比例完整缩放到框内，不裁剪、不拉伸。
5. 图片与图题作为不可拆分单元，不能跨页分离。
6. 最后一页只有一张照片时放在左栏，右栏留空。
7. 图题使用模板配置的前缀与确认照片编号，并保留确认标题；不得按插入位置重新编号。
8. 没有关联照片的正式病害仍可进入病害表，但不生成虚假照片占位。
9. 归档中已引用的照片文件无法读取时，生成前检查必须阻断任务。

## 12. 与历史检查结果对比

### 12.1 检查选择

用户在生成报告前手动选择一条当前检查之前、已经正式确认的历史检查记录。系统保存其检查 ID，而不是只保存年份文本。

模板标题建议带入明确年份，例如：

```text
与 {{comparison_year}} 年度检查结果对比
```

从而避免用户选择的记录并非时间上最近一次时，报告仍声称“与最近一次检查结果对比”。

如果当前桥梁不存在任何可供选择的历史正式检查，系统允许生成，并在对应内容块输出固定说明“暂无可供对比的历史正式检查记录”。只要存在可选历史检查，生成前必须完成选择。

### 12.2 第一版能力边界

第一版能力名称固定为：

```text
observation_count_delta_v1
```

它只计算正式病害观测记录条数差：

```text
delta = current_observation_count - selected_previous_observation_count
```

按全桥及桥面系、上部结构、下部结构分别输出“增加多少条、减少多少条或持平”。例如：

> 2025 年上部结构共记录病害 18 条，本次检查共记录 23 条，较所选检查记录增加 5 条。

禁止写成：

- 新增 5 处病害；
- 5 处病害已经修复；
- 5 处病害消失；
- 病害发展了 5 条。

条数变化不能证明两次检查中的病害身份关系。报告页面和生成正文都必须显示：

> 当前仅比较两次检查的病害记录条数，不代表新增、消失或修复了相应病害。

### 12.3 后续替换边界

病害对比模块完善并经过人工确认后，替换为：

```text
confirmed_defect_comparison_v2
```

届时由新的对比数据提供器读取人工确认的 `defect_comparisons`，生成新增、持续、消失或修复等语义。下列内容保持不变：

- `[[REPORT:PREVIOUS_COMPARISON]]` 锚点；
- 模板章节和版式；
- Docx Builder 的内容块插入接口；
- 前端生成任务流程。

这项限制必须写入实现测试，不得只作为容易遗失的代码注释。

## 13. 技术状况评定和附录一

第四章与附录一读取当前有效的正式评定运行记录：

- 部件评分；
- 桥面系、上部结构、下部结构评分和等级；
- 全桥综合评分和等级；
- 正式评定表需要的扣分结果。

若正式病害、构件档案修订或评分标准已经变化，使当前评定运行不再对应当前正式输入，报告生成必须阻断并要求重新评定。

生成器不得读取或复用旧 Word 中的评分数字。

## 14. 第六章结论与建议

第一版使用确定性规则，不使用自由文本生成：

1. 输出全桥总体技术状况等级。
2. 输出桥面系、上部结构和下部结构的评定结果。
3. 按正式评定中的主要扣分病害生成概括。
4. 从受控规则文本中选择建议。
5. 不生成数据库中没有依据的维修工程量、预算、工期或结构安全结论。

规则输入、排序和措辞模板必须可测试。同一 `ReportContext` 不得因为运行时间或外部模型不同产生另一套结论。

## 15. 人员和设备

### 15.1 人员库

`report_personnel` 建议保存：

- 姓名；
- 单位或部门；
- 职务、职称；
- 资格证书信息；
- 联系方式；
- 启用状态。

### 15.2 设备库

`report_equipment` 建议保存：

- 设备名称；
- 型号规格；
- 出厂编号或资产编号；
- 测量范围和精度；
- 检定或校准证书编号；
- 有效期；
- 启用状态。

### 15.3 年度配置

每个年度检查保存一份当前报告配置：

- 当前选择的模板；
- 手动选择的对比检查 ID；
- 本次人员及角色和排序；
- 本次设备、用途和排序；
- 最近配置人和配置时间。

建议关系表：

```text
inspection_report_settings
inspection_report_personnel
inspection_report_equipment
```

角色使用稳定代码，例如 `approver`、`reviewer`、`lead_inspector`、`compiler` 和 `participant`。模板配置声明所需角色，年度报告页面据此动态显示必填项。

人员或设备被年度配置引用后不得硬删除，只能停用。已停用项目仍可显示历史配置，但再次生成前必须由用户重新确认或替换，不能静默使用。

第一版只输出姓名及身份信息，签名位置留空，不自动插入电子签名图片。

## 16. 生成前检查

创建任务前至少检查：

1. 年度检查数据已经正式确认。
2. 所有正式病害都绑定当前锁定构件档案中的实际构件。
3. 存在与当前正式输入一致的正式评定运行记录。
4. 所选模板已启用且最近校验有效。
5. 模板要求的人员角色已经配置。
6. 本次检测设备已经配置。
7. 存在历史正式检查时，已经选择对比检查。
8. 所有将要插入的归档照片都存在、可读且属于当前桥梁和年度。
9. 当前机器至少有一个可用的 Word 或 WPS 字段更新器。

第三章、第五章和附录二的空白是首个标准模板的有意设计，不属于缺失内容，不应阻断生成。

第一章尚未建设的可选桥梁档案字段只给出提示，不阻断生成。

## 17. 生成任务

### 17.1 临时任务表

`report_generation_jobs` 是运行设施，不是报告版本表。建议保存：

| 字段 | 含义 |
| --- | --- |
| `id` | 任务 ID |
| `inspection_year_id` | 年度检查 |
| `requested_by` | 创建人 |
| `status` | 当前阶段 |
| `progress` | 进度信息 |
| `template_id` | 创建任务时选择的模板 |
| `template_checksum` | 仅用于本次任务诊断 |
| `temporary_file_path` | 受控临时文件路径 |
| `error_code` / `error_message` | 失败原因 |
| `created_at` / `finished_at` | 时间信息 |
| `expires_at` | 自动清理时间 |

任务及临时文件默认保留 24 小时，具体时长作为部署配置。到期后删除任务输入、模板副本和输出文件；任务行可同时删除或仅保留不含路径和业务正文的短期运行指标。

### 17.2 状态机

```text
queued
  -> validating_data
  -> assembling_docx
  -> updating_fields
  -> validating_docx
  -> ready
  -> expired
```

任意处理中状态均可进入 `failed`。失败任务不能提供下载。

### 17.3 并发和幂等

- 前端提交后立即禁用重复生成按钮并显示任务状态。
- 后端对同一用户、同一年度检查的相同运行中请求返回已有任务，而不是重复启动。
- 新任务开始后允许桥梁数据继续被其他流程修改，但该任务只使用开始时形成的临时 `ReportContext`。
- 模板替换和停用不影响已经复制模板并进入执行阶段的任务。

## 18. Docx Builder

Python Docx Builder 按以下顺序工作：

1. 在任务临时目录复制当前模板。
2. 解析并校验标量占位符、内容锚点和模板配置。
3. 按文档顺序替换标量和锚点。
4. 生成病害表、照片页、评定表、历史对比和结论。
5. 保留原模板的段落样式、表格样式、页眉页脚、分节、页面尺寸和方向。
6. 标记允许更新的 Word 字段为需要刷新。
7. 保存中间 `.docx`。

生成器对模板段落或表格单元格的修改必须尽可能保留原有 run 样式。插入动态内容时只使用模板中约定的命名样式，不在代码中散落字体、字号和边距常量。

## 19. Word/WPS 字段更新

定义统一接口 `OfficeFieldUpdater`，至少提供：

```text
probe()
update_fields(input_docx, output_docx)
```

实现优先级：

1. `MicrosoftWordUpdater`；
2. `WpsWriterUpdater`。

更新器在隐藏窗口中打开中间文档，更新目录、页码和总页数，保存后退出。生成服务必须：

- 设置超时；
- 确保异常时关闭本次启动的文档进程和临时文件；
- 不终止用户已经打开的 Word/WPS 实例；
- 记录选择了哪个更新器及失败阶段；
- 禁止更新器执行模板宏或访问外部文件关系。

Word 不可用时尝试 WPS。两者都不可用或更新失败时任务进入 `failed`，不交付目录页码未知的半成品。

## 20. 最终 DOCX 校验

字段更新后至少校验：

1. 文件是结构完整的 OOXML ZIP。
2. 不残留 `[[REPORT:...]]` 锚点。
3. 不残留未知 `{{...}}` 占位符。
4. 必要内容块已经生成。
5. 图片关系完整，媒体文件可读取。
6. 只存在允许的 Word 字段和内部关系。
7. 页面分节、纸张方向和页眉页脚关系仍存在。
8. 文件可以再次被解析器打开。
9. 输出路径位于当前任务临时目录中。

最终文件名：

```text
{报告编号}{行政区}{路线编号}{路线名称}{桥梁名称}定期检测报告（{综合等级}）.docx
```

示例：

```text
Q202604001-JZ-113太和区S320大养线百股大桥定期检测报告（2类）.docx
```

只在文件名层面清理 Windows 非法字符，不修改文档内部业务值。

## 21. 界面设计

### 21.1 系统管理：报告模板

列表显示：模板名称、模板代码、启用状态、默认状态、校验状态和更新时间。

操作包括：

- 上传模板；
- 替换当前模板；
- 下载当前模板源文件；
- 查看锚点及文档顺序；
- 配置表号、图号格式；
- 配置所需人员角色；
- 使用内置示例数据测试生成；
- 启用、停用和设为默认模板。

### 21.2 系统管理：报告人员

提供新增、编辑、查看、启用和停用。被引用人员不允许硬删除。

### 21.3 系统管理：检测设备

提供新增、编辑、查看、启用和停用，并显示检定有效期状态。被引用设备不允许硬删除。

### 21.4 年度检查：生成报告

页面分为：

1. **生成条件**：显示正式病害、正式评定、模板、照片和字段更新环境状态，并给出阻断项处理入口。
2. **报告配置**：选择模板、历史检查、人员及角色、设备及用途。
3. **内容摘要**：显示有病害构件数、病害记录数、照片数、对比条数差、当前等级以及空白内容块。
4. **任务与下载**：保存配置、创建任务、显示阶段、下载、重新生成和错误信息。

成功文件过期后不显示历史下载，只显示“重新生成”。

## 22. 权限

- 管理员维护模板、人员库和设备库。
- 拥有该年度检查编辑权限的用户可以保存报告配置并创建生成任务。
- 拥有查看权限的用户可以在临时文件有效期内下载任务结果。
- 查看权限不包含修改配置或重新生成。
- 下载接口必须按桥梁和年度检查权限校验，不得依赖不可猜测的临时路径作为唯一保护。

## 23. 错误处理和安全

### 23.1 模板上传

- 只接受标准 `.docx`。
- 校验 ZIP 条目，拒绝路径穿越和异常压缩比。
- 限制模板文件、单个媒体文件和解压后总大小。
- 拒绝宏、嵌入对象及外部文件关系。
- 未知占位符、缺少核心锚点、重复锚点或不支持字段均使校验失败。
- 模板必须通过测试生成后才能启用。

### 23.2 生成任务

- 每个任务使用 GUID 独立临时目录。
- 所有输入文件必须来自受控模板或归档文件 ID，不能接受用户提供的任意服务器路径。
- 任一阶段失败都不提供不完整 Word。
- 清理程序只删除已校验属于报告任务临时根目录的具体任务目录。
- 错误响应提供稳定错误码、用户可理解信息和服务端诊断信息。

建议错误码：

```text
REPORT_TEMPLATE_INVALID
REPORT_FORMAL_DATA_REQUIRED
REPORT_ASSESSMENT_REQUIRED
REPORT_ASSESSMENT_STALE
REPORT_COMPARISON_REQUIRED
REPORT_PERSONNEL_REQUIRED
REPORT_EQUIPMENT_REQUIRED
REPORT_PHOTO_UNREADABLE
REPORT_FIELD_UPDATER_UNAVAILABLE
REPORT_FIELD_UPDATE_FAILED
REPORT_DOCX_VALIDATION_FAILED
REPORT_JOB_ALREADY_RUNNING
REPORT_JOB_EXPIRED
```

## 24. 兼容性要求

生成物统一为标准 `.docx`。必须验证：

| 字段更新器 | Word 打开 | WPS 打开 |
| --- | --- | --- |
| Microsoft Word | 必须通过 | 必须通过 |
| WPS Writer | 必须通过 | 必须通过 |

同时验证：

- Word 制作的合规模板；
- WPS 制作并另存为 `.docx` 的合规模板；
- 顺序不同、章节名不同、编号规则不同的至少两套模板。

通过的含义包括：无需修复即可打开、目录和页码正确、图片正常、分节方向正确、可继续人工编辑。

## 25. 测试策略

### 25.1 单元测试

- 跨 run 标量替换；
- 锚点扫描、重复检测和文档顺序；
- 模板编号规则；
- 只输出有病害构件；
- 构件自然编号排序；
- 照片确认编号排序；
- 两栏图片布局和奇数尾图；
- `observation_count_delta_v1` 的增加、减少、持平和无历史记录；
- 对比文字禁用“新增、修复、消失”等语义；
- 第六章确定性规则；
- 文件名非法字符清理；
- Word 字段允许和禁止清单。

### 25.2 集成测试

- C++ 从正式数据构造 `ReportContext`；
- Python 使用两种章节顺序的模板生成；
- Word 和 WPS 更新器探测、超时和失败清理；
- 下载权限和任务过期；
- 模板替换期间运行中任务保持一致；
- 正式评定失效时阻断生成；
- 照片缺失时阻断生成。

### 25.3 真实规模验收

使用两份正式报告对应的数据规模：

- 常规规模：约 34 页、50 余张图片；
- 大型规模：约 120 页、470 余张图片。

大型报告测试记录生成总时长、Python 峰值内存、字段更新时长、输出文件大小和打开时间。不得只用少量模拟图片证明功能完成。

## 26. 验收标准

1. 管理员能够维护多套当前模板，并设置一个默认模板。
2. 普通用户生成时能选择任意已启用模板。
3. 更换模板顺序后，报告内容严格跟随锚点位置，不跟随生成器硬编码顺序。
4. Word 和 WPS 均能打开生成结果，且不提示修复文档。
5. 病害表只包含有病害的实际构件，数量与正式病害一致。
6. 照片编号、标题和顺序与确认数据一致；图片不裁剪、不拉伸。
7. 对比只表达病害记录条数增加、减少或持平，并显示能力限制说明。
8. 正式评定表和附录一与当前有效评定运行一致。
9. 第三章、第五章和附录二按首个标准模板保持空白。
10. 第六章内容可由正式数据和固定规则完全解释。
11. 目录、页码、横竖版分节和文件名正确。
12. 系统不永久保存生成的报告文件；临时文件过期后可以重新生成。
13. 大型真实规模报告能够在设定的资源和时间限制内完成，且 Word/WPS 打开正常。

## 27. 实施顺序建议

1. 先制作首个干净标准模板并完成模板契约验证器。
2. 验证 Microsoft Word 和 WPS Writer 的隐藏字段更新最小原型。
3. 建立模板、人员、设备和年度报告配置的数据表及 API。
4. 建立 `ReportContext` 和 C++ 生成前检查。
5. 实现 Python Docx Builder 的标量、锚点、表格和照片装配。
6. 实现评定、历史条数对比和第六章确定性规则。
7. 接入临时任务、下载和清理。
8. 完成系统管理页面和年度检查生成页面。
9. 使用两份真实报告规模执行 Word/WPS 兼容及压力验收。

在设计文档完成评审之前，不进入实现阶段。
