## 1. 背景

系统已经具备桥梁档案、构件档案、年度检查、正式病害、病害照片和正式技术状况评定等数据能力。报告模块不应重新建立一套构件或病害事实，而应把现有正式数据装配为可继续编辑的 `.docx` 文件。

本次设计参考 `docs/` 下两份正式定期检测报告：

- `Q202604001-JZ-113太和区S320大养线百股大桥定期检测报告-（2类）.docx`（真 `.docx`，模板版面以它为基线）
- `Q202605001-JZ-067锦州市凌海市G102京抚线大凌河桥定期检测报告-3类.docx`（实为二进制 `.doc` 套了 `.docx` 扩展名，前 8 字节 `D0 CF 11 E0`；需经 Word COM `SaveAs2(FileFormat=16)` 转换后才能解析）

两份报告章节骨架一致，差异只是措辞漂移（「与最近一次检查结果对比」对「与历次检查结果对比情况」）和原件中的手工编号错误（百股大桥 2.3 节的小标题写成了 `2.2.3病害成因分析`，与 2.2 节重复）。

实测两份原件的 Word 域数量：**`STYLEREF` 913 个、`SEQ` 458 个、`REF` 455 个**，另有 1 个 `TOC`（内含 42 个 `PAGEREF`/`HYPERLINK`）。直接把其中一份旧报告持续改造成新报告，会把这些历史遗留的动态编号和手工格式差异整体带入系统。

因此第一阶段采用“新建干净模板 + 语义锚点装配”的方案。正式报告只作为版式和内容参考，不直接作为运行时模板反复修改。

## 2. 本次目标

1. 在系统管理中提供报告模板、报告人员和检测设备维护界面。
2. 允许管理员维护多套当前有效模板，并设置一个默认模板。
3. 允许年度检查用户选择模板、历史对比检查、签字人员和检测设备。
4. 从当前数据库正式数据即时生成完整 `.docx`。
5. 模板决定章节顺序、章节名称、分页和横竖版，生成器不写死章节编号。
6. Word 和 WPS 均可打开、编辑生成结果，并可作为字段更新程序。
7. 大型报告仍能稳定生成，包括约 120 页、470 余张图片的报告规模。
8. 对当前不完善的历史对比能力建立明确的替换边界，避免把条数差误写成病害语义变化。

## 3. 不在本次范围内

1. 不保存生成报告的历史版本。
2. 不把生成报告作为正式档案长期归档。
3. 不支持用户把下载后人工修改的最终报告上传回系统。
4. 不提供电子签名图片自动盖章；第一版只填写人员信息并保留手写签名位置。
5. 不开发第 3 章材质状况检测评定对应的业务数据。
6. 不开发各结构部位「病害成因分析」小节的内容——它需要自由文本，与第 9 条同源。
7. 不开发附录2 桥梁基本状况卡片的数据填报能力。卡片的版式由生成器画出（九十六格齐全），但九十六格里绝大多数（路线等级、设计荷载、各类净空、各部位的形式与材料、档案资料）库里没有对应字段，一律留空等档案补，不编数据。
8. 不实现病害“新增、持续、消失、修复”的自动语义判断。
9. 不使用大模型自由编写结论与建议。
10. 不输出 PDF。
11. 不把正式旧报告作为可自动识别任意结构的模板；上传模板必须遵守本设计的模板契约。

## 4. 与早期总设计的关系

本设计是报告模板套用和 Word 生成第一阶段的实施依据。若与 `2026-07-01-bridge-report-system-design.md` 中下列旧设想冲突，以本设计为准：

- 生成报告归档；
- 草稿、审核版、最终版等报告版本管理；
- 基于上一年度正式报告直接生成桥级模板；
- 用户上传人工修改后的最终报告；
- 以历史 Word 文件作为下一年度报告生成依据。

结构化数据库事实仍是后续年度的依据。Word 只是随时可以重新生成的输出物。

## 5. 核心原则

### 5.1 业务事实只来自现有正式数据

- 构件存在性来自当前年度正式评定所锁定的构件档案修订版。
- 每条正式病害已经绑定实际构件；报告生成不得再猜测或创建构件。
- 病害表只输出有正式病害记录的构件。
- 无病害构件不进入病害表，也不生成“构件不存在”占位行。
- 技术状况等级和扣分结果来自当前有效的正式评定运行记录。
- 照片来自正式病害关系和文件归档记录。

### 5.2 模板控制结构，生成器提供语义内容

生成器不假定病害必须位于第二章，也不假定评定必须位于第四章。模板通过语义锚点决定内容块出现的位置和顺序。

### 5.3 系统即时生成，不管理报告版本

- 不建立 `generated_reports`。
- 不保存报告版本、永久输入快照或历史 Word 文件。
- 每次生成读取当时数据库中的当前正式数据和当前模板。
- 模板或桥梁档案变化后，重新生成的 Word 可以与过去不同。
- 系统不承诺重现过去某次下载文件的每一个字节。

### 5.4 一次生成内部必须一致

虽然不永久保存快照，但同一个生成任务不能混入生成过程中发生的后续修改。C++ 后端在一次一致性读取中构造临时 `ReportContext`；Python 仅使用该上下文完成本次任务。任务过期后上下文一并删除。

### 5.5 确定性生成

同样的模板文件和 `ReportContext` 必须生成相同的业务内容、顺序、编号和文字。第一版不让大模型参与正式内容编写。

## 6. 总体架构

```text
年度检查生成报告页面
        |
        v
C++ 报告编排服务
  - 权限与生成前检查
  - 一致性读取
  - ReportContext
        |
        v
Python Docx Builder
  - 模板字段替换
  - 语义锚点装配
  - 表格、图片和文字生成
        |
        v
OfficeFieldUpdater
  - Microsoft Word Updater
  - WPS Writer Updater
        |
        v
DOCX 最终校验 -> 临时下载 -> 到期清理
```

职责边界：

- React/TypeScript 负责配置、预检结果、任务进度和下载交互。
- C++ 后端是权限、正式数据选择、生成规则编排和任务状态的权威入口。
- Python 不直接连接数据库，只接收 C++ 生成的 `ReportContext` 和模板副本。
- Word/WPS 只负责需要真实排版引擎的目录、页码和总页数字段更新，不参与业务计算。

## 7. 模板管理

### 7.1 模板记录

`report_templates` 每行代表一套可选模板，只保存当前文件，不维护修订历史。建议字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 模板 ID |
| `template_code` | 稳定、唯一的模板代码 |
| `template_name` | 用户可见名称 |
| `description` | 模板说明 |
| `contract_type` | 第一版固定为 `periodic_inspection_v1` |
| `file_id` | 当前模板文件 |
| `file_checksum` | 当前文件校验值 |
| `contract_config_json` | 编号规则、所需角色及其他模板配置 |
| `validation_status` | `valid` 或 `invalid` |
| `validation_result_json` | 最近一次校验明细 |
| `is_enabled` | 是否可供普通用户选择 |
| `is_default` | 是否为默认模板 |
| `updated_by` / `updated_at` | 最近修改信息 |

系统同时只能有一个已启用的默认模板。

模板替换流程必须先把新文件放入暂存位置，完成结构校验和测试生成，再原子替换当前文件。校验失败时保留旧模板。替换完成后不保留旧模板版本。

运行中的生成任务在开始时已复制模板到自己的临时目录，因此模板随后被替换不会改变该任务。

### 7.2 标量占位符

标量占位符用于把短文本写入现有段落或表格单元格。契约 `periodic_inspection_v1` 的标量集合是**闭集**——未知占位符使模板校验失败，因此这里是完整清单而不是举例：

```text
{{report_no}}                 报告编号        inspection_years.report_number
{{bridge_name}}               桥梁名称        bridges.bridge_name
{{route_code}}                路线编号        bridges.route_number
{{route_name}}                路线名称        bridges.route_name
{{administrative_region}}     行政区          bridges.administrative_region
{{inspection_date}}           检测日期        inspection_years.inspection_date
{{inspection_year}}           检测年度        inspection_years.inspection_year
{{project_name}}              项目名称        inspection_years.project_name
{{inspection_org}}            检测单位        inspection_years.inspection_org
{{report_date}}               报告日期        ReportContext 构造时写定
{{overall_grade}}             综合等级        当前正式评定结果
{{comparison_year}}           对比年度        所选历史检查的年度
```

后四项是照两份正式报告的封面和页眉补齐的：封面要年份、检测单位、报告日期，页眉要项目名称。`report_date` 数据库中没有对应列，由 `ReportContext` 在构造时一次性写定（§5.4 的一次生成内部一致）。

封面的「委托单位」在两份正式报告中都存在，但桥梁档案和年度检查都没有对应字段，第一版作为模板固定文字处理，不设占位符。

人员角色可使用语义字段，例如：

```text
{{personnel.approver.names}}
{{personnel.reviewer.names}}
{{personnel.lead_inspector.names}}
{{personnel.compiler.names}}
```

同一角色有多人时，先按年度人员配置的 `sort_order`、再按配置记录 ID 稳定排序，标量占位符使用中文顿号 `、` 连接。人员表锚点则保持一人一行，不把多人压成一格。

替换器必须支持占位符被 Word 拆分为多个 run 的情况，不能依赖单个 run 内完整命中。未知占位符使模板校验失败。

### 7.3 内容块锚点

内容块锚点必须独占一个普通段落。锚点语法有两种形态：

```text
[[REPORT:<内容块>]]                 全篇只出现一次的内容块
[[REPORT:<内容块>:<结构部位>]]      按结构部位各出现一次的内容块
```

第一版语义锚点：

```text
[[REPORT:BRIDGE_PROFILE]]                       桥梁概况
[[REPORT:PERSONNEL_TABLE]]                      人员表（可选）
[[REPORT:EQUIPMENT_LIST]]                       设备表（可选）
[[REPORT:ASSESSMENT_RESULT]]                    技术状况评定结果
[[REPORT:CONCLUSION]]                           结论与建议
[[REPORT:ASSESSMENT_APPENDIX]]                  附录1 桥梁技术状况评定卡片
[[REPORT:BRIDGE_CARD]]                          附录2 桥梁基本状况卡片

[[REPORT:DEFECT_TABLES:<结构部位>]]             该部位的病害表
[[REPORT:DEFECT_PHOTOS:<结构部位>]]             该部位的病害照片
[[REPORT:PREVIOUS_COMPARISON:<结构部位>]]       该部位与所选历史检查的对比
```

结构部位代码与 `defect_observations.structure_part` 的字面值一一对应，顺序即报告输出顺序：

```text
SUPERSTRUCTURE  上部结构
SUBSTRUCTURE    下部结构
DECK            桥面系
WHOLE_BRIDGE    全桥
OTHER           其他
```

**为什么病害相关的三个内容块必须按部位拆分。** 两份正式报告的第 2 章都不是"一张病害表 + 一组照片 + 一段对比"，而是按上部结构、下部结构、桥面系各起一节，每节自带这三样：

```text
2.1 上部结构    表2.1-1 上部结构病害检查表 + 照片(216 张) + 2.1.2 与上次对比
2.2 下部结构    表2.2-1 下部结构病害检查表 + 照片(106 张) + 2.2.2 与上次对比
2.3 桥面系      表2.3-1 桥面系病害检查表   + 照片(133 张) + 2.3.2 与上次对比
```

一个锚点表达不了三个位置。让生成器自己写出 2.1/2.2/2.3 三级标题也不行——那违反 §5.2 与 §7.4：标题和编号由模板控制，生成器只提供语义内容。

**覆盖一致性约束。** 模板校验必须保证：三个按部位拆分的内容块覆盖**同一组**结构部位。否则会出现"病害表分了三部位、照片只放了上部"这样的模板，生成时下部和桥面系的照片无处输出，只能被静默丢掉。

模板不必覆盖全部五个部位。当前实测数据只有上部结构、下部结构、桥面系三类（`全桥` 与 `其他` 各 0 条），首个标准模板因此只做三节。数据落在模板未覆盖的部位时由生成前检查阻断（§16），不在报告层任选归属。

锚点名称描述业务内容，不携带章节号。Docx Builder 按锚点在文档中的真实位置替换整个锚点段落。

`periodic_inspection_v1` 定义必需核心锚点和允许的可选锚点。模板可以改变章节顺序、标题名称及锚点间距，但启用前必须包含该契约要求的全部核心内容。若将来出现内容体系完全不同的报告，应新增契约类型，而不是在生成器中根据模板名称写分支。

### 7.4 模板决定顺序

模板 A 可以是：

```text
1 桥梁概况
[[REPORT:BRIDGE_PROFILE]]

2 病害检查
2.1 上部结构
[[REPORT:DEFECT_TABLES:SUPERSTRUCTURE]]
[[REPORT:DEFECT_PHOTOS:SUPERSTRUCTURE]]
```

模板 B 可以是：

```text
1 技术状况评定
[[REPORT:ASSESSMENT_RESULT]]

2 检查结果
2.1 桥面系
[[REPORT:DEFECT_PHOTOS:DECK]]
[[REPORT:DEFECT_TABLES:DECK]]

3 桥梁概况
[[REPORT:BRIDGE_PROFILE]]
```

生成器不得按章节编号排序内容块。标题编号、分页符、横竖版分节和目录层级全部由模板控制。

### 7.5 表号和图号

因为章节顺序可以变化，生成器不得写死“表 2-1”或“照片 2-1”。**报告里的所有表号和图号都在生成时现编**，格式由模板配置决定，配置键与锚点同形：

```text
DEFECT_TABLES:SUPERSTRUCTURE   表2.1-{n}
DEFECT_TABLES:SUBSTRUCTURE     表2.2-{n}
DEFECT_TABLES:DECK             表2.3-{n}
DEFECT_PHOTOS:SUPERSTRUCTURE   照片2.1-{n}
DEFECT_PHOTOS:SUBSTRUCTURE     照片2.2-{n}
DEFECT_PHOTOS:DECK             照片2.3-{n}
ASSESSMENT_RESULT              表4-{n}
ASSESSMENT_APPENDIX            附表1-{n}
```

顺序不同的模板配成不同前缀即可。**`{n}` 按编号格式串分序列**：配了同一个格式串的内容块共用一条序列，按文档顺序递增；格式串不同的各排各的。

这样两种需求用同一条规则表达：

- 按部位拆分的病害表配不同前缀（表2.1-、表2.2-、表2.3-），于是各自从 1 起排，与正式报告一致；
- 4.1.1 的部件权重表和 4.1.2 的总体评定表同属 4.1 节，都配 `表4.1-{n}`，于是按文档顺序得到 表4.1-1 和 表4.1-2。

谁跟谁共号由模板决定，不写死在生成器里。

### 7.5.1 第 4 章的内容块划分（2026-09-07 按正式报告修订）

第 4 章按正式报告拆成三节，四个内容块：

```text
4 全桥技术状况综合评定
  4.1 桥梁技术状况综合评定
    4.1.1 部件权重分配        [[REPORT:COMPONENT_WEIGHTS]]   表4.1-1 桥梁部件权重计算表
    4.1.2 桥梁技术状况等级     [[REPORT:ASSESSMENT_RESULT]]   表4.1-2 总体技术状况评定表
  4.2 桥梁技术状况等级单项控制指标  [[REPORT:CONTROL_INDICATOR]]
  4.3 桥梁技术状况等级综合评定      [[REPORT:OVERALL_ASSESSMENT]]
```

**表4.1-1 桥梁部件权重计算表**，列结构照正式报告：`部位 / 序号 / 名称 / 权重 / 重新分配后权重 / 构件数量 / 备注`。

关键点是它**必须列出本桥没有的部件**并在备注写"无此构件"，其「重新分配后权重」与「构件数量」写 `/`。那一行的权重正是被摊给同部位其余部件的那部分；不列出来，读者看不懂重分配后的数字是怎么来的。评定结果里只有实际存在的部件，所以这份完整清单只能取自规范包的权重集（`h21.weight_set.*`），且必须保留规范原表的行序——`ReportContextRepository` 因此需要 `StandardRegistry`。桥型和所锁规范包都取自评定运行本身，不按今天的规范重新推。

**表4.1-2 总体技术状况评定表**，11 列：`结构 / 类别 / 评价部件 / 构件数量 / 构件评分 / 桥梁部件技术状况评分 / 桥梁结构技术状况评分 / 桥梁结构组成权重 / 等级 / 桥梁总体技术状况评分 / 综合评级`。

每个评价部件下**按构件评分分档**，一档一行，「构件数量」是该档的构件数（如上部承重构件：7 个 65 分、39 个 75 分、779 个 100 分）。分档合计必须等于该部件的构件总数——读者会拿这一列核对构件数量，对不上说明有构件被漏掉或重复计入。合并规则：「结构」「桥梁结构技术状况评分」「桥梁结构组成权重」「等级」按结构合并，「桥梁总体技术状况评分」「综合评级」贯通全表。「等级」列只印数字（2），「综合评级」带"类"（2类）。表后紧跟一句「由以上评定过程可知，该桥评定为 X 类，处于"…"」。

#### 报告只转述评定，不复算（2026-09-07 定案）

**报告层不得再算一遍评定已经算过的任何数。** 评分、等级、权重、重分配后权重一律从 `assessment_runs` / `assessment_part_results` / `assessment_component_results` 读出来直接印；报告层只做取数、排序、合并单元格和格式化。

这条的收益是：**改评定算分逻辑时，报告一行都不用改。** 反过来，一旦报告层自己算了一份，两边就会各自漂移，而漂移的那天没人会想到去查报告代码。

由此确定的两件事：

1. **权重列印两位小数，不做任何凑整调整。** 引擎算的是 `effective_weight = configured_weight / Σ(有构件部件的配置权重)`，用于 `结构评分 = Σ(部件评分 × effective_weight)`；`assessment_part_results.weight` 存的就是它，报告印的就是它。取两位小数后这一列可能合计 1.01（0.30/0.98 = 0.3061 印成 0.31，0.28/0.98 = 0.2857 印成 0.29），这不是错，是全精度值的两位小数视图。参考报告把 0.29 手工压回 0.28 以凑成 1.00，本设计**不复现**这种调整——报告写的必须是程序算的。

2. **拿印出来的权重乘部件评分，复原不出结构评分**，差在被截掉的小数上。要核对算式的读者应看评定运行的 trace，不是报告表格。

引擎的重分配行为和"权重列即算分所用值"这条，由 `H21PartEvaluationTest.MissingCategoryWeightIsRedistributedProportionally` 与 `PartScoreIsTheSumOfCategoryScoresTimesEffectiveWeight` 守住；报告层不调整这一列，由 `test_weight_column_prints_what_the_engine_used_without_adjustment` 守住。（原先只有一条用"部件齐全的桥"跑的用例，`configured_total` 恰为 1.0，重分配分支从未被执行过。）

系统管理界面提供编号格式输入和示例预览，管理员不需要直接编辑 JSON。生成正文中的表图引用使用同一编号服务，以普通文本写入。

#### 照片编号：报告号与系统号是两回事

**报告里的照片编号按模板结构现编，与数据库中存的 `defect_photos.photo_number` 无关。** 这一条是本设计早期版本的反转，理由是实测出来的：

1. **系统里的编号不是来源事实。** 当前数据全部经由来源软件导入（`source_type='接口同步'`）。来源库用 `images.ForeignKey` 直接把照片绑在病害上，它自己的 `photoNum` 列 887 张全为空，`noteContent` 与 `oriFileName` 同样全空——来源软件根本没有照片编号这个概念。库里那些 `2.1-1` 是导入器为了填满契约必填字段现编的。

2. **而且编得是乱的。** 导入时按病害 UUID 顺序发号。实测同一年度上部结构，编号 1..10 对应的构件台账顺序是 1319、1086、1086、1174、308、407、1296、1375、1111……完全跳跃。直接用它当图号，会做出一份病害表里编号乱跳、读者无法按号找图的报告。

3. **换模板必然错位。** `2.1` 的含义是"第 2 章第 1 节"。模板一旦重排章节，这个前缀就与新文档的章节号对不上，而 §7.4 明确允许重排。

因此：

- **排序**：照片顺序跟随病害表的行序（§10.2 的排序规则），同一条病害内的多张照片按其入库顺序。这样读者顺着表往下看，图号是递增的。
- **编号**：按上述顺序在每个 `DEFECT_PHOTOS:<部位>` 内从 1 起排，套模板配置的前缀。
- **图题**：`{生成的图号}  {photo_title}`，两个空格分隔，与正式报告一致（原件为「照片2.1-1  1-1#板」）。`photo_title` 为空时只输出图号，不得用病害描述臆造标题。
- **病害表的「照片编号」列必须写同一套现编号码**，与图题共用同一个编号服务。两处若各算各的，读者按表里的号就找不到图——这是本方案唯一的致命失败模式，必须有测试守住。

数据库里的 `defect_photos.photo_number` 降级为 **Word 导入路的内部匹配键**，不进报告，也不作为面向用户的业务编号（详见 §9.1）。

### 7.6 Word 域约束

允许使用：

- `TOC`；
- `PAGE`；
- `NUMPAGES`；
- TOC 结果内部由 Word/WPS 生成的内部超链接和页码引用。

禁止把以下字段用于业务题注、交叉引用或动态页眉：

- `SEQ`；
- 独立的 `REF`；
- TOC 之外的独立 `PAGEREF`；
- `STYLEREF`。

表号、图号、正文引用和动态页眉文字由生成器确定性写入。模板上传时校验字段；字段更新后再次校验。

### 7.7 表头样表：列宽和表头交给模板（2026-09-10 定案）

模板可以为每个表格类内容块画一张**只有表头行的样表**，标记独占一行、样表紧随其后：

```text
[[TABLE:DEFECT_TABLES]]  病害检查表：拖列宽、改表头文字即可；行数由病害条数决定。
┌────┬────────┬────────┬ … ┐
│序号│部件名称│构件编号│ … │      ← 一行，就这一行
└────┴────────┴────────┴ … ┘
```

职责划分：

| 归谁 | 内容 |
|---|---|
| **模板**（在 Word 里改） | 列宽、表头文字、列数、边框样式、表格宽度 |
| **生成器** | 加几行、哪儿到哪儿合并、每格填什么 |

**为什么不把整张表放进模板。** 列结构每次都一样，行数不是：百股大桥 2026 年上部结构 297 行、下部结构 49 行、桥面系 84 行；表4.1-2 的行数同一座桥三个年度分别是 24、29、30 行，合并跨度也跟着变（桥墩 2025 年占 7 行、2026 年占 4 行，取决于其构件评分落在几个档上）。模板画不出"取决于数据"的行数与合并。

**列数是契约，不是版式。** 模板作者删掉一列或调换两列，生成器照填不误——「病害位置」的内容会印到「病害类型」下面，看着完全正常但全错。所以 `contract.TABLE_COLUMNS` 定死每个块的列数，样表对不上就拒绝启用模板。这是这层校验唯一必须拦住的事。

其余规则：

- **样表是可选的**：没画就退回"占满版心、列宽由 Word 按内容分配"，老模板照常能用。
- **标记必须在段首**，后面可以跟一句给模板作者看的说明——整段生成时删掉，说明也跟着走。写在句子中间会连累前面的话，校验拒绝。
- **样表放在它对应的表真正渲染的那一节**：正文表放正文节（版心 16cm），附表1 放横向的附录节（24.62cm）。放错节，在 Word 里量到的宽度与实际排版对不上。
- **生成时连标记带表一起删掉**，包括样表之间垫的空段。**但带分节符的段落绝不能碰**：它除了 `sectPr` 什么都没有，看着也是"空段"，删掉正文就失去自己的页面设置、继承最后那个横向节——实测报告从 104 页涨到 166 页。

实测效果（百股大桥 2026，430 条病害）：自动列宽 104 页，样表列宽 101 页。

首个标准模板从两份正式报告提炼版式，但重新建立样式和字段，避免继承旧文档内部漂移。

实测两份原件里有 **913 个 `STYLEREF`、458 个 `SEQ`、455 个 `REF`**，还有把 2.3 节小标题写成「2.2.3病害成因分析」这类手工编号错误——§7.6 拒绝这些域不是洁癖，是有实证的。

## 9. ReportContext

### 9.1 照片与病害的关联：两条导入路不同

报告生成必须理解这一点，否则会把一个内部匹配键当成业务编号印进交付文件。

| | Word 导入（`软件导出Word` / `正式Word`） | 来源软件导入（`接口同步`） |
| --- | --- | --- |
| 照片如何绑到病害 | **靠照片编号的文字匹配** | **靠 UUID 外键直连** |
| 编号来自哪里 | Word 文档里真实写着 | 来源软件没有这个概念 |
| 题注来自哪里 | Word 里的题注文字 | 来源软件没有，由导入器按构件编号 + 病害类型生成 |
| 缺了编号会怎样 | 彻底无法关联 | 毫无影响 |

Word 那条路里，病害表最后一列写着 `2.1-5`，图片题注写着「照片2.1-5」，除这个字符串外没有任何线索能把图和表对上。来源软件那条路里，`images.ForeignTable='outerCheckData'` + `images.ForeignKey` 直接指向病害记录的主键。

契约据此定规则：`photo_number` 可以缺省，但 `resolution` 为 `pending` 或 `missing` 时必须有——这两种状态下 `photo_candidate_id` 必为空，编号是该引用仅有的标识。其余状态一律用 `photo_candidate_id` 配对。

正式表 `defect_photos.photo_number` 相应改为可空（迁移 `031`），并已清空既有的来源软件导入编号。它**不进报告**：报告图号在生成时按模板结构现编（§7.5）。

### 9.2 内容

`ReportContext` 是一次生成的临时、只读输入模型。它至少包括：

```text
report_identity
bridge_profile
inspection
inventory_revision
defect_observations[]
defect_photos[]
assessment_run
assessment_results[]
comparison
personnel_assignments[]
equipment_assignments[]
template_config
```

关键约束：

1. `defect_observations[].bridge_component_id` 必须存在并属于评定锁定的构件档案修订版。
2. `defect_photos[]` 只引用正式病害关联的归档文件。
3. `assessment_run` 必须是该年度修订唯一的当前正式评定，并与年度锁定的构件档案、评分树和标准包一致。
4. `comparison` 明确包含所选检查 ID、年份、当前来源病害计数、历史来源病害计数、五类结构部位计数和 `comparison_mode`。
5. 人员和设备读取本次年度配置及当前资料库字段。
6. `ReportContext` 不写入永久报告快照表；任务结束或过期后删除。

## 10. 病害表生成规则

### 10.1 数据范围

- 只读取当前年度正式病害观测。
- 只输出有病害的构件。
- 不输出“基本完好”的无病害构件行。
- 不输出“无此构件”或“构件不存在”行。
- 一个构件有多条正式病害时，输出多条病害记录。

#### 「部件名称」与「构件编号」是两件事（2026-09-09 定案）

病害表这两列含义不同，取值来源也不同：

| 列 | 含义 | 来源 |
|---|---|---|
| 部件名称 | H21 部件泛称：桥墩、上部一般构件 | 台账已确认的规范映射 → 规范包里该类别的名称 |
| 构件编号 | 含类型字的完整记号：`1#墩盖梁`、`1-1#铰缝` | 台账条目的 `component_number` |

盖梁归**桥墩**、铰缝归**上部一般构件**——「部件名称」与 §13 的 表4.1-2「评价部件」同源，读者才能顺着病害行找到对应的部件评分；这是第 2 章与第 4 章之间唯一的连接线索。

**不得直接印 `defect_observations.part_name`。** 百股大桥三个年度 1197 行实测，这一列**全部**等于构件编号——来源软件那一列根本不是部件名称。规范映射取不到时才退回它（Word 导入路的那一列可能本来就是泛称）。

**报告印的名称去掉规范里的举例括号**：`上部承重构件（主梁、挂梁）` → `上部承重构件`。括号里是规范给的举例说明，不是名称本身；不截的话病害表那一格 15 个字要折三四行，而上部一般构件一类就占了 200 条。规范包和评定结果里存的仍是全称——这是印刷用词，不是事实变更。截断只影响 6 个部件名称，彼此不重名；`桥面板`、`索塔`、`横向联结系` 那几组同名的分属不同桥型，一份报告只涉及一种桥型。

报告的取数单位是用户选择的**当前年度检查修订行**，不是前端临时选择的某个导入记录。该年度的权威来源由当前正式 `assessment_run` 确定：

- 正常情况下，年度内所有正式病害、照片和评定投影的 `source_import_record_id` 必须与该正式评定一致；
- 来源导入记录被合规删除、外键已统一置空时，仍可按该年度修订的结构化正式事实生成；
- 同一年度修订内出现两个非空正式来源，或正式评定来源与病害来源不一致时，视为数据不变量损坏并阻断生成，不允许把多次导入静默拼成一份报告。

### 10.2 排序

排序固定为：

1. 当前评定引擎及构件档案的结构顺序：上部结构、下部结构、桥面系、全桥、其他；
2. 构件档案自然编号顺序；
3. 同一构件内正式病害记录顺序。

五个合法结构部位必须全部有稳定位置，不能静默丢弃“全桥”或“其他”病害。这里的“全桥”是数据库中的字面结构部位；与历史对比中的“全部结构部位合计”不是同一概念。

生成器不得根据构件名称字符串临时猜测结构部位，也不得根据 Word 模板顺序重新解释业务排序。

### 10.3 无病害情况

某个结构部位没有正式病害时，不生成虚假表格行。模板需要概述文字时，可以输出“本次检查未记录明显病害”之类的确定性结论，不能据此声称构件不存在。

### 10.4 病害检查表前的部件病害概要（2026-09-09 定案）

每张病害检查表前先按评价部件概述查到了什么，一行一个部件：

```text
上部承重构件：受渗水侵蚀，混凝土剥蚀破损、渗水泛碱、纵向裂缝、水蚀、锈胀开裂。
上部一般构件：渗水泛碱、勾缝砂浆脱落。
支座：支座状况良好，未见明显病害。
```

规则：

1. 部件清单取自 表4.1-1 的权重表，**顺序跟规范原表走**（上部承重构件、上部一般构件、支座……），不按"谁有病害谁在前"。
2. **没有病害的部件也要列出来**：「支座状况良好，未见明显病害」本身就是检查结论，漏掉它读者不知道支座查没查过。措辞只说"未见明显病害"，不说"构件完好"——后者是评定结论，不是检查记录。
3. 病害类型按在病害表里首次出现的次序去重，与表格顺序一致，重复生成结果相同。
4. 拿不到部件清单（没有规范包）时不出概要，退回 §10.3 的那句笼统结论——宁可不出，也不出一份漏了部件的清单。

### 10.5 第 4 章各节的引语

4.1.1 与 4.1.2 的引语是受控文本，表号由生成器按模板配置填入，不写死在文字里（§7.5、§7.6）：

```text
4.1.1  按照《公路桥梁技术状况评定标准》（JTG/TH21-2011）中的评定方法，根据该桥的
       结构型式，将桥梁各部件权重值重新分配，见{表号}所列。
4.1.2  按照《公路桥梁技术状况评定标准》（JTG/TH21-2011）中的评定方法，桥梁综合评定
       等级结果见{表号}所示。
```

规范全称由 `STANDARD_CITATION` 统一提供，4.2 的单项控制指标说明也引它——同一份报告里不能这一节写 `JTG/TH21-2011`、那一节写 `JTG/T H21-2011`。

## 11. 病害照片生成规则

1. 照片顺序跟随病害表行序（§10.2），同一条病害内的多张照片按入库顺序；顺序必须确定，同一份 `ReportContext` 重复生成结果一致。
2. 图号在每个 `DEFECT_PHOTOS:<部位>` 内按上述顺序从 1 起排，套模板配置的前缀（§7.5）。不使用 `defect_photos.photo_number`。
3. 固定两栏布局，左右图片框等宽、等高。
4. 图片按比例完整缩放到框内，不裁剪、不拉伸。

   **嵌入前按版面尺寸重采样（2026-09-08 实测定案）**：归档原图是证据，必须原样保留；嵌进报告的是按目标印刷分辨率重新采样的副本。百股大桥 2026 年度实测——455 张 1600×1200 的原图（合计 125MB）原样嵌入做出一份 **126MB** 的报告，而版面上每张只有 6.9cm 宽（2.7 英寸）。按 200 dpi 重采样后同一份报告 **21.3MB**，Word 刷新域的耗时也从 38.7 秒降到 9.1 秒。

   分辨率是 `photo_resampler.TARGET_DPI` 一个常量。200 dpi 对连续色调的照片在纸面上与 300 dpi 无可见差别；要更清晰调高它即可。原图本来就不比版面框大时不再编码一次——放大只会变糊，还更占地方。

   顺带修掉一个既有缺陷：python-docx 不认 JPEG 的 EXIF 方向标记，竖拍的照片原样嵌进去会躺着。重采样时按 EXIF 转正，写出的副本不再带方向标记。
5. 图片与图题作为不可拆分单元，不能跨页分离。
6. 最后一行只有一张照片时放在左栏，右栏留空。
7. 图题为“{生成的图号}␠␠{photo_title}”（两个空格），与正式报告一致；`photo_title` 为空时只输出图号，不得用病害描述臆造标题。
8. 病害表的「照片编号」列与图题共用同一个编号服务，两处号码必须完全一致。
9. 没有关联照片的正式病害仍可进入病害表，但不生成虚假照片占位。
10. 归档中已引用的照片文件无法读取时，生成前检查必须阻断任务。
11. 题注在正式报告中位于单行小表格的单元格内，不在普通段落里；生成器应沿用该载体，以保证与参考版式一致。

**实现落点（2026-09-07）**：题注确实落在表格单元格里，但载体是**整块照片一张表**，每两行一组（上排图片、下排图题），而不是"一行照片一张小表"。原因是实测发现的：紧挨着的两张表会被 Word 合并——一次装配写进 6 张表，经 Word 域更新读回来只剩 5 张，两张 2 列的照片表被并成了一张 4 行表。列数相同时并起来看不出问题，列数不同时就是废版面。因此：

- 照片块内部不留表间相邻，做成一张表；
- 内容块之间由装配器在两张表相邻时垫一个空段落隔开。

不可拆分靠两条：每行 `w:cantSplit`，以及「报告照片」样式的段中不分页（`keep_with_next`）。Word 与 WPS 各跑一遍域更新后，表格结构（3×6、2×9、3×10、4×2、2×10）与装配结果逐项一致。

## 12. 与历史检查结果对比

### 12.1 检查选择

用户在生成报告前手动选择一条当前检查之前的历史检查记录。候选项必须同时满足：同一桥梁、`is_current = true`、`status in ('已确认', '已归档')`、`inspection_year < 当前年度`，并排除当前记录自身。

选择结果直接保存到 `inspection_years.report_comparison_inspection_id`，作为唯一真源；`inspection_report_settings` 不再重复保存对比检查 ID。该列由迁移 `030` 从 002 起就无人读写的 `previous_inspection_id` 改名而来——旧名字的字面含义是"上一次检查"，与本节允许用户选择非最近一次检查的语义不符。保存时后端重新校验上述条件，生成时也再次校验，避免修订或归档状态变化后继续引用无效记录。

该列外键为 `on delete set null`：被引用的历史年度被删除后，本列会静默清空。年度和桥梁删除预览必须统计并提示有多少份报告配置的对比选择会因此失效（见 §17.4）。

模板标题建议带入明确年份，例如：

```text
与 {{comparison_year}} 年度检查结果对比
```

从而避免用户选择的记录并非时间上最近一次时，报告仍声称“与最近一次检查结果对比”。

如果当前桥梁不存在任何可供选择的历史正式检查，系统允许生成，并在对应内容块输出固定说明“暂无可供对比的历史正式检查记录”。只要存在可选历史检查，生成前必须完成选择。

### 12.2 第一版能力边界

第一版能力名称固定为：

```text
source_defect_count_delta_v1
```

它只比较“来源病害条数”，不能直接 `count(defect_observations)`。构件范围拆分会把一条来源病害展开为多条正式观测，直接计数会把操作粒度误写成病害数量变化。

每条正式观测的来源计数键定义为：

```text
source_defect_key =
  source_import_record_id（为空时使用 inspection_year_id）
  + ':' +
  source_raw_cells_json.range_split_origin.source_candidate_id
    （不存在时使用 defect_observation_id）
```

同一来源病害拆分出的观测具有相同 `source_candidate_id`，因此只计一次；未拆分观测没有 `range_split_origin`，每条正式观测计一次。若同一来源计数键跨越多个 `structure_part`，说明解析绑定违反业务不变量，生成前阻断，不由报告层任选归属桶。

差值计算为：

```text
delta = current_source_defect_count - selected_previous_source_defect_count
```

对比结果按结构部位分别写入各自的 `[[REPORT:PREVIOUS_COMPARISON:<部位>]]` 锚点——正式报告里这段话就在每个部位自己的小节内（2.1.2 / 2.2.2 / 2.3.2），不是集中成一段。

`ReportContext.comparison` 仍按五个数据库结构部位分别计算，另算一个“全部结构部位合计”。合计按唯一来源计数键直接汇总，不能把五个桶简单相加后假定没有跨桶异常。模板未覆盖的部位若有数据，由生成前检查阻断（§16），不静默丢弃。

合计值供正文引用或概述使用；单个部位的例句形如：

> 2025 年上部结构共记录病害 18 条，本次检查共记录 23 条，较所选检查记录增加 5 条。

禁止写成：

- 新增 5 处病害；
- 5 处病害已经修复；
- 5 处病害消失；
- 病害发展了 5 条。

条数变化不能证明两次检查中的病害身份关系。报告页面和生成正文都必须显示：

> 当前仅按来源病害行比较两次检查的记录条数；构件范围拆分只计一次。本结果不代表新增、消失或修复了相应病害。

### 12.3 后续替换边界

病害对比模块完善并经过人工确认后，替换为：

```text
confirmed_defect_comparison_v2
```

届时由新的对比数据提供器读取人工确认的 `defect_comparisons`，生成新增、持续、消失或修复等语义。下列内容保持不变：

- `[[REPORT:PREVIOUS_COMPARISON:<部位>]]` 锚点及其按部位拆分方式；
- 模板章节和版式；
- Docx Builder 的内容块插入接口；
- 前端生成任务流程。

这项限制必须写入实现测试，不得只作为容易遗失的代码注释。

## 13. 技术状况评定和附录1

第 4 章与附录1 读取当前有效的正式评定运行记录：

- 部件评分；
- 桥面系、上部结构、下部结构评分和等级；
- 全桥综合评分和等级；
- 正式评定表需要的扣分结果。

当前架构通过年度修订保证正式事实不可原地替换。生成前不重新跑一遍评定来猜测“是否失效”，而是校验可落地的不变量：当前年度修订只能有一个 `is_current = true` 的正式评定；该评定锁定的构件档案修订、评分树版本和标准包必须与年度记录一致；正式事实来源必须满足第 10.1 节的单一来源约束。任一条件不满足都阻断生成。未来若开放正式病害原地编辑，再增加评定输入摘要重建与 `input_checksum` 比对。

生成器不得读取或复用旧 Word 中的评分数字。

#### 「构件评分」是构件级的，不是病害级的（2026-09-09 实测记录）

病害表里「构件评分」一列在同一构件的多行上重复出现，容易被读成"这条病害的分"。实测遇到的例子：`2-1#板` 有两条病害，一条是标度 2 的渗水侵蚀（扣 25），另一条是无标度的「其它病害」；两行都印 75 分，单看后一行像是算错了。

**这不是缺陷。** 48 个只有非评分病害的构件全部评 100 分，引擎是一致的。「病害扣分」列正是用来解释这 75 从哪来的——第 30 行扣 25、第 31 行扣 0，读者据此看出是哪条病害造成的。因此这一列保留。

若将来仍嫌混淆，可把同一构件的「构件评分」纵向合并成一格，与 表4.1-2 的做法一致；不改列结构。

#### 病害扣分的归属（2026-09-07 实测定案）

H21 对同一构件、同一病害指标只按**最重标度扣一次**。评定引擎照此实现：`AssessmentService` 在构造评定输入时按 `(构件, 指标)` 聚合，只把最大标度送进评估器，因此 `assessment_component_results.result_json->'defects'` 里的扣分是 **`(构件, 指标)` 这一组的属性，不是单条病害观测的属性**——评定输入里根本没有病害观测 ID。

病害表却是一行一条观测。归属规则定为：

- 同一 `(构件, 指标)` 组内，按病害表行序，**第一条**写该组的扣分值；
- 同组其余行写 **`0`**，表示"按规范没有额外扣分"；
- 该年度没有生效正式评定时，整列为**空**，表示"没有依据"。

`0` 与空必须区分：前者是规范的结论，后者是数据缺失。选 `0` 而不是留空，是为了让读者把这一列加起来时对得上，不会因为看到两个相同的扣分数字而重复计算。

第 4、5 章和附表1 都以正式评定为前提；生成时评定已不在，装配层报 `report_assessment_missing` 中止，绝不出一份没有评分的定期检测报告。

## 14. 第 5 章结论与建议

第一版使用确定性规则，不使用自由文本生成：

1. 输出全桥总体技术状况等级。
2. 输出桥面系、上部结构和下部结构的评定结果。
3. 按正式评定中的主要扣分病害生成概括。
4. 从受控规则文本中选择建议。
5. 不生成数据库中没有依据的维修工程量、预算、工期或结构安全结论。

规则输入、排序和措辞模板必须可测试。同一 `ReportContext` 不得因为运行时间或外部模型不同产生另一套结论。

## 16. 生成前检查

创建任务前至少检查：

1. 年度检查数据已经正式确认。
2. 所有正式病害都绑定当前锁定构件档案中的实际构件，且该构件在锁定修订版中 `is_active = true`；出现停用构件属于数据不变量错误并阻断生成。
3. 存在唯一当前正式评定，且通过第 13 节所列版本与来源一致性检查。
4. 所选模板已启用且最近校验有效。
5. 模板要求的人员角色已经配置。
6. 本次检测设备已经配置。
7. 存在历史正式检查时，已经选择对比检查。
8. 所有将要插入的归档照片都存在、可读且属于当前桥梁和年度。
9. 当前机器至少有一个可用的 Word 或 WPS 字段更新器。
10. **本次数据涉及的每个结构部位，所选模板都有对应的按部位锚点。** 模板只覆盖上部结构、下部结构、桥面系时，若出现 `全桥` 或 `其他` 的正式病害，必须阻断并指明是哪个部位——这些病害没有输出位置，静默丢弃会让病害表数量与正式病害对不上（§26 第 5 条）。

第 3 章、各部位的「病害成因分析」小节和两张附录卡片里没有数据来源的格子，是首个标准模板的有意设计，不属于缺失内容，不应阻断生成。

第一章尚未建设的可选桥梁档案字段只给出提示，不阻断生成。

| `created_at` / `finished_at` | 时间信息 |
| `expires_at` | 自动清理时间 |

任务输入、模板副本和输出文件默认保留 24 小时，具体时长作为部署配置。到期后删除全部临时文件，把任务行改为 `expired`，并清空文件路径、输入摘要和可能含业务正文的诊断内容。`expired`、`failed` 和已经清理文件的终态任务行仅保留 7 天用于界面说明和运行排障，随后物理删除。

### 17.2 状态机

```text
queued
  -> validating_data
  -> assembling_docx
  -> updating_fields
  -> validating_docx
  -> ready
  -> expired
```

任意处理中状态均可进入 `failed`。失败任务不能提供下载。

### 17.3 并发和幂等

- 前端提交后立即禁用重复生成按钮并显示任务状态。
- 后端对同一用户、同一年度检查的相同运行中请求返回已有任务，而不是重复启动。
- 新任务开始后允许桥梁数据继续被其他流程修改，但该任务只使用开始时形成的临时 `ReportContext`。
- 模板替换和停用不影响已经复制模板并进入执行阶段的任务。
- Docx Builder 可以并行准备文档，但同一台字段更新主机上的 Word/WPS 更新步骤进入一个全局 FIFO 队列，并发上限固定为 1；任务页面显示“等待字段更新”而不是误报卡死。

队列已实现（`bridge_report_tools.reports.field_update_queue`），要点：

- **用票号而不是互斥锁。** `threading.Lock` 不保证先来先服务，排在后面的任务可能被后到的请求反复插队，等待时长无法预期，界面也说不出“你前面还有几个”。票号队列两者都能保证。
- **探测也排队。** `probe()` 同样会 `DispatchEx` 起一个 Word，超时清理同样走进程差集。凡是起 Word 的动作都必须串行，否则探测超时会杀掉别人正在跑的更新。代价是另一份报告更新域时，§16 第 9 条的预检会等在队列里——那时本来也轮不到你用 Word。
- **排队上限 1800 秒**，超时抛 `REPORT_FIELD_UPDATE_QUEUE_TIMEOUT`，且放弃者的票号会被跳过，不会把后面的人永久挂住。不设无限等待：一个卡死的更新不该拖垮整条队列。
- `UpdateOutcome` 分别记录 `queued_seconds` 与 `elapsed_seconds`，供 §25.3 的规模验收取数。

**为什么串行是正确性要求而不只是性能取舍。** `_run_isolated` 的超时清理靠“动手前后的 `WINWORD.EXE` 进程差集”认领自己起的实例。两次更新的时间窗一旦重叠，A 的差集里就会混进 B 刚起的 Word——A 超时会把 B 正在干活的进程一起杀掉，B 那份报告莫名失败且日志上看不出所以然。队列从根上消除这个可能。

### 17.4 删除和文件引用语义

报告模块增加表后，必须同步修改 `InspectionYearDeletionRepository`、`BridgeDeletionRepository`、`ImportRecordDeletionRepository` 以及归档文件引用检查，不能只依赖数据库外键报错：

- `inspection_report_settings`、`inspection_report_personnel`、`inspection_report_equipment` 随所属 `inspection_years` 级联删除，并进入年度和桥梁删除预览计数；
- 运行中的 `report_generation_jobs` 阻断年度或桥梁删除，用户取消或任务终态化后才可继续；终态任务行随年度级联删除；
- 报告配置和任务不直接依赖 `import_records`，删除导入记录时不删除报告配置，但仍须重新通过第 10.1、13 节的一致性检查；
- `report_templates.file_id` 对 `archived_files` 使用 `ON DELETE RESTRICT`，模板当前文件必须计入归档文件引用；
- 替换或删除模板时，先原子更新/删除模板引用，再仅清理已经没有任何业务引用的旧模板文件；停用模板不删除文件；
- 人员、设备被年度分配引用后不得硬删除，只能停用，年度分配随年度删除。

## 18. Docx Builder

Python Docx Builder 按以下顺序工作：

1. 在任务临时目录复制当前模板。
2. 解析并校验标量占位符、内容锚点和模板配置。
3. 按文档顺序替换标量和锚点。
4. 生成病害表、照片页、评定表、历史对比和结论。
5. 保留原模板的段落样式、表格样式、页眉页脚、分节、页面尺寸和方向。
6. 标记允许更新的 Word 字段为需要刷新。
7. 保存中间 `.docx`。

生成器对模板段落或表格单元格的修改必须尽可能保留原有 run 样式。插入动态内容时只使用模板中约定的命名样式，不在代码中散落字体、字号和边距常量。

### 18.1 分页与表格排版（2026-09-08 / 09-09 定案）

**每章另起一页**：`Heading 1` 样式带 `pageBreakBefore`，不在生成器里逐章插分页符。模板作者加一章就自动生效，生成器也不必知道哪儿该断页。

已经位于页首的标题不会因此多出一页空白——Word 对页首段落的 `pageBreakBefore` 是空操作。第 1 章和第 6 章分别位于正文节和附录节的首页，实测六章标题全部落在页首，正文页数 101 → 103（只有原先接在上一章后面的两章被推到了新页）。

| | 字体 | 字号 | 字重 | 对齐 |
|---|---|---|---|---|
| `报告表头` | 宋体 | 五号（10.5pt） | 加粗 | 水平居中 |
| `报告表格文字` | 宋体 | 五号（10.5pt） | 常规 | 水平居中 |

两个样式都取消段前段后间距、行距单倍——十列的病害表否则会被撑得很高。

**垂直居中在代码里设，不在样式里。** 它是单元格属性（`w:vAlign`）而不是段落属性，命名样式表达不了；合并单元格本来就垂直居中，普通单元格若顶端对齐，两者并排会明显错位。这是"版式常量不散落在生成器里"的唯一例外，理由是 OOXML 的属性归属，不是图省事。

## 19. Word/WPS 字段更新

定义统一接口 `OfficeFieldUpdater`，至少提供：

```text
probe()
update_fields(input_docx, output_docx)
```

实现优先级：

1. `MicrosoftWordUpdater`；
2. `WpsWriterUpdater`。

第一版的部署边界是本地 Windows 桌面应用：字段更新 worker 必须运行在已经登录的交互式用户会话中，目标主机安装 Microsoft Word 或 WPS Writer。不得把 Office 自动化直接部署在 Windows Service、无桌面会话或通用 Linux 服务端。若未来改为服务端部署，需要替换字段更新实现，不能沿用本节假设。

更新器由独立桌面 worker 在隐藏窗口中打开中间文档，更新目录、页码和总页数，保存后退出。同一主机字段更新并发固定为 1。生成服务必须：

- 设置超时；
- 确保异常时关闭本次启动的文档进程和临时文件；
- 不终止用户已经打开的 Word/WPS 实例；
- 记录选择了哪个更新器及失败阶段；
- 禁止更新器执行模板宏或访问外部文件关系。

Word 不可用时尝试 WPS。两者都不可用或更新失败时任务进入 `failed`，不交付目录页码未知的半成品。

两条真机实测的约束，写在这里免得后人再踩：

1. **遍历故事区不能串 `NextStoryRange`。** WPS（对外自称 Microsoft Word 12.0）在页眉页脚那条链上不收敛，同一个页眉无限重复，域更新永远跑不完——21MB 的报告 900 秒超时都刷不完，改成"各顶层故事区 + 按节取页眉页脚"后 8.2 秒完成。多节且每节带页眉页脚的文档才暴露得出来，单节文档测不到。
2. **超时清理不能等线程。** `ThreadPoolExecutor` 的 `with` 语句退出时会 `shutdown(wait=True)`，等那个已经超时的 COM 调用返回；杀进程没杀到时（例如 WPS 抢注了 `Word.Application`，按 `WINWORD.EXE` 找 PID 一个都找不到）就永远等下去，超时异常抛了却传不回调用方。必须 `shutdown(wait=False)`，并且认领进程时两个映像名都要看。误伤用户实例仍由 PID 差集拦住。

## 20. 最终 DOCX 校验

字段更新后至少校验：

1. 文件是结构完整的 OOXML ZIP。
2. 不残留 `[[REPORT:...]]` 锚点。
3. 不残留未知 `{{...}}` 占位符。
4. 必要内容块已经生成。
5. 图片关系完整，媒体文件可读取。
6. 只存在允许的 Word 字段和内部关系；目录更新后由 Word/WPS 自动生成的 TOC 内部 `PAGEREF`、`HYPERLINK` 和内部书签属于明确白名单，TOC 之外的独立同类字段仍按第 7.6 节拒绝。
7. 页面分节、纸张方向和页眉页脚关系仍存在。
8. 文件可以再次被解析器打开。
9. 输出路径位于当前任务临时目录中。

最终文件名：

```text
{报告编号}{行政区}{路线编号}{路线名称}{桥梁名称}定期检测报告（{综合等级}）.docx
```

示例：

```text
Q202604001-JZ-113太和区S320大养线百股大桥定期检测报告（2类）.docx
```

这是第一版有意采用的规范化文件名，不复现两份参考报告中连字符和行政区缺省位置的历史差异，也不由模板自定义。缺失的可选片段直接省略，不留下 `null`、连续占位符或多余空格。只在文件名层面清理 Windows 非法字符，不修改文档内部业务值。

提供新增、编辑、查看、启用和停用，并显示检定有效期状态。被引用设备不允许硬删除。

### 21.4 年度检查：生成报告

页面分为：

1. **生成条件**：显示正式病害、正式评定、模板、照片和字段更新环境状态，并给出阻断项处理入口。
2. **报告配置**：选择模板、历史检查、人员及角色、设备及用途。
3. **内容摘要**：显示有病害构件数、病害记录数、照片数、对比条数差、当前等级以及空白内容块。
4. **当前报告**：创建任务、显示阶段、下载、重新生成和错误信息。

**只呈现「当前报告」一个状态，不列历史。** 系统不保存报告版本（§17.1）：上一次生成的临时文件到期就删了，摆一张历史表会让人以为那些旧文件还能下。界面上永远只有一个状态——没生成过、正在生成、可下载、失败、已过期，成功文件过期后只显示「重新生成」。

接口相应地只给「当前那一个」：`GET /api/inspection-years/{id}/report-jobs/current` 返回最近的那个任务或 `null`，没有列表接口。终态任务行在库里还留 7 天，那是给排障用的，不是给界面翻的。

### 21.5 桥梁总览：桥梁概况

桥梁工作台总览页的一张卡片，管理员可编辑，普通用户只读。报告 §1.1 的那几段叙述和附录2 卡片的
十几格都从这里取数——档案不录，报告那一节就是空的，所以录入入口要和报告在同一条路上看得见。

两条纪律：**只显示已经录了的项**，没录的不占位、不写「未知」，跟报告的规矩一致；**保存是整体
覆盖**，表单一打开就装满当前值，清空某一项就是把它从档案里去掉，报告里对应的那半句话也随之不出。

它取代了原来的「最近动态」卡片：那张卡片列的是最近三次年度检测，而年度检测本来就有自己的入口。

#### 实测结果（2026-09-11，百股大桥 2024 / 2026 两个年度）

| | 常规规模（2024） | 大型规模（2026） |
| --- | --- | --- |
| 正式病害 / 有病害构件 | 362 条 / 337 个 | 430 条 / 376 个 |
| 页数 / 图片 | 59 页 / 166 张 | 101 页 / 455 张 |
| 装配 | 51.8 s | 92.7 s |
| 刷域（Word 里） | 8.8 s | 10.7 s |
| 刷域排队 | 0 s | 0 s |
| 生成总时长 | 68.6 s | 110.5 s |
| 输出文件 | 5.9 MB | 21.3 MB |
| Python 峰值工作集 | 123 MB | 182 MB |
| Office 打开 | 0.8 s | 1.0 s |

**两份数据都来自同一座桥。** 库里目前只有百股大桥的三个年度，没有 34 页那一档的数据，所以「常规规模」实测是 59 页 / 166 张，比设计里的参照规模大。大型那一档 101 页 / 455 张与参照规模（120 页 / 470 张）基本相当。要真正覆盖 34 页那一档，得先把第二份正式报告的数据导进来。

**并发（两个请求同时提交）**

- **任务层是串行的**：C++ 执行器只有一条工作线程，两个任务严格一前一后（每 0.5 秒采样一次，同时处在「排队之后」的采样次数为 0）。这比 §17.3 要求的更严——那里只要求刷域那一步串行，装配允许并行。目前不并行是有意的：装配一份大报告要一分半，同时跑两份只会一起堵在下游那道单并发的队列前面，还多占一份内存和磁盘。
- **刷域队列确实在排队**：直接对 `/reports/fields/update` 并发打两发，后到的那发等了 6.89 秒，先到的那发在 Word 里用了 6.9 秒，两段不重叠；等待时长由 `queued_seconds` 如实报出，界面据此显示「等待字段更新」。
- **超时只杀本次新起的进程**：先起一个「用户的」实例并打开一份文档，再故意让一次刷域超时（给 1 秒刷 21 MB 的报告）。超时按预期抛出并强杀了本次新起的 2 个进程；「用户的」实例仍在运行、文档仍可访问，也没有留下半成品文件。

**Word / WPS 双端（§26 第 4 条）只验到一半。** 本机 `Word.Application` 与 `KWPS.Application` 两个 ProgID 都注册在 WPS 名下（WPS 抢注了 Word 的 CLSID），没有装真正的 Microsoft Word。两个 ProgID 各打开两份成品，表数、图数、节数与 python-docx 读到的完全一致，文档名没有被改成「[已修复]」，即 WPS 侧不提示修复。**Microsoft Word 侧待在装有真 Word 的机器上补测。**

## 26. 验收标准

1. 管理员能够维护多套当前模板，并设置一个默认模板。
2. 普通用户生成时能选择任意已启用模板。
3. 更换模板顺序后，报告内容严格跟随锚点位置，不跟随生成器硬编码顺序。
4. Word 和 WPS 均能打开生成结果，且不提示修复文档。
5. 病害表只包含有病害的实际构件，数量与正式病害一致。
6. 报告图号按病害表行序在每个结构部位内从 1 连续递增；病害表「照片编号」列与图题号码逐条一致；图片不裁剪、不拉伸。两条导入路（照片有编号与无编号）产出的报告在这一点上没有差别。
7. 对比按来源病害去重，只表达记录条数增加、减少或持平，并显示能力限制说明；每个部位的对比出现在该部位自己的小节内。
8. 正式评定表和附录1 与当前有效评定运行一致。
9. 第 3 章、各部位「病害成因分析」小节按首个标准模板保持空白；两张附录卡片版式齐全，没有数据来源的格子留空。
10. 第 5 章结论内容可由正式数据和固定规则完全解释。
11. 目录、页码、横竖版分节和文件名正确。
12. 系统不永久保存生成的报告文件；临时文件过期后可以重新生成。
13. 大型真实规模报告能够在设定的资源和时间限制内完成，且 Word/WPS 打开正常。
