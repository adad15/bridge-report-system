## 缺陷一：切换页面就重新加载整份台账（已修）

提交：`8020514`（fix(inventory): move the inventory off the overview page onto its own route）

### 现象

从桥梁总览页切到"年度检测"或"构件病害档案"，再切回总览页，台账区域重新显示"加载中…"并等待数秒。每次切回都要重来一次。

### 根因

`ComponentInventoryEditor` 直接挂在 `BridgeOverviewPage` 上，而总览页是 `/bridges/:bridgeId` 这条路由的 index 页：

```
/bridges/:bridgeId              → BridgeOverviewPage   ← 台账挂在这里
/bridges/:bridgeId/inspections  → InspectionWorkspacePage
/bridges/:bridgeId/components   → ComponentArchivePage
```

React Router 在离开路由时会**卸载**组件，组件内 state 随之丢弃；切回来重新挂载，`useEffect(() => { void load(); }, [load])` 再次触发，整份台账重新拉取。系统没有任何缓存层，所以每次挂载都是一次完整加载。

两个因素叠加放大了影响：

1. 该桥台账有 4941 条构件，原始数据约 2.4 MB，序列化成 JSON 后更大，需重新传输、解析并建立约 4941 条前端状态；
2. 总览页是点进一座桥的**落地页**——只想看"最新结论"或"待办事项"的人，也必须先等台账加载完。

### 修复

台账改为独立路由 `/bridges/:bridgeId/inventory`（新增 `ComponentInventoryPage`），并加入工作区标签导航（桥梁概览 / **构件台账** / 年度检测 / 构件病害档案）。总览页只保留一个入口链接，**不再加载任何台账数据**。

选择这个方案而非加缓存，理由有二：

- 加缓存只是把等待藏起来，台账仍然在每个访问者的必经路径上；
- 缓存需要处理失效（生成、编辑、确认后都要让缓存过期），否则会显示过期台账，正确性风险高于本方案。

对"切走再切回仍会重新加载台账页本身"这一点：本方案没有消除它，只是把代价从落地页移到了主动进入的工具页。**该遗留问题已由后续提交 `92d236c` 解决**——改为再挂载时先渲染缓存、后台重新校验，见 [2026-07-23-workspace-navigation-caching.md](2026-07-23-workspace-navigation-caching.md)。

## 缺陷二：导入 Word 后弹窗长时间停在"处理中…"（已诊断，未修）

### 现象

上传 Word 资料后，弹窗停在"正在解析病害、照片和评分…"与"处理中…"，长时间没有变化，看上去像卡死。

### 已查明的事实

数据库中导入记录的实际耗时：

| 导入记录 | 状态 | 耗时 |
| --- | --- | --- |
| DRJL-000006（7 月 21 日） | 待校对 | **14 秒** |
| DRJL-000009 | 待校对 | **6 分 39 秒** |
| DRJL-000010（现象发生时那次） | 待校对 | **42 秒** |

结论：**解析没有卡死，全部最终成功了**，但耗时从 14 秒涨到分钟级。期间该桥构件数从几十条增长到 4941 条，两者高度相关，但**具体是哪一段变慢尚未定位**（用户要求暂停排查）。

一个可排除项：python-tools 服务（`127.0.0.1:18081`）在现象发生时 `/health` 20 秒无响应，一度怀疑是它挂起；但该进程累计 CPU 仅 22 秒（已运行 4 小时余），并非在做重计算，且随后恢复正常。后端进程同期累计 CPU 95 秒，耗时更可能集中在后端侧。

### 与之独立的前端缺陷

`ImportWordDialog` 用**单个 HTTP 请求**等待整个解析完成：

```ts
setPhase("parsing");
await parseWordImport(...);   // 无轮询、无超时、无进度
onCompleted(importRecordId);
```

由此产生两个问题，且与解析快慢无关：

1. 解析耗时数分钟时，用户只看到一个不动的"处理中…"，无从判断是在跑还是已经死了；
2. 连接一旦中断（超时、代理、后端重启），服务端可能**已经解析成功**，弹窗却永远停在"处理中…"——前端没有任何机制去查询真实状态。

### 待办

1. 定位解析耗时随构件数增长的具体环节（疑似后端匹配/持久化路径，需实测确认，不要凭猜测改）；
2. 弹窗改为提交后轮询导入记录状态，而非依赖单个长请求的返回；补充超时与进度反馈。

两项均未开始。

## 经验

1. **落地页不该挂重量级组件。** 判断标准不是"这个信息重不重要"，而是"不需要它的人是否也必须等它"。
2. **路由卸载即状态丢失。** 无缓存的前提下，"切回来重新加载"是 React Router 的默认行为而非缺陷；要避免，只能让重量级内容不在高频路径上，或显式引入缓存并承担失效的复杂度。
3. **长耗时操作不能用单个请求的返回作为完成信号。** 请求成功与操作成功是两回事：连接断了不代表服务端没做完，而前端若没有独立的状态查询手段，就永远无法自我纠正。
