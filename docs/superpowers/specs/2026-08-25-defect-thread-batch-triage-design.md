# 2026-08-25 设计：病害线索批量整理

- 状态：**设计完成，待实施**（v2，已按 2026-08-25 评审意见修订）
- 相关模块：06 构件病害档案（线索整理页）
- 起因：百股大桥 1197 条未绑定观测，现有逐条整理流程实际不可用
- 下游：模块 07 跨年病害对比
- 评审记录：`2026-08-25-defect-thread-batch-triage-design-review.txt`

## 1. 背景

模块 06 的线索整理页按"一条观测一张卡"设计，让人为每条正式观测选择归属线索。
在真实数据上这套流程走不通。

百股大桥当前状态（2024 / 2025 / 2026 三个年度均已入库）：

| 指标 | 数值 |
| --- | ---: |
| 未绑定观测 | 1197 |
| 涉及构件 | 409 |
| 已有线索 | **0** |
| 已绑定观测 | **0** |

三个毛病叠在一起：

**其一，候选永远转圈。** 每张卡片 mount 时各发一个 `thread-suggestions` 请求
（`ThreadBindingCard.tsx`）。1197 张卡片同时发 1197 个请求，浏览器每域名 6 条连接，
排不完，界面上每张卡都停在"正在加载候选…"。

**其二，冷启动时候选注定为空。** 候选推荐的是**已有线索**，而线索数为 0。就算请求
全部返回，也一条都推不出来。人只能逐条点"创建新线索" 1197 次——这个机制把自己锁死了：
它要到第 2、第 3 次遇到同一处病害时才有价值，而第 1 次的成本全压在人身上。

**其三，卡片认不出是哪个构件。** 表头渲染 `structure_part｜component_type`，也就是
"下部结构｜盖梁"。实际上那些卡分别是 `1#墩盖梁`、`10#墩盖梁`、`11#墩盖梁`……
`business_component_code` 就在接口返回里，只是没渲染。人无从判断，也就无从整理。

## 2. 目标、非目标与信任模型

### 2.1 目标

1. 让 1197 条观测能在合理时间内整理完，且线索关系准确到可以支撑报告叙述。
2. 同一套机制既覆盖冷启动（线索为 0，批量新建），也覆盖每年增量（批量绑定已有线索）。
3. 修掉现有整理页的构件标识缺失与候选请求 N+1。

### 2.2 非目标

1. 自动落库——任何线索的建立或绑定都必须由人显式发起。
2. 生成病害发展、减轻、修复等对比结论（模块 07）。
3. 修改任何年度事实（标度、尺寸、照片、评分）。
4. 线索命名的批量编辑。

### 2.3 信任模型：批次级抽样确认

**采用抽样确认，不要求逐组查看。** 完整表述：

> 每个**批次**必须经过人工确认；系统必须在组批之前排除全部已知异常；用户可以展开
> 批次、逐组查看并剔除个别组。系统**不宣称**每一个组都被人逐一看过。

这是一次有意的取舍。批次的语义是"同一个判断重复 N 次"——"这 166 个铰缝，各自三年的
渗水泛碱记录是同一处病害"是一句话的判断，不是 166 句。要求逐组勾选会把决策数打回
481，批量也就失去了意义。

安全边界靠三件事守住，而不是靠"看过每一组"：

1. **异常必须先被排除。** 语义上有任何歧义的组（第 4.4 节四类）一律不进批次，
   走人工簇。批次里只留语义单一的组。
2. **批次键足够窄。** 部位、部件类型、归一化病害类型、归一化位置、年份集合全部相同
   才算同一批。同一批内各组的差别只有构件编号。
3. **可展开可剔除。** 用户随时能翻完全部 481 组并剔掉任何一组，剔掉的落入人工簇。

对应地，第 2.3 节旧版"不允许任何一组在没有人看过的情况下落库"的表述作废——它与
批次界面自相矛盾，且无法验收。

### 2.4 用途约束

整理出的线索有两个下游用途：写下一年度报告的"病害发展情况"，以及按处查看历史档案。
前者更严，压着后者走：**宁可漏归让人补，也不能错归让报告写出错误的发展结论。**
这条约束的落点是第 4.4 节的异常排除，而不是要求人看遍每一组。

## 4. 概念模型

```
批次 batch  ── 长相相同的一组"组"，一次确认整批落库
  └ 组 group ── 未来的一条线索：同一构件上同一处病害的历年观测
      └ 观测 observation ── 某年度的一条记录
```

### 4.1 组的键

`(bridge_component_id, normalized_defect_type, normalized_defect_location)`

**病害类型与位置都要归一化。** 归一化复用 `normalize_suggestion_text`
（`backend-cpp/src/review/ThreadSuggestions.cpp`）：去空白、全角转半角、中文标点归一、
ASCII 转小写。候选算法本来就对两者都做归一化，组键只归一化位置会造成
"候选认为相同、批量归组认为不同"的分裂。

组保留病害类型与位置的**原文**，用于界面展示和新建线索时写入数据库。

**空位置相等是一条额外的业务规则，不是归一化的自然产物。** 候选算法的 `location_exact`
要求双方位置**非空**（`!thread_location.empty() && !observation_location.empty()`），
复用 `normalize_suggestion_text` 得不到"空位置相等"的行为。批量归组必须显式规定：

> 归一化后两侧位置**都为空**时，视为位置相等。

否则 166 个无位置铰缝会各自散成孤组。

`null` 与空字符串在归一化后统一为同一个空值，键上不作区分。

### 4.2 批次的键

`(structure_part, component_type, normalized_defect_type,
  normalized_defect_location, year_set, action)`

- **`structure_part` 进键**：像"其他""附属构件"这类宽泛的部件类型可能出现在不同结构
  部位。本桥台账中 `component_type` 未出现跨分部的情况（已核实），但一座桥的台账不构成
  通用保证，而加上这一维成本为零。
- **`year_set` 进键**：`{2024,2025,2026}` 与 `{2025}` 是两种完全不同的判断，
  不该混在一屏里让人一起点。

### 4.3 动作类型

| 动作 | 判定 | 落库行为 |
| --- | --- | --- |
| `create` | 组没有精确命中任何已有线索 | 新建一条线索，绑上组内全部观测 |
| `bind` | 组精确命中**恰好一条**已有线索 | 把组内观测绑到该线索 |

**"精确命中"的口径与组键一致**：已有线索的 `bridge_component_id`、归一化
`defect_type`、归一化 `defect_location` 三项与本组完全相同（空位置按 4.1 的规则相等）。
位置相近但不相同**不算命中**，走 `thread_location_overlap` 交人工判断。

冷启动时全是 `create`；按上面的模拟，明年 84% 是 `bind`。

**一个 `bind` 批次覆盖多个构件，因此会绑定到多条不同的线索**——线索属于具体构件，
不存在"整批绑到同一个 BHXS 编号"。界面表述见 7.3。

### 4.4 不进批次的四类

挑出来进人工簇，各带原因码：

| 原因码 | 情形 | 当前数量 |
| --- | --- | ---: |
| `multiple_in_year` | 组内某年出现多条观测 | 3 组 / 14 条 |
| `group_location_overlap` | 同构件同类型下存在**另一个未绑定组**位置文字互相包含，相关组全部踢出 | 4 对关系 / 7 组 |
| `thread_location_overlap` | 同构件同类型下存在**已有线索**位置文字与本组互相包含但不相等 | 当前 0（增量场景才会出现） |
| `ambiguous_thread` | 组精确命中多于一条已有线索 | 当前 0 |

`thread_location_overlap` 是评审补出来的增量场景漏洞。举例：

```
未绑定观测位置：大小里程侧
已有线索位置：  大小里程侧及左悬臂底部
```

两者不精确相等，若 overlap 只检查未绑定组之间的关系，这一组会被判成 `create`，
凭空造出一条与已有线索疑似重复的线索。必须同时对同构件已有线索做包含检测。

`group_location_overlap` 的实例说明为什么必须人判：

```
16#墩盖梁 · 受渗水侵蚀:  "大小里程侧"(2024)  ／  "大小里程侧及左悬臂底部"(2025,2026)
    → 几乎肯定是同一处渗水扩展了范围，应当并成一条线索

19#跨桥面铺装 · 网状裂缝: "右侧行车道"(2026)  ／  "右侧行车道19#墩处"(2026)
    → 同一年两条，多半是两处，不应合并
```

四类合计当前 10 组 / 23 条观测，剩下 481 组 / 1174 条观测落在 144 个批次里。

人工簇的响应必须携带**相关对象的完整标识**：相关组的组键、相关已有线索的 `id`、
`thread_name`、`system_number`，否则人无从判断该合还是该分。

## 5. 接口设计

三个端点，读写分开。

### 5.1 批次摘要

```
GET /api/bridges/{bridge_id}/thread-batches
```

返回：

- `snapshot_id`：本次归组快照的标识（见 5.4）；
- `batches[]`：批次摘要——`batch_id`、`action`、`structure_part`、`component_type`、
  `defect_type`（原文）、`defect_location`（原文，可为 null）、`year_set`、
  `group_count`、`observation_count`、`sample_groups`（2–3 条，仅含构件标识与逐年缩略信息）；
- `manual[]`：人工簇——组键、原因码、相关组与相关已有线索的标识。

当前 144 条摘要，几 KB。**绝不在这里返回全部观测**——一次性推 1197 条正是现有页面的死法。

### 5.2 批次明细

```
GET /api/bridges/{bridge_id}/thread-batches/{batch_id}/groups?cursor=&limit=
```

展开批次时才拉。返回组及组内逐年观测——含照片、尺寸、位置原文、标度。分页。

### 5.3 批量落库

```
POST /api/bridges/{bridge_id}/thread-batches/apply

{
  "snapshot_id": "...",
  "batch_id": "...",
  "excluded_group_keys": ["...", "..."],
  "idempotency_key": "..."            // 客户端生成，重试时保持不变
}
```

**请求只表达用户的选择，不携带业务事实。** 这是本次评审最重要的修正：

- 旧设计让客户端提交 `bridge_component_id`、`defect_type`、`defect_location` 和全部
  观测 ID——服务端若信任这些，前端一个缺陷就能把跨桥、跨构件、跨类型的观测塞进同一组，
  或让同一条观测出现在两个组里，绕过所有归组语义写出错误关系；
- 更实际的问题是**客户端根本拿不到这些数据**：明细是分页的，用户不展开就点"确认这
  166 组"时，前端手里只有摘要和 3 条样例，构造不出 498 条观测的清单。

改为提交 `batch_id` + 排除清单后，两个问题一起消失：服务端在事务内从数据库重新归组、
自己算出最终清单，客户端只需要说"这一批，除了这几组"。

**没有客户端拆分。** 旧设计一边写"整批一个事务全成或全败"，一边写"超过 500 组由前端
拆分"——拆开就不再原子。服务端设上限（按观测数与请求体大小），超限直接拒绝并说明；
当前最大批次 166 组 / 498 条观测，离任何合理上限都很远。

### 5.4 快照与并发

`snapshot_id` 是本次归组结果的指纹：覆盖参与归组的全部观测的 `id` 与 `updated_at`，
以及全部相关线索的 `id` 与 `updated_at`。

apply 时服务端重新归组并重算指纹：

- 指纹一致 → 用户看到的就是即将处理的；
- 指纹不一致 → 返回 `snapshot_stale`，要求刷新后重做。

这取代了旧设计里逐条 `updated_at` 令牌的作用，并且与分页明细天然兼容——客户端不需要
持有任何一条观测的令牌。

`batch_id` 的编码规则见第 11 节（P2 未决项）。在此之前，`batch_id` 视为
**仅在同一 `snapshot_id` 内有效的不透明标识**；换了快照就必须重新读取批次列表。

## 6. 落库事务

### 6.1 三阶段：批量锁定 → 完整校验 → 批量写入

不允许"处理一组就写一组"。那样最后一组失败时虽然能回滚，却只能报出第一个错误，
兑现不了"返回失败明细"的承诺。

1. **收集与排序**：服务端按 `batch_id` + 排除清单从数据库重新归组，得到最终观测集合；
   去重后**按 UUID 固定顺序**排列。固定锁序同时降低两个重叠批量请求互相死锁的概率。
2. **批量锁定**：一次或分块 `SELECT ... FOR UPDATE`，锁定全部观测（以及 `bind` 涉及的
   目标线索）。避免 498 次独立 SQL 往返。
3. **只读校验**：对全部组执行第 6.2 节的校验，**收集全部错误而非遇错即返**。
4. **有错即回滚**，返回完整错误列表。
5. **全通过后批量写入**：批量创建线索、批量绑定观测。
6. **集中重算** 涉及线索的 `first_seen_inspection_id` / `latest_seen_inspection_id`。

### 6.2 服务端必须重新验证的事实

现有 `validate_observation_state`（`DefectThreadRepository.cpp`）的四项逐观测校验
一条不减：年度 `is_current` 且已确认、观测是正式事实（已确认/已修改）、
未被模块 07 已确认对比引用、以及并发校验（此处由 `snapshot_id` 承担）。

在此之上，**必须从数据库重新计算并验证组的业务含义**：

| 校验项 | 失败码 |
| --- | --- |
| 全部观测属于 URL 指定的 `bridge_id` | `observation_bridge_mismatch` |
| 每组观测属于同一 `bridge_component_id` | `group_component_mismatch` |
| 每组观测的归一化病害类型一致 | `group_defect_type_mismatch` |
| 每组观测的归一化位置一致 | `group_location_mismatch` |
| 每组每个年度至多一条观测 | `group_multiple_in_year` |
| 最终清单内无重复观测 ID | `duplicate_observation` |
| `create` 组当前确实没有精确匹配线索 | `unexpected_existing_thread` |
| `bind` 组当前恰好精确匹配一条线索 | `bind_target_not_matched` |
| 目标线索与观测同桥、同构件 | `thread_component_mismatch` |
| 请求的 `action` 与服务端重算结果一致 | `action_mismatch` |

即使清单由服务端自己算出，这些校验也要执行——它们同时是防御归组代码自身缺陷的护栏，
并且是第 12 节测试的断言对象。

### 6.3 幂等：判定顺序必须先于并发校验

旧设计要求"完整复用乐观并发校验"又要求"重复提交返回已完成"，这两条在顺序上冲突：
第一次成功后绑定操作会更新 `updated_at`，重试携带的快照指纹必然过期，服务端会先返回
`snapshot_stale`，根本走不到"已完成"的判定。

固定处理顺序：

1. 按固定顺序锁定请求涉及的全部观测；
2. **先判已完成**：组内全部观测是否都已绑定到**同一条**、且其键与本组完全一致的线索；
3. 全部组都符合 → 返回 `already_completed`（HTTP 200），**允许过期快照**；
4. 不是已完成状态 → 再校验 `snapshot_id`；
5. 部分观测已绑、绑到了别的线索、或组内观测分散在多条线索上 → 返回明确冲突
   （`partially_bound` / `bound_to_other_thread` / `thread_split_conflict`），
   **不得误判为已完成**。

`idempotency_key` 在首版随请求上送并记入审计，但判定仍以业务状态为准。若实现中发现
分支过多难以覆盖，可升级为服务端请求表回放（P1 备选，见第 11 节）。

### 6.4 空位置

现有单条创建接口用 `non_empty_string_member` 取 `defect_location`
（`DefectThreadRoutes.cpp:63`），**位置为空直接拒绝**。166 个无位置铰缝组按现有规则
一条线索都建不出来。批量接口必须放开，并明确写法：

- 批量创建**接受空位置**；
- 数据库存 `null`，不转成空字符串（`defect_threads.defect_location` 本就可空）；
- 归组与精确匹配时，`null` 与空字符串归一化后统一视为同一个空值；
- **默认线索名**：位置为空时用 `病害类型`（不带分隔符），非空时沿用现有
  `病害类型｜位置`。旧默认逻辑在空位置下会产出 `渗水泛碱｜` 这种带悬空分隔符的名字。
- **单条创建接口同步放开空位置**，与批量保持同一规则；否则同一份数据经两条路径会得到
  不同结果，而人工簇用的正是单条路径。

### 6.5 线索字段

- `thread_name`：按 6.4 的规则生成。批量场景不提供命名入口——166 条不可能逐个起名。
- `confirmation_status`：写 `人工已确认`。批次是人确认过的。
- `first_seen_inspection_id` / `latest_seen_inspection_id`：由现有 `recompute_thread_span`
  计算，批次写入后集中重算。

**已知缺口**：系统当前**没有修改 `thread_name` 的接口或界面**（`DefectThreadRoutes.cpp`
只注册了创建与绑定两个处理器）。因此批量创建的默认名必须是可长期使用的名字，而不是
临时占位。单条线索改名能力列为 P2（第 11 节），在它落地之前不得在任何文案里暗示
"事后可改"。

## 7. 界面

### 7.1 批次视图

整理页从"一观测一卡"改成"一批次一卡"（当前 144 个），按**覆盖观测数降序**排列——
先消掉 166 个铰缝那种大批次，进度一次走掉四成。

```
铰缝 · 渗水泛碱 · （无位置）                    [新建线索]
2024 → 2025 → 2026 连续三年
166 个构件 · 498 条观测

  1#铰缝    [2024照片][2025照片][2026照片]
  2#铰缝    [2024照片][2025照片][2026照片]
  3#铰缝    [2024照片][2025照片][2026照片]
                              …还有 163 个

  [确认这 166 组]  [展开逐组核对]  [暂不处理]
```

默认摊开三条样例，**逐年横向并排**——这是"写病害发展"最需要的视角。

展开则分页列出全部组，每组一行带勾选框，可把个别不对劲的剔出去；剔掉的落入人工簇。
**跨页剔除的选择必须在整个批次范围内保持**，提交时一并作为 `excluded_group_keys` 上送。

### 7.2 提交前的确认

点击"确认这 N 组"时，先显示最终处理量——"将处理 166 组、498 条观测，其中排除 2 组"
——再提交。用户在没展开的情况下也能看到自己实际在批准多大范围。

### 7.3 `bind` 批次的目标线索

线索属于具体构件，一个跨多构件的 `bind` 批次会**分别绑定到多条线索**。因此批次卡片上
**不能**写成"将绑到：渗水泛碱｜大小里程侧（BHXS-000123）"——那是错的。

正确表述：

> 将分别绑定到各构件中精确命中的已有线索

展开明细后，每组各自显示对应线索的 `thread_name` 与 `system_number`。

### 7.4 人工簇，不是散装单条卡片

`group_location_overlap` 与 `thread_location_overlap` 描述的是**组与组之间的关系**。
把相关观测打散成"一观测一卡"会丢掉异常上下文，人根本判断不了两个位置该合还是该分。

人工区按**异常簇**组织：

- 同屏展示相关的全部位置组及其历年观测（`thread_location_overlap` 还要展示相关已有线索）；
- 明确显示异常原因与相关对象；
- 动作：**合并为一条线索** / **分别创建** / **绑定已有线索** / 暂不处理；
- `multiple_in_year` 把同一年的多条观测并排显示，供人判断是两处还是记了两遍。

**统计口径统一为"组"**：当前是 **10 组 / 23 条观测**。旧版"10 条逐条项"的说法作废——
若退化成逐观测卡片实际是 23 个操作项，与异常簇设计也不一致。

### 7.5 "暂不处理"的语义

首版语义：**仅当前页面会话内折叠，不写服务端，不做本地持久化**。

必须在界面上说清后果：刷新页面、离开再回来、换一台设备，被折叠的批次都会重新出现；
若期间提交过其他批次，归组会重算，`snapshot_id` 与 `batch_id` 都可能变化。

服务端持久化的"待处理/已跳过"状态列为 P2（第 11 节）。

### 7.6 顺手修掉的两个硬伤

1. **卡片渲染 `business_component_code`**：从"下部结构｜盖梁"改成"1#墩盖梁"。
   现有页面因为这一处从根上没法用。
2. **候选请求改为点开才发**：批次视图下不需要逐条候选——归组时已经把匹配算完了；
   人工簇保留候选，但不再 mount 即请求。

## 8. 响应约定

### 8.1 成功

HTTP 200：

```json
{
  "outcome": "applied" | "already_completed",
  "created_thread_ids": ["..."],
  "bound_observation_count": 498,
  "group_results": [
    { "group_key": "...", "bridge_component_id": "...",
      "thread_id": "...", "outcome": "created" | "bound" | "already_completed" }
  ]
}
```

`already_completed` 是**成功**，不是冲突——它表示"你要的状态已经达成"。

### 8.2 失败

HTTP 409（业务冲突）或 400（请求本身不合法）：

```json
{
  "code": "batch_apply_rejected",
  "message": "...",
  "errors": [
    { "code": "group_component_mismatch",
      "message": "...",
      "group_key": "...",
      "bridge_component_id": "...",
      "observation_id": "...",
      "reason_code": "..." }
  ]
}
```

整批失败时 `errors` 列出**全部**问题，不止第一个。

### 8.3 错误码

| 场景 | HTTP | code |
| --- | ---: | --- |
| 快照过期 | 409 | `snapshot_stale` |
| 批次在本快照内不存在 | 409 | `batch_not_in_snapshot` |
| 空的 `excluded_group_keys` 把整批排空 | 400 | `empty_group_selection` |
| 超过服务端上限 | 400 | `batch_too_large` |
| 组语义校验失败（10 项） | 409 | 见 6.2 表 |
| 幂等冲突（3 种） | 409 | 见 6.3 第 5 步 |

## 9. 验收标准

1. 打开线索整理页，144 个批次摘要在一次请求内返回，页面不再出现批量并发的候选请求。
2. 不展开批次直接确认"铰缝·渗水泛碱·三年"，166 条线索建成、498 条观测完成绑定；
   提交前界面显示过"将处理 166 组、498 条观测"。
3. 展开批次跨页剔掉任意两组后提交，被剔的组仍未绑定并出现在人工簇。
4. 归组数据在读取与提交之间发生变化时，提交被 `snapshot_stale` 拒绝且数据库无任何写入。
5. 提交成功后用同一请求重试，返回 `already_completed`，不产生重复线索。
6. 卡片显示构件业务编号，可区分 `1#墩盖梁` 与 `10#墩盖梁`。
7. `bind` 批次卡片不出现单一 BHXS 编号；展开后每组显示各自的线索编号。
8. 166 个无位置铰缝组批量创建成功，数据库中 `defect_location` 为 `null`，
   线索名为 `渗水泛碱`（不带悬空分隔符）；再次归组时这些组精确命中新建的线索。
9. 全部批次与人工簇处理完后，构件病害档案页顶部的"尚未归入跨年线索"提示消失。

## 10. 测试策略

### 10.1 归组规则（纯函数，无数据库）

参照 `ThreadSuggestions` 的组织方式：

- 同构件同类型同位置跨三年 → 归一组；
- 病害类型或位置只差全角空格、中文标点、ASCII 大小写 → 归一化后同组；
- **两侧位置都为空 → 视为位置相等**；`null` 与空字符串等价；
- 组内某年两条 → 踢出，标 `multiple_in_year`；
- 未绑定组之间位置互相包含 → **相关组全部踢出**，标 `group_location_overlap`；
- 未绑定组与同构件**已有线索**位置互相包含但不相等 → 踢出，标 `thread_location_overlap`；
- 精确命中两条已有线索 → 踢出，标 `ambiguous_thread`；
- 年份集合不同 → 不同批次；`structure_part` 不同 → 不同批次；
- 有命中 → `bind`，无命中 → `create`。

### 10.2 落库事务（数据库集成，复用 `test_defect_thread_repository.cpp` 夹具）

服务端不信任客户端的证明：

1. 请求指向的批次含跨桥观测 → 整批拒绝；
2. 组内混入跨构件观测 → 整批拒绝；
3. 组内归一化病害类型或位置不一致 → 整批拒绝；
4. 同一观测出现在两个组 → 整批拒绝；
5. `bind` 目标不是服务端重算出的精确匹配线索 → 拒绝。

幂等与并发：

6. 提交成功后携带过期快照重试 → `already_completed`；
7. 部分观测已绑、部分未绑 → 不误判为已完成，返回 `partially_bound`；
8. 观测已绑到同键但非预期目标的线索 → 返回 `bound_to_other_thread`；
9. 两个并发创建请求不会为同一批观测生成重复线索；
10. 两个观测集合交叉的批量请求不发生死锁（固定 UUID 锁序）。

写入正确性：

11. 整批 N 组一次落库：线索数、绑定数、`first_seen` / `latest_seen` 均正确；
12. 旧修订版年度的观测 → 拒绝；
13. 被模块 07 已确认对比引用的观测 → 拒绝；
14. 空位置批量创建后的数据库值为 `null`、默认名无悬空分隔符、再次精确匹配命中；
15. 任一校验失败 → 整批回滚且 `errors` 列出全部问题而非第一个。

### 10.3 前端（防回归）

16. 批次卡片渲染出 `1#墩盖梁` 而非"盖梁"；
17. **不展开就不发 `thread-suggestions` 请求**；
18. 分页浏览、跨页剔除与最终提交的 `excluded_group_keys` 保持一致；
19. `bind` 批次卡片不显示单一 BHXS 编号，展开后每组显示各自编号；
20. 提交前显示最终处理数量。

### 10.4 真实数据夹具

把百股大桥这份数据做成归组夹具，断言：

```
1197 条观测 → 491 组
   481 组进批次，落在 144 个批次里，覆盖 1174 条观测
     3 组 multiple_in_year
     7 组 group_location_overlap（4 对关系）
     0 组 thread_location_overlap / ambiguous_thread（冷启动无线索）
```

夹具必须携带**数据来源说明与内容指纹**（导出日期、导入记录编号、观测集合哈希）。
否则将来源数据变化时，只能看到数量断言失败，追不回是数据变了还是规则变了。

### 10.5 性能

不在设计中断言绝对耗时。可验证的目标：

- 最大真实批次（166 组 / 498 条观测）的 apply 在本地基准库上 P95 低于既定目标值；
- 事务时长不超过 HTTP 与数据库的超时配置；
- 锁定与更新必须是批量语句，不得退化成 498 次独立往返——用集成测试统计 SQL 往返次数。

## 11. 未决项（P2）

以下不阻塞首版，但要在实施计划里留位置：

1. **`batch_id` 的稳定编码。** 首版按 5.4 视为"仅在同一快照内有效的不透明标识"。
   若将来需要跨快照稳定，须明确：哈希算法与截断长度、批次键的规范化序列化、年份集合
   排序、`null` 与空字符串的编码区别、碰撞检测方式、以及 `batch_id` 失效时返回
   404 还是 409。
2. **"暂不处理"的服务端持久化。** 首版仅会话内折叠（7.5）。
3. **单条线索改名能力。** 当前完全缺失（6.5）。在它落地前，批量默认名必须可长期使用。
4. **`idempotency_key` 的服务端回放。** 首版仅记入审计，判定以业务状态为准（6.3）。
5. **性能基准的具体目标值。** 待首版实测后确定（10.5）。

## 12. 风险与取舍

**抽样确认的信任边界。** 见 2.3。曾考虑"高置信一键全建"（481 组直接落库），否决理由
是它等于对着报告精度要求闭眼签字——没有任何一处让人真正看过数据。也曾考虑"逐组勾选"，
否决理由是决策数打回 481，批量失去意义。取中间：批次必须确认、异常必须先排除、
展开与剔除必须随时可用。

**严格匹配会漏归。** `大小里程侧` 与 `大小里程侧及左悬臂底部` 不会自动并成一条。
这是有意的：宁可漏归让人补，也不能错归让报告写出错误的发展结论。当前这类只有
4 对关系、7 个组，放进人工簇的成本可以接受。

**归组不做物化。** 曾考虑在年度入库时算好批次存表，否决理由是构件改名、观测重绑、
年度修订都会让它过期，需要一整套失效重算逻辑。1197 条的实时归组是一个 `group by`，
不值得为一个还没出现的性能问题引入缓存失效。

**每年重复使用。** 本设计不含"入库后自动预归组"。年度入库那一刻线索状态可能仍在
变动，算早了容易过期；手动进入整理页触发即可。
