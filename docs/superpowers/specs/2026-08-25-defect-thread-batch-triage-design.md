# 2026-08-25 设计：病害线索批量整理

- 状态：**设计完成，待实施**
- 相关模块：06 构件病害档案（线索整理页）
- 起因：百股大桥 1197 条未绑定观测，现有逐条整理流程实际不可用
- 下游：模块 07 跨年病害对比

## 1. 背景

模块 06 的线索整理页按"一条观测一张卡"设计，让人为每条正式观测选择归属线索。
在真实数据上这套流程走不通。

百股大桥当前状态（2024 / 2025 / 2026 三个年度均已入库）：

| 指标 | 数值 |
| --- | ---: |
| 未绑定观测 | 1197 |
| 涉及构件 | 409 |
| 已有线索 | **0** |
| 已绑定观测 | **0** |

三个毛病叠在一起：

**其一，候选永远转圈。** 每张卡片 mount 时各发一个 `thread-suggestions` 请求
（`ThreadBindingCard.tsx`）。1197 张卡片同时发 1197 个请求，浏览器每域名 6 条连接，
排不完，界面上每张卡都停在"正在加载候选…"。

**其二，冷启动时候选注定为空。** 候选推荐的是**已有线索**，而线索数为 0。就算请求
全部返回，也一条都推不出来。人只能逐条点"创建新线索" 1197 次——这个机制把自己锁死了：
它要到第 2、第 3 次遇到同一处病害时才有价值，而第 1 次的成本全压在人身上。

**其三，卡片认不出是哪个构件。** 表头渲染 `structure_part｜component_type`，也就是
"下部结构｜盖梁"。实际上那些卡分别是 `1#墩盖梁`、`10#墩盖梁`、`11#墩盖梁`……
`business_component_code` 就在接口返回里，只是没渲染。人无从判断，也就无从整理。

## 2. 目标与非目标

### 2.1 目标

1. 让 1197 条观测能在合理时间内整理完，且线索关系准确到可以支撑报告叙述。
2. 同一套机制既覆盖冷启动（线索为 0，批量新建），也覆盖每年增量（批量绑定已有线索）。
3. 修掉现有整理页的构件标识缺失与候选请求 N+1。

### 2.2 非目标

1. 自动认定跨年观测是同一病害并直接落库——每一批都必须人工确认。
2. 生成病害发展、减轻、修复等对比结论（模块 07）。
3. 修改任何年度事实（标度、尺寸、照片、评分）。
4. 线索命名的批量编辑。

### 2.3 用途约束

整理出的线索有两个下游用途，取更严的那个作为设计约束：

- **写下一年度报告的"病害发展情况"**——归错组会让报告写出错误结论，因此不允许
  任何一组在没有人看过的情况下落库；
- **按处查看历史档案**——要求覆盖面尽量全，漏归会让档案缺少跨年脉络。

前者压着后者走：宁可把可疑的挑出来单独处理，也不能为了覆盖率放松确认。

## 4. 概念模型

```
批次 batch  ── 长相相同的一组"组"，一次确认整批落库
  └ 组 group ── 未来的一条线索：同一构件上同一处病害的历年观测
      └ 观测 observation ── 某年度的一条记录
```

### 4.1 组的键

`(bridge_component_id, defect_type, 归一化位置)`。

归一化复用 `normalize_suggestion_text`（`backend-cpp/src/review/ThreadSuggestions.cpp`）：
去空白、全角转半角、中文标点归一、ASCII 转小写。

**必须与候选推荐用同一个函数。** 两处口径若不一致，会出现"批次说这两条不是一处、
候选说是一处"的自相矛盾。

**空位置算"位置全等"。** 166 个铰缝的位置字段为空，排除空值会让这批直接散架。
语义上没有问题：同一个铰缝 + 同一种病害 + 无更细位置，本来就唯一。

### 4.2 批次的键

`(部件类型, 病害类型, 归一化位置, 年份集合, 动作类型)`。

年份集合进键是有意的——"三年连续"和"只有 2025 一年"是两种完全不同的判断，
不该混在一屏里让人一起点。

### 4.3 动作类型

| 动作 | 判定 | 落库行为 |
| --- | --- | --- |
| `create` | 组没有精确命中任何已有线索 | 新建一条线索，绑上组内全部观测 |
| `bind` | 组精确命中**恰好一条**已有线索 | 把组内观测绑到该线索 |

"精确命中"的口径与组的键一致：已有线索的 `bridge_component_id`、`defect_type`、
归一化后的 `defect_location` 三项与本组完全相同。位置相近但不相同**不算命中**——
那种情况走 `location_overlap` 交人工判断。

冷启动时全是 `create`；按上面的模拟，明年 84% 是 `bind`。

### 4.4 不进批次的三类

挑出来单独走逐条流程，各带原因码：

| 原因码 | 情形 | 当前数量 |
| --- | --- | ---: |
| `multiple_in_year` | 组内某年出现多条观测 | 3 组 / 14 条 |
| `location_overlap` | 同构件同类型下存在位置文字互相包含的另一组，**相关组全部踢出** | 4 对关系 / 7 组 |
| `ambiguous_thread` | 组精确命中多于一条已有线索 | 当前 0 |

`location_overlap` 的实例说明为什么必须人判：

```
16#墩盖梁 · 受渗水侵蚀:  "大小里程侧"(2024)  ／  "大小里程侧及左悬臂底部"(2025,2026)
    → 几乎肯定是同一处渗水扩展了范围，应当并成一条线索

19#跨桥面铺装 · 网状裂缝: "右侧行车道"(2026)  ／  "右侧行车道19#墩处"(2026)
    → 同一年两条，多半是两处，不应合并
```

三类合计 10 组 / 23 条观测，剩下 481 组 / 1174 条观测全部落在 144 个干净批次里。

## 5. 接口设计

读写分开，三个端点。

### 5.1 批次摘要

```
GET /api/bridges/{bridge_id}/thread-batches
```

只返回批次摘要：批次 id、动作类型、部件类型、病害类型、位置、年份集合、组数、
观测数，外加两三条样例组供扫一眼。当前 144 条摘要，几 KB。

**绝不在这里返回全部观测。** 一次性推 1197 条正是现有页面的死法。

`batch_id` 是批次键的哈希，只用于取明细。

同一响应里另附 `manual` 分区：不进批次的组及其原因码。

### 5.2 批次明细

```
GET /api/bridges/{bridge_id}/thread-batches/{batch_id}/groups
```

展开某个批次时才拉。返回组及组内逐年观测——含照片、尺寸、位置原文、标度。分页。

### 5.3 批量落库

```
POST /api/bridges/{bridge_id}/thread-batches/apply

{
  "action": "create" | "bind",
  "groups": [{
    "bridge_component_id": "...",
    "thread_id": "..."            // bind 时必填，create 时为 null
    "defect_type": "...",
    "defect_location": "..." | null,
    "observations": [{ "id": "...", "updated_at": "..." }]
  }]
}
```

**负载不引用 `batch_id`，而是显式列出要处理的组。** 前端把某几组剔掉之后，提交的
就是剔完的清单；服务端不需要知道"原本的批次长什么样"，也就不存在批次在两次请求
之间发生变化的问题。

每条观测携带 `updated_at` 乐观令牌。

上限 500 组/次，超出由前端拆分。当前最大批次 166 组、498 条观测。

## 6. 落库事务

### 6.1 校验

整条复用现有 `validate_observation_state`（`DefectThreadRepository.cpp`），一条不减：

1. 观测所属年度必须 `is_current` 且 `status = '已确认'`；
2. 观测 `review_status` 必须是 `已确认` 或 `已修改`（正式事实）；
3. `updated_at` 乐观令牌必须匹配；
4. 未被模块 07 已确认的对比结论引用。

批量不是放松校验的理由。

### 6.2 事务语义

**整批一个事务，全成或全败。**

批次的语义是"这 N 个构件适用同一个判断"。部分成功会留下一个谁也说不清的中间态，
人还得反过来查哪些成了、哪些没成。任一组的任一观测校验失败即整批回滚，返回失败
明细：构件、观测、原因码。前端标红那几组，处理完再提交。

498 次 `FOR UPDATE` 在单事务内是毫秒级；单人整理单桥，锁竞争基本不存在。

### 6.3 线索字段

- `thread_name` 沿用现有默认 `病害类型｜位置`（`DefectThreadRepository.cpp` 现有逻辑）。
  批量场景不提供命名入口——166 条不可能逐个起名；事后可在档案页修改。
- `confirmation_status` 写 `人工已确认`：批次是人确认过的。
- `first_seen_inspection_id` / `latest_seen_inspection_id` 由现有 `recompute_thread_span` 计算。

### 6.4 重试

提交成功后重复提交，会因观测已绑而被 `observation_already_bound` 挡下，**不会重复建线索**。

但为避免让人对着一个假失败发懵：apply 要认出这种情形——组内观测已经绑在一条与本组
键完全一致的线索上时，该组报「已完成」而不是失败。

## 7. 界面

### 7.1 批次视图

整理页从"一观测一卡"改成"一批次一卡"（当前 144 个），按**覆盖观测数降序**排列——先消掉 166 个
铰缝那种大批次，进度条一次走掉四成。

```
铰缝 · 渗水泛碱 · （无位置）          [新建线索]
2024 → 2025 → 2026 连续三年
166 个构件 · 498 条观测

  1#铰缝    [2024照片][2025照片][2026照片]
  2#铰缝    [2024照片][2025照片][2026照片]
  3#铰缝    [2024照片][2025照片][2026照片]
                              …还有 163 个

  [确认这 166 组]  [展开逐组核对]  [暂不处理]
```

默认摊开三个样例，**逐年横向并排**——这是"写病害发展"最需要的视角，一眼看出三年
怎么变的。

展开则分页列出全部组，每组一行带勾选框，可把个别不对劲的剔出去；剔掉的自动落到
逐条区。

`bind` 批次多一行"将绑到：`渗水泛碱｜大小里程侧` (BHXS-000123)"。

### 7.2 需单独处理区

不进批次的组单独一区，走现有逐条卡片流程；从批次里剔出来的也进这里。当前 10 组
23 条观测，逐条看完全扛得住。

### 7.3 顺手修掉的两个硬伤

1. **卡片渲染 `business_component_code`**：从"下部结构｜盖梁"改成"1#墩盖梁"。
   现有页面因为这一处从根上没法用。
2. **候选请求改为点开才发**：批次视图下不需要逐条候选——归组时已经把匹配算完了；
   逐条区保留候选，但不再 mount 即请求。

## 8. 测试策略

### 8.1 归组规则（纯函数，无数据库）

参照 `ThreadSuggestions` 的组织方式：

- 同构件同类型同位置跨三年 → 归一组；
- 位置只差全角空格或中文标点 → 归一化后同组；
- **空位置仍算位置全等**；
- 组内某年两条 → 踢出批次，标 `multiple_in_year`；
- 位置互相包含 → **两组都踢出**，标 `location_overlap`；
- 精确命中两条已有线索 → 踢出，标 `ambiguous_thread`；
- 年份集合不同 → 不同批次；
- 有命中 → `bind`，无命中 → `create`。

### 8.2 落库事务（数据库集成，复用 `test_defect_thread_repository.cpp` 夹具）

- 整批 N 组一次落库：线索数、绑定数、`first_seen` / `latest_seen` 均正确；
- **任一观测乐观令牌过期 → 整批回滚，一条都没落**（保证"全成或全败"不是嘴上说说）；
- 旧修订版年度的观测 → 拒绝；
- 被模块 07 已确认对比引用的观测 → 拒绝；
- 重复提交 → 报「已完成」而非 `observation_already_bound` 失败。

### 8.3 前端（防回归）

- 批次卡片渲染出 `1#墩盖梁` 而非"盖梁"；
- **不展开就不发 `thread-suggestions` 请求**；
- 剔掉两组后提交，负载中不含这两组。

### 8.4 真实数据夹具

把百股大桥这份数据做成归组夹具，断言：

```
1197 条观测 → 491 组
   481 组进批次，落在 144 个批次里，覆盖 1174 条观测
     3 组 multiple_in_year
     7 组 location_overlap（4 对关系）
```

归组口径将来但凡改动，这条立刻变红，改的人必须解释清楚为什么。

## 9. 验收标准

1. 打开线索整理页，144 个批次摘要在一次请求内返回，页面不再出现批量并发的候选请求。
2. 确认"铰缝·渗水泛碱·三年"批次后，166 条线索建成，498 条观测完成绑定，档案页
   对应构件能看到三年并排的观测。
3. 展开批次剔掉任意组后提交，被剔的组仍留在未绑定状态并出现在逐条区。
4. 任一观测被并发修改导致令牌过期时，整批提交失败且数据库中无任何新线索。
5. 卡片显示构件业务编号，可区分 `1#墩盖梁` 与 `10#墩盖梁`。
6. 全部批次与逐条项处理完后，构件病害档案页顶部的"尚未归入跨年线索"提示消失。

## 10. 风险与取舍

**批量确认的信任边界。** 批次是"同一个判断重复 N 次"，人做一次判断是合理的；但必须
能展开看、能剔除，且异常样本绝不混进批次。曾考虑"高置信一键全建"（481 组直接落库），
否决理由是它等于对着报告精度要求闭眼签字——没有任何一处让人真正看过数据。

**严格匹配会漏归。** `大小里程侧` 与 `大小里程侧及左悬臂底部` 不会自动并成一条。这是
有意的：宁可漏归让人补，也不能错归让报告写出错误的发展结论。当前这类只有 4 对关系、7 个组，
放在逐条区人工判断的成本可以接受。

**归组不做物化。** 曾考虑在年度入库时算好批次存表，否决理由是构件改名、观测重绑、
年度修订都会让它过期，需要一整套失效重算逻辑。1197 条的实时归组是一个 `group by`，
不值得为一个还没出现的性能问题引入缓存失效。

**每年重复使用。** 本设计不含"入库后自动预归组"。年度入库那一刻线索状态可能仍在
变动，算早了容易过期；手动进入整理页触发即可。
