# 2026-08-25 设计：病害线索整理工作台

- 状态：**设计修订完成，待实施**
- 相关模块：06 构件病害档案、病害线索整理工作台
- 起因：百股大桥 1197 条未绑定观测，现有逐条整理流程实际不可用
- 下游：模块 07 跨年病害对比
- 修订原则：档案只读、整理独立；批次是展示与确认单位，不是持久化实体

## 1. 背景

模块 06 当前同时承担档案查询、历史修订、证据查看、候选推荐、线索创建、绑定、解绑和
换绑。只读查询与数据治理混在同一模块中，页面状态和接口职责逐渐重叠。

现有线索整理页又按“一条观测一张卡”设计。百股大桥当前有 2024、2025、2026 三个已确认
年度，真实数据状态如下：

| 指标 | 数值 |
| --- | ---: |
| 未绑定观测 | 1197 |
| 涉及构件 | 409 |
| 已有线索 | **0** |
| 已绑定观测 | **0** |

现有流程有三个直接问题：

1. 每张 `ThreadBindingCard` 在 mount 时请求一次 `thread-suggestions`，1197 张卡产生 1197 个
   并发候选请求，页面长期停留在“正在加载候选”。
2. 冷启动时已有线索为 0，候选必然为空，用户只能逐条创建 1197 次。
3. 卡片没有渲染已经返回的 `business_component_code`，只显示“下部结构｜盖梁”，用户无法
   区分 `1#墩盖梁`、`10#墩盖梁` 等实际构件。

如果只在旧页面上叠加批量按钮，会同时保留逐条候选、逐条创建、批次摘要、批次明细、批量
创建、批量绑定和异常处理两套重叠流程。因此本设计不是给旧卡片增加一个功能，而是重新划分
档案查询与线索整理的边界，并用新的整理工作台替换旧整理流程。

## 2. 模块边界

### 2.1 构件病害档案

构件病害档案是**只读结果页**，负责展示已经形成的事实与关系：

- 构件清单、结构分部和业务编号；
- 按病害线索组织的历年观测；
- 尚未归入线索的观测数量；
- 构件年度评分；
- 年度修订历史；
- 照片、尺寸和原始证据。

档案页不承担批量候选计算和复杂绑定操作。需要纠正观测归属时，用户从档案页进入线索整理
工作台，并定位到对应构件或观测。

首版可以保留现有重新绑定入口作为兼容能力，但新功能不得继续向档案页堆叠。整理工作台稳定
后，重新绑定也应复用同一套服务端线索解析能力。

### 2.2 病害线索整理工作台

线索整理工作台是**数据治理页**，只负责：

- 展示待整理批次；
- 展示需要人工判断的异常簇；
- 批量创建线索；
- 批量绑定已有线索；
- 从批次中剔除可疑组；
- 手工合并、拆分或暂缓异常项；
- 处理并发冲突和失败恢复。

新的工作台不再为每条观测单独请求候选。批次、精确匹配和异常关系由服务端一次计算，前端
卡片只负责展示和收集用户选择。

### 2.3 数据流

```text
已确认年度观测
    ↓
病害线索整理工作台
    ↓ 人工确认身份关系
病害线索
    ↓
构件病害档案（只读结果）
    ↓
模块 07 跨年病害对比
```

## 3. 目标、非目标与信任边界

### 3.1 目标

1. 让 1197 条观测能在合理时间内整理完，且线索关系足以支撑报告叙述。
2. 同一套机制覆盖冷启动时的批量新建和以后年度的批量绑定。
3. 消除候选请求 N+1，不再一次性渲染 1197 张独立业务卡片。
4. 所有构件均显示 `business_component_code`。
5. 批量操作仍执行与单条绑定等价的服务端校验、事务和并发保护。
6. 档案查询与线索整理形成清晰、可维护的职责边界。

### 3.2 非目标

1. 未经人工确认自动创建或绑定线索。
2. 自动生成“发展、减轻、修复”等模块 07 对比结论。
3. 修改年度事实，包括标度、尺寸、照片、评分和病害原文。
4. 建设通用工作流引擎或持久化批次表。
5. 批量修改线索名称。
6. 跨浏览器或跨设备持久化“暂不处理”的个人工作状态。

### 3.3 人工确认边界

本设计采用**批次级人工确认**，不要求用户逐一打开批次中的每个组。

一个批次表达“同一种明确规则在多个构件上的重复应用”。系统必须先排除所有已知异常，并
提供代表性样例、完整展开能力和组级剔除能力；用户确认的是该规则可以应用于当前批次。

不得再表述为“每一个组都被人逐一看过”。真正需要逐组判断的内容必须进入异常簇，不能混入
干净批次。

## 4. 数据观察

按 `(构件, 病害类型, 归一化位置)` 对当前 1197 条未绑定观测做的原始分析结果如下：

| 指标 | 数值 |
| --- | ---: |
| 归组后 | **491 组** |
| 横跨三个年度 | 321 组（968 条观测） |
| 横跨两个年度 | 59 组（118 条观测） |
| 只有一个年度 | 111 组（111 条观测） |
| 组内每年至多一条 | 488 组 / 1183 条 |
| 组内某年出现多条 | 3 组 / 14 条 |
| 位置文字互相包含 | 4 对关系 / 7 组 |
| 排除已知异常后 | **481 组 / 1174 条观测** |

原分析再按 `(部件类型, 病害类型, 归一化位置, 年份集合)` 聚合，得到 144 个批次。主要批次
包括：

| 部件·病害·位置·年份 | 涉及构件数 |
| --- | ---: |
| 铰缝 · 渗水泛碱 · （无位置）· 2024,2025,2026 | 166 |
| 板 · 上部其它病害 · 板底 · 三年 | 50 |
| 盖梁 · 受渗水侵蚀 · 大小里程侧 · 三年 | 29 |
| 板 · 受渗水侵蚀，混凝土剥蚀破损 · 右侧翼缘板及腹板 · 三年 | 19 |
| 铰缝 · 渗水泛碱 · （无位置）· 仅 2025 | 18 |
| 铰缝 · 渗水泛碱 · （无位置）· 仅 2026 | 17 |
| 铰缝 · 渗水泛碱 · （无位置）· 2024,2025 | 11 |

最终实现的批次键增加 `structure_part`、病害类型统一归一化后，已在当前数据上重算核实：
**组数 491、进批次 481 组 / 1174 条观测、批次数 144，与原始分析完全一致**。原因是本桥台账中
`component_type` 未跨结构部位，且归一化不改变本数据的分组结果。

即便如此，144 仍是当前数据快照下的基线，不作为脱离固定夹具的永久业务常量。

增量模拟中，把 2024、2025 视为已有线索、2026 视为新导入年度，430 条新观测中有 363 条
（84%）能够精确命中已有线索。这说明同一工作台可以同时覆盖冷启动和年度增量。

## 5. 概念模型

### 5.1 持久化实体

数据库层面继续保留两个核心实体，不新增批次表：

```text
病害线索 thread
    └── 年度观测 observation
```

- `observation` 是某个年度的正式事实。
- `thread` 表示同一构件上同一处病害的跨年身份关系。

### 5.2 整理期只读模型

整理工作台在读取时临时计算三种模型：

```text
批次 batch
    └── 组 group
            └── 观测 observation

异常簇 manual cluster
    └── 相互关联、必须共同判断的一个或多个组/已有线索
```

- `group` 是未来一条线索的干净候选。
- `batch` 是多个“长相相同、动作相同”的组，只是展示和确认单位。
- `manual cluster` 保存歧义上下文，不能退化为互相孤立的单观测卡片。
- 以上模型均不持久化；每次进入工作台时根据当前有效事实重新计算。

## 6. 归一化、归组与匹配

### 6.1 规范化函数

病害类型和位置都复用 `normalize_suggestion_text` 的基础规则：

- 去除空白；
- 全角 ASCII 转半角；
- 约定范围内的中文标点归一；
- ASCII 转小写。

在其上增加明确的空值规则：`null`、空字符串以及仅含空白的字符串统一得到规范化空值 `""`。

应提取一个共享的“线索规范键”函数，由批次归组、精确匹配和候选展示共同使用，避免三处各自
拼接字符串。

### 6.2 组键

```text
(bridge_component_id,
 normalized_defect_type,
 normalized_defect_location)
```

规范化空位置允许参与全等匹配。同一构件、同一规范化病害类型、位置都为空时，可以组成一组。

组中每个年度最多只能有一条观测。某年度出现多条时，不自动决定是否为重复记录或不同病害，
整个关联范围进入异常簇。

组 ID 使用组键的稳定编码或哈希，仅用于本次只读模型。必须定义规范序列化、哈希算法、长度和
碰撞检测，不能依赖语言运行时自带的不稳定 hash。

### 6.3 批次键

```text
(structure_part,
 component_type,
 normalized_defect_type,
 normalized_defect_location,
 inspection_year_set,
 action)
```

`structure_part` 进入批次键，避免“其他”“附属构件”等宽泛部件类型跨结构部位混批。

年份集合进入批次键是有意的。“三年连续”和“仅 2025 年”是两种不同判断，不应混在同一个
确认动作里。

批次 ID 同样使用稳定编码或哈希。数据变化导致批次消失时，明细接口返回
`triage_batch_changed`，前端刷新摘要。

### 6.4 精确匹配已有线索

对每个组查询同构件已有线索，并使用与组键相同的规范键比较：

| 结果 | 动作 |
| --- | --- |
| 没有精确匹配，且没有位置重叠关系 | `create` |
| 恰好一条精确匹配，且没有其他冲突 | `bind` |
| 多于一条精确匹配 | 进入 `ambiguous_thread` 异常簇 |

空位置与空位置可以精确匹配。原候选算法中“双方位置非空才算全等”的限制不适用于本设计，
需要同步调整共享匹配函数。

一个 `bind` 批次跨多个构件时，每个组会绑定到各自构件下的不同 `thread_id`。批次只有共同的
动作模式，没有唯一的目标线索编号。

### 6.5 位置重叠

只有两个非空规范化位置互相包含且不完全相等时，才算 `location_overlap`。

检测范围包括：

1. 未绑定组与同构件、同病害类型的其他未绑定组；
2. 未绑定组与同构件、同病害类型的已有线索。

相关对象全部进入同一个异常簇，响应中附上关联组、已有线索和原因。不能只检查未绑定组，
否则增量场景可能为一个位置相近的已有病害重复创建线索。

例如：

```text
16#墩盖梁 · 受渗水侵蚀
  “大小里程侧”(2024)
  “大小里程侧及左悬臂底部”(2025,2026)
  → 可能是同一处渗水扩展，应共同判断

19#跨桥面铺装 · 网状裂缝
  “右侧行车道”(2026)
  “右侧行车道19#墩处”(2026)
  → 同年两条，可能是两处，不应自动合并
```

### 6.6 异常原因

| 原因码 | 含义 |
| --- | --- |
| `multiple_in_year` | 同一候选组中某年度出现多条观测 |
| `location_overlap` | 与其他未绑定组或已有线索存在非全等的位置包含关系 |
| `ambiguous_thread` | 精确命中多于一条已有线索 |

一个异常簇可以同时携带多个原因码。数量统计按簇、组和观测分别返回，避免把“10 组”写成
“10 条逐条项”。

`location_overlap` 合并了两种来源，但**界面要展示的对象不同**：与未绑定组重叠时要摆出
对方的组及其历年观测，与已有线索重叠时要摆出线索的 `thread_name` 与 BHXS 编号。因此异常簇
必须携带 `overlap_targets`，逐个标明对方类型与标识：

```json
"overlap_targets": [
  { "kind": "group",  "group_id": "...", "normalized_location": "..." },
  { "kind": "thread", "thread_id": "...", "thread_name": "...",
    "system_number": "BHXS-000123", "normalized_location": "..." }
]
```

只给原因码而不给对方是谁，人在异常簇里依然无从判断该合还是该分。

## 7. 后端职责

### 7.1 TriageQueryService

新增只读的整理查询服务，负责：

- 查询当前有效、已确认或已修改、尚未绑定的正式观测；
- 查询相关构件的已有线索；
- 计算规范键、组、批次和异常簇；
- 生成稳定 group ID、batch ID 和批次指纹；
- 返回批次样例、完整明细和异常上下文。

它不写数据库，也不把批次物化。

### 7.2 ThreadResolutionService

新增统一的线索解析服务，负责：

- 批量创建线索并绑定组内观测；
- 批量绑定精确匹配的已有线索；
- 处理异常簇的人工创建、合并和绑定；
- 统一执行桥梁、构件、年度状态、观测状态、并发令牌、已有绑定和模块 07 引用校验；
- 重算线索首见和末见年度。

现有单条创建、绑定、解绑和换绑能力可以逐步委托给该服务，避免单条流程与批量流程维护两套
事务规则。

### 7.3 服务端不信任客户端组装结果

客户端提交的组和观测清单只表达用户选择。服务端必须从锁定后的数据库行重新验证：

1. 所有观测属于 URL 指定桥梁；
2. 每组观测属于同一构件；
3. 每组规范化病害类型和位置一致；
4. 每个年度最多一条观测；
5. 请求内没有重复观测 ID；
6. `create` 组当前仍无精确匹配和位置重叠；
7. `bind` 组当前仍恰好命中指定线索；
8. 目标线索与观测属于同桥、同构件。

客户端提交的 `defect_type`、`defect_location` 或 `thread_id` 不能绕过服务端重新计算。

## 8. 接口设计

### 8.1 工作台摘要

```http
GET /api/bridges/{bridge_id}/thread-triage
```

返回：

- 总未绑定观测数、批次组数、异常簇数；
- 批次摘要；
- 每个批次三条确定性样例；
- 异常簇及其相关组、已有线索和观测摘要。

批次按覆盖观测数降序排列。样例按构件业务编号稳定排序后，从头部、中部和尾部各取一组，
避免每次刷新样例随机变化。

摘要不返回全部批次观测，也不触发逐观测候选请求。异常簇预计数量较小，可以直接返回完整
上下文；若真实数据增长后响应过大，再为异常簇增加明细接口。

### 8.2 批次明细

```http
GET /api/bridges/{bridge_id}/thread-triage/batches/{batch_id}
```

一次返回该批次的全部紧凑明细：

- batch ID、动作、批次指纹；
- 全部 group ID；
- 构件业务编号；
- 每组目标线索摘要（仅 `bind`）；
- 每条观测的 ID、`updated_at`、年份、位置原文、标度、尺寸摘要和照片 ID。

当前最大批次为 166 组、498 条观测，只返回 JSON 元数据，不返回照片二进制。按每条观测
300–500 字节（ID、`updated_at`、年份、位置原文、标度、尺寸摘要、照片 ID 数组）估算，
最大批次明细约 **150–250 KB**，可以接受。前端使用折叠或虚拟列表控制渲染，照片仍通过既有
内容接口按可见区域加载。

实际大小由 §12.6 的基准记录，不停留在估算。

首版不分页，从而保证跨页选择、剔除和提交清单一致。如果真实数据证明单批明细过大，再在保持
完整 apply manifest 的前提下引入分页。

### 8.3 批量应用

```http
POST /api/bridges/{bridge_id}/thread-triage/apply
```

请求示例：

```json
{
  "batch_id": "...",
  "batch_fingerprint": "...",
  "action": "create",
  "groups": [
    {
      "group_id": "...",
      "target_thread_id": null,
      "observations": [
        { "id": "...", "updated_at": "..." }
      ]
    }
  ]
}
```

- `create` 时 `target_thread_id` 必须为 `null`。
- `bind` 时每个组必须提供自己的 `target_thread_id`。
- 从批次中剔除的组不出现在请求中，并在当前页面会话中移动到人工处理区。
- 服务端根据数据库事实重新计算所有组和匹配结果，不信任客户端 group ID、动作和目标线索。
- 指纹用于发现读取与提交之间的批次变化，但不能代替逐观测校验。
- 一个业务批次只允许一次请求，不由前端拆分；事务单位始终是本次提交的全部组。

成功响应示例：

```json
{
  "status": "applied",
  "groups_applied": 166,
  "threads_created": 166,
  "observations_bound": 498,
  "results": [
    {
      "group_id": "...",
      "thread_id": "...",
      "thread_system_number": "BHXS-000123"
    }
  ]
}
```

### 8.4 异常簇人工处理

```http
POST /api/bridges/{bridge_id}/thread-triage/resolve
```

一次请求表达一个异常簇中的一次明确人工决策，例如：

- 把多个不同位置文本的观测合并为一条新线索；
- 将选中的观测绑定到某条已有线索；
- 将同年多条观测拆成不同线索。

异常处理允许用户明确选择标准病害类型、标准位置和观测集合。非精确合并必须携带显式确认
字段，服务端仍验证同桥、同构件、正式状态和并发令牌。

“暂不处理”只在当前页面会话中折叠，不产生服务端事实。刷新页面后会重新出现。

### 8.5 旧接口迁移

新工作台不再调用：

```http
GET /api/bridges/{bridge_id}/unbound-defect-observations
GET /api/defect-observations/{observation_id}/thread-suggestions
```

旧接口可以在迁移期保留给现有功能和测试，但不得成为新批次页的依赖。工作台稳定后，再删除
无人使用的旧页面逻辑、候选请求和对应测试。

## 9. 事务、并发与幂等

### 9.1 三阶段事务

一个批量请求使用一个 PostgreSQL 事务，按以下顺序执行：

1. 收集并去重全部观测 ID；
2. 按 UUID 固定顺序批量 `SELECT ... FOR UPDATE`，降低交叉请求死锁风险；
3. 对所有观测和组执行完整只读校验，收集全部错误；
4. 存在任何错误时回滚，不执行任何写入；
5. 全部通过后批量创建线索和绑定观测；
6. 集中重算所有受影响线索的首见、末见年度；
7. 提交事务。

禁止“处理一组、写一组、最后遇错再返回一个错误”的实现方式。虽然数据库可以回滚，但那样
无法稳定返回完整失败明细，也会产生大量不必要的 SQL 往返。

### 9.2 必须执行的观测校验

每条观测均执行：

1. 所属年度 `is_current = true` 且 `status = '已确认'`；
2. `review_status` 为 `已确认` 或 `已修改`；
3. `updated_at` 与请求令牌一致；
4. 当前绑定状态符合本次动作；
5. 未被模块 07 的人工已确认对比阻止修改。

模块 07 引用检查不是 `validate_observation_state` 当前实现的一部分。该函数只做上面第 1–3 项；
引用检查是独立的 `referenced_by_confirmed_comparison`，而且现有代码只在
`old_thread_id.has_value()`（即重绑路径）时才调用它——**首次绑定根本不查**
（`DefectThreadRepository.cpp:300`）。批量服务必须显式调用，不能写成“复用现有校验”了事。

**目标线索侧的引用检查是一个未决边界。** 现状不构成漏洞：未绑定观测不可能被已确认对比
引用，因为对比建立在线索之上。但批量 `bind` 时，若**目标线索**已被模块 07 的人工已确认
对比引用，往其中追加历年观测会改变该线索的跨年跨度，进而影响已确认的对比结论。

首版取保守口径：**目标线索被已确认对比引用时，该组拒绝**，原因码
`thread_referenced_by_confirmed_comparison`，提示用户先在模块 07 撤销对比结论。冷启动阶段
不会触发（线索全新），代价为零；等模块 07 落地后再根据实际对比语义决定是否放宽。

### 9.3 幂等判断顺序

第一次成功提交会更新观测的 `updated_at`。网络响应丢失后，原请求重试必然携带旧令牌，因此
必须在普通令牌冲突之前识别“已经按本请求完成”。

处理顺序为：

1. 锁定请求显式列出的观测；
2. 判定该组是否 `already_completed`——`create` 与 `bind` 的判据不同：
   - `create` 组的 `target_thread_id` 为 `null`，没有“预期线索”可比。判据是：组内全部观测
     绑定到**同一条**线索，且该线索的规范键（构件、规范化类型、规范化位置）**等于本组规范键**；
   - `bind` 组在上述条件之外，还要求该线索就是请求里的 `target_thread_id`。
   满足则该组为
   `already_completed`；
3. 所有组都为 `already_completed` 时，返回成功，不再检查旧令牌；
4. 否则执行正常 `updated_at` 校验；
5. 部分完成、绑定到其他线索或分散到多条线索时返回冲突。

这样可以处理“事务已成功、响应丢失”的真实重试，同时不会把其他操作造成的绑定误认为幂等。

### 9.4 失败响应

整批失败使用 `409 Conflict`，响应至少包含：

```json
{
  "code": "thread_triage_conflict",
  "message": "批次中的部分观测已经变化，请处理后重试。",
  "issues": [
    {
      "group_id": "...",
      "bridge_component_id": "...",
      "observation_id": "...",
      "reason_code": "observation_revision_conflict",
      "message": "该观测已被其他操作更新。"
    }
  ]
}
```

任一问题都会使整个请求回滚。前端标出涉及的组，用户刷新工作台后再处理。

## 10. 新建线索字段

批量创建时，服务端从锁定后的组内观测派生线索字段，不使用客户端未经验证的文本：

- `bridge_id`、`bridge_component_id`：来自观测；
- `defect_type`：取最新年度观测的去首尾空白原文；
- `defect_location`：取最新年度观测的去首尾空白原文；全部为空时写 `null`；
- `thread_name`：有位置时为 `病害类型｜位置`，无位置时仅为 `病害类型`；
- `confirmation_status`：写 `人工已确认`；
- `first_seen_inspection_id`、`latest_seen_inspection_id`：绑定完成后统一重算。

同一规范键可能包含标点或空格形式略有差异的原文。选择最新年度原文作为展示标准，规则稳定、
可解释，也更符合后续报告的最新用语。

`defect_threads.defect_location` 已允许 `null`。批量服务和单条创建路径应统一 null 语义，避免
数据库中同时出现 null、空字符串和纯空白三种“无位置”。

批量命名编辑仍为非目标。若产品声称“事后可修改名称”，必须另行提供真实存在的单条线索编辑
接口；在该能力实施前，不在本页面作此承诺。

## 11. 界面设计

### 11.1 工作台总览

```text
病害线索整理

铰缝 · 渗水泛碱 · （无位置）                    [批量新建]

  1#铰缝       [2024] [2025] [2026]
  84#铰缝      [2024] [2025] [2026]
  166#铰缝     [2024] [2025] [2026]

  [确认这 166 组] [展开全部] [暂不处理]
```

- 批次按覆盖观测数降序排列。
- 默认展示三条稳定样例，并明确写出“当前为批次级确认”。
- 展开后以构件为行、年份为列横向展示，可勾选剔除个别组。
- 所有构件显示 `business_component_code`，缺失时回退到构件系统编号。
- 照片只在样例或可见行加载。
- 提交前显示最终组数、观测数和 create/bind 动作。

### 11.2 bind 批次

bind 批次显示：

```text
将分别绑定到各构件中精确命中的已有线索
```

不能展示一个虚假的批次级 BHXS 编号。展开后逐组显示对应的线索名称和系统编号。

### 11.3 异常簇

异常区按“需要共同判断的关系”展示，而不是复用旧的一观测一卡：

```text
16#墩盖梁 · 位置可能发生扩展                   [位置重叠]

大小里程侧
  2024 [照片] [尺寸]

大小里程侧及左悬臂底部
  2025 [照片] [尺寸]
  2026 [照片] [尺寸]

[合并为一条新线索] [绑定已有线索] [分别处理] [暂不处理]
```

`multiple_in_year` 必须把同一年多条观测并排展示。`ambiguous_thread` 必须列出所有精确命中的
已有线索及其 BHXS 编号。

### 11.4 前端状态归属

- 页面统一加载批次和异常簇；
- 批次卡片是纯展示组件，不自行请求候选、不自行写数据库；
- 页面或专用 hook 统一管理展开、剔除、提交、刷新和错误；
- 创建与绑定成功后只刷新受影响的工作台数据，不让每张卡独立触发全页 reload；
- “暂不处理”和从批次剔除只在当前会话生效，刷新后按数据库事实重新计算。

## 12. 测试策略

### 12.1 归组纯函数

- 同构件、规范化同类型、规范化同位置、跨年度 → 同一组；
- 病害类型的空格、全角字符和 ASCII 大小写差异 → 规范化后一致；
- 位置只差空白或约定标点 → 规范化后一致；
- `null`、空字符串和纯空白位置 → 统一空位置；
- 空位置与空位置 → 可以精确匹配；
- 组内某年多条 → `multiple_in_year`；
- 未绑定组之间位置包含 → 同一 `location_overlap` 异常簇，`overlap_targets` 中对方
  `kind` 为 `group`；
- 未绑定组与已有线索位置包含 → `location_overlap`，`overlap_targets` 中对方 `kind` 为
  `thread` 且带 `system_number`；
- 精确命中多条已有线索 → `ambiguous_thread`；
- 年份集合不同 → 不同批次；
- `structure_part` 不同 → 不同批次；
- 恰好一个无冲突精确命中 → `bind`；
- 无精确命中且无重叠 → `create`。

### 12.2 服务端请求重验证

- URL 桥梁与观测所属桥梁不同 → 整批拒绝；
- 同组跨构件 → 整批拒绝；
- 同组规范键不同 → 整批拒绝；
- 同一观测出现在两个组 → 整批拒绝；
- create 实际存在精确匹配 → 拒绝并要求刷新；
- bind 目标不是服务端重新算出的精确线索 → 拒绝；
- bind 目标跨桥或跨构件 → 拒绝。

### 12.3 数据库事务

- N 组一次落库，线索数、绑定数、首见和末见年度正确；
- 任一令牌过期 → 整批回滚；
- 旧修订版或未确认年度 → 整批拒绝；
- 非正式观测 → 整批拒绝；
- 被模块 07 人工已确认对比阻止修改 → 整批拒绝；
- `bind` 的目标线索已被模块 07 人工已确认对比引用 → 该组拒绝，原因码
  `thread_referenced_by_confirmed_comparison`；
- `create` 组成功后用旧令牌重试 → `already_completed`（判据为线索规范键等于组规范键，
  而非比对 `target_thread_id`）；
- `bind` 组成功后用旧令牌重试 → `already_completed`；
- 组内观测绑到了规范键相同但并非 `target_thread_id` 的另一条线索 → 冲突，不算幂等；
- 部分已绑定、部分未绑定 → 冲突，不误判为幂等；
- 已绑定到其他同键线索 → 冲突；
- 两个交叉观测集合的并发请求使用固定锁顺序，不发生应用级死锁；
- 空位置创建后数据库值为 null，默认名称正确，再次匹配正确。

### 12.4 前端

- 首屏只发一个工作台摘要请求；
- 未展开时不发逐观测候选请求；
- 卡片显示 `1#墩盖梁` 等业务编号；
- 打开一个批次只拉一次完整明细；
- 剔除两组后 apply 请求不含这两组；
- bind 批次逐组显示不同的目标 BHXS 编号；
- 异常簇保持相关组上下文；
- 失败响应能标记对应组和观测；
- 暂不处理只在当前会话折叠，刷新后重新出现。

### 12.5 真实数据夹具

把百股大桥当前数据制作成固定、可审计的归组夹具，并记录：

- 数据快照来源或指纹；
- 观测总数；
- 最终组数；
- 批次数；
- 各异常原因涉及的簇、组和观测数。

原始分析基线为：

```text
1197 条观测 → 491 组
481 组可批量处理，覆盖 1174 条观测
3 组存在 multiple_in_year
7 组存在 location_overlap（4 对关系）
```

加入 `structure_part` 与病害类型规范化后已重算核实：组数、进批次组数、观测数与批次数
（144）与上述原始分析**完全一致**，无差异。夹具期望值直接按此写死；将来若数据快照更换，
连同指纹一并更新并说明差异来源。

### 12.6 性能基准

不预先断言“498 次 FOR UPDATE 是毫秒级”。实现应使用批量锁定和批量更新，并在真实最大批次
夹具上记录：

- 摘要查询耗时；
- 最大批次明细大小与耗时；
- 166 组、498 条观测 apply 的事务耗时；
- SQL 查询次数；
- 前端首屏请求数和照片请求数。

性能目标在实施计划中根据当前本地环境确定，并纳入回归测试或基准记录。

## 13. 验收标准

1. 构件病害档案保持只读结果页定位，复杂线索整理在独立工作台完成。
2. 打开工作台只发一个摘要请求，不产生逐观测候选请求风暴。
3. 批次摘要显示结构分部、部件类型、病害类型、位置、年份集合、动作、组数和观测数。
4. “铰缝·渗水泛碱·三年”批次可以在一次事务中创建对应线索并绑定全部选中观测。
5. 展开批次剔除任意组后，被剔组保持未绑定，并在当前会话进入人工处理区；
   **刷新页面后该组重新出现在原批次中**（剔除不持久化，见 §14.4）。
6. `bind` 批次逐组绑定到各构件自己的精确匹配线索，不使用批次级单一 thread ID。
7. 未绑定组与已有线索存在位置包含关系时，不自动 create，而是进入异常簇。
8. 任一观测并发变化时，整批失败且数据库无部分写入。
9. 成功请求因网络原因重试时返回 `already_completed`，不重复创建线索。
10. 空位置能够批量创建、正确命名，并在以后年度精确匹配。
11. 所有卡片显示构件业务编号，可区分 `1#墩盖梁` 与 `10#墩盖梁`。
12. 异常簇能够在同一上下文中完成合并、绑定或拆分，不退化为互相孤立的单条卡片。
13. 全部批次和异常簇处理完后，档案页“尚未归入跨年线索”提示消失。
14. 新工作台不依赖旧 `unbound-defect-observations + thread-suggestions` 的逐卡流程。

## 14. 风险与取舍

### 14.1 批次级确认不是逐组确认

批量能力成立的前提就是允许人确认一条重复规则，而不是逐个点击每一组。本设计通过严格归组、
异常隔离、稳定样例、完整展开和组级剔除控制风险，但不宣称每个组都被逐一查看。

### 14.2 严格匹配会留下人工项

`大小里程侧` 与 `大小里程侧及左悬臂底部` 不会自动归为同一线索。宁可将可疑关系留给异常
簇，也不为了覆盖率生成错误的跨年发展关系。

### 14.3 不物化批次

构件调整、年度修订、观测绑定和线索修改都会让批次失效。当前规模下实时计算成本可控，因此
不新增批次表，也不承担缓存失效机制。批次指纹只用于一次读取到提交之间的并发检查。

### 14.4 剔除和暂缓不持久化

为避免引入个人任务状态表，首版中的“剔除”和“暂不处理”只属于当前页面会话。用户刷新后会
根据当前数据库事实重新获得整理建议。若未来确实需要多人分工或跨日续办，再单独设计持久化
任务状态，而不是把它混入病害事实表。

### 14.5 保留必要的领域复杂度

观测与线索分离、年度版本过滤、乐观并发、模块 07 引用保护和事务回滚都属于必要复杂度。
本次收敛删除的是重复入口、重复请求、重复状态和重复事务实现，不通过放松正确性换取表面简单。
