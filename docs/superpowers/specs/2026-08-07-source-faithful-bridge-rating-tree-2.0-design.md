# 仿照来源软件的桥梁评定树 2.0 设计

日期：2026-08-07
状态：已实施（当前发布 2.0.3；2.0.2 为首个完整来源快照修正版）

> 2026-08-14：2.0.3 保持 2.0.2 的树、映射与评分语义，仅升级版本并锁定 H21 1.0.4，以配套河床台账生成准入。详见 `2026-08-14-riverbed-inventory-generation-design.md`。

## 1. 背景

系统当前发布的单位桥梁评定树为 `organization-bridge/1.0.3`。实际核对来源软件的
Electron 离线库和评定树截图后，确认当前树没有完整表达来源软件的桥梁层级、指标复用关系、
显示编号和单位扩展病害。

典型问题是 `9.1.2 盖梁和系梁`。来源软件实际显示：

```text
9.1.2 盖梁和系梁
├─ 9.1.1-1 蜂窝、麻面
├─ 9.1.1-2 剥落、露筋
├─ 9.1.1-3 空洞、孔洞
├─ 9.1.1-4 钢筋锈蚀
├─ 9.1.1-5 混凝土碳化、腐蚀
├─ 9.1.2-1 裂缝
└─ 9.1.2-2 盖梁和系梁病害
```

这里前五项是来源软件将已有指标复用到盖梁分组下，不应因为父节点是 `9.1.2` 就把显示编号
改写成 `9.1.2-*`。当前前端从 `node_key` 推导显示编号，并为盖梁裂缝增加单点覆盖，只解决了
页面显示，没有解决来源数据的上下文匹配。

本设计发布新的 `organization-bridge/2.0.0`，让桥梁评定树的结构、顺序、显示编号和指标复用
关系与来源软件一致，同时继续由本系统的 JTG/T H21—2011 规范包执行评分。

## 2. 核心结论

1. 来源软件只作为检测数据来源和评定树结构参照，不是运行时依赖，也不是评分依据。
2. 2.0.0 只包含来源软件第 5–10 节的桥梁内容。
3. 第 11、12、13、14 节完全不在本项目范围内，不建立节点、映射、状态或后续模块。
4. 页面编号由节点的显式 `display_number` 决定，不再根据 `node_key` 猜测。
5. 同一来源指标出现在不同分组时，建立不同的上下文节点，但可以引用同一个 H21 指标。
6. 2.0.0 取消名称、别名、关键词和模糊匹配，只允许结构化身份的精确对表。
7. H21 继续提供标度、扣分、权重、累计公式、等级边界和单项控制。
8. “其它病害”和没有 H21 评分依据的来源扩展病害可以选择、记录和出报告，但暂不扣分。
9. 来源软件的 `judgeStandard`、扣分值和评分结果只用于核查，不进入本系统计算。
10. 现有数据均为测试数据，不建设 1.0.3 到 2.0.0 的历史数据迁移流程。

## 3. 范围

### 3.1 纳入范围

只纳入来源软件桥梁树的以下章节：

```text
第5节  梁式桥上部结构
第6节  拱式桥上部结构
第7节  悬索桥
第8节  斜拉桥
第9节  桥梁下部结构
第10节 桥面系
```

纳入内容包括：

- 分组层级、名称和顺序；
- 分组与病害指标之间的关系；
- 来源软件页面显示的病害编号和名称；
- 同一个指标在多个分组中的复用关系；
- 来源软件的桥梁扩展病害；
- 经确认的“参照某 H21 指标执行”关系；
- 明确、不产生评分的“其它病害”节点。

当前离线库中，第 5–10 节共有 403 组唯一的“分组—指标”关系，生成结果必须逐项覆盖。

### 3.2 不在范围内

- 第 11 节“其它”；
- 第 12 节涵洞；
- 第 13 节隧道；
- 第 14 节“涵洞 JTG 5120—2021”；
- 运行时读取来源软件的评定树表；
- 复制来源软件自己的扣分表、分数、等级或权重；
- 文字、别名、关键词或模糊匹配；
- 在线评定树编辑器；
- 对现有测试数据实施版本迁移；
- 为涵洞或隧道预留当前不需要的业务逻辑。

## 4. 三类来源的职责

### 4.1 来源软件

来源软件的离线库负责提供桥梁、构件和病害等原始检测数据。一条病害至少保留来源记录身份、
来源指标身份和能够确定所属评定分组的结构化上下文。

来源软件的评定树表只在开发 2.0.0 时用于一次性提取和核对结构。正式运行时，系统不启动
来源软件、不访问网站、不从其安装目录动态加载评定树。

### 4.2 单位桥梁评定树 2.0.0

单位桥梁评定树负责：

- 病害位于哪个桥型、结构和部件分组；
- 页面显示的编号、名称和顺序；
- 来源结构化身份到内部节点的精确映射；
- 节点是否评分；
- 评分节点引用哪个 H21 指标。

### 4.3 H21 规范包

H21 规范包是评分权威来源，继续负责：

- 病害标度及判定依据；
- 标度对应扣分；
- 多病害累计扣分；
- 构件、部件和结构评分；
- 权重、等级边界和单项控制。

单位评定树不得覆盖 H21 数值规则。

## 5. 总体数据流

```text
来源软件离线库
  │ 只读提取检测数据
  v
来源导入转换层
  │ 来源分组身份 + 来源指标身份
  v
organization-bridge/2.0.0
  │ 节点位置、显示编号、评分引用
  v
JTG/T H21—2011 规范包
  │ 标度与扣分计算
  v
本系统评分结果
```

构建 2.0.0 时另有一条离线、一次性的开发流程：

```text
来源评定树表
  v
脱敏结构快照
  v
修正清单
  v
确定性生成器
  v
organization-bridge/2.0.0
```

这条构建流程不进入产品运行时。

## 6. 包结构

2.0.0 包至少包含：

```text
standards/rating-tree/organization-bridge/2.0.0/
├─ manifest.json
├─ tree.json
├─ source-index-map.json
├─ corrections.json
└─ sources.json
```

- `manifest.json`：包身份、版本、状态、文件校验值和默认版本信息；
- `tree.json`：正式桥梁评定树；
- `source-index-map.json`：来源结构化关系到内部节点的精确对表；
- `corrections.json`：相对来源快照的已确认修正；
- `sources.json`：来源摘要、导出时间、原始数据库校验值和快照校验值。

2.0.0 不携带文字别名和模糊匹配规则。若现有加载器要求相关文件存在，应调整加载契约使其可选，
而不是迁移 1.0.3 的规则或放入有实际行为的占位规则。

脱敏结构快照放在独立的开发来源目录中，不把完整来源数据库提交到仓库。快照只包含生成树所需
的 `judgeTree`、`judgeIndex`、`judgeTree2Index` 字段和必要的核查信息，不包含用户、账号、
令牌、任务、桥梁业务数据或照片。

## 7. 节点模型

### 7.1 基本字段

每个节点显式保存：

```text
node_key
parent_key
node_type
display_number
name
display_order
is_selectable
scoring_mode
h21_node_key
```

`display_number` 是正式数据，不是派生展示值。2.0.0 页面和接口优先读取该字段。为读取旧包而
保留的编号推导逻辑不得覆盖 2.0.0 的显式值。

### 7.2 直接 H21 节点

```json
{
  "node_key": "org.bridge.defect.9_1_2_1",
  "parent_key": "org.bridge.group.9_1_2",
  "node_type": "defect",
  "display_number": "9.1.2-1",
  "name": "裂缝",
  "display_order": 6,
  "is_selectable": true,
  "scoring_mode": "inherit_h21",
  "h21_node_key": "h21.defect.9_1_2"
}
```

### 7.3 上下文复用节点

```json
{
  "node_key": "org.bridge.defect.9_1_2__9_1_1_1",
  "parent_key": "org.bridge.group.9_1_2",
  "node_type": "defect",
  "display_number": "9.1.1-1",
  "name": "蜂窝、麻面",
  "display_order": 1,
  "is_selectable": true,
  "scoring_mode": "reference_h21",
  "h21_node_key": "h21.defect.9_1_1_1"
}
```

该节点在页面上属于盖梁，显示来源软件编号 `9.1.1-1`，评分复用 H21 的同一指标。墩身下的
`9.1.1-1` 是另一个内部节点。两个内部节点可引用同一个 H21 指标，但不能共享 `node_key`。

### 7.4 暂不评分节点

```json
{
  "node_key": "org.bridge.defect.9_1_2_2",
  "parent_key": "org.bridge.group.9_1_2",
  "node_type": "defect",
  "display_number": "9.1.2-2",
  "name": "盖梁和系梁病害",
  "display_order": 7,
  "is_selectable": true,
  "scoring_mode": "non_scoring",
  "h21_node_key": null
}
```

该节点可以保存位置、数量、程度、描述和照片，也可以进入病害列表及报告，但不产生扣分。

## 8. 评分策略

2.0.0 只支持三种评分模式：

| 模式 | 使用条件 | 行为 |
| --- | --- | --- |
| `inherit_h21` | 来源指标与 H21 指标直接对应 | 使用对应 H21 标度和扣分 |
| `reference_h21` | 来源明确写明参照关系，或上下文节点复用现有 H21 指标 | 使用被引用的 H21 指标评分 |
| `non_scoring` | 其它病害或没有合法 H21 依据的扩展病害 | 可记录，不扣分 |

来源软件自带的自定义等级或扣分表不能成为第四种评分模式。无法证明 H21 依据时，一律使用
`non_scoring`，不能根据名称猜测评分规则。

例如来源软件中的“水损（参照混凝土碳化执行）”，只有在参照关系明确并经过核查后才配置
`reference_h21`。评分追踪同时保留单位显示节点和实际 H21 指标。

## 9. 精确来源对表

### 9.1 映射键

来源软件中的一个 `judgeIndex` 可以通过 `judgeTree2Index` 挂在多个评定分组下。因此仅使用
`judgeIndexId` 或指标编号不能确定页面位置。映射必须同时包含：

```text
来源评定分组身份 + 来源指标身份
```

`source-index-map.json` 的一条关系示意如下：

```json
{
  "source_group_id": "judgeTree.id",
  "source_index_id": "judgeIndex.id",
  "source_group_number": "9.1.2",
  "source_index_number": "9.1.1-1",
  "target_node_key": "org.bridge.defect.9_1_2__9_1_1_1"
}
```

来源病害记录不一定直接保存 `judgeTree.id`。导入适配器应从来源任务树、构件类型和已经验证的
结构化关系中解析来源评定分组身份；不能使用病害名称反推分组。无法取得唯一分组时，该记录
进入无法识别。

### 9.2 匹配顺序

```text
1. 来源分组 ID + 来源指标 ID 精确匹配
2. 来源分组编号 + 来源指标编号精确匹配，且组合必须唯一
3. 无法唯一确定时进入无法识别
```

第二步是结构化编号的精确匹配，不属于文字匹配。以下字段不参与 2.0.0 自动绑定：

- 病害名称；
- 病害描述；
- 别名；
- 关键词；
- 相似度；
- 正则猜测。

只有文字“盖梁裂缝”的记录不会自动绑定；来源上下文为 `9.1.2` 且指标为 `9.1.2-1` 的记录
可以精确绑定。无法识别的记录允许用户手工选择节点。

### 9.3 导入记录追踪

导入后的病害应保留足够的来源证据：

```text
source_record_id
source_group_id
source_index_id
source_group_number
source_index_number
rating_tree_version
rating_tree_node_key
mapping_status
```

字段是否直接进入业务契约或存入来源引用对象，在实施计划中结合当前导入契约确定，但不得丢失
区分上下文节点所需的信息。

## 10. 修正清单

来源快照保持原样，不直接修改。所有相对来源软件的改动都进入 `corrections.json`，至少记录：

```text
correction_id
source_group_number
source_index_number
field
source_value
corrected_value
reason
impact
scoring_policy
```

第一项已确认的修正示例：

```json
{
  "correction_id": "C001",
  "source_group_number": "9.2.1",
  "source_index_number": "9.2.1-11",
  "field": "name",
  "source_value": "墩身其它病害",
  "corrected_value": "台身其它病害",
  "reason": "指标位于9.2.1台身分组，原名称疑似复制自9.1.1墩身",
  "impact": "display_only",
  "scoring_policy": "non_scoring"
}
```

允许修正：

- 分组与病害名称明确不一致；
- 明确错别字；
- 编码错误或乱码；
- 经规范和来源结构共同证明的错误引用。

不得擅自修正：

- 同一指标位于多个分组；
- 编号不连续；
- 子节点编号前缀与父分组不同；
- 来源软件存在、H21 没有的扩展病害；
- 仅仅看起来不规整的编号。

修正条目必须严格校验原值。如果新快照中的原值已经变化，生成器应停止并要求重新核查，不能
继续强行应用旧修正。

## 11. 生成与发布

### 11.1 确定性生成

生成器读取脱敏快照和修正清单，按明确顺序生成 `tree.json` 与 `source-index-map.json`。
相同输入必须产生字节一致的输出和校验值。不能依赖 SQLite 未声明的自然行顺序；来源字段不足以
确定顺序时，应在快照中保存已核对的显式关系顺序。

### 11.2 发布策略

- 新包版本为 `organization-bridge/2.0.0`；
- 2.0.0 设置为当前默认评定树；
- 1.0.3 文件保持原样作为历史参照，但不再作为默认版本；
- 不修改已发布的 1.0.3；
- 2.0.0 发布后不可变，后续修正发布新的补丁或次版本；
- 当前测试数据可以清理重建或重新导入，不开发历史版本迁移流程。

### 11.3 运行时

正式系统只加载已发布的 2.0.0 包。运行时不访问来源软件的评定树表。用户执行来源数据导入时，
导入器只读打开其离线业务数据库，提取桥梁、构件、病害和照片等检测数据。

## 12. 校验与错误处理

以下情况必须阻止生成或发布：

- 同一个“来源分组 ID + 来源指标 ID”指向多个内部节点；
- 内部 `node_key` 重复；
- 同一父节点下顺序冲突且无法确定；
- 评分节点引用不存在的 H21 指标；
- `non_scoring` 节点仍配置 H21 扣分引用；
- 修正条目找不到对应源记录；
- 修正条目的原值与快照不一致；
- 第 5–10 节的来源关系在生成结果中遗漏；
- 结构化编号回退映射存在多个候选节点。

以下情况是合法结构，不应阻止发布：

- 相同显示编号出现在不同父节点下；
- 编号不连续；
- 子节点编号与父分组编号前缀不同；
- 来源扩展病害没有 H21 指标并被标为 `non_scoring`。

导入时无法精确映射的单条病害进入“无法识别”，不应导致整次导入失败，也不得回退到文字匹配。

## 13. 前端显示

评定树页面、病害选择器和病害详情统一使用节点的 `display_number`。显示格式为：

```text
{display_number} {name}
```

分组节点也拥有自己的显式编号。2.0.0 不再需要针对 `9_1_2` 的显示覆盖。旧包需要兼容时，
可以保留原编号解析器作为缺少 `display_number` 时的回退，但该回退不得作用于 2.0.0。

页面必须允许同一显示编号出现在不同分组下，节点选择和保存始终使用唯一 `node_key`，不能使用
显示编号作为数据库主键或前端列表键。

## 14. 验收标准

### 14.1 结构完整性

1. 生成树只包含第 5–10 节。
2. 当前快照的 403 组唯一“分组—指标”关系全部有对应内部节点。
3. 分组层级、显示顺序、显示编号和名称与来源软件一致，仅允许修正清单中的差异。
4. 来源关系与内部节点是一对一映射。

### 14.2 典型结构

至少验证：

- `9.1.2` 下复用的 `9.1.1-1` 至 `9.1.1-5` 保持原显示编号；
- `9.1.2-1` 盖梁裂缝引用 H21 表 9.1.2；
- `9.1.2-2` 可以选择和保存，但不扣分；
- `9.2.2` 等其他包含复用指标的分组保持正确上下文；
- 水损等明确参照项引用经核查的 H21 指标；
- 无 H21 依据的来源扩展病害全部为 `non_scoring`。

### 14.3 匹配行为

至少验证：

```text
来源分组 9.1.2 + 来源指标 9.1.2-1
→ org.bridge.defect.9_1_2_1

来源分组 9.1.2 + 来源指标 9.1.1-1
→ org.bridge.defect.9_1_2__9_1_1_1

只有文字“盖梁裂缝”
→ 无法识别

只有文字“裂缝”
→ 无法识别
```

“其它病害”只允许来源精确对表或用户手工选择，不允许关键词自动绑定。

### 14.4 评分行为

- 每个 `inherit_h21` 和 `reference_h21` 节点引用的 H21 指标存在；
- H21 标度、扣分和最终评分公式没有被单位树覆盖；
- `non_scoring` 节点不产生扣分；
- 评分追踪能够同时说明单位节点和实际 H21 指标。

### 14.5 确定性与界面

- 相同快照和修正清单连续生成两次，输出和校验值完全一致；
- 前端检查第 5–10 节的展开、折叠、编号和长名称布局；
- 页面允许同编号节点位于不同分组，不发生键冲突；
- 重点截图核对 `9.1.2`、`9.2.2` 等复用关系较多的分组。

## 15. 与既有设计的关系
