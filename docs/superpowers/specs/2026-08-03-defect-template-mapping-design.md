# 用来源软件的病害描述模板建立受控映射

> **状态：2026-08-07 放弃。不要按本文档施工，方案已被数据证伪。**
>
> 本文档想建的是「病害描述模板 → 评定树病害」的映射表。查过来源软件的离线库之后，
> 这张表**在数学上就不存在**：模板与评定指标是多对多关系。
>
> 证据（读自 `judgeIndex2diseaseType`，730 行链接记录、266 个模板）：
>
> - 模板「受渗水侵蚀，混凝土剥蚀破损」**一个模板同时挂在 9 个指标下**——
>   5.1.1-2 剥落掉角、9.1.1-2 剥落露筋、9.1.1-10 水损害、9.2.1-10 水损害、
>   9.2.2-1 破损、9.2.2-2 混凝土碳化腐蚀、1.3.1-2 混凝土剥离、1.3.2-4 露筋锈蚀、
>   6.2.2-6 表面缺陷；
> - **266 个模板里有 94 个被 2 个以上指标引用**；
> - 百股大桥 2024 那 279 条实测数据里就出现了 3 例同模板落不同指标：
>   「破损」→ 10.1.1-3 / 10.2.1-3，「受渗水侵蚀」→ 9.1.1-5 / 9.2.2-2，
>   「破损露筋」→ 10.3.1-1 / 10.4.1-2。
>
> 同一句描述文字，在桥面铺装上和在伸缩缝上是不同的规范病害。用模板去反推指标，
> 等于丢掉「检测员当初选的是哪个指标」这个已知条件再去猜它。
>
> **正确做法**：每条病害记录自带 `judgeIndexId`，直接读它。见
> `2026-08-05-source-system-direct-import-design.md`。
>
> 配套代码 `tools-python/bridge_report_tools/standards/defect_template_source.py`
> 与其测试已于 2026-08-07 删除（零生产引用）。本文档仅作决策留档。

日期：2026-08-03
状态：待实施

## 1. 为什么做

现有 2024 年度导入记录 361 条病害，只有 185 条定到了评定树节点：

| 病害类型 | 总数 | 已定 | 未定 |
| --- | ---: | ---: | ---: |
| 渗水泛碱 | 184 | 184 | 0 |
| （病害类型为空） | 52 | 0 | 52 |
| 受渗水侵蚀，混凝土剥蚀破损 | 33 | 0 | 33 |
| 受渗水侵蚀 | 32 | 0 | 32 |
| 横向裂缝 | 26 | 0 | 26 |
| 其余 8 类 | 34 | 1 | 33 |

定上的 184 条靠的是有人手写的 3 条受控别名（`渗水泛碱` / `泛碱` / `受渗水侵蚀` → 水损）。
规则包里别名总共只有 6 条、关键词规则 4 条——机制有效，但覆盖面太窄。

检测人员并不是自由造句：来源软件在每个构件分组下给出固定的病害描述模板，
模板与评定指标的对应关系在那套软件里是**已经确定的事实**，不需要从字面推断。
把这批对应关系搬进受控别名表，就是把一个已被验证有效的机制铺满。

## 2. 核心判断：不新建机制

受控别名表现有结构与来源软件的组织方式同构：

```json
{"alias": "受渗水侵蚀",
 "target_node_id": "org.bridge.defect.5_1_1_water_damage",
 "bridge_type_id": "h21.bridge_type.beam",
 "component_category_id": "h21.component.beam.upper_general"}
```

作用域是 **桥型 + 构件类别 + 文本 → 节点**；来源软件是 **构件分组 → 评定指标 → 模板**。
两者可以对接。因此本设计**不引入新的匹配层，也不改匹配算法**，只做一件事：
把别名表从 6 条扩到覆盖实际使用的模板。

分层匹配的其余各层（精确名、关键词、叙述片段、模糊候选）保持不变。别名层变厚之后，
后面几层自然退化为兜底。这是刻意的：删掉它们会让未收录的模板直接变成"无匹配"，
而不是给出候选。

## 3. 数据来源

来源软件是 `bridge.ilis.cn` 的 Electron 外壳，它把整套规则库下载到了本机：

```
%APPDATA%\datacheck.hitek.com\databases\https_bridge.ilis.cn_0\1
```

279.9 MB 的 SQLite（2026-07-30 快照）。取数**不访问对方服务器**。

相关表：

| 表 | 行数 | 含义 |
| --- | ---: | --- |
| `judgeTree` | 223 | 构件分组（章节号 + 名称，如 `5.1.1 上部承重构件、上部一般构件`） |
| `judgeIndex` | 580 | 评定指标（如 `5.1.1-2 剥落、掉角`） |
| `sysConfig` (`catag='diseaseType'`) | 308 | 病害描述模板 |
| `judgeTree2Index` | 662 | 分组 ↔ 指标 |
| `judgeIndex2diseaseType` | 730 | 指标 ↔ 模板 |

三表联查去重后得到 **808 条**「构件分组 + 评定指标 + 模板」三元组，这是全部原料。

**`tableNum` 不是唯一键。** 同一个编号在不同分组下是不同的指标：`5.1.1-13` 既是
「桥面板其它病害」（挂在 6.x 的桥面板分组），又是「水损（参照混凝土碳化执行）」
（挂在 5.1.1 上部承重构件）；`1.3.1` 重复 24 次。导出一律按 `judgeIndex.id` 取，
按编号取会张冠李戴。

## 4. 生成链路

```
模板名 + 源构件分组
   │
   ├─ 源分组 ──[人工对表]──→ H21 构件类别集合
   │
   └─ 源指标编号 ──[机械映射]──→ h21.defect.X_Y_Z ──→ 评定树节点（按 h21_indicator_id 反查）
                                                          │
                                                          └─→ 节点自带的桥型 × 构件类别
   ↓
别名条目 (alias, target_node_id, bridge_type_id, component_category_id)
```

指标编号那一段是机械的：`5.1.1-2` → `h21.defect.5_1_1_2` → 评定树里 `h21_indicator_id`
等于它的节点。构件分组那一段不是——见下一节。

## 5. 人工对表：本期唯一的人工工作量

808 条三元组分三档：

| 档 | 条数 | 含义 | 处理 |
| --- | ---: | --- | --- |
| a | 362 | 指标编号对上 H21，且分组本身属于定检章节 | 机械映射 |
| b | 12 | 同章节但超出 H21 编号，是单位扩展项 | 需要一张 7 行的指标对表 |
| c | 434 | 经常检查（1.x）、隧道（13.x）、涵洞（12.x）等别的标准 | 排除 |

a 档涉及来源软件的 **45 个构件分组**。

**分档要同时看指标编号和分组章节。** 只看编号会漏掉这种情况：涵洞的
`12.4-4 排水沟` 分组底下挂着桥梁栏杆的 `10.4.1-2 破损`——编号是 H21 的，但分组属于
涵洞，不该按桥梁定检处理。实测这类污染 11 条，全部来自这一个分组。

**b 档不能扔。** H21 的 5.1.1 只到 `-12`，没有"水损"这个指标；单位评定树自己加了
`org.bridge.defect.5_1_1_water_damage` 节点——291 个病害节点里唯一一个非编号型 id，
靠编号反查不到。b 档的 7 个指标恰好包含 `9.1.1-10 水损害`（墩身）与
`9.2.1-10 水损害`（台身），正是 §9 验收里点名的那几组。

**两张对表，45 行 + 7 行。** 构件分组那张 46 行，指标那张 7 行（b 档的扩展项 →
评定树节点 id）。后者虽小但不可省，理由见上。

这 45 个分组必须人工对到 H21 构件类别，因为两套体系的粒度不同：来源软件的分组细到
`6.2.9 桥面板`、`1.2.7.1`，而 H21 包的目录只有 10 个粗键（`5.1.1`、`6.1`、`7`、`8`…）。
机械按章节号匹配的实测结果是只能生成 102 条、其中 76 条冲突——不可用。

对表产物是一张 45 行的表：

```
源分组编号  源分组名称                    →  H21 构件类别
5.1.1      上部承重构件、上部一般构件         →  h21.component.beam.upper_bearing,
                                              h21.component.beam.upper_general
9.1.1      墩身                          →  h21.component.lower.pier
10.1.1     沥青混凝土桥面铺装               →  h21.component.deck.pavement
...
```

这张表随规则包一起入库，是本期的核心交付物。

## 6. 两类歧义，两种处理

同一个模板在同一构件下指向多个指标时产生歧义。实测数据里存在两类，**成因不同，
不能用同一种办法对付**。

### 6.1 A 类：构件粒度不够

26 条「横向裂缝 @ 桥面铺装」。来源软件把桥面铺装拆成两个分组，各自的裂缝指标不同：

- `10.1.1 沥青混凝土桥面铺装 → 10.1.1-4 裂缝`
- `10.1.2 水泥混凝土桥面铺装 → 10.1.2-7 裂缝(板角断裂、破碎板)`

各自唯一，歧义只因为本系统的构件类别不分材质：H21 分类里只有一个
`h21.component.deck.pavement`，台账条目的 `site_component_type` 也只写"桥面铺装"。

**处理：本期不补这一维，按多候选交给人。** 补材质要动构件分类体系或台账字段，
是独立一件事，不塞进本期。记入已知取舍。

### 6.2 B 类：模板本身语义不足

30 条「受渗水侵蚀 @ 桥墩」。来源软件在 `9.1.1 墩身` 下把同一模板挂了两个指标：

- `9.1.1-10 水损害`
- `9.1.1-5 混凝土碳化、腐蚀`

检测员写下这个模板时心里知道是哪一个，但**模板名里没有这个信息**。补任何构件属性
都救不了——区别在病害性质，不在构件。

**处理：只能人判。** 系统给出两个候选、标注来源指标编号，人点一个。同批同性质的
可以批量确认。

### 6.3 生成时的冲突策略

对表完成后重新生成，若同一 `(模板, 桥型, 构件类别)` 仍指向多个节点：**不写入别名表**，
改为写入候选规则，让匹配结果落到 `candidates` 而不是 `auto_bound`。
绝不在生成阶段替人挑一个。

## 7. 版本与不可变性

别名随不可变评定树包版本发布，这条约束不变：

- 新别名必须发布为新的包版本（如 `organization-bridge/1.0.4`），不得改写已发布版本。
- 年度要用上新别名，必须在构件绑定页重新绑定到新版本。**重绑会派生新的台账修订版
  并重算该年度全部病害匹配**——2024 年度那 361 条会被重新匹配一遍。
- 已确认、已忽略、组已确认、人工选择的病害在重新匹配时被跳过，不会被自动结果覆盖。
  这意味着已经人工定好的结果不会因为新别名而改变。

## 8. 范围边界

**做：**

1. 从本机离线库导出 808 条三元组，过滤出 H21 定检的 373 条。
2. 人工完成 46 行的「源构件分组 → H21 构件类别」对表。
3. 生成别名条目，冲突项降级为候选规则。
4. 发布为新的评定树包版本，配套 checksum 与 smoke。
5. 提供可复跑的导出脚本，供来源软件更新规则库后重新生成。

**不做：**

1. 不改匹配算法、不删现有匹配层。
2. 不引入构件材质维度（A 类歧义留给后续独立设计）。
3. 不覆盖经常检查、隧道、涵洞等 H21 之外的标准。
4. 不自动替人消歧义。
5. 不迁移历史数据，不改写已确认的病害。

## 9. 验收标准

1. 导出脚本可复跑，对同一份离线库产出字节一致的结果。
2. 生成的别名条目全部通过规则包 schema 校验，checksum 稳定。
3. 冲突项零漏报：任何 `(模板, 桥型, 构件类别)` 多指向都不得进入别名表。
4. 用 2024 年度那份草稿离线验证：可自动定节点的条数由 185 提升到 230 上下
   （新增 33 条剥落掉角、10 条桥面破损、2 条桥台水损害），另 26 条横向裂缝与
   30 条墩身水损以候选形式出现。该数字以实际重新匹配结果为准，不作为硬指标。
5. 后端与前端既有测试全绿，迁移各跑两遍。

## 10. 已知取舍

1. **桥面铺装材质未建模**，26 条横向裂缝要人工点选。补这一维需要动构件分类体系，
   本期刻意不做。
2. **对表是人工的，且会过期**。来源软件更新规则库后新增的分组需要补对表，
   导出脚本会报告未覆盖的分组。
3. **只覆盖 H21 定检**。用同一套软件做经常检查的数据仍走原有匹配层。
4. **模板名带数量时可能对不上**。如「1处涂层脱落，钢梁锈蚀」，若检测员把"1处"改掉，
   精确别名失效，落到后面的匹配层。实测本年度数据未出现该情况，暂不特殊处理。
5. **启用需要年度重绑**，代价是该年度全部病害重新匹配一遍。建议在一个年度校对开始前
   完成升级，而不是校对进行到一半时。
