# 2026-08-12 设计：构件范围拆分预览性能优化

## 1. 背景

构件绑定界面支持用户选择范围构件并预览拆分影响，例如：

- `1-1#板～1-25#板`
- `2-1#板～2-25#板`

当前点击“拆分构件”后，前端先请求 `split-preview`，直到后端完成预览才打开对话框。用户在此期间看不到加载状态，容易认为按钮没有响应。

后端预览也不是单纯统计。当前实现会读取整份导入候选 JSON 和完整构件台账，调用完整拆分规划器，复制病害和照片候选、改写引用和警告、重新匹配构件、生成完整拆分后 JSON，再把原始数据、台账和完整计划序列化后计算影响令牌。对话框实际只展示少量统计数据，因此预览阶段承担了大量只有正式应用才需要的工作。

本设计是对既有《构件绑定中的用户选择式范围拆分》设计的性能补充。范围语法、拆分规则、照片复制、自动绑定、评分语义、追溯信息和事务原子性均保持不变。

## 2. 目标

1. 点击“拆分构件”后立即显示对话框和明确的计算状态。
2. 将预览从“生成完整拆分结果”改为“只验证并计算摘要”。
3. 仅在用户确认后生成完整病害、照片和警告结果。
4. 简化影响令牌的输入，同时保持预览过期检测能力。
5. 保持正式拆分结果、业务规则和并发安全语义不变。
6. 增加分段耗时记录，用真实数据确认后续优化方向。

## 3. 非目标

本轮不包含：

1. 全局构件台账缓存或跨请求匹配索引缓存。
2. 异步任务队列、后台作业或进度轮询。
3. 修改数据库结构。
4. 修改范围解析语法、数量上限或拆分资格规则。
5. 修改病害、照片、警告或 `range_split_origin` 的生成规则。
6. 修改构件匹配规则或评分算法。
7. 信任客户端提交的展开编号、计数或绑定结果。

照片关联索引和构件匹配索引可以在实测仍不达标时作为后续优化，但不纳入本次实现范围。

## 4. 现状与主要成本

当前调用链如下：

```text
点击拆分构件
→ 请求 split-preview
→ 读取 parsed_result_json
→ 加载完整构件台账
→ 完整模拟拆分病害与照片
→ 对新病害重新匹配构件
→ 生成完整 result_json
→ 序列化原始数据、台账和计划并计算影响令牌
→ 返回摘要
→ 前端打开对话框
```

完整规划器中的主要重复扫描包括：

```text
选择范围数 × 全部病害
+ 生成病害数 × 全部照片
+ 生成病害数 × 全部台账构件
```

此外，预览还会复制大量 `Json::Value` 并序列化完整拆分结果。这些工作不会写入数据库，却会在正式应用时再次执行。

## 5. 总体设计

拆分逻辑分为两个职责明确的阶段。

### 5.1 轻量分析

新增独立分析单元，概念接口为：

```cpp
analyze_component_range_splits(current, revision, targets)
```

它负责：

- 规范化、排序并去重选择目标；
- 验证目标存在、状态合法且范围可安全展开；
- 查找每个范围对应的来源病害；
- 统计展开构件数、来源病害数和结果病害数；
- 统计结果照片候选数；
- 判断每条结果病害将自动绑定、歧义还是未匹配；
- 校验单范围和整批生成数量上限；
- 生成稳定的预览摘要。

它不负责：

- 复制完整病害对象；
- 复制照片候选；
- 创建新候选 ID；
- 改写照片引用、警告或错误；
- 创建 `range_split_origin`；
- 生成完整 `result_json`。

### 5.2 结果物化

保留或提取独立结果生成单元，概念接口为：

```cpp
materialize_component_range_splits(current, revision, analysis)
```

它只在正式应用阶段调用，使用已经重新验证的分析结果生成：

- 拆分后的病害候选；
- 复制后的照片候选；
- 新候选 ID 和关联关系；
- 改写后的对象级及导入级警告、错误；
- 永久 `range_split_origin`；
- 最终 `parsed_result_json`。

分析器和物化器之间使用内部结构化结果传递来源病害、展开编号和匹配判断，避免两者对业务规则作不同解释。外部接口不暴露这些内部数据。

## 6. 前端交互

### 6.1 状态模型

拆分对话框具有三种显式状态：

1. `loading`：正在计算预览。
2. `ready`：预览完成，可以确认拆分。
3. `error`：预览失败，可以重新计算或关闭。

点击“拆分构件”后，前端先打开对话框并进入 `loading`，再发起接口请求。不得等接口返回后才创建对话框。

### 6.2 计算状态

`loading` 状态显示“正在计算拆分影响”，并禁用“确认拆分”。用户可以关闭对话框。

`ready` 状态沿用现有摘要内容，包括：

- 选择范围数；
- 来源病害数；
- 结果病害数；
- 结果照片候选数；
- 自动绑定、歧义和未匹配数量；
- 评分影响提示。

`error` 状态在对话框内显示后端具体错误，并提供“重新计算”和“关闭”。页面级错误区不作为预览错误的主要展示位置。

### 6.3 异步请求边界

- 同一时刻只允许一个预览请求。
- 用户关闭对话框后，应中止请求；若现有请求工具不支持中止，则必须忽略迟到响应。
- 切换导入记录后，旧请求结果不得更新新页面状态。
- 重新计算沿用当前有效选择；概览刷新后已失去资格的目标按现有规则从选择中移除。
- 预览期间禁止重复触发拆分按钮，其他会改写同一导入草稿的操作继续受现有 `busy` 状态约束。

## 7. 预览接口

接口路径和主要响应形状保持兼容：

```text
POST /api/import-records/{import_id}/component-binding/split-preview
```

请求仍只提交原始目标：

```json
{
  "targets": [
    {
      "part_name": "上部承重构件",
      "component_number": "1-1#板～1-25#板"
    }
  ]
}
```

响应仍包含 `items`、`totals` 和不透明的 `impact_token`。预览接口不得返回完整病害、照片或拆分后 JSON。

```json
{
  "items": [
    {
      "part_name": "上部承重构件",
      "component_number": "1-1#板～1-25#板",
      "expanded_component_count": 25,
      "source_defect_count": 1,
      "result_defect_count": 25,
      "result_photo_count": 0,
      "bound_count": 25,
      "ambiguous_count": 0,
      "unmatched_count": 0
    }
  ],
  "totals": {
    "selected_range_count": 1,
    "source_defect_count": 1,
    "result_defect_count": 25,
    "result_photo_count": 0,
    "bound_count": 25,
    "ambiguous_count": 0,
    "unmatched_count": 0
  },
  "impact_token": "sha256:..."
}
```

前端现有预览类型可继续使用，减少接口迁移范围。

## 8. 轻量影响令牌

### 8.1 目的

影响令牌用于保证用户确认时的输入仍与预览时一致。客户端只负责原样回传，不解析令牌，也不能用令牌替代服务端重新验证。

### 8.2 令牌输入

令牌覆盖决定拆分结果的稳定输入：

- 导入记录 ID；
- 当前 `parsed_result_json` 的稳定摘要；
- 已确认构件台账修订版 ID；
- 规范化、排序并去重后的选择集合；
- 轻量分析摘要。

概念形式为：

```text
sha256(
  import_id
  + parsed_result_digest
  + inventory_revision_id
  + canonical_targets
  + canonical_analysis_summary
)
```

不再把完整台账 JSON 和完整拆分后 JSON 放入令牌输入。台账内容由不可变修订版 ID 标识；如果系统允许原地修改已确认修订版，则必须先修正该不变量，或额外加入台账内容摘要，不能仅依赖 ID。

稳定摘要必须使用确定的字段顺序和目标排序，不能依赖容器迭代顺序。

### 8.3 过期判断

正式应用时重新分析并计算令牌。以下变化必须导致令牌不一致：

- 来源病害内容或集合变化；
- 照片关联变化；
- 构件绑定或处理状态变化；
- 构件台账修订版变化；
- 选择目标变化；
- 范围展开、匹配结果或统计摘要变化。

令牌不一致时返回现有 `component_range_split_stale`，事务内不写入任何结果。

## 9. 正式应用流程

应用接口保持不变：

```text
POST /api/import-records/{import_id}/component-binding/split-apply
```

流程如下：

1. 开启事务并锁定导入记录。
2. 校验导入仍处于 `待校对`。
3. 读取当前已确认台账修订版。
4. 使用客户端提交的原始目标重新执行轻量分析。
5. 重新计算影响令牌并与预览令牌比较。
6. 不一致时回滚并返回预览过期错误。
7. 一致时调用结果物化器生成完整拆分结果。
8. 写入 `parsed_result_json` 并提交事务。
9. 返回拆分摘要和最新构件绑定概览。

后端不得接受客户端提交的展开编号、统计数字或自动绑定结果作为权威输入。任一目标失效、超过上限或物化失败时，整批零写入。

## 10. 错误处理

沿用现有稳定错误码和后端校验规则。

- 预览计算失败：弹框显示具体错误并允许重新计算。
- `component_range_split_stale`：保留当前选择，回到计算状态重新请求预览。
- 目标不存在、已绑定、已标记缺失或范围失效：指出具体 `part_name` 和 `component_number`；用户关闭弹框后刷新构件绑定概览。
- 导入状态或台账状态变化：拒绝操作，不保留部分结果。
- 数据库或事务失败：显示服务端错误，不关闭弹框，不清空用户选择。

预览失败不得留下数据库记录或修改草稿。应用失败不得留下部分拆分结果。

## 11. 性能观测

后端为预览和应用记录结构化分段耗时：

```text
load_import_ms
load_inventory_ms
analyze_ms
token_ms
materialize_ms
persist_ms
total_ms
```

预览请求的 `materialize_ms` 和 `persist_ms` 应为零或不记录。日志同时记录：

- 导入记录 ID；
- 选中范围数；
- 来源病害数；
- 结果病害数；
- 结果照片候选数；
- 请求类型为 `preview` 或 `apply`。

日志不得记录完整病害 JSON、照片内容、认证令牌或影响令牌原文。

## 12. 性能目标

1. 点击按钮后 `100ms` 内出现弹框计算状态。该指标主要由前端状态更新保证。
2. 常见 25～50 个展开构件的预览，以 Release 后端和真实数据为基准，目标为 `500ms` 内完成。
3. 预览响应不得包含完整病害或照片对象，响应大小应只随选择范围数线性增长。
4. 预览阶段不得物化完整 `result_json`。
5. 即使超出 `500ms`，界面仍必须显示明确加载状态，不能表现为按钮无响应。

`500ms` 是真实环境的性能验收目标，不作为持续集成中的硬超时断言，以免测试受机器负载影响而不稳定。

## 13. 测试

### 13.1 轻量分析单元测试

- 单范围和多范围统计正确；
- 一行引用多条病害；
- 无照片、单照片和多照片统计；
- 自动绑定、歧义和未匹配混合统计；
- 非法、失效、已处理及超限范围仍按原规则拒绝；
- 分析结果不包含完整拆分后 JSON；
- 轻量分析统计与现有完整规划器在相同输入下保持一致。

### 13.2 结果物化测试

- 正式拆分生成的病害内容与当前实现一致；
- 照片候选、引用和候选 ID 改写一致；
- 对象级及导入级警告、错误改写一致；
- `range_split_origin` 内容一致；
- 自动绑定、歧义和未匹配结果一致；
- 任一失败时不产生可持久化的部分结果。

### 13.3 令牌和仓储测试

- 相同输入生成相同令牌；
- 目标顺序不同但集合相同时令牌相同；
- 病害、照片关系、处理状态或台账修订版变化时令牌失效；
- 预览只返回摘要，不写数据库；
- 应用在事务内重新分析，过期令牌整批拒绝；
- 达到生成数量上限时保持当前错误语义。

### 13.4 前端测试

- 点击后立即出现 `loading` 对话框；
- 预览完成前“确认拆分”禁用；
- 成功后显示摘要并启用确认；
- 失败后显示错误并支持重新计算；
- 关闭对话框后迟到响应被忽略；
- 切换导入记录后旧响应不得污染新页面；
- 连续点击不会产生多个并发预览；
- 应用成功后关闭弹框、清空选择并刷新统计；
- 应用失败时保留选择和弹框。

### 13.5 性能验证

使用真实 25～50 个展开构件的数据，在 Release 后端记录：

- 各阶段耗时；
- 预览响应大小；
- 优化前后 `total_ms`；
- 点击到弹框加载状态的前端耗时。

若轻量预览仍未达到目标，先根据分段日志确认瓶颈，再为照片关联或构件匹配增加请求内索引；不得在没有测量依据时直接引入全局缓存。

## 14. 验收标准

1. 点击“拆分构件”后立即出现计算中的弹框。
2. 预览完成前无法确认拆分，用户可以关闭弹框。
3. 预览接口只做轻量分析，不生成完整拆分结果。
4. 正式应用前重新分析并验证影响令牌。
5. 预览期间数据或台账变化时，应用被判定为过期且零写入。
6. 拆分后的病害、照片、警告、来源、绑定和评分输入与优化前一致。
7. 任一目标失败时整批原子回滚。
8. 预览错误、过期和重试都在弹框内形成完整操作闭环。
9. 后端日志能够区分读取、分析、令牌、物化和持久化耗时。
10. 常见 25～50 个展开构件在 Release 真实数据环境中的预览以 `500ms` 为目标。

## 15. 后续优化门槛

本设计完成后先依据分段日志判断是否需要第二阶段：

- `analyze_ms` 主要消耗在反复扫描照片时，增加请求内 `defect_candidate_id → photos` 索引；
- `analyze_ms` 主要消耗在构件匹配时，增加请求内“归一化编号 + 类别”索引；
- `load_inventory_ms` 仍占主导且跨请求重复明显时，再设计按台账修订版缓存的只读匹配视图；
- 不在本轮直接增加全局缓存，避免提前引入失效、内存和并发复杂度。
