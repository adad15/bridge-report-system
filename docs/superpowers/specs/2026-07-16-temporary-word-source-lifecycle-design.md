# 临时 Word 来源文件生命周期设计

## 1. 文档状态

- 日期：2026-07-16
- 所属范围：模块 06.5 交互与数据流优化补充
- 状态：已确认，待实施
- 用户决策：方案 B + C1
- 历史迁移：当前没有上传成功的原始 Word，不需要迁移或清理历史文件

## 2. 背景与问题

年度检测工作台当前先把上传的 Word 登记到 `archived_files`，再按桥梁、年度、导入记录和原始文件名生成长期归档路径。该设计存在两个问题：

1. 桥梁、年度和导入关系已经由 PostgreSQL 保存，磁盘目录再次表达这些关系，造成路径层级和信息重复。
2. Windows 下将 UTF-8 原始文件名转换为本地文件系统路径时，特殊破折号、全角符号或当前代码页无法表示的字符可能导致归档失败。

本次实际失败日志为：

```text
No mapping for the Unicode character exists in the target multi-byte code page.
```

用户进一步确认：原始 Word 不需要作为正式档案长期保留。系统只需要在上传和解析期间临时持有 Word；解析成功立即删除，解析失败保留 24 小时以支持重新解析。

## 3. 核心决策

### 3.1 原始 Word 的定位

原始 Word 是“解析输入”，不是“正式归档文件”。

系统长期保留：

- 导入记录及其状态；
- 原始文件名、扩展名、大小、SHA-256 和上传时间等元数据；
- 解析后的 `BridgeAnnualInspectionData` JSON；
- 校对草稿、正式病害、技术状况评分和来源表格定位；
- 从 Word 提取并归档的病害照片。

系统不长期保留：

- 上传的原始 `.docx` 二进制文件；
- 依赖原 Word 重新运行未来新版解析器的能力；
- Word 中未被解析器提取的其他内容。

### 3.2 临时路径

新增独立配置 `temporary_storage.root`。Word 直接保存到该根目录，不再按桥梁、年度和导入记录建立多层目录。

```text
<temporary_storage.root>/<随机 UUID>.docx
```

本地配置示例：

```json
{
  "temporary_storage": {
    "root": "runtime/temp/word-imports",
    "failed_word_retention_hours": 24
  }
}
```

示例物理路径：

```text
runtime/temp/word-imports/883a08d4-557d-4421-8cc3-c1036e19b56a.docx
```

文件名只包含 UUID 和 ASCII 扩展名。用户原始文件名仅保存在数据库中，不参与磁盘路径构造。

### 3.3 生命周期策略 C1

- 解析成功：立即进入清理流程。
- 解析失败：保留 24 小时，允许重新解析。
- 24 小时到期：后台清理，不再允许使用原文件重试。
- 到期后再次处理：页面要求用户重新选择 Word 上传。
- 物理删除失败：记录失败原因和下次重试时间，后端启动或定时任务继续清理。

## 4. 为什么仍需短暂写入磁盘

现有流程由两个后端动作组成：

1. 上传 Word 并创建导入记录；
2. 使用导入记录调用 Python 解析器。

上传 HTTP 请求结束后，浏览器发送的文件内容不会继续留在后端内存中。解析失败后若要支持 24 小时内直接重试，也必须有一份临时文件。因此 C1 不是“永远不写磁盘”，而是“只写受控临时目录，并按生命周期删除”。

不采用“上传、等待 Python、保存结果全部塞进一个 HTTP 请求”的方式，因为长请求更容易受页面刷新、网络中断和超时影响，也无法自然支持失败重试。

## 5. 数据模型

新增表 `import_source_files`，与正式归档表 `archived_files` 分离。

建议字段：

| 字段 | 说明 |
| --- | --- |
| `id` | UUID 主键，同时用于生成临时磁盘文件名 |
| `system_number` | 临时来源文件编号，例如 `LSWJ-000001` |
| `import_record_id` | 一对一关联导入记录 |
| `original_file_name` | 用户上传时的原始文件名 |
| `storage_relative_path` | 相对于 `temporary_storage.root` 的 UUID 文件名 |
| `file_extension` | 当前固定为 `.docx` |
| `file_size_bytes` | 上传文件大小 |
| `file_hash` | SHA-256 |
| `status` | 临时文件当前状态 |
| `expires_at` | 解析失败后的到期时间 |
| `last_error` | 最近一次解析或清理失败原因 |
| `cleanup_attempt_count` | 清理尝试次数 |
| `next_cleanup_at` | 清理失败后的下次重试时间 |
| `created_at` / `updated_at` | 创建和更新时间 |
| `deleted_at` | 物理文件确认删除时间 |

一个导入记录最多关联一个原始 Word 临时文件。新导入记录不再设置 `import_records.main_file_id`，也不再为原始 Word 新建 `archived_files` 或“主报告”类型的 `import_record_files` 记录。

`import_records.main_file_id` 暂时保留，保证旧结构和既有测试数据兼容；本次不做破坏性删列。

### 5.1 状态机

```text
待解析
  └─开始解析→ 解析中

解析中
  ├─解析失败→ 解析失败（expires_at = 当前时间 + 24小时）
  └─结果入库成功→ 待清理

解析失败
  ├─24小时内重试→ 解析中
  └─到期→ 待清理

待清理
  ├─删除成功或文件已不存在→ 已删除
  └─删除失败→ 清理失败

清理失败
  ├─下次重试成功→ 已删除
  └─再次失败→ 清理失败（指数退避）
```

“文件已不存在”按删除成功处理，使清理操作保持幂等。

## 6. 端到端数据流

### 6.1 上传

1. 前端提交 Word 和业务字段。
2. C++ 校验扩展名、非空、大小和 SHA-256。
3. 数据库创建导入记录和 `import_source_files` 记录。
4. C++ 使用 `import_source_files.id` 生成 UUID 文件名，并以临时文件加原子重命名方式写入临时目录。
5. 文件写入或数据库提交任一步失败时回滚导入记录，并尽力删除已写入的临时文件。
6. 上传接口返回导入记录，前端继续调用解析接口。

数据库仍保存完整 Unicode 原文件名，但任何原文件名都不会进入 `std::filesystem::path`。

### 6.2 解析成功

1. 解析接口锁定导入记录和临时来源文件记录。
2. 状态从“待解析”或有效期内的“解析失败”变为“解析中”。
3. Python 读取临时 `.docx`，将提取照片写入工作目录。
4. C++ 校验合同并事务写入解析 JSON、照片归档元数据和导入状态。
5. 同一数据库事务把临时来源文件状态改为“待清理”。
6. 事务提交后立即删除临时 Word。
7. 删除成功后标记“已删除”；删除失败则标记“清理失败”，由后台继续重试。

先提交解析结果、再删除 Word，可以避免“Word 已删除但解析结果事务回滚”造成无法重试。

### 6.3 解析失败

1. 导入记录改为“解析失败”，保存可展示的错误信息。
2. 临时来源文件改为“解析失败”。
3. `expires_at` 设置为失败时刻后 24 小时。
4. 前端显示“重新解析”和剩余有效期提示。
5. 重试不要求重新选择文件，继续使用同一个 UUID 临时文件。

### 6.4 到期与清理

后台清理器在以下时机运行：

- C++ 后端启动时；
- 按现有清理间隔定时运行；
- 解析成功后即时尝试一次。

清理器有界批量认领：

- 已到期的“解析失败”；
- “待清理”；
- 已到下次重试时间的“清理失败”；
- 超过合理执行时限仍停留在“解析中”的异常记录。

异常“解析中”记录先恢复为“解析失败”，从恢复时刻开始保留 24 小时，避免后端崩溃导致文件永久滞留。

## 7. 删除年度和删除桥梁的联动

删除年度或桥梁时，未清理的临时 Word 也必须进入受控删除流程。

数据库删除事务在移除导入记录前，先把相关 `import_source_files.storage_relative_path` 复制到对应删除审计的文件清理队列。业务数据删除成功后，现有后台清理协调器负责物理删除。

删除影响预览应区分：

- 正式归档文件；
- 临时来源文件。

这样管理员能够看到实际要清理的物理文件数量，同时不会把临时 Word 描述成正式档案。

## 8. 来源证据边界

原 Word 删除后，“查看来源证据”仍保留：

- 导入记录编号；
- 原始文件名；
- 来源表标题、表序号、行号和原始单元格 JSON；
- 解析器名称和版本；
- 文件大小和 SHA-256；
- 已归档的病害照片。

界面不得暗示原 Word 仍可下载或打开。需要明确显示：

```text
原始 Word 已按临时文件策略清理，当前证据来自解析快照。
```

BridgeAnnualInspectionData 1.1 当前要求解析请求携带 `archived_file_system_number`。为避免本次扩大公共合同变更，兼容层暂时传入 `import_source_files.system_number`；它只用于解析快照中的来源标识，不代表文件被长期归档。后续升级合同时再将字段重命名为更准确的来源文件编号。

## 9. 崩溃恢复与一致性

必须覆盖以下情况：

| 异常位置 | 恢复策略 |
| --- | --- |
| 文件写入成功、数据库事务失败 | 请求内立即删除；后台扫描超过宽限期且无数据库记录的孤立 UUID 文件 |
| 数据库记录成功、文件写入失败 | 回滚数据库事务，不产生可见导入记录 |
| Python 调用期间后端退出 | 启动清理器恢复超时“解析中”为“解析失败”，保留 24 小时 |
| 解析结果已提交、删除前退出 | 临时状态已经是“待清理”，启动清理器继续删除 |
| 文件已删、状态更新前退出 | 下次删除发现文件不存在，按成功处理 |
| 清理时文件被占用 | 标记“清理失败”，指数退避后重试 |

所有路径必须经过受控根目录校验，拒绝绝对路径、`..` 和越界路径。

## 10. 接口与页面行为

上传接口继续返回导入记录，不暴露服务器绝对路径。

解析失败时，年度工作台应显示：

- 解析失败原因；
- 临时文件将在何时到期；
- “重新解析”按钮；
- “重新上传”入口。

临时文件到期后：

- 隐藏或禁用“重新解析”；
- 显示“原文件已过期，请重新上传”；
- 保留失败导入记录，供用户查看失败原因或取消。

解析成功后：

- 正常进入校对工作台；
- 不显示 Word 下载入口；
- 来源证据提示原始 Word 已清理。

## 11. 验收标准

1. 含中文、特殊破折号、全角括号、空格或 emoji 的 `.docx` 文件名可以上传并进入解析。
2. 临时磁盘文件名只使用 UUID 和 `.docx`，不包含桥名、年度、导入编号或原始文件名。
3. 新上传的原始 Word 不写入 `archived_files`。
4. 解析成功后，临时 Word 被立即删除；删除暂时失败时进入可重试状态。
5. 解析失败后，24 小时内无需重新上传即可重新解析。
6. 超过 24 小时后临时 Word 被清理，页面要求重新上传。
7. 后端重启能够恢复超时解析任务和未完成清理。
8. 年度或桥梁删除会同时清理关联临时 Word，并保留删除审计。
9. 临时文件清理失败不会回滚已经成功提交的解析结果或业务删除事务。
10. 提取照片仍按正式归档策略保存并可由受控接口读取。
11. 原始文件名、大小、哈希、解析结果和来源单元格快照继续可查询。
12. 上传、解析、重试、过期、启动恢复和删除联动均有 C++ + PostgreSQL 自动化测试；前端状态和提示有组件测试。

## 12. 非目标

- 本次不长期保存或提供原 Word 下载。
- 本次不改变病害照片的正式归档策略。
- 本次不迁移历史 Word；当前不存在上传成功文件。
- 本次不重构所有归档照片路径。
- 本次不升级 BridgeAnnualInspectionData 合同版本。
- 本次不保证未来解析器可重新处理已经成功并清理原 Word 的历史导入。
