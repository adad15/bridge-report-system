# 桥梁报告系统分块开发与技术文档评审机制

日期：2026-07-01

> 2026-09-04 现行修订：项目已经完成模块 01～06 主体及后续构件台账、系统自主评定、
> 导入解析关系化和批量病害线索整理。原模块 08“章节规则生成”和模块 09“Word 模板与生成”
> 在第一版合并为“报告模板管理与 Word 即时生成”，设计依据为
> `docs/superpowers/specs/2026-09-04-report-template-word-generation-design.md`。不再单独实施持久化
> 章节草稿或报告版本管理。模块 07 完整语义对比和模块 10 AI/Milvus 均不是第一版报告前置条件。

## 1. 目的

桥梁报告系统涉及数据模型、Word 解析、人工校对、历史对比、章节生成、Word 装配、AI 润色和文件归档。任何一个模块都可能影响后续模块。如果一次性写完整实施计划，容易把边界、依赖和风险混在一起。

后续开发按依赖链拆成小模块推进。每个模块先写技术文档，由 Codex 做第一轮技术把关，再交给用户确认。确认后，才写该模块实施计划并进入开发。

## 2. 总体原则

1. 按依赖链拆分，不按技术层孤立拆分。
2. 每个模块只解决一个边界清楚的问题。
3. 每个模块文档都要说明输入、输出、依赖、边界、验收标准和风险。
4. 先审文档，再写计划，最后动代码。
5. 已确认文档不是一次性产物，后续发现问题时要修订当前有效文档。
6. 当前有效文档要保持干净，历史原因放到变更记录或单独的变更提案里。
7. 任何影响多个模块的改动，都要先写变更提案，再同步更新受影响模块文档。

## 3. 模块拆分顺序

第一阶段按以下依赖链推进：

1. `01-tech-stack-and-project-skeleton`
   - 确认技术栈、目录结构、本地运行方式、测试方式和开发约束。
2. `02-postgresql-schema-and-file-archive`
   - 定义 PostgreSQL 事实主库 schema 初稿和文件归档目录规则。
3. `03-bridge-annual-inspection-data-contract`
   - 定义 `BridgeAnnualInspectionData` 稳定数据契约。
4. `04-word-importer-prototype`
   - 定义软件 Word 报告和正式 Word 报告导入原型边界。
5. `05-review-workspace`
   - 定义病害事实、照片、评分和来源的人工校对工作台。
6. `06-component-defect-archive`
   - 定义构件病害档案页和构件生命周期事实。
7. `07-defect-comparison-engine`（延期，不阻断第一版报告）
   - 定义病害身份候选匹配、人工确认、撤销和语义对比关系。
   - 当前已有最近两年度病害记录条数统计，但不能据此判断新增、修复或消失。
8. `08-09-report-template-and-word-generation`（当前下一阶段）
   - 合并原章节规则生成和 DOCX 模板装配。
   - 定义模板管理、语义锚点、人员设备配置、确定性章节规则、Word/WPS 字段更新和临时下载。
   - 不建立持久化章节草稿、报告版本或生成报告归档。
9. `10-milvus-ai-polish-and-fact-check`（后续可选）
   - 定义相似段落检索、AI 润色和事实校验边界，不作为第一版报告生成前置条件。

第一批优先完成前四个模块，因为它们决定项目底座、事实存储、数据契约和样例导入。

## 4. 每个模块技术文档的固定结构

每份模块技术文档必须包含以下章节：

1. 背景与目标
   - 本模块为什么存在。
   - 第一阶段要达到什么结果。
2. 范围
   - 本模块做什么。
   - 本模块不做什么。
3. 上游依赖
   - 依赖哪些已确认文档。
   - 依赖哪些数据、文件、模板或外部服务。
4. 下游影响
   - 会影响哪些后续模块。
   - 哪些字段、接口或约定不能随意改。
5. 核心设计
   - 数据结构、表结构、接口、服务边界或流程。
   - 必要时包含示例 JSON、SQL 或伪代码。
6. 错误处理与人工校对点
   - 哪些情况必须保留 warning。
   - 哪些结果必须人工确认。
7. 测试与验收标准
   - 单元测试、集成测试或样例资料验收方式。
   - 通过标准必须具体可验证。
8. 风险与取舍
   - 主要技术风险。
   - 暂不处理的内容及原因。
9. Codex 技术把关意见
   - 是否建议进入实施计划。
   - 需要用户重点确认的问题。
10. 变更记录
    - 记录每次修订的日期、原因、影响模块和处理结果。

## 5. 两级把关流程

每个模块按以下流程推进：

1. Codex 根据总设计文档和已确认上游文档起草模块技术文档。
2. Codex 自审文档，检查范围、依赖、字段命名、数据流、风险和验收标准。
3. Codex 在文档中写入“技术把关意见”。
4. 用户阅读该模块技术文档并提出修改意见。
5. Codex 根据用户意见修订文档。
6. 用户确认该模块文档。
7. Codex 为该模块写实施计划。
8. 用户确认实施计划后，再进入代码开发。

任何模块未完成第 6 步，不进入该模块实施计划。

## 6. 变更处理规则

开发过程中发现新问题时，先判断它属于哪一类变更。

### 6.1 模块内部小改动

如果改动只影响当前模块，例如字段说明、错误信息或页面筛选项的微调，直接修订当前模块文档，并在变更记录中说明。

### 6.2 影响上游或下游的改动

如果改动影响其他模块，例如第三阶段的数据契约新增字段并影响第二阶段数据库 schema，则必须同步更新所有受影响文档。

处理步骤：

1. 在当前模块文档中记录改动原因。
2. 列出受影响模块。
3. 修改受影响模块的当前有效文档。
4. 在每份被修改文档的变更记录中注明来源。
5. 如果已有实施计划，也同步修订实施计划。

### 6.3 跨模块重大改动

如果改动会改变系统边界、核心数据模型或主流程，例如改变 `DefectThread` 和 `DefectObservation` 的绑定关系，不能直接修改多份文档。

处理步骤：

1. 新建变更提案文档，命名为 `docs/superpowers/specs/changes/YYYY-MM-DD-change-NNN-topic.md`。
2. 写清楚问题、候选方案、推荐方案、影响模块、迁移策略和验收方式。
3. Codex 做第一轮技术把关。
4. 用户确认变更提案。
5. 将已确认结论合并回相关模块的当前有效文档。
6. 保留变更提案作为决策记录。

## 7. 文档命名与目录

总设计文档放在：

```text
docs/superpowers/specs/2026-07-01-bridge-report-system-design.md
```

分块评审机制文档放在：

```text
docs/superpowers/specs/2026-07-01-modular-technical-doc-review-design.md
```

模块技术文档放在：

```text
docs/superpowers/specs/modules/NN-topic.md
```

示例：

```text
docs/superpowers/specs/modules/01-tech-stack-and-project-skeleton.md
docs/superpowers/specs/modules/02-postgresql-schema-and-file-archive.md
docs/superpowers/specs/modules/03-bridge-annual-inspection-data-contract.md
docs/superpowers/specs/modules/04-word-importer-prototype.md
```

跨模块变更提案放在：

```text
docs/superpowers/specs/changes/YYYY-MM-DD-change-NNN-topic.md
```

模块实施计划放在：

```text
docs/superpowers/plans/NN-topic-implementation-plan.md
```

如果项目还没初始化 Git，也按以上目录维护文档；初始化 Git 后，再把这些文档纳入版本管理。

## 8. 当前有效文档规则

每个模块只有一份当前有效技术文档。后续修改优先修订原文档，而不是另起一份重复文档。

不建议这样做：

```text
03-bridge-annual-inspection-data-contract-v2.md
03-bridge-annual-inspection-data-contract-new.md
03-bridge-annual-inspection-data-contract-final.md
```

建议这样做：

```text
03-bridge-annual-inspection-data-contract.md
```

并在文档底部维护变更记录。项目初始化 Git 后，普通历史版本由 Git 保留；跨模块重大改动由变更提案保留。

## 9. 第一批文档推进顺序

第一批先写：

1. `01-tech-stack-and-project-skeleton`
2. `02-postgresql-schema-and-file-archive`
3. `03-bridge-annual-inspection-data-contract`
4. `04-word-importer-prototype`

这四份文档确认后，再写第一阶段的第一个实施计划。实施计划只覆盖“可运行项目骨架、数据库 schema、文件归档、年度数据契约、样例 Word 导入原型”，不包含完整病害校对页面、对比页面、正式报告生成和 AI 能力。

## 10. Codex 把关标准

Codex 在每份文档中重点检查：

1. 是否和总设计文档冲突。
2. 是否超出第一阶段范围。
3. 是否把事实判断交给 AI。
4. 是否缺少人工确认点。
5. 是否缺少来源追溯、置信度或校对状态。
6. 是否破坏 PostgreSQL 作为事实主库的原则。
7. 是否让后续模块依赖不稳定输入格式。
8. 是否有无法验证的验收标准。
9. 是否有会导致后续返工的数据模型缺口。
10. 是否需要同步修订其他模块文档。

## 11. 进入实施计划的条件

模块进入实施计划前必须满足：

1. 模块文档已写完。
2. Codex 已完成技术把关。
3. 用户已确认模块文档。
4. 文档没有未解决的范围问题。
5. 文档中的验收标准可测试。
6. 如果该模块影响上游文档，相关文档已经同步修订。

满足以上条件后，才为该模块或一组强相关模块写实施计划。

## 12. 与总设计文档的关系

总设计文档定义系统方向、边界和第一阶段验收标准。模块技术文档把总设计拆成可实现、可审查、可测试的小块。

如果文档发生冲突，按“当前代码和数据库迁移 → `PROJECT_CONTEXT.md` → 用户确认的较新日期设计或
变更文档 → 已同步的模块规格 → 早期总设计和历史实施计划”判断。早期总设计保留项目立项背景，
不能覆盖后续已经确认或实施的跨模块变更。
