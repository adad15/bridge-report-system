构件台账聚合接口设计审查报告

审查对象：2026-08-16-component-inventory-aggregate-api-design.md
审查日期：2026-08-16
审查结论：主体方案已经基本稳定，但 blocker 契约、空台账恢复、写后明细一致性、
事务快照以及旧全量端点的退出方式仍未闭环，不建议按当前版本直接开始实现。

===============================================================================
一、必须修正的问题
===============================================================================

1. “API 可以确认重复编号台账”的前提不成立

设计仍写着绕过前端 API 可以确认重复编号台账，并要求构造重复编号连库测试。
但数据库已有：

  unique (inventory_revision_id, site_component_type, component_number)

位置：database/migrations/011_component_inventory_revisions.sql:93

add_entry()、update_entry() 也会主动检查重复。因此：

- 正常 API 无法制造重复编号；
- 直接插数据库也会被唯一约束拒绝；
- 文档要求的连库 fixture 无法构造；
- confirm 没有重复检查，在当前 schema 下只是逻辑上不完整，不是实际可绕过漏洞。

建议二选一：

- 删除 duplicate_component_number blocker，以数据库唯一约束为权威；
- 保留为历史脏数据防御，但将检测抽成可接受合成数据的纯函数，用单元测试覆盖，
  不再要求连库构造重复数据。

不建议为了测试临时删除唯一约束。

-------------------------------------------------------------------------------

2. 旧的 /latest 全量端点没有被纳入删除范围

设计新增：

  GET /api/bridges/{bridge_id}/component-inventories/latest/summary

但“随之删除”只写了：

  GET /api/component-inventories/{revision_id}

没有说明如何处理现有端点：

  GET /api/bridges/{bridge_id}/component-inventories/latest

当前 /latest 仍调用 get_latest_revision()，继续装配全部 entries 和 mappings。
如果不删除或改造它：

- inventory_revision_json() 仍然有调用者；
- load_revision() 全量路径仍然有调用者；
- 文档所说“失去调用者”不成立；
- 旧端点依然可能产生 3.4 MB 响应。

必须明确选择：

- 同时删除 /latest 和按 revision id 的两个全量 GET；
- 保留 /latest 兼容旧客户端，此时不能删除全量装配路径；
- 或让旧 /latest 返回明确的弃用/替代响应。

-------------------------------------------------------------------------------

3. blocker 的“其余 N 项”计算仍然错误

当前定义是：

- total：所有 blocker 数量；
- samples：只包含重复编号和完全无映射；
- 待确认映射不进入 samples；
- “其余 N 项”使用 total - samples.length。

例如有 100 个待确认映射，没有无映射和重复编号：

  pending_count = 100
  samples.length = 0
  total = 100

页面会同时显示：

  100 个构件的规范映射待确认
  ……其余 100 项

建议新增 individual_total，关系定义为：

  pending_total = sum(groups[].pending_count)

  individual_total =
      inventory_empty
    + duplicate_component_number
    + unmapped_count

  total = pending_total + individual_total
  remaining = individual_total - samples.length

不能继续使用 total - samples.length。

-------------------------------------------------------------------------------

4. inventory_empty 没有可展示载体

设计规定 samples 只含重复编号和完全无生效映射的构件，所以 inventory_empty 不会
进入 samples。空台账时可能出现：

  blockers.total = 1
  samples = []
  pending_count = 0

页面只能看到“还需处理 1 项”，却没有具体说明。

建议选择一种：

- 让 inventory_empty 进入 samples；
- InventoryBlockersPanel 专门处理 by_code.inventory_empty；
- 增加单独的 revision-level blocker 列表。

同时，by_code 示例应包含 inventory_empty，并明确 by_code 是固定字段还是动态键。

-------------------------------------------------------------------------------

5. “台账为空”与“没有启用构件”被混为一谈

当前 confirm 的 inventory_empty 实际口径是“启用构件数量为 0”。它包含：

- 修订版一条构件都没有：groups = []；
- 有构件但全部停用：groups 非空，每组 active_count = 0。

设计却把“台账为空”统一描述为 groups = []、显示向导，这不适用于全部停用的情况。

建议明确区分：

- inventory_has_no_entries：物理条目数为 0；
- inventory_empty：启用条目数为 0。

也可以不新增 code，但前端必须分别处理“无任何条目”和“全部停用”。

-------------------------------------------------------------------------------

6. 空草稿显示向导后无法生成

当前 generate_draft() 只要发现桥梁已有草稿就返回 Conflict。

位置：backend-cpp/src/db/ComponentInventoryRepository.cpp:293

删除最后一个构件后：

- 草稿修订版仍然存在；
- entries 变为 0；
- 页面显示向导；
- 用户点击生成；
- 后端发现已有草稿，返回 409。

这是用户无法自行恢复的死路。必须选择：

- 保持“不改生成逻辑”：空修订版继续显示编辑器，只允许手工添加；
- 修改生成逻辑：允许在现有空草稿中重新生成；
- 新增“废弃空草稿并重新生成”的明确操作。

若选择后两种，应从非目标中删除“不改生成逻辑”。

-------------------------------------------------------------------------------

7. 写成功后分组明细和搜索结果仍会陈旧

“不进入 resourceCache”只能避免跨组件挂载缓存，不能清除当前 React 状态中的：

  groupEntries
  searchResults
  drafts
  editingEntryId

会出现以下问题：

- 删除后 summary 已减少，但弹窗仍显示被删除行；
- 批量确认后 summary 显示已确认，但已打开行仍显示待确认；
- 修改类别后构件应移到新分组，旧分组仍保留；
- 修改编号后当前搜索结果可能已经不再匹配；
- 停用后汇总已更新，当前明细仍是旧状态；
- 写入已确认版本后 revision id 已变化，旧明细仍属于原版本。

建议写成功后的统一流程为：

1) 采纳响应中的新 summary 和 revision id；
2) 清除旧 revision 对应的 drafts；
3) 取消旧 revision 的所有在途请求；
4) 若分组弹窗打开，重新请求当前分组和页码；
5) 若搜索词有效，重新执行当前搜索；
6) 根据新 total 夹取页码，必要时再请求一次；
7) 如果组已经不存在，关闭弹窗。

只 patch 响应里的 entry 不够，因为删除、批量确认没有 entry，修改类别还会改变
分页集合。

-------------------------------------------------------------------------------

8. 防抖没有解决异步响应乱序

250 ms 防抖只能减少请求量，不能保证返回顺序。例如：

  请求 A：number=3
  请求 B：number=33
  B 先返回，页面显示 33 的结果
  A 后返回，又把页面覆盖成 3 的结果

分组快速翻页也有相同问题。必须使用以下一种机制：

- AbortController 取消旧请求；
- 单调递增 request sequence；
- 响应落地前比较 revisionId、query、page、size 是否仍与当前状态一致。

revision id 因写操作变化时，旧 revision 的响应必须直接丢弃。

===============================================================================
二、事务与并发问题
===============================================================================

9. “同一个事务”不等于“同一个快照”

PostgreSQL 默认隔离级别是 READ COMMITTED。在这个级别下，同一事务中的多条 SELECT
仍可能看到不同的已提交状态。

因此，仅要求“在同一个只读事务里执行”不能保证 groups 和 blockers 来自同一快照。

必须明确使用：

  BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY;

或者把 revision、groups、blockers 合成一条 SQL，使它们使用同一个语句快照。

如果使用 REPEATABLE READ，还需规定：

- 序列化失败如何映射；
- 是否重试；
- 最大重试次数；
- 写事务是否也提高隔离级别。

-------------------------------------------------------------------------------

10. 写入与汇总同事务需要重构现有提交顺序

当前仓储大致流程是：

  执行写入
  finish() 提交事务
  get_revision() 在事务外重新读取
  返回

新设计要求：

  执行写入
  同事务计算 summary
  提交成功
  返回 summary

这不能只修改 respond_inventory_outcome()，必须重构所有仓储写方法。

还应明确：

- summary 在提交前计算；
- 必须等待提交确认；
- 提交失败不能返回已计算的成功响应；
- confirm 被 blocker 拒绝时返回事务内计算结果；
- 派生草稿时 summary 必须基于派生后的 revision id。

-------------------------------------------------------------------------------

11. 无锁并发下 position 只能是尽力定位

blocker 生成后、用户点击定位前，其他用户可能添加、删除、移动构件，使原 position
发生变化。

建议明确：

- position 是 summary 生成时的快照位置；
- 前端取页后若找不到 entity_id，重新拉 summary；
- 仍找不到则提示问题已经变化或被其他操作解决。

===============================================================================
三、SQL 与字段契约问题
===============================================================================

12. structure_part 是否可空存在直接矛盾

“可空字段”一节规定 structure_part 为 string | null，无映射时为 null；第 7 节和 SQL
却规定无映射时为 other，并写了：

  coalesce(..., 'other') as structure_part

应统一为：

  first_number: string | null
  last_number: string | null
  structure_part: StructurePart，非空，缺省为 other
  standard_package_id: string | null
  standard_component_category_id: string | null

整组全部停用时，按当前 SQL，structure_part 同样为 other。

-------------------------------------------------------------------------------

13. 完整 SQL 没有返回 standard_package_id

接口契约要求 standard_package_id，CTE 也计算了 package_id，但外层 SELECT 没有返回。
建议完整写出：

  (array_agg(em.package_id order by e.sort_order, e.id)
    filter (where e.is_active and em.inventory_entry_id is not null))[1]
    as package_id

package 和 category 必须使用相同过滤和排序，保证来自同一个构件。

-------------------------------------------------------------------------------

14. 分组与搜索不是“同一响应形状”

分组响应包含 total、page、size、entries；搜索响应只包含 total、entries。
建议定义两个明确类型：

  InventoryGroupEntriesResponse
  InventorySearchResponse

可以复用同一路由和 entry 序列化，但不要声称响应 envelope 完全相同。

-------------------------------------------------------------------------------

15. “三个端点共用同一个 CTE”无法按字面实现

分组读取、搜索、blocker 汇总是独立请求和独立 SQL，不可能在运行时共用同一个 CTE。
真正需要共用的是 position 的窗口定义。

建议改成：

- 共用 SQL 片段生成函数；
- 或建立数据库 view；
- 或使用 repository 私有查询构造器；
- 三处测试验证 position 一致。

-------------------------------------------------------------------------------

16. 查询参数边界没有完整定义

尚未定义：

- size=0；
- limit=0；
- page=abc；
- size=1.5；
- 超过 int 范围；
- number= 空字符串；
- group= 空字符串；
- 只有空白字符；
- limit 超上限是截断还是 400；
- page * size 溢出。

建议统一契约：

  page：整数，0..INT_MAX，非法返回 400
  size：整数，1..200，超过 200 截成 200
  limit：整数，1..100，超过 100 截成 100
  group：非空
  number：trim 后非空

偏移计算使用 64 位整数并检查溢出。否则 number= 可能形成 LIKE '%%'，搜索全部构件。

-------------------------------------------------------------------------------

17. 搜索零命中时 count(*) over() 没有结果行

count(*) over() 在有命中时能带回未截断总数，但零命中时查询返回零行，没有任何一行
携带 total=0。

实现需要明确：

  rows.empty() => total = 0

-------------------------------------------------------------------------------

18. 页码越界返回真实 total 通常需要独立计数

越界页返回零行。如果 total 只依赖窗口函数，就无法得到真实 total。

分组分页需要选择：

- 独立 count 查询；
- 单条 SQL 返回 count 和聚合后的 entries；
- 或 CTE + 左连接，保证无分页行时仍返回 total。

===============================================================================
四、载荷与模型设计问题
===============================================================================

19. 返回完整 mappings 使 100 KB 门槛无法保证

每次修改映射，旧映射会变成 inactive 并保留。一个构件理论上可以积累很多历史映射。
如果 100 个构件返回全部历史 mappings，“约 70 KB”和“≤100 KB”都不是稳定门槛。

建议选择：

- 明细只返回 is_active=true 的 mappings；
- 映射历史另设按需端点；
- 或承认 100 KB 只是当前数据估算，不作为硬门槛。

-------------------------------------------------------------------------------

20. 缺少 entry 序列化函数设计

删除 inventory_revision_json() 后，分组分页、搜索和写响应的可选 entry 仍需要完整
entry JSON。当前 entry 序列化嵌在 inventory_revision_json() 内。

至少需要新增：

  inventory_mapping_json()
  inventory_entry_json()
  located_inventory_entry_json()

-------------------------------------------------------------------------------

21. 后端领域模型定义不完整

建议明确新增：

  InventoryRevisionSummary
  InventoryGroupSummary
  InventoryBlockerSummary
  InventorySummary
  InventoryEntryPage
  InventorySearchResult
  LocatedInventoryEntry

还需明确：

- position 放在哪里；
- total/page/size 使用什么整数类型；
- nullable 字段怎样表达；
- by_code 是 map 还是固定 struct；
- samples 截断前总数放在哪里。

不建议复用 InventoryRevision 并把 entries 留空，否则摘要版与全量版容易混用。

-------------------------------------------------------------------------------

22. ComponentInventoryOutcome 的变更没有写清楚

当前 outcome 只有 revision、entry_id 和 blockers。新响应需要 summary、完整可选 entry、
结构化 blocker summary。

建议改成类似：

  struct ComponentInventoryOutcome {
      ComponentInventoryStatus status;
      std::optional<InventorySummary> summary;
      std::optional<InventoryEntry> entry;
  };

只返回 entry_id 再到事务外加载 entry，会破坏同事务自洽要求。

===============================================================================
五、接口兼容与前端行为问题
===============================================================================

23. 删除读端点属于破坏性 API 变更

“前端无调用者”只能证明当前 Web 前端不用，不代表没有开发脚本、外部集成或手工调试。
若系统明确只有单一前端，可以直接删除；否则建议先弃用、观察一版后再删除。

至少应在设计中标记为 breaking change。

-------------------------------------------------------------------------------

24. 写后 refetch 与 revision id 变化的顺序需要规定

正确顺序应为：

1) 接收写响应；
2) 用响应 summary 替换当前 summary；
3) 更新 revision id；
4) 清除旧 revision 的明细和 drafts；
5) 使用新 revision id 重新请求分组和搜索。

如果先 refetch 后更新 revision id，会继续请求旧版本。

-------------------------------------------------------------------------------

25. blocker 定位失败的回退流程未定义

建议流程：

1) 按 position 计算页码并请求；
2) 在返回页中按 entity_id 查找；
3) 找不到则重新加载 summary；
4) 读取新 sample 的 group/position；
5) 再尝试一次；
6) 仍不存在则提示问题已变化，不无限重试。

===============================================================================
六、测试与验收问题
===============================================================================

26. 缺少写后明细刷新测试

必须增加：

- 删除后重新拉当前分组页；
- 修改类别后原分组重拉；
- 批量确认后分组和搜索结果重拉；
- 写入已确认版本后用新 revision id 重拉；
- 页码越界时夹取并二次请求；
- 分组 total 变成 0 时关闭弹窗；
- 旧搜索响应不能覆盖新搜索结果。

-------------------------------------------------------------------------------

27. 缺少快照一致性的并发测试

应覆盖：

- summary 查询期间并发更新映射；
- groups 与 blockers 必须来自同一快照；
- 写事务计算 summary 时另一个写请求等待或冲突；
- commit 失败不能返回成功 summary。

-------------------------------------------------------------------------------

28. blocker 截断顺序没有定义和测试

需要明确：

- inventory_empty 是否优先；
- duplicate 和 unmapped 谁先；
- 组之间如何排序；
- 同组按 sort_order,id 还是按 code；
- 一个构件同时有多个问题时的顺序；
- 重复编号第一条是否产生 blocker。

建议采用稳定顺序：revision-level blocker 在前，构件按 sort_order,id，同一构件内
duplicate 在 mapping blocker 前。

-------------------------------------------------------------------------------

29. 重复组的 blocker 数量语义未定义

若历史脏数据中同一编号出现 3 次，需要明确：

- 第一条为基准，后两条各产生一个 blocker，共 2 个；
- 或整个重复编号组只产生 1 个 blocker。

否则 total、samples 和迁移前端逻辑会不一致。

-------------------------------------------------------------------------------

30. “18 组 × 9 字段逐字段一致”缺少投影说明

旧前端字段包含 mappingLabel，新接口返回 standard_package_id 和
standard_component_category_id，不能直接逐字段比较。

一次性比对脚本必须说明：

- 是否用同一 catalog 解析 mappingLabel；
- 或比较旧逻辑内部选出的 package/category；
- structure_part 如何比较；
- nullable number 如何转换成界面的破折号。

===============================================================================
七、文档内部的小矛盾
===============================================================================

31. 性能实测数字不一致

前面写汇总查询 76.0 ms，末尾仍写“已实测 52 ms”。应统一并注明：

- 是否为同一 SQL；
- 是否为 Release；
- 是否为热缓存；
- 是否包含 blockers；
- 是否包含事务开销。

-------------------------------------------------------------------------------

32. 4.5 KB 与 10 KB 门槛需要明确测量对象

应明确响应体积是否：

- 按 UTF-8 原始 JSON 字节数；
- 包含 HTTP header；
- 开启压缩；
- blocker samples 达到 30 条时仍要求不超过 10 KB；
- 带可选 entry 时仍要求不超过 10 KB。

单条写响应带一个完整 entry 和大量历史 mappings 时可能超过 10 KB。可以拆分为：

  summary-only 写响应 <= 10 KB
  带 entry 写响应 <= 20 KB

或者限制 entry 只返回生效 mappings。

===============================================================================
八、建议修订顺序
===============================================================================

1. 处理重复编号目标与不可构造测试。
2. 明确删除或保留旧 /latest 端点。
3. 重做 blocker 的 total、individual_total、samples 契约。
4. 区分“无条目”和“无启用构件”。
5. 决定空草稿显示编辑器还是支持重新生成。
6. 加入写后分组/搜索 refetch 和请求乱序保护。
7. 明确事务隔离级别及提交顺序。
8. 统一 structure_part 空值语义并补齐 package SQL。
9. 补充 C++ 模型、serializer 和 outcome 结构。
10. 完善参数边界、测试与性能口径。

最终评价：聚合方案和多映射 SQL 已经基本正确；当前主要风险不再是汇总算法，而是
blocker 契约、空台账恢复、写后明细一致性，以及旧全量端点是否真正退出。
