# 模块 06.5 补充设计：导入记录删除、无照片规则与校对定位

> 日期：2026-07-16
>
> 状态：已实施并通过自动化回归（2026-07-17）
>
> 关联设计：`docs/superpowers/specs/modules/06-5-bridge-centric-interaction-redesign.md`

> 2026-08-10 现行修订：新发起的导入在解析、调用 Python 或 4.0 契约校验失败时，由导入仓储事务自动删除导入记录、来源引用、候选关联和可独占归档，前端刷新年度工作台且只在弹窗保留错误提示。“解析失败记录继续保留并允许重试”仅适用于本修订前的历史实现。

## 1. 背景

模块 06.5 已将导入资料归入具体桥梁和年度，但当前流程仍有三个使用问题：

1. 管理员无法单独删除误传、解析失败或尚未确认的导入记录，只能保留无效记录或删除整个年度。
2. 解析器把“病害行没有填写照片编号”视为警告，但实际报告允许病害没有照片；只有报告引用了照片编号而系统没有找到图片时，才是真正的缺图问题。
3. 大型报告可能包含数百条病害。“需要处理”能列出问题，却不能快速定位到对应病害、照片或评分项。

本设计在不改变正式年度事实、评分算法和模块 05 校对主流程的前提下，补齐管理员受控删除、无照片业务语义和校对定位能力。

## 2. 已确认决策

1. 只有管理员可以删除导入记录。
2. 采用受控永久删除：删除前预览影响，填写原因，并输入完整确认文字。
3. 只允许删除尚未形成正式事实的记录；已确认记录必须通过现有“删除年度检测”能力处理。
4. 活动编辑锁阻断删除；删除接口不隐式抢锁或强制解锁。
5. 病害行照片编号为空是正常情况，不产生警告，也不要求确认缺图。
6. 病害行填写了照片编号但找不到对应图片时，继续产生缺图警告并要求人工处理。
7. 每条病害显示按当前导入记录顺序生成的只读序号 `1..N`；序号不写入合同或正式档案。
8. 可定位的待处理项均可跳到对应病害、照片或评分项。
9. 不迁移、不兼容已有导入记录中的旧 `photo_number_missing` 警告；现有数据由用户删除后重新上传。

## 3. 范围与非目标

### 3.1 本次范围

- 导入记录删除影响预览、强确认、删除审计和文件清理；
- Python 病害表解析器的无照片规则；
- 校对页病害显示序号；
- 待处理项的业务化对象名称与精确跳转；
- 对应的权限、并发、错误反馈和自动化测试。

### 3.2 非目标

- 不允许单独删除已确认导入记录；
- 不通过删除导入记录级联删除正式病害、评分或年度结论；
- 不修改 `BridgeAnnualInspectionData` 合同版本；
- 不把病害序号变成跨年度病害身份或持久业务编号；
- 不为旧导入 JSON 编写迁移脚本；
- 不改变模块 05 的编辑锁租约、草稿 revision、确认入库和修订规则；
- 不实现撤销删除或从删除审计恢复数据。

## 4. 管理员永久删除导入记录

### 4.1 入口与权限

年度检测工作台的每条导入资料卡片增加“删除”动作。该动作只对管理员显示，普通用户既看不到入口，也不能调用后端接口。

允许删除的业务状态为：

- 已上传；
- 解析中；
- 解析失败；
- 待校对；
- 已取消。

以下情况阻断删除：

- 导入记录已确认或属于其他只读正式终态；
- 已有正式年度事实引用该导入记录；
- 当前存在有效编辑锁；
- 导入记录不属于 URL 指定的年度或桥梁上下文。

活动编辑锁阻断时，界面显示编辑人。管理员若确需处理，必须先使用现有强制解锁能力，再重新发起删除；删除接口本身不隐式解锁。

### 4.2 影响预览

点击“删除”先请求实时影响预览，弹窗至少显示：

- 导入记录系统编号、名称和当前状态；
- 所属桥梁、检测年度和年度版本；
- 病害候选、照片候选、评分候选和解析图片数量；
- 已归档提取照片数量；
- 临时 Word 是否仍存在；
- 是否存在活动编辑锁；
- 是否存在正式事实引用；
- 本次删除是否可执行及阻断原因；
- 不透明的 `impact_token`。

响应不得包含服务器绝对路径。`impact_token` 由后端根据记录身份、状态、revision、影响计数、锁和正式事实引用等稳定信息生成，防止用户预览后数据已变化仍按旧影响执行删除。

### 4.3 强确认

删除弹窗要求：

1. 填写非空删除原因；
2. 输入完整确认文字 `永久删除 DRJL-xxxxxx`；
3. 影响预览仍允许删除；
4. 提交期间禁用关闭、重复点击和表单修改。

确认文字必须与当前导入记录系统编号完全一致，不能只输入“确认”或记录名称。

### 4.4 接口

```http
GET /api/import-records/{import_record_id}/deletion-impact
DELETE /api/import-records/{import_record_id}
```

删除请求体：

```json
{
  "reason": "测试导入错误，准备重新上传",
  "confirmation_text": "永久删除 DRJL-002407",
  "impact_token": "opaque-token"
}
```

后端在删除事务内重新锁定导入记录并复算影响。预览后状态、锁、revision、文件引用或正式事实引用发生变化时，返回稳定的 `deletion_impact_changed` 冲突，不执行部分删除。

稳定错误码：

- `import_record_not_found`；
- `import_record_not_deletable`；
- `import_record_edit_locked`；
- `import_record_has_formal_facts`；
- `deletion_impact_changed`；
- `confirmation_text_mismatch`。

认证和权限错误继续使用统一的 401/403 响应。

### 4.5 数据库事务

新增 `import_record_deletion_audits`，保存：

- 审计 ID 和审计系统编号；
- 可空的原导入记录 ID，以及导入编号、名称、状态快照；
- 桥梁、年度、年度版本和来源类型快照；
- 操作者 ID、用户名和显示名快照；
- 删除原因和删除时间；
- 病害、照片、评分、解析图片和待清理文件数量；
- 删除影响快照；
- 文件清理状态、完成时间和最近错误。

审计不保存 Word 二进制、照片二进制、完整解析 JSON 或服务器绝对路径，也不能用于恢复导入记录。

单个数据库事务按依赖顺序完成：

1. 锁定记录并复核权限、状态、影响令牌、活动锁和正式事实引用；
2. 计算仅由该导入记录拥有且删除后不再被引用的文件；
3. 写入删除审计和文件清理任务；
4. 删除校对草稿、候选关联、编辑锁及锁事件等导入级数据；
5. 删除导入记录及只属于它的文件元数据；
6. 提交事务。

任何数据库步骤失败时全部回滚，不生成“已删除”审计，也不提前删除磁盘文件。外键继续作为最后保护；未来新增引用未纳入删除计划时，应让删除失败，而不是遗留孤儿数据。

### 4.6 解析中的并发删除

“解析中”允许删除，时序如下：

1. 管理员完成强确认，数据库事务删除导入记录；
2. 已在运行的 Python 解析可以自然结束；
3. C++ 收到解析结果后重新检查导入记录；
4. 记录已不存在时不得重建记录或写入解析 JSON；
5. 本次解析产生但尚未归档的临时结果进入清理流程。

因此删除后的记录不会因迟到的解析回调重新出现。

### 4.7 文件清理

新增与删除审计关联的 `import_record_file_deletion_queue`。清理项区分：

- 正式归档存储中的提取照片；
- 临时存储中的原始 Word；
- 解析工作目录中属于本次导入的临时结果。

清理项只保存受控存储类型和相对标识，实际路径必须通过相应受控根目录解析。拒绝绝对路径、`..` 和越界路径。

现有 `ArchiveFileCleanupCoordinator` 扩展为调度第三类“导入记录删除”任务，并复用已有规则：

- 数据库提交后立即尝试；
- 后端启动时恢复未完成任务；
- 运行期间定时重试；
- 有界批量领取并避免多个清理器重复处理；
- 文件不存在按幂等成功处理；
- 暂时失败记录次数、错误和下一次重试时间；
- 全部完成后更新删除审计。

数据库业务删除成功后，即使物理文件暂时清理失败，导入记录也不恢复。前端只提示“导入记录已删除，部分孤立文件等待后台清理”。

## 5. 无照片病害规则

### 5.1 正常无照片

当病害表中照片编号单元格为空时：

- 解析结果中的 `photo_numbers` 为 `[]`；
- Python 不再生成 `photo_number_missing`；
- 该病害不因没有照片进入“需要处理”；
- 校对卡片显示“查看照片（0）”；
- 用户可以正常确认病害，不需要执行“确认缺图”；
- 如果该病害还有构件编号、位置或病害类型等其他问题，仍按相应规则警告。

### 5.2 真正缺图

当病害表填写了一个或多个照片编号，但提取图片中没有匹配项时：

- 保留原始照片编号；
- 生成 `photo_number_unmatched`；
- 计入“需要处理”；
- 页面显示具体缺失编号；
- 用户必须补充关联、确认缺图或按现有业务规则处理后才能完成校对。

一个病害同时引用多张照片时，仅对未匹配的编号警告，已匹配照片仍正常展示。

### 5.3 历史数据边界

本次不修改已有导入记录的 `parsed_result_json`，也不增加数据库迁移来过滤旧 `photo_number_missing`。旧记录在删除并重新上传前仍可能显示旧警告；重新解析的数据使用新规则。

## 6. 病害显示序号

### 6.1 序号定义

校对工作台按当前草稿 `defects` 数组的展示顺序派生序号：第一条为“病害 1”，第二条为“病害 2”，依次到“病害 N”。

序号具有以下边界：

- 只用于当前导入记录的页面识别和定位；
- 不写入 `BridgeAnnualInspectionData`；
- 不写入数据库正式病害事实；
- 不替代构件编号、照片编号、候选 ID 或跨年病害线索 ID；
- 编辑病害字段不会改变序号；
- 若未来新增删除或重排病害能力，序号可以随新的展示顺序重新计算。

病害卡片左上角显示清晰的“病害 19”等只读标签，内部候选 ID 不作为普通用户的主要标识。

### 6.2 稳定定位标识

每个可定位对象具有稳定的页面锚点：

- 病害卡片：由病害候选 ID 生成；
- 病害字段：由候选 ID 和字段名生成；
- 已关联照片：由照片候选 ID 生成；
- 未关联照片区域及其照片：由照片候选 ID 生成；
- 评分项：由评分候选 ID 生成。

DOM 标识只承担页面定位，不进入业务合同。生成时必须进行安全规范化，不能把任意来源文本直接作为 HTML ID。

## 7. 待处理项与精确跳转

### 7.1 业务化对象名称

“需要处理”列表优先显示用户可识别的对象：

- 病害问题显示“病害 19”；
- 已关联照片显示“病害 19 · 照片 2.1-8”；
- 未关联照片显示“未关联照片 · 2.1-8”；
- 评分问题显示对应评分项名称；
- 内部候选 ID 只作为调试信息或辅助 `title`，不作为主文案。

同一病害有多个问题时，每个待处理项都显示相同病害序号并定位到各自字段。

### 7.2 导航行为

点击可定位的待处理项后：

1. 自动切换到目标栏目；
2. 确保目标分组已经渲染；
3. 展开目标病害或选中目标照片；
4. 将目标滚动到可视区域中央；
5. 对目标卡片或字段短暂高亮约 2 秒；
6. 有明确可编辑字段时，将焦点放到该字段。

具体规则：

| 待处理项 | 目标行为 |
| --- | --- |
| 病害字段警告 | 切换“病害与照片”，展开病害，滚动并聚焦对应字段 |
| 病害级警告 | 切换“病害与照片”，展开并高亮整个病害卡片 |
| 已关联照片警告 | 切换“病害与照片”，展开所属病害并激活该照片 |
| 未关联照片警告 | 切换“病害与照片”，滚动到未关联照片区域并选中照片 |
| 评分警告 | 切换“技术状况评定”，滚动并高亮对应评分项 |
| 无具体对象的导入级警告 | 保留在“需要处理”，显示完整说明，不伪造跳转 |

目标栏目通常在点击后才渲染，因此前端保存一个待执行的导航目标，在 React 完成栏目切换和展开渲染后再执行滚动与聚焦，不能在旧 DOM 上立即查找。

重复点击同一待处理项应再次滚动和高亮。高亮动画遵循 `prefers-reduced-motion`；减少动态效果时仍保留静态边框或背景提示。

### 7.3 无效目标降级

如果草稿在待处理列表生成后发生变化，导致目标候选已经不存在：

- 不抛出未捕获异常或显示空白页；
- 保持当前栏目；
- 显示“目标数据已变化，请刷新待处理列表”；
- 刷新统计后移除已经失效的待处理项。

## 8. 组件边界

### 8.1 后端

- `ImportRecordDeletionPlanner`：计算可删除性、影响计数和影响令牌；
- `ImportRecordDeletionRepository`：事务内复核、写审计、创建清理任务并删除业务数据；
- 导入记录删除路由：认证、管理员鉴权、请求校验和稳定错误响应；
- `ArchiveFileCleanupCoordinator`：调度导入记录删除产生的持久化清理任务；
- 解析结果提交边界：阻止迟到结果写回已删除记录。

删除逻辑不塞入现有年度删除或校对仓储；共享文件安全解析和物理删除核心可以复用。

### 8.2 Python

病害表解析器只负责按新业务语义生成 `photo_numbers` 和警告：空照片编号不告警，引用未匹配照片继续由照片匹配阶段生成 `photo_number_unmatched`。

### 8.3 前端

- 年度导入资料卡片：管理员删除入口和删除完成后的列表刷新；
- `DeleteImportRecordDialog`：影响预览、原因、精确确认、提交状态和错误提示；
- 校对统计/分组：按新解析警告自然计算需要处理数量；
- 病害卡片：接收派生序号并提供字段锚点；
- 待处理列表：生成业务化标签和导航目标；
- 校对工作台导航协调器：在栏目渲染后执行展开、选中、滚动、高亮和聚焦。

## 9. 错误处理与安全

1. 删除接口服务端重复验证管理员权限，不能只依赖前端隐藏按钮。
2. 删除原因去除首尾空白后不能为空，前后端统一限制为最多 1000 个字符。
3. 删除接口不接受或返回物理文件绝对路径。
4. 影响令牌变化、活动锁和正式事实引用均返回 409，不转换成通用 500。
5. 数据库失败完整回滚；磁盘失败进入持久清理队列，两类失败的用户文案必须区分。
6. 删除成功后刷新年度工作台；刷新失败时明确提示记录已删除，可手动重试加载，不能让用户重复提交删除。
7. 跳转、滚动或聚焦失败不能破坏草稿，也不能触发保存或改变校对状态。
8. 序号和 DOM 锚点均由当前受控数据派生，避免 HTML 注入和不稳定选择器。

## 10. 测试与验收

### 10.1 管理员删除

1. 普通用户看不到删除入口，直接调用预览或删除接口返回 403；
2. 管理员可以预览并删除已上传、解析中、解析失败、待校对和已取消记录；
3. 已确认、已有正式事实引用或其他只读正式终态记录不能单独删除；
4. 活动编辑锁返回编辑人并阻断删除；强制解锁后可重新预览和删除；
5. 原因空白或确认文字不完整时前后端均拒绝；
6. 预览后状态、revision、锁或文件影响变化时，旧令牌返回 `deletion_impact_changed`；
7. 删除事务清理草稿、候选关系、编辑锁和导入记录，不遗留孤儿数据库数据；
8. 数据库中途失败时完整回滚且不提前删文件；
9. 删除成功写入不可恢复的审计快照和删除原因；
10. 解析中删除后，迟到的 Python 结果不能重建记录或写入 JSON；
11. 文件立即清理成功、文件不存在、暂时失败后重试、后端重启恢复和并发清理领取均有覆盖；
12. 删除完成后年度工作台刷新，记录数量和空状态正确。

### 10.2 无照片规则

1. 照片编号为空时 `photo_numbers=[]`，不生成 `photo_number_missing`；
2. 无照片病害不增加需要处理数量，可以正常确认；
3. 有照片编号且匹配成功时正常关联；
4. 有照片编号但图片缺失时生成 `photo_number_unmatched` 并显示具体编号；
5. 多照片编号仅对未匹配项告警；
6. 构件编号、位置、病害类型等其他警告不受影响；
7. 不运行旧 JSON 数据迁移，重新上传后的解析记录使用新规则。

### 10.3 序号与导航

1. N 条病害按当前展示顺序显示“病害 1”到“病害 N”；
2. 编辑病害字段不会改变序号，序号不进入保存或确认入库请求；
3. 待处理项使用病害序号、照片编号和评分名称，不以内部候选 ID 作为主文案；
4. 点击病害字段警告会切换栏目、展开病害、滚动、高亮并聚焦字段；
5. 点击病害级、已关联照片、未关联照片和评分警告分别到达正确目标；
6. 重复点击同一项会重新定位；
7. 无具体对象的导入级警告不伪造定位；
8. 目标已失效时显示可恢复提示，不出现空白页或未捕获异常；
9. 大型样例中可从需要处理列表直接定位到任意病害，不需要人工滚动查找。

## 11. 实施顺序约束

实施计划应按风险边界拆分：

1. 先固定无照片解析规则及其 Python/前端测试；
2. 再实现只读病害序号和待处理定位，不改变保存合同；
3. 然后新增删除审计、影响预览和原子删除事务；
4. 接入文件清理持久重试和解析迟到结果保护；
5. 最后接入管理员删除弹窗并执行全量回归。

每一步都必须保持现有确认入库、年度删除、桥梁删除、临时 Word 生命周期和文件清理能力可回归。
