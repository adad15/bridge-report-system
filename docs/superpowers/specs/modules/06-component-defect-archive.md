## 0. 当前实现边界

1. 构件存在性来自版本化完整构件档案，不由病害记录临时创建。
2. 档案默认读取当前有效、已确认年度的正式病害、照片、线索和正式评定结果。
3. 正式评分由系统 evaluator 产生并关联规范包、评定树、构件档案修订和 `assessment_run`。
4. 档案页只读；线索创建、合并、绑定、解绑和换绑属于独立整理工作台。
5. 大规模未绑定观测按批次和异常簇整理，批次是实时读模型，不是持久化业务实体。
6. 线索身份以标准评分树节点等正式语义为基础；原始病害文字只作为来源证据。
7. 模块 07 的新增、持续、消失、修复等对比结论仍未实现。

## 1. 背景与目标

模块 05 已把人工确认的构件、病害、尺寸、照片和技术状况评分写入 PostgreSQL。模块 06 的合理定位不是立刻做跨年变化判断，而是先把这些正式事实组织成稳定、可追溯、默认只读的构件病害档案，并让用户人工整理“哪些年度观测属于同一处病害”。

本模块采用“只读档案优先”：主页面以查询和查证为主，唯一有限写操作是病害线索创建与绑定。病害发展、减轻、修复、新增等结论留给模块 07。

## 2. 范围

### 2.1 包含

1. 按桥梁列出曾经出现当前有效病害事实的构件。
2. 构件详情以病害线索为基本单位，纵向展示各年度观测。
3. 展示病害详细位置、病害标度、扣分、尺寸、照片、来源证据和构件年度评分。
4. 默认只读取各年度当前有效版本，旧修订版通过独立入口查看。
5. 对尚未绑定线索的正式病害观测提供候选建议。
6. 允许用户绑定已有线索、创建新线索或暂时保持不确定。
7. 展示构件评分的 Word 来源值、规范复算值、最终值和校验状态。

### 2.2 不包含

1. 自动认定跨年观测是同一病害。
2. 生成病害发展、减轻、修复、新增等对比结论。
3. AI 修改或创造病害事实。
4. 维修记录编辑和维修效果判定。
5. 正式报告章节生成。
6. 完整桥梁构件树维护、构件合并或构件更名。
7. 从病害标度独立推导病害扣分的完整规范规则库。

## 3. 上游与下游

### 3.1 上游

- 模块 02：正式事实表、文件归档、年度修订和病害线索表。
- 模块 03 1.2：详细位置、标度、扣分和构件评分双值合同。
- 模块 04：从真实 Word 抽取上述候选并复算构件评分。
- 模块 05：人工校对、显式处理评分差异并事务入库。

### 3.2 下游

- 模块 07 读取病害线索及相邻年度观测，生成对比候选。
- 报告生成模块读取已确认事实和已确认对比，不读取未绑定建议。

## 4. 核心信息架构

```text
桥梁
  -> 构件列表
      -> 构件档案
          -> 构件年度评分
          -> 病害线索卡片
              -> 标准病害类型 + 标准详细位置
              -> 2026 年观测
              -> 2025 年观测
              -> 2024 年观测
          -> 未绑定观测
```

页面不是“2026 年 -> 一组病害、2025 年 -> 一组病害”，而是“蜂窝、麻面 -> 2026/2025/2024”。年度是病害线索下的次级维度。

## 5. 默认事实口径

### 5.1 构件纳入条件

构件列表收录：任意年度的当前有效版本中，至少有一条状态为已确认或已修改的正式病害观测的构件。它不要求该构件在最新年度仍有病害。

默认排除：

- 仅有导入候选、尚未正式入库的构件；
- 仅有已忽略、已取消或旧修订版记录的构件；
- 从未出现正式病害或维护事实的空构件；
- 仅手工预建但没有事实的构件。

### 5.2 年度修订

默认查询只使用 `inspection_years.is_current=true` 的版本。旧版本不参与构件计数、病害线索统计、首见/末见年份或评分趋势。用户可从“历史修订”入口单独查看，页面必须明确旧版本身份，不得与当前有效事实混排。

新修订版的病害观测不会自动继承旧版本的 `defect_thread_id`，需要重新确认绑定，避免旧事实关系静默污染新事实。

## 6. 数据模型

### 6.1 年度病害观测

`defect_observations` 表示某次当前有效年度检测中的事实：

- `bridge_component_id`
- `inspection_id`
- `defect_type`
- `defect_location`：该年度实际位置原文
- `scale`
- `defect_deduction`
- `defect_thread_id`：可空
- 状态、来源和审计字段

### 6.2 病害线索

复用 `defect_threads`。线索表达人工确认的跨年追踪单位：

- 始终绑定同一桥梁构件；
- 保存标准病害类型；
- 保存标准详细位置 `defect_location`；
- 维护当前有效观测的 `first_seen_year` 和 `latest_seen_year`；
- 不保存“发展/减轻/修复”等结论。

位置分为两层：

| 层级 | 字段 | 用途 |
|---|---|---|
| 病害线索 | `defect_threads.defect_location` | 跨年识别用的标准位置，如“左侧端部” |
| 年度观测 | `defect_observations.defect_location` | 当年报告实际原文，如“左侧端部靠近0#台” |

第一版保留完整可编辑文本，不拆分里程方向、立面、端部等子字段。

### 6.3 构件年度评分

以 `condition_ratings` 中 `rating_level='构件'` 且绑定 `bridge_component_id` 的记录为规范来源：

- `score`：最终确认值；
- `source_score`：Word 来源值；
- `calculated_score`：规范复算值；
- `score_validation_status`：校验状态；
- `score_resolution_reason`：人工选择来源分或复算分时的原因；
- `calculation_details_json`：扣分顺序、参与观测和公式版本。

同一当前有效检测、同一构件只允许一条构件评分记录。历史 `defect_observations.component_score` 仅作兼容展示，不作为新数据唯一来源。

### 6.4 建议不持久化

线索候选根据当前正式事实即时计算，不新增“建议表”。建议可以使用：

- 同一构件；
- 规范化后的相同病害类型；
- 规范化后的相同或相似详细位置；
- 非同一年度或非同一观测。

候选只是排序依据，不能自动写 `defect_thread_id`。

## 7. 页面设计

### 7.1 路由

```text
/bridges/:bridgeId/components
/bridges/:bridgeId/components/:componentId
/bridges/:bridgeId/defect-threads/review
```

### 7.2 构件档案主页面

采用左列表、右详情的 A 布局。

左侧构件列表展示：

- 构件类别、部件名称、构件编号；
- 当前有效病害线索数、未绑定观测数；
- 首次和最近出现年份；
- 搜索及结构分部、是否存在未绑定观测等筛选。

右侧详情首先展示构件基本信息和年度评分摘要，之后按病害线索显示 A1 卡片：

```text
蜂窝、麻面｜标准位置：左侧端部
  2025  标度 2｜扣分 20｜尺寸……｜照片……
  2024  标度 2｜扣分 15｜尺寸……｜照片……

横向裂缝｜标准位置：底板跨中
  2025  标度 2｜扣分 35｜尺寸……｜照片……
```

每个年度观测可展开查看原始位置、尺寸原文与结构化值、照片、来源表格和导入记录。图片必须通过 C++ 受控接口读取，不暴露绝对归档路径。

### 7.3 线索整理页面

集中显示未绑定的当前有效正式观测。每条记录提供：

- 年份、构件、病害类型、详细位置、尺寸和照片；
- 同构件内的线索候选及匹配依据；
- “绑定已有线索”“创建新线索”“暂不确定”三个动作。

“暂不确定”不创建新事实，只保持 `defect_thread_id=null`。页面和 API 不把未绑定状态视为错误。

### 7.4 历史修订入口

历史修订按年份和 revision 独立展示，只读，并标注当前版本替代关系。旧版不出现绑定操作，也不计入主档案统计。

## 8. API 设计

### 8.1 查询接口

```http
GET /api/bridges/{bridge_id}/components
GET /api/bridge-components/{component_id}/defect-archive
GET /api/bridge-components/{component_id}/defect-archive/revisions
GET /api/bridges/{bridge_id}/unbound-defect-observations
GET /api/defect-observations/{observation_id}/thread-suggestions
GET /api/defect-photos/{defect_photo_id}/content
GET /api/defect-observations/{observation_id}/evidence
```

主档案响应按线索组织，不要求前端自行把年度扁平记录重新分组。未绑定观测放在独立数组中。

### 8.2 写接口

```http
POST /api/defect-threads
PUT /api/defect-observations/{observation_id}/defect-thread
```

创建线索请求至少包含 `bridge_component_id`、标准病害类型、标准详细位置和首条观测 ID。绑定请求包含目标线索 ID、观测当前 revision 或等价并发令牌；重新绑定需要显式确认。

## 9. 线索绑定事务

绑定或重新绑定在单一 PostgreSQL 事务中完成：

1. 锁定目标 `defect_observations`。
2. 验证它来自当前有效检测版本，状态为已确认或已修改。
3. 验证客户端 revision，拒绝过期写入。
4. 验证目标线索与观测属于同一桥梁、同一构件。
5. 写入或更新 `defect_thread_id`。
6. 根据当前有效绑定重新计算线索 `first_seen_year / latest_seen_year`。
7. 提交事务。

若该观测已参与模块 07 的已确认对比，模块 06 不允许直接重新绑定；需要先由后续对比模块撤销相关结论。此约束应在数据库事务内再次校验。

## 10. 构件评分展示与校验

模块 06 不重新决定最终分值，但应清楚展示：

- Word 来源分；
- 按 JTG/T H21-2011 4.1.1 计算的规范分；
- 最终确认分；
- `一致`、`不一致`、`无法复算`、`人工接受Word值`、`人工采用复算值`；
- 参与复算的病害、扣分和计算步骤；
- 人工选择及原因。

旧 1.1 年度没有上述明细时，显示“历史数据缺少评分校验明细”，不得在页面端猜测。

## 11. 错误、空状态与人工处理

### 11.1 允许展示但提示

- 病害没有照片；
- 来源证据文件暂不可用；
- 观测尚未绑定病害线索；
- 旧数据缺少标度、扣分或评分校验明细；
- 某年度构件没有评分。

### 11.2 阻止写入

- 跨桥或跨构件绑定；
- 绑定旧修订版观测；
- 绑定非正式或已取消观测；
- 并发 revision 已变化；
- 重新绑定已被已确认对比引用的观测；
- 创建没有病害类型或标准详细位置的线索。

错误响应使用稳定错误码并包含用户可操作信息；不得只返回数据库异常文本。

## 12. 测试策略

### 12.1 评分公式与合同

- `[35] -> 65`；
- `[35, 20] -> 55.81`；
- 输入顺序变化结果不变；
- 任一 `DP=100 -> 0`；
- 计算过程中不提前舍入；
- JSON Schema、Python、C++、TypeScript 对 1.2 字段和枚举一致；
- `severity` 与 `defect_scale` 不可互换。

### 12.2 真实 Word 回归

原基线保持：25 条病害、31 个照片候选、36 个 Word 图片、31 张归档照片、15 个原评分项。

新增精确断言：

- `1-1#板`：标度 2、扣分 35、构件评分 65；
- `1-2#板`：标度 2、扣分 35、构件评分 65；
- `2-1#板`：扣分 35、20，复算 55.81；
- 上部承重构件评分 86.62；
- 全桥评分 85.61。

### 12.3 档案查询

- 最新年度无病害但旧年度有当前有效事实的构件仍在列表；
- 旧修订版不进入默认统计；
- 同一线索年度倒序且不混入其他构件；
- 未绑定观测独立返回；
- 照片和证据只通过受控接口读取；
- 缺照片、缺评分和旧数据缺明细时页面仍可读。

### 12.4 线索事务

- 同构件绑定成功并更新首见/末见年份；
- 跨构件、旧 revision、旧年度版本均失败；
- 两个并发绑定只有一个成功；
- 重新绑定需要显式确认；
- 被已确认对比引用时不能重新绑定；
- 新年度修订不自动继承旧版绑定。

## 13. 验收标准

1. 用户能从桥梁进入构件档案，并在左侧看到所有曾有当前有效正式病害的构件。
2. 默认页面不混入旧修订版、候选、已忽略或已取消数据。
3. 选中构件后，病害是一级卡片，年度观测纵向排列在卡片内。
4. 线索标准位置和年度实际位置均可查看且语义清楚。
5. 年度观测可查看标度、扣分、尺寸、照片和来源证据。
6. 构件评分显示来源值、复算值、最终值、校验状态和计算证据。
7. 旧 1.1 数据可读，并明确提示缺少评分校验明细。
8. 未绑定观测可绑定已有线索、创建新线索或保持不确定。
9. 系统只给候选建议，不自动确认同一病害。
10. 所有绑定写操作经过并发、当前版本、同桥同构件和下游引用校验。
11. 图片读取不暴露服务器绝对路径。
12. 模块 06 不生成任何病害发展、减轻、修复或新增结论。

## 14. 风险与取舍

### 14.1 自由文本位置

自由文本最忠于原报告，也便于当前人工校对，但不利于稳定自动匹配。第一版以人工确认为准，后续可以增加结构化位置辅助字段，不能覆盖原文。

### 14.2 病害线索先于对比

先整理“是不是同一病害”，再判断“发生了什么变化”，能把身份关系和变化结论分开审计。代价是用户可能需要先处理未绑定观测，模块 07 才能获得高质量输入。

### 14.3 只读档案优先

把事实编辑留在模块 05，避免档案页形成第二套年度事实修改入口。模块 06 的有限写操作只改变观测与线索的组织关系，不修改病害本身。
