# 从来源软件的离线库直接导入检测数据

日期：2026-08-05
状态：待实施

## 1. 为什么做

现有导入靠解析来源软件导出的 Word。实测 2024 年度百股大桥那份数据，解析结果里：

| 字段 | 填充率 |
| --- | ---: |
| 评定树节点（指标） | 51%（185/361） |
| 位置 | 47% |
| 照片引用 | 44% |
| 病害类型 | 85% |
| 结构化尺寸 | 85% |

而来源软件的桌面程序会把整座桥的检测数据下载到本机离线库，同一份数据在那里是结构化的：
**每条病害自带评定指标、标度、拆好的尺寸、所属台账节点，照片按外键直接绑定。**
实测该桥 275 条真实病害，带明确指标的比例是 **100%**。

Word 那条路要靠分层匹配去猜的指标、要靠正则去抠的尺寸、要靠编号去配的照片，
在源头都是已知的。本设计把数据来源换到离线库，**其余功能一律不变**。

## 2. 数据来源与前置操作

```
%APPDATA%\datacheck.hitek.com\databases\https_bridge.ilis.cn_0\1
```

Electron 应用的 WebSQL 库（SQLite）。**只读打开，不写回。**

| 表 | 内容 |
| --- | --- |
| `tasks` | 检测任务：桥名、检测日期、得分、等级 |
| `taskTrees` | 该次检测涉及的构件与部位树：层级码、构件类型、`memberCount` |
| `outerCheckData` | 病害记录：`judgeIndexId`、`degree`、数量/长度/宽度/面积、`treeId` |
| `images` | 照片：base64 存 `fileName`，`ForeignKey` 指向病害记录 |
| `CustomPropertyValue` | 桥梁基本信息，十组共 114 项 |

**前置操作是人工的**：数据只在用户于桌面程序中打开该桥时才落盘。实测三年百股大桥
下载后库从 279.9 MB 涨到 347 MB。导入流程必须在界面上明确提示这一步。

## 3. 解耦结构

契约 `BridgeAnnualInspectionData` 本身就是解耦层。Python 工具服务并排加一个端点，
Word 那条路一个字不动：

```
POST /imports/word/parse      现有，不动
POST /imports/source/parse    新增
    入：离线库路径 + taskId + 临时照片目录 + 同一套导入上下文
    出：{ data: BridgeAnnualInspectionData, temporary_photo_files: [...] }
```

两条路产出同一形状，C++ 侧只多一个来源分支决定调哪个端点；`WordImportRepository`
之后的全部流程（照片归档、写 `parsed_result_json`、校对、确认入库、H21 评分）不变。

`import_context.source_type` 用契约里已有的枚举值 **`接口同步`**，契约不需要修改。

**两处必须避免的耦合：**

1. 新模块**不得 import `importers/measurements.py`**。源库的尺寸已经拆好，不需要
   文本解析；引用它会让将来摘除 Word 解析时拖泥带水。
2. 照片临时文件列表交由 C++ 统一归档——这是两条路共用的下游，属于正常复用。

## 4. 字段映射

| 契约字段 | 来源 |
| --- | --- |
| `inspection.inspection_date` | `tasks.checkDate` |
| `inspection.project_name` | `taskFolder` 项目树 |
| 病害 `component_number` | `taskTrees.name`（经 `treeId` 关联） |
| 病害 `component_name` | `taskTrees` 父级（构件类别）名称，**不得为空**——见下 |
| 病害 `defect_type` | `outerCheckData.name`，允许为空（来源允许不选类型；C++ 侧 `require_string` 放行空串） |
| 病害 `defect_description` | `outerCheckData.data` |
| 病害 `defect_location` | `pos` / `posStake` / `posPart1..5` |
| 病害 `defect_scale` | `degree` |
| 病害 `measurements` | 数量 / 长度 / 宽度 / 高度 / 面积一 及各自单位列 |
| 病害 指标 | `judgeIndexId` → 指标编号 → `h21.defect.*` → 评定树节点 |
| 照片 | `images`，`ForeignKey` = 病害 id |
| 桥梁基本信息 | `CustomPropertyValue`（本期只读取不落库，见 §9） |

**`component_name` 必须非空。** C++ 契约校验对它用的是 `require_non_empty_string`，
而 `defect_type` 用的是 `require_string`——两者宽严不同。源库里构件名取自 `taskTrees`
的父级节点，父级缺失或名称为空时会导致整份契约校验失败、导入整体报错。取不到时
必须回退（依次尝试：父级名 → 构件类型 `memberTypeName` → 上级部位名），仍为空则
该条病害带警告落入待人工处理，而不是让整次导入失败。

**不导入**：`DP`（扣分值）、`score`（构件/部位/全桥得分）、`grade`（等级）、
`weightStd` / `weightCustom`（权重）。这些由本系统按 H21 自行计算。

指标映射沿用 `defect_template_source.py` 已有的三档判定：编号直接对上 H21 的走机械
映射；单位扩展指标（水损、减震装置、各类"其它病害"，共 7 个）走一张小对表；
其余按无匹配处理，走现有的人工选择流程。

## 5. 台账：不接管

来源软件的 `taskTrees` **不是完整台账**，只列出有病害的构件。实测该桥：

| 构件类别 | `memberCount` | 实际列出 |
| --- | ---: | ---: |
| 上部承重构件 | 825 | 37 |
| 上部一般构件 | 792 | 150 |
| 支座 | 3300 | **0** |
| 墩台基础 | 34 | **0** |
| 翼墙、耳墙 | 4 | **0** |

它算 H21 得分只需要"总数 + 有病害的那几个"，不需要逐个列出。而本系统需要完整台账
支撑构件绑定、逐构件档案与跨年度追溯。

**因此台账继续由本系统的编号引擎生成，源数据只用于认领构件、挂载病害。**
实测 259 个构件里 213 个编号与本系统完全一致；对不上的 46 个中 19 个是范围写法，
其余（`0#台盖梁`、`33#台盖梁`、`18-27#铰缝`）走现有的构件匹配流程，匹配不上就报出来
让人在校对页确认——与当前 Word 导入的行为一致。

## 6. 照片

来源库照片全部为 JPEG、多数 1600×1200，`ForeignKey` 直接绑定病害，**归属确定，
不需要按编号猜**。实测 170 张中 166 张挂在病害上，覆盖 159/275 条病害。

缺两样，都要生成：

**编号**：来源库没有。本系统现有编号是按部位分段的连续流水号，实测 2.1 段 1~78、
2.2 段 1~21、2.3 段 1~67，各自连续无断号。生成规则：

```
按台账层级码首段分组（001 上部 → 2.1，002 下部 → 2.2，003 桥面系 → 2.3）
组内按层级码与病害顺序排序，从 1 起连续编号
```

部位到章节号的映射**做成可配置**，不写死。写死会在遇到章节结构不同的桥时静默出错。

**题注**：来源库 `noteContent` 与 `oriFileName` 全空。生成规则：

```
题注 = 构件编号 + 空格 + 病害类型
     └ 病害类型为空时，退回 构件编号 + 病害描述
```

题注允许重复——报告里靠前面的照片编号区分（实测现有报告中「两侧护栏破损露筋」
连续出现三次，编号分别是 2.3-63/64/65）。**不加序号后缀。**

**落盘**：`fileName` 是 base64，一座桥约 42 MB。Python 侧解码写入临时照片目录，
交由 C++ 现有归档流程处理，与 Word 路完全一致。

## 7. 构件编号与范围拆分

来源库使用范围写法，形态高度统一——同孔、同类型、连续序号：

```
1-1#板~1-25#板
10-20#铰缝~10-22#铰缝
3-15#铰缝~3-24#铰缝
```

三个年度分别有 15 / 19 / 19 个。本系统现有的 `ComponentRangeParser` 已覆盖该格式
（其测试用例中就有 `1-1#板~1-25#板`），并已处理全角、空格、跨孔、倒序等异常，
**直接复用，不新写**。

范围行上的病害在拆分后复制到每个构件（现状即如此：`1-1#板~1-25#板` 上一条
「存在熏黑痕迹」在本系统展开为 25 条）。范围行若带照片，挂到拆分后的第一个构件并
在校对页标出待确认——实测本例范围行均无照片，但不能假定其他桥也如此。

## 8. 契约里填不满的两项

- `comparison_candidates`（跨年度对比）：来源库没有，`srcDataId` 全空。**本期留空数组。**
  注意本系统已可拿到同一座桥的多个年度数据，跨年度对比自行计算比从 Word 表格抠取更可靠，
  但那是独立一件事，不在本期。
- `report_text_candidates`（报告正文）：来源库没有，`tasks.judgeMemo` 为空。**本期留空数组。**

两者契约上允许为空数组，不阻塞导入。

## 9. 范围边界

**做：**

1. Python 新增源库读取模块与 `/imports/source/parse` 端点，产出与 Word 路同形状的响应。
2. 指标、标度、位置、尺寸、照片绑定的映射与生成。
3. 照片编号与题注生成，base64 解码落盘。
4. C++ 导入路由增加来源分支；前端导入对话框增加来源选项。
5. 以百股大桥三个年度为验收样本。

**不做：**

1. 不改契约。
2. 不动 Word 解析链——保留完整可用。
3. 不接管台账生成。
4. 不导入扣分、得分、等级、权重。
5. 不做跨年度对比与报告正文。
6. 不落库桥梁基本信息（本期只验证可读；接入桥梁档案是独立一件事）。
7. **不删除任何现有代码。**

## 10. 验收标准

1. 对同一份离线库、同一个 taskId 反复导入，产出的契约 JSON 逐字节一致。
2. 百股大桥 2024 年度导入结果与现有 Word 导入结果对账可解释：
   来源 279 条 = 262 条逐条对应 + 13 条渗水泛碱范围行 + 2 条熏黑痕迹范围行 + 2 条占位；
   本系统 361 条 = 263 条对应 + 46 条范围拆分产物 + 52 条范围拆分产物。
3. 导入后**指标填充率不低于 99%**（现状 51%）。
4. 三个年度导入均无 `component_name` 为空导致的契约校验失败。
5. 照片编号在每个部位段内连续无断号；题注非空。
6. 离线库文件在整个导入过程中修改时间不变（只读校验）。
7. 后端、Python、前端三套测试全绿；Word 导入路径的既有测试一条不改、全部通过。

## 11. 已知风险与取舍

1. **依赖对方的内部实现。** 离线库不是对外接口，表结构可能随其版本升级而变。缓解：
   导入前校验关键表与列存在，缺失时明确报错而不是静默产出残缺数据。
2. **需要人工前置操作。** 用户必须先在桌面程序里打开目标桥，数据才会落盘。导入界面
   要写清这一步，并在读不到 taskId 时给出可操作的提示。
3. **`weightCustom` 与 `weightStd` 可能不同**（实测桥墩 0.31 vs 0.30，说明有人调过权重）。
   本期不导入权重，本系统按 H21 标准权重计算，因此评分结果可能与来源软件不一致。
   这是刻意的：评分口径以本系统为准。
4. **照片题注是拼出来的，不是人写的。** 与 Word 报告里人工撰写的题注相比信息量更少。
5. **本期不删任何代码。** 数据源切换稳定运行一段时间后再评估清理，前置条件见 §12。

## 12. 后续：清理的前置条件

新导入投入使用后，下列代码可能成为死代码，但**必须满足前置条件才评估删除**：

| 候选 | 规模 | 前置条件 |
| --- | ---: | --- |
| Word 解析链（Python `importers/` 下 docx 相关 + C++ Word 上传/仓储/临时存储） | 约 2000 行 | 新导入至少完整走过一个真实年度并确认入库；且确认不再需要导入历史 Word |
| 病害匹配整套（分层匹配器、受控别名、关键词规则、匹配端点与前端面板） | — | 确认源库指标能 100% 落到评定树节点上，包括"其他"这类兜底指标 |
| `measurements.py` 尺寸解析 | 261 行 | **大概率不能删**——人工新增病害仍需从文字解析尺寸 |

清理不在本设计范围内，此处仅记录清单与门槛，避免日后忘记这些代码为何保留。
