程序锁相关问题严重性排序
==========================

审查范围
--------

本排序基于当前工作区代码，按照以下因素综合判断：

1. 对业务数据完整性的影响；
2. 问题触发概率；
3. 失败后是否容易恢复；
4. 是否突破后端权限或独占编辑边界。


严重性总表
----------

第 1 名：P1 高
问题：构件绑定写接口绕过编辑租约锁
后果：其他登录用户可在别人持锁时修改同一导入草稿；后续保存可能覆盖这些修改，直接破坏“独占编辑”语义。

第 2 名：P1 高
问题：Word 解析年度查询被临时移除 FOR UPDATE
后果：同年度并发操作可能让构件匹配、评定树匹配和年度锁定版本不一致，产生不容易立即发现的业务数据污染。

第 3 名：P1/P2 较高
问题：普通绑定、批量绑定、标记缺失和范围拆分未稳定锁住年度
后果：不同导入记录共享同一年度时，可能按旧台账版本修改草稿，但年度已经切换到新版本。

第 4 名：P2 中
问题：保存、确认与删除路径的数据库行锁顺序相反
后果：可能形成 PostgreSQL 死锁。数据库会中止其中一个事务，表现为偶发保存、确认或删除失败，一般不会写入错误数据。

第 5 名：P3 较低
问题：照片接口只在事务外检查编辑锁
后果：编辑锁恰好在检查后过期或被管理员强制解除时，原页面仍可能成功新增或删除一张照片。


一、构件绑定写接口绕过编辑租约锁
----------------------------------

涉及接口：

- POST /api/import-records/{id}/component-binding/rating-tree
- POST /api/import-records/{id}/component-binding/bind
- POST /api/import-records/{id}/component-binding/bind-batch
- POST /api/import-records/{id}/component-binding/mark-missing
- POST /api/import-records/{id}/component-binding/clear
- POST /api/import-records/{id}/component-binding/split-apply

严重原因：

1. 这不只是并发性能问题，而是后端独占编辑边界缺失。
2. 持锁用户认为自己独占编辑，但另一个已登录用户仍可直接调用这些接口修改数据。
3. 这些接口修改的同样是 import_records.parsed_result_json。
4. 校对草稿保存会整份写回 JSON，因此可能覆盖绑定接口刚刚写入的修改。

建议：

这些写接口必须接收 X-Edit-Lock-Token。仓储事务应先锁住 import_records，再在同一事务内校验用户、登录会话、令牌哈希和 expires_at，校验通过后才允许修改。


二、Word 解析缺少年度行锁
--------------------------

当前代码虽然注释说明必须在年度行锁内读取版本，但实际 SQL 为普通查询，并带有：

    // TEMP: 去掉行锁试探

缺少的锁是：

    FOR UPDATE

可能的并发过程：

1. Word 解析事务锁住导入记录，并读取年度台账版本 R1；
2. 另一事务把同一年度切换到 R2；
3. Word 解析事务继续按照 R1 完成构件匹配和评定树匹配；
4. 事务提交时，年度实际已经指向 R2。

这类错误不一定在提交时立即报错，可能到后续保存、预检或正式评定时才暴露。

建议：

恢复 inspection_years 查询的 FOR UPDATE，并统一采用以下锁顺序：

    import_records -> inspection_years

年度台账版本、规范组合和评定树上下文都应在持有年度行锁时重新读取。


三、构件绑定路径没有稳定锁住年度
----------------------------------

普通绑定、批量绑定、标记缺失、清除绑定和范围拆分通常只执行：

    FOR UPDATE OF ir

这只锁定 import_records，JOIN 查询得到的 inspection_years 行并没有被锁住。

当年度已经存在台账版本时，lock_pending_year_revision() 可能只比较调用方传入的旧快照值并直接返回，不一定真正访问和锁定年度行。

可能的后果：

1. 导入记录 A 按年度版本 R1 开始绑定；
2. 同年度的导入记录 B 把年度切换到 R2；
3. 导入记录 A 仍然按照 R1 写入病害构件关联；
4. 最终草稿中的版本信息与年度上下文不一致。

建议：

所有会写入版本化构件关联的路径，都应按照相同顺序锁住导入记录和年度记录，并在年度锁内重新解析台账版本。


四、数据库行锁顺序相反
------------------------

当前主要写路径采用：

    import_records -> inspection_years

但年度删除和整桥删除采用：

    inspection_years -> import_records

可能形成以下循环等待：

1. 事务 A 持有 import_records，等待 inspection_years；
2. 事务 B 持有 inspection_years，等待 import_records；
3. PostgreSQL 检测到死锁并中止其中一个事务。

影响：

- 通常不会产生错误业务数据；
- 会造成偶发保存、确认、年度删除或整桥删除失败；
- 用户看到的可能只是数据库不可用或操作失败；
- 新的草稿保存事务也采用 import_records -> inspection_years，因此发生冲突的写路径比以前更多。

建议：

1. 为全系统制定唯一的行锁顺序；
2. 删除路径也应遵循相同顺序；
3. 多行锁定时按稳定 ID 排序；
4. 对 PostgreSQL 40P01 deadlock_detected 做有限次数重试。


五、照片接口存在编辑锁检查时序窗口
------------------------------------

当前照片新增和删除流程大致为：

1. 在事务外检查编辑锁；
2. 解析上传文件或读取照片信息；
3. 开启数据库事务；
4. 只锁定 import_records 并检查状态；
5. 修改照片 JSON 和归档文件关联。

如果编辑锁恰好在步骤 1 和步骤 5 之间过期，或者被管理员强制释放，照片事务仍可能成功。

该问题触发窗口较窄，影响通常局限于一张照片，而且导入记录仍必须处于“待校对”状态，因此严重性低于前四项。

建议：

把编辑锁凭证传入照片写入事务。在锁住 import_records 后，于同一事务内重新校验编辑锁，再执行文件关系和 parsed_result_json 修改。


建议修复顺序
------------

第一批：修复构件绑定接口的编辑锁校验。

第二批：一起修复 Word 解析和构件绑定路径的年度行锁，统一 import_records -> inspection_years 顺序。

第三批：调整年度删除、整桥删除的锁顺序，并增加死锁有限重试。

第四批：把照片编辑锁校验移动到写事务内部。

推荐执行顺序：

    1 -> 2 和 3 一起 -> 4 -> 5

----------------------

补充与订正
----------

第 3 条的可达性比原文暗示的窄。能把年度台账版本从 R1 改成 R2 的**唯一**写入口是
bind_rating_tree（那句 update inspection_years 只有 id 和 status 谓词）。除它以外
年度版本只会 NULL -> R，而那条竞态已被 lock_pending_year_revision() 的回读兜住。
所以第 3 条要触发，必须是同年度的另一条导入记录重新绑定了评定树。仍然可达。

第 4 条没有自动化测试。锁顺序只在交错的中间态才可观测，而 delete_year 在自己的事务里
失败即回滚、锁随之释放，从公开接口探不到它先拿了哪个。要覆盖得起一个多连接带线程的
夹具，代价超过这条 P2 的收益。

顺带修掉的：TemporaryWordCleanupCoordinator 的一条测试今天开始偶发失败（6d0e6fa）。
不是被测代码的问题——两个夹具的 TearDown 只删 import_records，而
import_source_files.import_record_id 是 on delete set null，来源文件行变成孤儿留在
测试库里，攒到 203 行后其中"解析失败"那批跨过 24 小时到期点，被那条测试的全局计数
一起认领了。已堵住泄漏、把全局计数断言改成隔离安全的，并清掉存量孤儿。
