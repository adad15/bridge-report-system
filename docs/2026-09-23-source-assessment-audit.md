## 数据身份和方法

读取私有验收库 `bridge_report_acceptance`（127.0.0.1:25432）中的当前正式评定 `87b04558-ed42-4b61-b097-6b0eb52783ae`。对应年度 `97ec1135-b88b-4b15-85d2-c700db63e3e2`，来源导入 `6471db0e-8bf4-490a-af13-9ae5ad8a758f`，正式修订号 1，状态成功。数据库会话强制只读，检查数据库名、端口、年度和来源身份。原来源 SQLite、业务 PostgreSQL 均未写入。

规范包为仓库锁定的 H21 `1.0.4`，内容校验和 `sha256:a6c95351c3799607f03772078a2f1121c82e36caac76ba52338208af208092e4`；评定树校验和也与正式输入摘要相符。审核脚本从**正式观测、已确认构件台账和版本化 JSON 规则**重新建立计算输入，不调用 C++ evaluator，也不以系统保存的扣分轨迹作为预期值：

1. 按实际构件与规范指标聚合重复观测，取最高标度；按规则包查扣分值，同构件多个扣分按降序递减计算。
2. 对每件构件计算分数；每类部件按平均分、最低分、构件数量系数及主要部件低分直取规则计算。数量系数超过 200 件时按规则使用 200 件对应值。
3. 在各结构内按实际存在的类别重新归一化权重，算上部、下部、桥面系与全桥分数和等级。
4. 逐层对比正式结果、评定投影与轨迹；数值对比考虑数据库六位小数存储。再核对不计分观测、范围展开、两侧构件和控制项。

脚本为 [只读导出](../scripts/acceptance/export_source_assessment.py) 和 [独立复算](../scripts/acceptance/audit_source_assessment.py)。证据保存在 Git 忽略的 `logs/acceptance/20260920-092955-b4e366/source-assessment-raw.json` 与 `source-assessment-audit.json`；前者含业务事实，不提交仓库。复跑方式及环境约束见[验收脚本说明](../scripts/acceptance/README.md)。

## 观测、扣分与轨迹

430 条正式观测中，376 条有规范指标和标度，按同一构件同一指标取最高标度后得到 354 个扣分组合。另 54 条走评定树的“不计分”节点，保留原始观测，但没有规范扣分轨迹。它们来自 6 条来源记录：其中 `source_defect_0317`、`source_defect_0328` 各展开成 25 件，共 50 条；两条原文均为“存在熏黑痕迹，已修补”，无可用标度。其余 4 条是不计分的“基本完好”。两组范围观测没有因为展开而多扣分。

`source_defect_0162` 对应的两侧护栏分别绑定左、右实际构件，均按指标 `h21.defect.10_4_1_2`、标度 3 扣分，各构件分数为 60。仅作敏感性分析：若漏掉右侧这条来源观测，右构件将为 100，护栏类别会从 56 升至 76，桥面系升至 67.59044606990693，全桥升至 81.50732993815814，即高 **0.4** 分。这个反事实未写入数据库。

共核对 5,602 条规则轨迹：5,174 条构件分、354 条规范扣分、15 条部件类别分、3 条结构分、1 条全桥分、1 条等级、54 条不计分过滤。控制项记录为 0，与正式结果一致；当前事实没有显式控制触发证据，结构等级组合也未触发控制。
